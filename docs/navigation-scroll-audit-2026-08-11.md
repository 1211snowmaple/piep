# 画面遷移後の表示位置・履歴操作・長文表示 監査レポート

実施日: 2026-08-11
対象: `src/app/router.tsx` / `src/app/AppFrame.tsx` / ライブラリ・作者・シリーズ・作品・リーダー・エディタの各画面 / `src/components/ListPager.tsx`

## 1. 結論

報告された2件はいずれも再現・原因特定できた。原因は当初の想定（ルーターのスクロール復元処理）ではなく、別々の場所にあった。

- **作者ページで「次へ」を押すと詳細の一番上に飛ぶ** → スクロール復元は**そもそも動いていない**。ページ切り替えで一覧がローディング表示に差し替わり、ページ全体の高さが数千pxから数百pxに縮む。ブラウザが `scrollTop` をその高さに切り詰めた結果、プロフィール先頭まで巻き戻る。
- **絞り込みが「戻る」で消える** → ライブラリの詳細フィルター（ソース／種別／タグ／タグ条件／文字数）だけが URL ではなく React の state に置かれていた。作品を開くとライブラリはアンマウントされ、戻ったときに初期値で再構築される。作者ページは同じ絞り込みを URL に持っているため消えない。**同じ操作が画面によって違う結果になる**状態だった。

この2件を含め、遷移後の表示位置と履歴操作に関する問題を **16件** 特定した。うち **14件を修正**、2件は方針の判断が必要なため本レポートに残した（第6節）。

さらに、長文キャプションとページャーの問題を **6件** 特定・修正した（第5節）。報告のあったキャプションの途中切れ、ページャー下部のボタン削除、ページボタンの拡大を含む。

検証: `tsc --noEmit` 通過、単体テスト 170件通過（新規10件）、Playwright 30件通過（画面位置と履歴操作の実ブラウザテスト4件を新設）。位置の復元は jsdom でも再現できない（レイアウトが無い）ため、実ブラウザでの検証を追加した。実際、静的レビューでは見つからなかった不具合を2件（S-3 の「成功直後に記録を再開すると壊れる」、S-3b の「離脱側エントリへの誤記録」）この実測で発見している。

## 2. 報告された2件の原因

### 2-1. ページ送りでプロフィール先頭に飛ぶ

`EntityPage` / `LibraryPage` はどちらも、ページ番号が変わると React Query のキーが変わり、`isLoading` が立って一覧全体が `<LoadingState />` に差し替わっていた（[EntityPage.tsx:300](src/features/library/EntityPage.tsx), [LibraryPage.tsx:732](src/features/library/LibraryPage.tsx)）。

```
2,237件の作者ページ = 高さ約6,000px、scrollTop 1,800（一覧の先頭付近）
  ↓ 「次へ」
一覧がスピナー1個に = 高さ約900px
  ↓ ブラウザが scrollTop を最大値へ切り詰め
scrollTop 0 = プロフィールの一番上   ← ここが「一定して一番上に戻る」の正体
  ↓ データ到着、高さは戻るが scrollTop は 0 のまま
```

ルーターの `useScrollRestoration` はこの経路では発火すらしていない。依存が `[navigationType, pathname]` だけで、同じパスへの連続 push では両方とも変化しないためである。

**副作用として一貫性も壊れていた。** 直前に絞り込み（`replace`）を挟むと `navigationType` が `replace → push` と変化して effect が再実行され、今度は明示的に `scrollTop = 0` が実行される。つまり「絞り込んでからページ送り」と「ページ送りを2回連続」で挙動が変わっていた。

**修正**
- 両画面のクエリに `placeholderData: keepPreviousData` を追加。ページ取得中も前ページを表示し続けるので高さが縮まない。スピナーの明滅も消える。
- `useRevealOnChange`（新規 `src/lib/scroll.ts`）で、ページ番号が変わったら**一覧の先頭**をヘッダー直下に持ってくる。プロフィール先頭ではなく「2ページ目の最初の作品」に着地する。
- `AppFrame` は、クエリ文字列だけが変わった push では位置に触れないようにした。同じ画面の中の移動は画面側が決める、という切り分け。

### 2-2. 絞り込みが「戻る」で消える

`LibraryPage` の `otherFilters`（`sources` / `contentType` / `tagsInclude` / `tagsExclude` / `tagMode` / `minChars` / `maxChars`）が `useState` で保持されていた。URL に載っていたのは `q` / `tab` / `favorite` / `watch` / `sort` だけ。

作品を開く → ライブラリがアンマウント → state 消滅 → 戻る → `initialFilters` で再構築、という流れになる。ソースコード上のコメントは「URLに置いているので戻るボタンが効く」と書かれていたが、実際に URL にあったのは半分だけだった。

**修正**: 全条件を URL に移した。パラメータ名は作者ページの既存規約に合わせている。

| 条件 | パラメータ |
|---|---|
| ソース | `source`（複数可） |
| コンテンツ種別 | `type` |
| 含めるタグ | `tag`（複数可） |
| 除外するタグ | `nottag`（複数可） |
| 複数タグの条件 | `tagmode=or`（and は省略） |
| 文字数 | `minchars` / `maxchars` |
| お気に入り・更新監視 | `favorite=1` / `watch=`（既存のまま） |

副次的な効果として、絞り込んだライブラリがそのままリンク・ブックマーク可能になり、保存した検索の復元経路も URL 一本に統一された。

## 6. 保留した判断事項

以下の2件は「直し方が一意に決まらない」ため、方針の確認をお願いしたい。R-3 は判断ではなく仕様の記録。

### R-1. ページ送りを履歴に残すか（H-5）

- **現状維持（残す）**: Web の一般的な挙動と一致。ページ2から戻るとページ1に戻る
- **残さない（`replace` にする）**: 作者ページから抜けるのが戻る1回で済む。ただしページ送りを戻るで取り消せなくなる

今回は現状維持とした。H-6 の修正により「何も起きない戻る」は解消済み。

### R-2. 絞り込み・並び替えを履歴に残すか（H-7）

検索ボックスは1文字ごとに履歴が増えると使い物にならないので `replace` が正しい。一方、タグチップや並び順のような**離散的な操作**は push でもよい。ただし push にすると H-5 と同じく履歴が増える。

今回は全て `replace` のままとし、代わりに H-1（戻ったときに条件が完全に復元される）を直した。実用上はこちらの方が効く。

### R-3. 「進む」で戻ったときのスクロール位置

履歴エントリ番号で位置を記録するようにしたため、進む・戻るとも正しい位置に復元される。ただし、一度 push で上書きされたエントリ番号の位置は失われる（ブラウザと同じ挙動）。実害はないと判断した。

| P-5 | **ライブラリの「作者・クリエイター」「シリーズ」タブがページ番号設定を無視**し、常にスクロール読み込みだった。原因は `<ListPager>` に `pages` を渡していなかったこと。`ListPager` は「番号を扱えない一覧」と解釈して自動に落とし、しかも理由も表示しない（`unavailableReason` も未指定のため）ので、設定が黙って効かない状態だった | 作者・シリーズもオフセット送りにして `pages` を渡した |
| P-6 | 上記に伴う `ListPager` 側の制約: **総件数が不明な一覧では番号送りが成立しなかった**。`total === null` のとき最終ページを現在ページとみなす実装で、「次へ」が常に無効になり1ページ目から動けない | 総数不明でも成立するようにした。次があることは分かるので「次へ」は有効、番号は辿った分だけ伸び、末尾に `…` を出す。件数行は `Nページ目` / `Nページ目（最後）`。※作者・シリーズについては第5次修正で総件数を取れるようにしたため、この経路は他の総数不明な一覧のための備えとして残っている |
| S-14 | **ページを変えてもスクロールが下のままになることがある**（再現性が低い）。押下時点で即座に最上部へ移動していたため、(a) ブラウザ側のスクロールアンカリングが直後に位置を戻す競合、(b) 移動先の行がまだ届いていない状態での移動、の2つが噛み合っていた | 移動を**新しいページの行が実際に画面に出た時点**に遅延（`isPlaceholderData` / `isFetching` の解消を待つ `useLayoutEffect`）。加えて `.app-main` に `overflow-anchor: none` を指定し、ブラウザ独自のアンカリングと競合しないようにした |
| S-15 | ページ切り替え時の**ちらつき**。「押した瞬間に最上部へ跳ぶ → 前のページの行がそこに見える → 行が入れ替わる」で移動が2回起きていた | 上記の遅延により**1回の移動**になった。行の差し替えと移動が同じフレームで起きる（`useLayoutEffect` なので描画前） |
| S-16 | キャッシュ済みのページ（例: 2→1）に戻ると移動が起きない | 「解決済みフラグ」だけを監視する実装では、同一レンダーで解決するキャッシュヒット時にフラグが変化せず effect が走らない。依存に `pageParam` を追加 |

実測（1200×800、5件/ページに一時変更して検証）: ページ送り前 `scrollTop 886` → 送り後 `0`（800ms 追跡して維持）。キャッシュ済みページへ戻る場合も `886 → 0`。

### 第5次修正

| P-7 | 作者・シリーズの**総件数が取れない**ため、番号送りが「次があるか」しか分からない状態だった | Rust に `count_entity_facets` を追加。集計の FROM・絞り込み・GROUP BY を `entity_facet_source` として1箇所に切り出し、**1ページ取得と総件数が同じ定義を共有**する（二重に書くと片方だけ条件が変わり「総数が数えている行と一致しない」という最も気付きにくい壊れ方をする）。件数表示も `6件以上` → `6件`、ページャーも `6件中 1 / 2ページ` になった |

S-17 の副次的効果として、同じ「1レンダー遅れ」に由来する不具合がまとめて消えた。

- 一覧表示（ギャラリー／リスト）が一瞬ギャラリーで描かれてから切り替わり、仮想化グリッドが読者の目の前で作り直される
- サイドバーが広い状態で開いてからレールに縮む
- 第3次修正で対処した S-12（作者ページを開くと作品一覧へ飛ぶ）の**根本原因そのもの**。当時は「押下から呼ぶ」方式に変えて症状を断ったが、原因はこちらだった

あわせて `usePageSize` の検証を「設定画面が提示する4つのいずれか」から「backend が受け付ける範囲（5〜200）」に変更した。提示リストは無難な選択肢の一覧であって妥当性の定義ではなく、手で設定された値を黙って20に戻す必要はない。これによりデモデータ（作者6件）でも複数ページを実際に踏むテストが書けるようになった。

検証: `?page=2` → 作者を開く → 戻る、でURLが `?tab=people&page=2` のまま（修正前は `?tab=people`）。Rust 側は「ページを辿った行数の合計＝総件数」を検証。

## 7. 調査したが問題がなかった箇所

- **リーダーの位置復元**（`ReaderPage.tsx:170-205`）: sessionStorage に作品・版ごとに保存し、2秒の期限付きでリトライ。復元 effect を保存 effect より先に宣言することで「未復元の0を保存してしまう」問題も回避済み。今回 `AppFrame` 側をこの実装に合わせた
- **エディタのスクロール同期**（`EditorPage.tsx:122-145`）: 独立したスクロール領域内の処理で、画面遷移とは無関係
- **設定画面のセクション切り替え**（`SettingsPage.tsx:70`）: URL 由来 + `replace` で正しい。各セクションは短く、切り詰めの実害がない
- **保存ワークスペースの戻る**（`SavePage.tsx:545`）: 内蔵ブラウザの履歴を戻すもので、アプリの履歴とは別系統。正しく分離されている
- **仮想化リストのスクロールマージン計算**（`VirtualizedWorkList.tsx:57`）: `ResizeObserver` でスクローラと自身の両方を監視しており、位置復元後の再計算も走る
