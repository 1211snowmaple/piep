## 0. 試験の方法と、その限界

利用者のライブラリ（`%APPDATA%/com.hiron.piep/piep.db`）を作業用ディレクトリへ**複製**し、複製に対してのみ候補生成を実行した。**本番のライブラリは読み取りのみで、一切書き換えていない。**

対象ライブラリの規模:

| 項目 | 値 |
|---|---:|
| 作品総数 | 2,415 |
| pixiv | 1,102 |
| FANBOX | 1,313 |
| 作者 | 22 |
| 公式シリーズに属する作品 | 471 |
| 同一作者・同一題名語幹で 2 件以上まとまる組 | 141 |

**限界（結果を読む際の注意）**: 複製側には全文索引（Tantivy）と意味索引が無いため、次の 2 signals は**評価できていない**。

- 逆方向リンクの全文検索による発見（「前編はこちら」で参照されている側からの引き寄せ）
- 本文の意味類似度

したがって以下の評価は、**公式シリーズ・作者・題名・本文リンク**の 4 signals に対するものである。本文リンクは保存済み JSON を直接読むため機能した。

## 1. うまく動いたこと

先に、実データで正しく動いた点を挙げる。

### 1-1. 話数の表記ゆれ吸収は実データで機能している

今回の修正（設計提案 6-3 への対応）は、実ライブラリの表記を正しく解釈できている。

| 実際の題名 | 抽出された順序 |
|---|---:|
| `①【現パロ】…` / `②` / `③` / `④` | 10 / 20 / 30 / 40 |
| `…お話 その１❤️` / `その２❤️` / `その３❤️` / `その４❤️` | 10 / 20 / 30 / 40 |
| `【前編】…` / `【中編】` / `【後編】` / `【完結編】` | 1 / 2 / 3 / 1000000 |
| `雪の降る夜、館にて　第一話` / `第二話` / `第三話` | 10 / 20 / 30 |
| `【雑談】第22回オススメの作家様紹介` | 220 |
| `…話#2` / `#3` | 20 / 30 |
| `藤堂君の就職活動　3話` | 30 |
| `【先行公開】…　最終話【先行公開】` | 1000000 |

丸数字（NFKC で `1` へ倒れる）、漢数字、`その`、`第N回`、`N話`、`#N` がいずれも通っている。

> **前回レポートの訂正**: 前回「`#12` と `航路 #2` は正規表現に一致する」と書いたのは誤りだった。実際には `normalize_search_text` が記号を空白へ潰すため `#` は判定前に消えており、**修正前は `第N…` 形しか拾えていなかった**。修正後は正規化後の裸の数字として拾えるため、結果的に `#N` 形も動く。

### 1-2. 根拠表示は検証可能な形で出ている

全候補に人間が読める根拠が付いており、設計提案 17-2 の「説明可能率 100%」は満たしている。

```
[  1] score=0.74 マイク・O / ②【現パロ】…
         · 同一作者 (+0.12)
         · タイトル語幹の類似度 100% (+0.62)
```

### 1-3. 素直な連番・前後編は正しくまとまる

`①〜④` の 4 部作、`【前編】〜【完結編】` の 4 部作とも、**過不足なく 4 件を正しい順序**で提案できた。公式シリーズがある場合は提案名もシリーズ名（`To LOVEる RE:DARKNESS`）が使われ、語幹からの機械的な名前より読みやすい。

## 2. 実データで見つかった不具合

### 2-1. 【重大】読む順が壊れる

> **この節の原因分析は誤りだった。7 節の訂正を参照。** 症状（並びが崩れる）は実在するが、原因は `mentions` ではなく `link_depth` の優先順位だった。

**再現**: 種 `#2`（id 490）から生成した提案の並び。

```
[0] 『同人女の感情』…話#2     ← 基準作品
[1] 『同人女の感情』…話        ← 無印（実質の第1話）
[2] 『同人女の感情』…話#3
         根拠: 本文・キャプションの直接リンク（mentions） (+0.59)
```

提示された読む順は **`#2` → 無印 → `#3`**。正しくは **無印 → `#2` → `#3`** である。

**原因**: 比較子が `link_order` を `episode_order` より先に見る。

```rust
compare_optional_order(left.link_order, right.link_order)
    .then_with(|| compare_optional_order(left.link_depth, right.link_depth))
    .then_with(|| compare_optional_order(left.series_order, right.series_order))
    .then_with(|| right.member_score.total_cmp(&left.member_score))
    .then_with(|| compare_optional_order(left.episode_order, right.episode_order))
```

しかも根拠は `mentions`（単なる言及）である。設計提案 6-4 は「おすすめ作品 / 参加作品一覧」の類を**単なる参照**と分類し、順序辺にしてはならないとしている。現状は `mentions` でも `link_order` が設定され、明示的な話数表記を上書きしてしまう。

**推奨**: `relation_type` が `precedes` / `continues` のときだけ `link_order` を順序に使い、`mentions` は候補収集の根拠に留める。あるいは `episode_order` を `link_order` より優先する。

### 2-2. 【重大】番号のない第1話が末尾に回る

`title_stem_and_order` は番号も前後編表記も無い題名に `None` を返し、`compare_optional_order` は `None` を**最後**に置く。連載の第1話は番号を振らないことが多く、実ライブラリにも多数ある。

| 無印（order=None） | 続き |
|---|---|
| `To LOVEる RE:DARKNESS` | `#2`(20) / `#3`(30) |
| `ダダ甘に甘やかされたいっ！` | `2`(20) |
| `『同人女の感情』…話` | `#2`(20) / `#3`(30) |
| `寝取られ同人誌…話` | `外伝`(1000020) |

上記のうち `To LOVEる` `ダダ甘` `寝取られ` は**公式シリーズが `series_order` を供給したため表面化しなかった**。公式シリーズが無い `『同人女の感情』` では実際に順序が崩れている（2-1 と複合）。

**推奨**: 同一語幹の兄弟に番号付きが存在し、自身に番号が無い作品は「第0話」相当（`Some(0)`）として扱う。少なくとも `None` を先頭側へ寄せる。

### 2-3. 【重大】公式の短編集が「順序付き」20作品のコレクションになる

**再現**: 種 id 2277（`寝取られ同人誌のヒロインたちと純愛ハーレムセックスさせられる話`）。

```
提案名: 「マイナーキャラ妄想短編集　純愛物」  種別: ordered  確度: 1.00
  [ 3] score=0.70 骸から生まれ－－
  [ 4] score=0.70 錬金術師の話
  [ 5] score=0.70 お嬢様の話
  …（同じ調子で 20 件）
         根拠はいずれも 公式シリーズ (+0.58) + 同一作者 (+0.12) のみ
```

問題は 3 点ある。

1. **短編集が `ordered` と判定される。** 種別判定が `any` になっているため、20 件のうち 1 件でも話数を持てば全体が「順序付き」になる。
   ```rust
   let collection_kind = if ranked.len() > 1 && ranked.iter().any(|value| {
       value.series_order.is_some() || value.link_order.is_some() || value.episode_order.is_some()
   }) { "ordered" } else { "unordered" };
   ```
   タイトルからして短編集であり、通読順は無い。設計提案 3-D / 10-4 が「順序なし」として扱うべきと定めた類型そのものである。

2. **公式シリーズ所属だけで閾値を超える。** `0.58 + 0.12 = 0.70` は足切り `0.44` を大きく上回るため、**シリーズに属する全作品が自動的に候補入り**する。結果としてこの提案は「公式シリーズの複製」になっている。設計提案 19 は「取得元のシリーズ情報をすべて永続コレクションへ自動複製」を**初期リリースに入れないもの**として明記している。

3. **無関係な作品が根拠 2 行だけで並ぶ。** 「骸から生まれ－－」と種の作品に物語上の関係は見えない。設計提案 6-6 の「候補集合内の各作品に、少なくとも 1 つ説明可能な**強い**根拠を要求する」を満たしていない。

**推奨**: 種別は `any` ではなく**過半数**が順序情報を持つ場合のみ `ordered`。公式シリーズ単独では候補に入れず、シリーズは既存エンティティとして閲覧させる（設計提案 19 の方針どおり）。

### 2-4. 【中】合本版が分冊と同時に収録され、本文が二重になる

**再現**: 種 id 985（`【前編】一介の男子高校…`）。

```
[1] 【中編】…
[2] 【後編】…
[3] 【完結編】…
[4] 【前編＋中編】…【本文全体17.5万文字】   ← 合本
[5] 【後編＋完結編】…【本文全体17.5万文字】 ← 合本
```

`【前編＋中編】` は `【前編】`+`【中編】` と同じ本文をまとめ直した投稿である。全選択のまま EPUB にすると**同じ本文が 2 回入る**。

現状は既定で全件 `selected: true` なので、利用者が気づいて外さない限りそのまま収録される。

**推奨**: 題名に `＋` / `まとめ` / `合本` / `総集編` を含み、かつ同一語幹の他候補を包含しうる作品は既定で未選択にし、「重複の可能性」と表示する。少なくとも文字数が突出している候補は警告する。

### 2-5. 【中】ライブラリに同一作品が二重に保存されている

題名・作者が完全に一致する組が複数見つかった。

| 題名 | id |
|---|---|
| `綱手のファン感謝祭　～五分パイズリ我慢出来たら一晩貸し出し生中セックス～` | 742 / 1363 |
| `八百万と拳藤に加え、ミッドナイトも…お話` | 740 / 1361 |
| `ジャンヌ・オルタ(Fate)と新宿の…話` | 828 / 2118 |
| `魔都精兵のキモデブ` | 749 / 1374 |
| `雪の降る夜、館にて　第一話` | 738 / 1358 |

pixiv と FANBOX の両方へ投稿された同じ作品か、再取り込みで増えたものかは今回確認していない。いずれにせよ**候補一覧に同じ題名が 2 行並ぶ**ため、コレクションと EPUB の品質に直接影響する。

**推奨**: まず実態の確認（`source` が異なるのか同一なのか）。異なる取得元の同一作品なら、候補生成側で「同一題名・同一作者・別取得元」を 1 件へ畳む余地がある。

## 3. 評価まとめ

設計提案 17-2 の指標に、今回の観察を当てはめた主観評価である。

| 指標 | 評価 | 根拠 |
|---|---|---|
| 説明可能率 | **良好（目標達成）** | 全候補に根拠行が出ていた |
| 候補再現率 | **良好** | 4 部作・前後編とも取りこぼしなし |
| 強い候補の適合率 | **要改善** | 公式短編集で無関係作品が 20 件混入（2-3） |
| 順序正解率 | **要改善** | 言及リンクと無番号第1話で順序が崩れる（2-1 / 2-2） |
| 過結合率 | **要改善** | 短編集全体の取り込み、合本の重複（2-3 / 2-4） |

**総評**: 素直な連載（連番・前後編）については、実データで**そのまま使える品質**に達している。修正した話数解析は実ライブラリの表記ゆれをよく吸収できていた。

一方で、**公式シリーズを持つ作品**を種にすると、シリーズ全体を丸ごと取り込んだ大きすぎる提案になりやすい。設計提案が繰り返し警告していた「過結合」が、まさにその形で現れている。優先して直すなら **2-3 → 2-1 → 2-2** の順を勧める。

# 第2回: 修正と再試験（同日）

第1回で挙げた重大 3 件を修正し、同じ実ライブラリの複製で再試験した。あわせて重複保存の実態を調査し、新たに 2 つの類型を見つけて対処した。

## 6. 重複保存の実態

題名と作者が一致する重複グループは **64 組**。上位 40 組の内訳:

| 種類 | 組数 | 例 |
|---|---:|---|
| **取得元をまたぐ**（pixiv ↔ FANBOX） | 31 | `マァムがレオナを助けようと…` id 750(pixiv) / 1376(fanbox) |
| 同一取得元 | 9 | 下記の 2 類型 |

**利用者の見立てどおり、大半は pixiv と FANBOX の両方へ投稿された同じ作品だった。** 本文長は FANBOX 版の方が長いことが多い（例: 39,977 / 43,576 文字）。`content_hash` は一致しないため、システムからは別作品に見える。

同一取得元の重複には、さらに注意すべきものが混ざっていた。

- **本文が空の保存**: `id 1174/1175`（`text_len = 0 / 1179`）、`id 1058/1059`（`text_len = 0 / 15,577`）。同じ FANBOX 記事に対して、本文 0 文字の行が別 `source_id` で残っている。取得失敗の残骸と見られる。
- **作者による再投稿**: `id 592/694`（ともに pixiv、`source_id` が別）。これは正当な別作品。

### 対処

取得元をまたぐ重複を候補生成側で検出し、**本文が長い方を既定に残し、もう一方は既定の選択から外す**ようにした。候補一覧からは消さない。どちらを採るかは利用者の判断に属するためである。

```
[ 0] [x] キモデブ君 / マァムがレオナを…（pixiv、基準作品）
[ 2] [ ] キモデブ君 / マァムがレオナを…
          · fanbox にも同じ題名の作品があります
```

基準作品は利用者自身が選んだものなので、重複していても既定から外さない。

> **未対処**: 本文 0 文字の保存行そのものは、コレクション機能の範囲外のため触れていない。診断画面での検出・整理を別途検討する価値がある。

## 7. 第1回の診断の訂正

「単なる言及リンクが `link_order` を設定して順序を壊す」と書いたが、**誤りだった**。`strongest_link_with_seeds` は `continues_to` / `continues_from` のときしか `link_order` を返しておらず、`mentions` は最初から順序辺になっていない。

実際の原因は **`link_depth`（基準作品からのリンク到達段数）が比較子の第 2 キーだったこと**である。これは「近さ」であって読む順ではない。基準作品から参照されているだけの作品が、題名に書かれた話数を追い越していた。

修正後の比較順:

```
link_order（continues_to/from の明示的な方向）
  → series_order（公式順）
  → episode_order（題名の話数）
  → link_depth（近さ。同点処理のみ）
  → member_score
```

### 再試験で新たに見つかり、対処した 2 件

**抜粋版の混入**: `【FANBOXサンプル】性杯戦争～…` が本編と一緒に既定選択されていた。本文が途中までしかない版で、一冊にすると同じ話の断片が混ざる。`サンプル / 体験版 / お試し / 抜粋` を含む題名を既定で未選択にした。

**弱いリンクの多段連鎖**: 用語集ページ `性杯戦争とは` が 4 段のリンク追跡で既定選択に入っていた。設計提案 6-6 の「弱い信号だけで 2 段以上連鎖させない」に反する。題名・公式順の裏付けが無い 2 段以上のリンク先は、候補には出すが既定では選ばないようにした。

## 13. テスト基盤: 一時ディレクトリの残留と、間欠失敗

### 判明したこと

`%TEMP%` に **5,786 個**の `piep_search_test_*` が残っていた。各テストは末尾で `remove_dir_all` を呼ぶが、panic や早期 return ではそこへ到達しない。1 つ 1 つが Tantivy 索引を含むため、容量も相当量に達していた。

`temp_paths()` に、1 時間より古い残骸を初回だけ掃除する処理を入れた（実行中の別プロセスを巻き込まないための時間条件）。既存の 5,786 個も削除済み。

### ただし、間欠失敗は解消していない

当初これがフレークの原因だと考えたが、**掃除後も 3 回に 1 回程度の頻度で失敗する**。

```
run 1: ok        252 passed
run 2: FAILED    251 passed; 1 failed
run 3: ok        252 passed
```

失敗するテストは毎回変わり、いずれも同じ症状:

```
Tantivy commit failed: An IO error occurred: 'アクセスが拒否されました。 (os error 5)'
```

- 単体実行では必ず成功する。並列実行時のみ発生する。
- **本作業の変更前から発生していた**（初回調査時点で確認済み）。今回の修正が持ち込んだものではない。
- CI は `cargo test` をゲートにしているため、**無関係な PR がランダムに赤くなる状態が続いている**。

残骸の掃除は容量とディスク負荷には効くが、この失敗の根本原因ではなかった。

### 解決（第3回・同日）

CI でも同じ形で 2 件落ち、リリースを止めた。原因は並列実行そのものだった。

Tantivy はディレクトリごとに `IndexWriter` を 1 つしか許さない。アプリは起動時に
ライブラリへ排他ロックを取るため、1 プロセスが開くライブラリは常に 1 つである。
索引を使うテストを同時に走らせると、その前提を外れて数十の writer が 1 プロセスに
並び、Windows ではそこでコミットが `Access is denied` になる。**製品が決して行わない
使い方をテストだけが行っていた。**

CI の `cargo test` を `--test-threads=1` にした。手元で 3 回連続 252 件緑を確認して
いる（並列では約 3 回に 1 回失敗していた）。所要は 7 秒から 25 秒になるが、この
step の大半は 20 分のコンパイルであり、体感差はない。

手元の既定は並列のままなので、ローカルでは引き続き間欠的に失敗しうる。ゲートで
ある CI が決定的であることを優先した。
