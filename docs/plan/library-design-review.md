# 新ライブラリ基盤の設計評価

評価日: 2026-11-11。対象: `codex/library-data-v2`（デスクトップ・サーバー）と
`piep-android` の `codex/android-library-v2-design`。設計文書 5 本と実装を読み、稼働棚
（27,847 作品・約 30 GiB）の全件試走と読み取り専用の調査で確かめた。

この文書は評価と決定を残す。仕様そのものは [データモデル](library-data-model.md)、
[可逆保管](library-lossless-storage.md)、[API v2](library-api-v2.md)、
[Android の境界](android-library-v2.md) を正本とする。

## 1. 結論

保管の土台とデータの分け方は良い。全棚 124,916 ファイルが長さと SHA-256 まで一致して
往復しており、ここは作り直さない。

問題は土台の外側にあった。

- 実データを通していなかったため、移行器が「一件の異常で領域全体を止める」作りだった。
- 保存と検証が、同じ実体を何度も読み直し、DB を長くふさいでいた。
- 削除と回収、切り替えの道筋、一つにまとめた配信（bundle）がまだ設計の文だけで、実装がない。
- デスクトップと携帯で同じものを二度作る構造が、新しい基盤でも残る。両リポジトリの
  設計文書は、実体取得の URL の形で既に食い違っている。

前の二つはこの評価で直した（3 章）。後の二つは決めることを 4 章に挙げる。

## 2. 変えないもの

| 設計 | 評価の根拠 |
| --- | --- |
| 作品・作者の改稿・保存状態・取得観測・元ファイル・物理保管を分ける | 旧棚で実際に起きていた問題（修復と改稿の混同、パスからの所属推測、原寸化で過去の表示が変わる）を構造で止められる |
| 内容ハッシュの不変実体、raw / Zstandard、検証してから公開 | 全棚で全件一致。壊れた実体は検証済みの中身で置き換えられる |
| STRICT・複合 FK・公開後は書き換えない | 別作品の保存状態を現在版・編集の基準・読書位置に指定できないことを DB が保証する |
| 要求 ID・期待する更新世代・端末の時計で勝者を決めない | 再送と遅れた応答で状態が戻らない |
| 通信では UUID・ハッシュ・64 bit 値を文字列で検査する | JavaScript で丸められない。未知の項目を黙って受け入れない |
| 所属を照合してから実体を渡す。ハッシュを知っているだけでは取れない | 重複排除が権限の境界を越えない |

容量は 0.89 倍にとどまる。棚の半分を占める PNG が縮まないためで、方式の欠陥ではない。
新基盤の利点は容量ではなく、版を固定した保存と完全性の検証にある。画面や説明で
「容量を減らす機能」として扱わない。

## 3. この評価で直したもの

### 3.1 保存のたびに同じ実体を三度読んでいた

一つのファイルを保管するたびに、書いた実体を「公開前の読み戻し」「登録前の検査」
「保存表現の確認」の三回、全部読んで展開し SHA-256 を計算していた。試走で読み込み量が
旧棚の約 10 倍（321 GB）になった主因の一つで、日常の保存でも同じ無駄が出る。

- 保管 crate に `put_stored` を足した。保管の中で読み戻して確かめた結果と、各部分の
  保存表現（raw / zstd と長さ）を一緒に返す。
- 登録前の検査は、保管したばかりのものでは省き、保管済みのものでは一度の読み取り
  （`inspect`）にした。`chunk_info` も一度だけ読む。
- 棚の側は `store_bytes`・`store_path` に置き換えた。保管後の読み取りは三回から一回になる。

再試走で、移行中の読み込み量は約 299 GiB から 194.6 GiB に減った。時間は変わらなかった（6 章）。

### 3.2 検証と読み取りが DB をふさいでいた

`Library` は接続を一本だけ持ち、読み取りも書き込みも同じ錠に並んでいた。全ファイルの
検証（全棚で 15.5 分）はその間ずっと錠を持つので、アプリへつなぐと検証中は保存も一覧も
読書も止まる。設計文書は「単一の書き手と読み取りプール」としていたが、実装がなかった。

- `Library::reader()` を足した。読み取り専用の接続を貸し出し、借りている間は同じ時点の
  状態を読む。WAL なので、保存の確定や検証と互いに待たない。
- 書き込みをしない 32 か所（読書用文書、資産の所属照合、履歴、一覧、保存した検索、
  配信の manifest など）を読み取り専用の接続へ移した。
- 検証は、一ファイルごとに DB を手放して実体を読む形にした。

### 3.3 一件の異常で領域全体の移行が止まっていた

試走の報告では「作者の一件」「作品の一件」が原因に見えたが、先頭の一件で止まって
いたので残りが見えていなかっただけだった。旧棚を読み取り専用で調べ直した結果は次のとおり。

| 領域 | 実際の件数 | 中身 |
| --- | ---: | --- |
| プロフィールの版 | 47 | 5 版は同じ中身の画像が別名で二つ。42 版は後から同じ場所へ足された別の表紙 |
| 作品とシリーズの所属 | 1 作品 | 作者がシリーズを移した後も、前のシリーズの行が旧表に残っていた |

直した規則。

- **異常は一件ずつ未解決にする。** 行ごとに savepoint で囲み、その行の書き込みだけを戻して
  理由と一緒に記録し、ほかの行は移行する。理由は移行先に保管し、再起動後も読める。
  表の完了の印は、未解決が一件もないときだけ付けるので、直した後にやり直せる。
  中止・錠・保存先の障害は、どの行にも起きるので今までどおり全体を止める。
- **同じ中身の別名は一つの画像として扱う。** 旧実装が名前の付け方を途中で変えた跡で、
  どちらのパスも移行済みにする。
- **中身の違う画像が並ぶ版は、その版の原本が記録した URL から付いた名前の一枚を採る。**
  42 版すべてで、記録した個数・容量とちょうど合うことを確かめた。足された一枚は使わずに
  置き、所属の未解決として残す（4.7 で規則を決める）。
- **版より前の配置から残った画像は、その版の画像にしない。** 原本に URL の記録がない
  用途の画像を外すと版の記録にちょうど合う場合に限る（5 版で確認）。
- **「画像なし・容量 0」と記録された版は、画像を持たない版として移す。** 再試走で初めて
  見えた 784 版（pixiv のシリーズ 750、作者 4 など）。原本に表紙の URL があれば、当時は
  未取得として残す。そのフォルダーに後から足された画像は使わずに置き、未解決に残す。
- **過去の保存状態とだけ一致する所属は、消し残りとして解決する。** 現在版の所属が
  すべて旧表にも載っているときに限り、一致した保存状態を証跡に残す。旧表に現在の所属が
  なく過去の所属だけがある場合は、食い違いなので未解決のままにする。

### 3.4 作り直せるものを原本として保管していた

- 全文索引（7.8 GiB）・意味検索のモデル（0.45 GiB）・索引の作業用の写しは、旧実装が
  保存フォルダーの下へ置いていた。読まずに除き、除いた理由だけを記録する。
- 索引の進み具合を持つ旧表 3 つと旧スキーマの版の印は、行を保管しない。行数や中身を
  証跡に入れないので、旧アプリを使って索引が進んでも移行のやり直しを止めない。
- 以前のバックアップのフォルダーは、変換も整理もせず元の場所に残す。
- 利用者が選んだ設定（意味検索を使うか）は派生物ではないので、規則ができるまで未解決に残す。

### 3.5 R-18 の制限画像 1,904 件

初回の保存で受け取った未ログイン向けの画像が、後の補完で版の記録から外れ、ファイルだけ
残っていた。移行済みの版の原本が `cover_url` に記録した名前で、その版の表紙の場所にある
ファイルだけを「差し替え前の表紙」として結び、原本のパスと URL を証跡に残す。名前が
似ているだけのファイルは結ばない。

### 3.6 確認

- 新ライブラリの試験 151 件と API v2 の試験 6 件。今回足した 6 件のうち 5 件は稼働棚で
  見つかった形をそのまま再現し、1 件は保存の確定の途中でも読み取りと検証が返ることを確かめる。
- デスクトップ全体の試験 1,124 件。
- 保管 crate の試験 14 件（3 件追加）、`cargo clippy -D warnings`、`cargo fmt --check`。
- 全棚の再試走（2026-11-12）。未解決は 10,997 件から 287 件になり、すべて 4.7 の表で
  説明がつく。131,977 ファイルの復元は全件一致した（6 章）。

## 4. 決めること

重い順に並べる。上の三つが、版を切れるかどうかを決める。

### 4.1 切り替えの道筋がない

新基盤は約 2.4 万行あるが、アプリのどこにもつながっていない。旧モデルの側は次の規模で、
設計文書は二重書き込みと恒久的な互換層を禁じている。このままだと、すべてを作り替えて
一度に切り替えるしかない。

| 旧モデルに依存するもの | 規模 |
| --- | ---: |
| 画面から呼ぶ IPC | 202 個 |
| 問い合わせの関数 | 276 個（約 4 万行） |
| 保存パスの列を使う箇所 | 877 か所 |
| サーバーの HTTP の入口（携帯向け API v1 を含む） | 33 個 |

**決定（提案）: 二重書き込みはしないまま、読み取りを先に一本通す。**

1. **移行をやり直せるものにする。** 旧棚を正本にしたまま、新しい棚を何度でも作り直せれば、
   二重書き込みは要らない。今は旧棚が少しでも変わると同じ移行先へ続けられないので、
   変わった分だけを足す再移行を作る。全件でも 20 分以内を目標に実測する。
2. **新しい棚を読み取り専用で開く。** 一覧 → 作品の詳細 → 読書を、移行した棚から表示する。
   ここで一覧に要る列、読み取りの速さ（従来比 `max(20%, 100ms)` 以内）、画像の配信の
   仕方が実測で決まる。画面は視覚基準で旧棚と突き合わせる。
3. **サーバーと携帯の読み取りを同じ契約へ移す。** 4.3 の bundle と 4.5 の共通化を先に入れる。
4. **書き込みを領域ごとに移す。** 取得と保存、お気に入り・位置・タグ・コレクション・編集、
   検索の索引づけ、EPUB / PDF。
5. 切り替える。旧棚は残し、容量の解放は別の操作にする。

新しい領域（ジョブの実行キュー、AI ノートなど）の移行は、2 が動くまで足さない。
土台を広げるほど、旧系統との差と、実データで初めて分かる問題が増える。

### 4.2 削除と回収がない

作品・保存状態・実体を消す操作が一つもない。保存の途中で落ちたときに残る実体と、
壊れて退けた実体（`.damaged`）を片付ける処理もない。スキーマの `storage_operations` は
どこからも使われていない。

- 作品の削除は `library_items` と現在の参照を外す操作として実装する（設計どおり）。
- 回収は「全参照から到達できる実体に印を付け、残りを隔離し、7 日後にも未参照なら消す」。
  読み取り専用の接続で印付けができるので、書き込みを止める時間は隔離の確定だけで済む。
- `storage_operations` は、使う処理と一緒に実装するか、初回の有効化の前に外す（4.6）。

4.1 の 4（書き込みの移行）より前に要る。

### 4.3 配信が一ファイルずつで、同時 4 件を越えると即座に断る

今の API v2 は、資産ごとに manifest を取り、部分ごとに取得する。画像 100 枚の作品は
201 回の要求になる。同時に読めるのは全端末あわせて 4 件で、越えた要求は待たせずに 429 を返す。
携帯が一台で並列に取るだけで、二台目は読めなくなる。

- **読書 bundle を一回の応答にする。** 読書用文書・対応表・全資産の file 記述（ハッシュ・
  長さ・部分の一覧）をまとめて返す。部分の取得は今の形を残す。
- **同時数は端末ごとに数え、短く待たせる。** 全体の上限は残し、一台が占有できないようにする。
- **実体取得の URL を一つに決める。** デスクトップの実装は
  `/entities/{e}/views/{snapshot|edit}/{id}/resources/{kind}/files/{file}/chunks/{ordinal}`、
  Android の設計文書は `/works/{w}/snapshots/{scope}/files/{fileHash}/chunks/{chunkHash}`。
  実装済みの前者を正とし、Android の文書を直す。
- 部分の取得に付けている ETag は役に立たない（中身のハッシュで指定して取るので、
  持っていれば要求しない）。304 のために実体を読んで検証する処理ごと外してよい。

### 4.4 利用者の単位

スキーマは利用者 ID を全面に持つが、使うのは一人である。API v2 の許可表
（端末登録・棚 → 利用者）はメモリー上だけで、再起動で消える。

**決定（提案）: 当面、棚の持ち主を唯一の利用者とする。** 登録済みの端末はすべて持ち主に
結ぶ。移行器は既に棚の ID を持ち主として使っている。利用者 ID の列は残す（安く、後で
増やせる）が、許可の管理画面や永続の許可表は、二人目が要るときまで作らない。

### 4.5 デスクトップと携帯で同じものを二度作っている

今の重複は次のとおり。片方を変えるたびに、もう片方を別のリポジトリで手で合わせている。

| 重複 | デスクトップ | Android |
| --- | --- | --- |
| 通信の型 16 個 | `src-tauri/src/server/dto.rs` | `pc_client.rs` と `pcApi.ts`（TypeScript 26 型） |
| 検索の要求と結果 | `MobileSearchRequest` / `MobileSearchPage` | `PcSearchCriteria` / `SearchPage` |
| 登録文字列・接続確認・登録結果 | `server/http.rs` | `PairingPayload` / `Hello` / `PairResult` |
| 本文リンクの判定 | `src/lib/contentLinks.ts` | `src/contentLinks.ts`（手写しで、既にずれている） |
| 本文から文字を取り出す | `plain_text_from_reader_html` | `offline_index.rs` の `page_text` |

新基盤でも、設計文書は「サーバーが生成した HTML を bundle に入れて携帯で表示する」として
おり、読書表示がサーバーと携帯の二段になる。

**決定（提案）: 読書の契約を一つにし、表示の生成も一つにする。**

- `piep-android` を `piep` リポジトリへ統合する（了承済み）。共通 crate は path で参照し、
  git rev の固定をやめる。サーバーと携帯を一つの PR で変えられる。
- 通信の型は crate に置き、TypeScript の型は生成する。v1 の型は `piep-reader-protocol`、
  v2 は既存の `piep-library-protocol`。
- 読書表示は Rust の共通 crate にする。入力は `piep-reader-v1` の文書、出力は表示用の
  HTML と位置の対応。デスクトップも携帯も Rust の層を持つので、同じ crate を手元で呼べる。
  bundle へ生成済みの HTML を入れる必要がなくなり、表示の規則を変えても取り直しが要らない。
- 画面の規則は、見た目を持たない TypeScript の共通パッケージに置く。2026-11-12 に両方を
  突き合わせると、表紙の模様（`coverSigil.ts`、67 行）は一字も違わない写しで、本文リンクの
  宛先の解釈（`contentLinkTarget`）も同じだった。最初に移すのはこの二つと、並べ替えの
  名前、作品の日付・進み具合の文言、API の型。
- 見た目は土台だけを共有する。配色・余白・文字・アイコンを一つの定義から、デスクトップの
  テーマと携帯の CSS 変数の両方へ出す。一覧・シート・下のナビなどの部品は携帯専用のまま
  残し、Mantine は携帯へ持ち込まない。

### 4.6 スキーマの整理は、最初の有効化の前に一度だけ

本番の棚はまだ一つもないので、今なら形を変えられる。有効化した後は前方移行しかできない。

- 9 段の移行を一つの定義にまとめる。途中で作って置き換えた表（`saved_searches` の旧定義など）を残さない。
- 連結表とハッシュを主キーにする表（`file_chunks`、`snapshot_tags`、`snapshot_media` など）を
  `WITHOUT ROWID` にする。行ごとの索引が一本減る。
- `chunk_storage` の主キーは `(chunk, codec)` だが、実体は部分ごとに一つしかない。
  主キーを部分だけにするか、実体のヘッダーから分かる値なので表を外す。
- 逆引きの索引（タグ → 作品、file → 参照元）は、4.1 の 2 と 4.2 で実際の問い合わせが
  決まってから、実行計画を見て足す。

効果は試走で、DB の大きさと時間を測って決める。測る前に変えない。再試走の DB は 430 MB
（プロフィール 5,058 版が入った分、初回の 380 MB より増えた）。これを整理の前の基準にする。

### 4.7 移行器に残る規則

| 残り | 件数 | 決め方 |
| --- | ---: | --- |
| シリーズの「完結」の印 | 142 | 今の値が保存済みの原本にない（128 件は 0、14 件は 1）。後の軽い確認で更新された値で、版を作らずに書き換えていた。新モデルに置き場所がないので、取得元の観測（`source_state`）へ移すか、保存状態を一つ足すかを決める |
| 画像ありの版へ後から足された表紙 | 47 | シリーズ 42、作者 5。今の `cover_path` が指すなら、同じ改稿の補完として保存状態を一つ足す |
| 画像なしの版へ後から足された表紙 | 61 | シリーズ 60、作者 1。上と同じ規則で扱える |
| 記録のない版のフォルダー | 6 ファイル | DB に行がない作者 1 人の 2 版と、現在版より先のシリーズ 1 版。保存の途中で残ったもの。原本は読めるので、孤立した保存状態として保管するか、理由を付けて除く |
| EPUB の雛形 | 27 | **実装済み（2026-11-12）。** 利用者が編集するファイルで、どの作品にも属さない。中身と元のパスをそのまま保管し、`__user_files__` の記録からパスで引く。専用の表は 4.6 の整理で足す |
| `settings.json` | 1 | **実装済み。** アプリの設定であって棚のデータではない。アプリのフォルダーに残し、棚へは写さない。理由を記録して済んだものとする |
| `server/` | 1 | **実装済み（2026-11-14）。** 下の「server/ の規則」 |
| 意味検索を使うかの設定 | 1 行 | **実装済み。** 行は原記録として保管し、正規化の対象にしない。切り替えのときにアプリの設定として引き継ぐ |

**2026-11-13 に、残りの規則も実装した。** 稼働棚の作者とシリーズの分（作者 370、シリーズ 1,657、
版 5,058、ファイル 8,995）だけを別の場所へ写して移行し、この範囲の未解決が 256 件から 0 件に
なること、移行先の検証が通ることを確かめた。

| 残り | 件数 | 規則 |

### 6.5 一覧を新しい棚から引く（4.1 の 2、2026-11-14）

一覧の表 `work_current_projection` を作り直した（スキーマ 10）。旧棚の並べ替え 9 種
（保存日・公開日・更新日・題・作者・文字数・容量・画像の数・版）の値を一行に持ち、
鍵ごとに索引を張る。続きのページは「前のページの最後の鍵と作品」で引くので、何ページ目でも
索引を読む量は同じ。全並べ替えで表を並べ替え直さないことを試験で確かめている
（`EXPLAIN QUERY PLAN` に一時の B 木が出ない）。

- **派生物として扱う。** 行は保存状態・有効な編集・利用者の状態から一つの問い合わせで作る。
  取り込み・編集の有効化・お気に入り・移行の各書き込みが同じ取引の中で作り直す。
  全件の検証は、保存状態から作った値と一行ずつ突き合わせる。
- **作り方の版（recipe）を持つ。** 版が古い行や欠けた行があれば、書き込みで開いたときに
  全行を作り直す（2.8 万件で一度だけ）。並べ替えの鍵や絞り込みの列を後から足すときは、
  列と索引を足して版を上げれば済み、棚の移行をやり直さなくてよい。
- 本文の文字数は本文ファイルだけで決まるので、ファイルごとに一度だけ数えて
  `body_text_stats` に残す（検証で本文と照らす）。一覧の表はこれを読むだけで作り直せる。
- 旧棚と意味を合わせた点: 保存日は「いまの改稿を初めて保存した時刻」（改稿の発見時刻。
  補完や同じ中身の取り直しでは変わらない）。公開日・更新日がなければ保存日へ寄せる。
  題は有効な編集の題を優先し前後の空白を除く。FANBOX の文字数は段落と見出しの空でない文を
  空行でつないで数える。pixiv の更新日は原本に載らないので、取得元の状態
  （`source_entity_state.source_updated_at`）へ移した。
- 旧棚と意味を変えた点: 容量は「保存した原本・画像・添付で、同じ中身は一度だけ」。
  原本から取り出した本文は数えない。旧棚は同じ画像の重複を二度数えていた。
- 一覧は今のところ持ち主一人のもの（編集の題とお気に入りは棚の持ち主の値）。
  利用者を分けるとき（4.4）は、利用者ごとの列を別の表に分ける。

**稼働棚から 602 作品を抜き出した棚での比較**（編集のある 2 作品を含む。旧棚は同じ作品だけの
DB の写しを、本番と同じ検索関数で引いた。1 ページ 80 件、release 版、ミリ秒）:

| 項目 | 旧棚 | 新しい棚 |
| --- | ---: | ---: |
| 並べ替え 18 通り（9 種×昇降）の順序 | — | **全部一致**（同じ値の中の順まで） |
| 値の食い違い | — | 容量の 2 作品だけ（上の重複の数え方の違い。中身は欠けていない） |
| 最初のページ（温まった状態、中央値） | 0.55〜2.60 | 0.55〜0.73 |

題の並べ替えは旧棚の 2.1〜2.6 から 0.7 前後になった（旧棚は編集の題を行ごとに引いて
並べ替えている）。最初の版では、カードごとに取得元の ID を引く問い合わせが索引を選び違え、
80 件で 2.7ms かかっていた。ID を一覧の表へ移して消えた。目標の `max(20%, 100ms)` には
どれも十分に収まる。比較の道具は `piep-library compare-list <旧棚の piep.db の写し>
<空の作業フォルダー> <新しい棚> [読書を比べる作品数]`。旧 DB は開くときに後片付けを
書き込むので必ず写しを渡す（写しの「中断した保存」の記録は、本物の保存先を動かさないよう消す）。

**全棚（27,847 作品）での比較。** 稼働棚の DB の写しと、それを移行した新しい棚で比べた
（移行 35 分・未解決 0・検証 11 分で 132,119 ファイルすべて一致。新しい DB は 421MB）。
一度目の比較で、602 作品の抜き出しでは出なかった食い違いが二つ見つかり、直して移行し直した。

- **後の版で消えた画像が、いまの保存状態に残っていた。** 旧棚の版は「その版のフォルダーの
  画像と添付がすべて」だが、移行の版は画像を「分かっている分だけ」として取り込んでいたので、
  前の版の画像を引き継いでいた（画像の数で 3 作品）。移行の版は画像も「その版で全部」にした。
- **題の末尾の改行と全角の空白。** 旧棚は保存時に Unicode の空白を除いていたが、
  新しい棚は ASCII の空白しか除いていなかった（69 作品、題の順序がずれた）。Unicode の
  空白まで除くようにした。残る 7 作品は、旧棚の題に末尾の全角空白や改行が残っているもので、
  新しい棚では除く。順序は一致している。

二度目（直したあと、下の鍵の書き方の修正も入れた release 版、1 ページ 80 件、ミリ秒、

| 項目 | 旧棚 | 新しい棚 |

二度目の数字が公平。表紙は新しい棚のほうが 0.09ms 遅い（指紋から実体を引く分）が、
目標の `max(20%, 100ms)` には収まる。

鍵の書き方を直す前は、公開日・更新日・題・作者の真ん中のページが 3〜12ms かかっていた。式（公開日が
なければ保存日、など）や大文字小文字を区別しない照合の索引では、`(鍵, 作品) < (?, ?)` という
組の比較を SQLite が索引の範囲に使えず、索引を頭から読んでいた（`EXPLAIN` で SCAN）。この 4 種は
「鍵の範囲で索引を絞ってから、同じ値の中を作品で絞る」書き方に変え、試験でも続きのページが
索引の途中から読む（SEARCH）ことを確かめる。列そのものの鍵は組の比較のままにする
（同じ値が数万件ある鍵では、こちらのほうが速い）。

まだのもの: 本文の検索、画面の視覚基準での突き合わせ、読書文書を HTML にする
ところの時間（旧棚は最初のページの HTML まで作る。新しい棚は本文と資産の対応までで、
描画をどこでするかは 4.5 の共通化と一緒に決める）。絞り込みは 6.6。

### 6.6 一覧の絞り込み（スキーマ 11）

旧棚の一覧の絞り込み（本文の検索を除く 25 種）を `WorkFilter` に移した。項目はすべて
「かつ」でつなぎ、件数とページは同じ条件で引く。

- **一覧の表の列で絞るもの:** 取得元・種類・お気に入り・監視・編集の有無・文字数・画像の数・
  容量・版・日付。日付は並べ替えと同じ式で絞るので、日付で並べて日付で絞るときは同じ索引を使う。
- **保存状態の関係から引くもの:** 表紙・シリーズの有無・画像と添付・タグ・作者・シリーズ。
  タグや名前の集まりは JSON の配列一つで渡し、数によって SQL の形が変わらないようにした
  （問い合わせを使い回せる）。作者・シリーズ・タグから作品を引く逆向きの索引を足した
  （作者やシリーズの画面でも使う）。
- **作品ごとの更新の監視**は、お気に入りと同じ利用者ごとの状態にした（`work_user_state.watching`）。
  旧棚の `downloads.watch_updates` は移行器が移していなかったので、移すようにした（今の棚では全件 0）。
- **取得元の候補**は旧棚と同じ三つの判断（未判断・保留・非表示）にした。以前の表は「非表示」を
  許さず、利用者が候補を外していると移行が止まるところだった。保留の理由（未完・閲覧制限など）は
  原本の JSON にしかなかったので、列に出した。
- **旧棚の「修復」の版。** 同じ版を取り直して欠けを埋めた版（2026-10-31 の取り直しなど）は、
  中身が違えば版を分けるが、作者の改稿ではない。旧棚は改稿の絞り込みに数えないので、新しい棚でも
  版に印（`source_revisions.repair`）を残して数えない。版の番号には数える（旧棚の表示と同じ）。
  602 作品の抜き出しでは 42 作品がこれで、最初の版の題が空で、タグ・説明がなかった。

旧棚と意味を変えたところ: 日付はミリ秒の範囲で受け取る（日の区切りは画面が決める。旧棚は
UTC の暦日だった）。公開日・更新日のない作品は保存日で絞る（並べ替えと同じ値）。作者の名前は、
いま名乗っている名前のほか、保存したどの版で名乗った名前でも引ける。作者・シリーズは取得元の
ID でなく棚の ID で指す（`entity_by_key` で引ける）。シリーズを題で探す旧棚の逃げ道はなくした。

比較の道具は `piep-library compare-filters <旧棚の piep.db の写し> <空の作業フォルダー> <新しい棚>`。
旧棚の実際の分布から値（よく使われるタグ・作者・シリーズなど）を選び、43 通りの絞り込みで
作品の集まりを全件突き合わせる。602 作品の抜き出しでは 43 通りすべてが一致した。全棚は未確認。
