# 新ライブラリ基盤の設計評価

評価日: 2026-11-11。対象: `codex/library-data-v2`（デスクトップ・サーバー）と
`piep-android` の `codex/android-library-v2-design`。設計文書 5 本と実装を読み、稼働棚
（27,847 作品・約 30 GiB）の全件試走と読み取り専用の調査で確かめた。

この文書は評価と決定を残す。仕様そのものは [データモデル](library-data-model.md)、
[可逆保管](library-lossless-storage.md)、[API v2](library-api-v2.md)、
[Android の境界](android-library-v2.md) を正本とする。

## 1. 結論

保管の土台とデータの分け方は良い。全棚 124,916 ファイルが長さと SHA-256 まで一致して
往復しており、ここは作り直さない。

問題は土台の外側にあった。

- 実データを通していなかったため、移行器が「一件の異常で領域全体を止める」作りだった。
- 保存と検証が、同じ実体を何度も読み直し、DB を長くふさいでいた。
- 削除と回収、切り替えの道筋、一つにまとめた配信（bundle）がまだ設計の文だけで、実装がない。
- デスクトップと携帯で同じものを二度作る構造が、新しい基盤でも残る。両リポジトリの
  設計文書は、実体取得の URL の形で既に食い違っている。

前の二つはこの評価で直した（3 章）。後の二つは決めることを 4 章に挙げる。

## 2. 変えないもの

| 設計 | 評価の根拠 |
| --- | --- |
| 作品・作者の改稿・保存状態・取得観測・元ファイル・物理保管を分ける | 旧棚で実際に起きていた問題（修復と改稿の混同、パスからの所属推測、原寸化で過去の表示が変わる）を構造で止められる |
| 内容ハッシュの不変実体、raw / Zstandard、検証してから公開 | 全棚で全件一致。壊れた実体は検証済みの中身で置き換えられる |
| STRICT・複合 FK・公開後は書き換えない | 別作品の保存状態を現在版・編集の基準・読書位置に指定できないことを DB が保証する |
| 要求 ID・期待する更新世代・端末の時計で勝者を決めない | 再送と遅れた応答で状態が戻らない |
| 通信では UUID・ハッシュ・64 bit 値を文字列で検査する | JavaScript で丸められない。未知の項目を黙って受け入れない |
| 所属を照合してから実体を渡す。ハッシュを知っているだけでは取れない | 重複排除が権限の境界を越えない |

容量は 0.89 倍にとどまる。棚の半分を占める PNG が縮まないためで、方式の欠陥ではない。
新基盤の利点は容量ではなく、版を固定した保存と完全性の検証にある。画面や説明で
「容量を減らす機能」として扱わない。

## 3. この評価で直したもの

### 3.1 保存のたびに同じ実体を三度読んでいた

一つのファイルを保管するたびに、書いた実体を「公開前の読み戻し」「登録前の検査」
「保存表現の確認」の三回、全部読んで展開し SHA-256 を計算していた。試走で読み込み量が
旧棚の約 10 倍（321 GB）になった主因の一つで、日常の保存でも同じ無駄が出る。

- 保管 crate に `put_stored` を足した。保管の中で読み戻して確かめた結果と、各部分の
  保存表現（raw / zstd と長さ）を一緒に返す。
- 登録前の検査は、保管したばかりのものでは省き、保管済みのものでは一度の読み取り
  （`inspect`）にした。`chunk_info` も一度だけ読む。
- 棚の側は `store_bytes`・`store_path` に置き換えた。保管後の読み取りは三回から一回になる。

再試走で、移行中の読み込み量は約 299 GiB から 194.6 GiB に減った。時間は変わらなかった（6 章）。

### 3.2 検証と読み取りが DB をふさいでいた

`Library` は接続を一本だけ持ち、読み取りも書き込みも同じ錠に並んでいた。全ファイルの
検証（全棚で 15.5 分）はその間ずっと錠を持つので、アプリへつなぐと検証中は保存も一覧も
読書も止まる。設計文書は「単一の書き手と読み取りプール」としていたが、実装がなかった。

- `Library::reader()` を足した。読み取り専用の接続を貸し出し、借りている間は同じ時点の
  状態を読む。WAL なので、保存の確定や検証と互いに待たない。
- 書き込みをしない 32 か所（読書用文書、資産の所属照合、履歴、一覧、保存した検索、
  配信の manifest など）を読み取り専用の接続へ移した。
- 検証は、一ファイルごとに DB を手放して実体を読む形にした。

### 3.3 一件の異常で領域全体の移行が止まっていた

試走の報告では「作者の一件」「作品の一件」が原因に見えたが、先頭の一件で止まって
いたので残りが見えていなかっただけだった。旧棚を読み取り専用で調べ直した結果は次のとおり。

| 領域 | 実際の件数 | 中身 |
| --- | ---: | --- |
| プロフィールの版 | 47 | 5 版は同じ中身の画像が別名で二つ。42 版は後から同じ場所へ足された別の表紙 |
| 作品とシリーズの所属 | 1 作品 | 作者がシリーズを移した後も、前のシリーズの行が旧表に残っていた |

直した規則。

- **異常は一件ずつ未解決にする。** 行ごとに savepoint で囲み、その行の書き込みだけを戻して
  理由と一緒に記録し、ほかの行は移行する。理由は移行先に保管し、再起動後も読める。
  表の完了の印は、未解決が一件もないときだけ付けるので、直した後にやり直せる。
  中止・錠・保存先の障害は、どの行にも起きるので今までどおり全体を止める。
- **同じ中身の別名は一つの画像として扱う。** 旧実装が名前の付け方を途中で変えた跡で、
  どちらのパスも移行済みにする。
- **中身の違う画像が並ぶ版は、その版の原本が記録した URL から付いた名前の一枚を採る。**
  42 版すべてで、記録した個数・容量とちょうど合うことを確かめた。足された一枚は使わずに
  置き、所属の未解決として残す（4.7 で規則を決める）。
- **版より前の配置から残った画像は、その版の画像にしない。** 原本に URL の記録がない
  用途の画像を外すと版の記録にちょうど合う場合に限る（5 版で確認）。
- **「画像なし・容量 0」と記録された版は、画像を持たない版として移す。** 再試走で初めて
  見えた 784 版（pixiv のシリーズ 750、作者 4 など）。原本に表紙の URL があれば、当時は
  未取得として残す。そのフォルダーに後から足された画像は使わずに置き、未解決に残す。
- **過去の保存状態とだけ一致する所属は、消し残りとして解決する。** 現在版の所属が
  すべて旧表にも載っているときに限り、一致した保存状態を証跡に残す。旧表に現在の所属が
  なく過去の所属だけがある場合は、食い違いなので未解決のままにする。

### 3.4 作り直せるものを原本として保管していた

- 全文索引（7.8 GiB）・意味検索のモデル（0.45 GiB）・索引の作業用の写しは、旧実装が
  保存フォルダーの下へ置いていた。読まずに除き、除いた理由だけを記録する。
- 索引の進み具合を持つ旧表 3 つと旧スキーマの版の印は、行を保管しない。行数や中身を
  証跡に入れないので、旧アプリを使って索引が進んでも移行のやり直しを止めない。
- 以前のバックアップのフォルダーは、変換も整理もせず元の場所に残す。
- 利用者が選んだ設定（意味検索を使うか）は派生物ではないので、規則ができるまで未解決に残す。

### 3.5 R-18 の制限画像 1,904 件

初回の保存で受け取った未ログイン向けの画像が、後の補完で版の記録から外れ、ファイルだけ
残っていた。移行済みの版の原本が `cover_url` に記録した名前で、その版の表紙の場所にある
ファイルだけを「差し替え前の表紙」として結び、原本のパスと URL を証跡に残す。名前が
似ているだけのファイルは結ばない。

### 3.6 確認

- 新ライブラリの試験 151 件と API v2 の試験 6 件。今回足した 6 件のうち 5 件は稼働棚で
  見つかった形をそのまま再現し、1 件は保存の確定の途中でも読み取りと検証が返ることを確かめる。
- デスクトップ全体の試験 1,124 件。
- 保管 crate の試験 14 件（3 件追加）、`cargo clippy -D warnings`、`cargo fmt --check`。
- 全棚の再試走（2026-11-12）。未解決は 10,997 件から 287 件になり、すべて 4.7 の表で
  説明がつく。131,977 ファイルの復元は全件一致した（6 章）。

## 4. 決めること

重い順に並べる。上の三つが、版を切れるかどうかを決める。

### 4.1 切り替えの道筋がない

新基盤は約 2.4 万行あるが、アプリのどこにもつながっていない。旧モデルの側は次の規模で、
設計文書は二重書き込みと恒久的な互換層を禁じている。このままだと、すべてを作り替えて
一度に切り替えるしかない。

| 旧モデルに依存するもの | 規模 |
| --- | ---: |
| 画面から呼ぶ IPC | 202 個 |
| 問い合わせの関数 | 276 個（約 4 万行） |
| 保存パスの列を使う箇所 | 877 か所 |
| サーバーの HTTP の入口（携帯向け API v1 を含む） | 33 個 |

**決定（提案）: 二重書き込みはしないまま、読み取りを先に一本通す。**

1. **移行をやり直せるものにする。** 旧棚を正本にしたまま、新しい棚を何度でも作り直せれば、
   二重書き込みは要らない。今は旧棚が少しでも変わると同じ移行先へ続けられないので、
   変わった分だけを足す再移行を作る。全件でも 20 分以内を目標に実測する。
2. **新しい棚を読み取り専用で開く。** 一覧 → 作品の詳細 → 読書を、移行した棚から表示する。
   ここで一覧に要る列、読み取りの速さ（従来比 `max(20%, 100ms)` 以内）、画像の配信の
   仕方が実測で決まる。画面は視覚基準で旧棚と突き合わせる。
3. **サーバーと携帯の読み取りを同じ契約へ移す。** 4.3 の bundle と 4.5 の共通化を先に入れる。
4. **書き込みを領域ごとに移す。** 取得と保存、お気に入り・位置・タグ・コレクション・編集、
   検索の索引づけ、EPUB / PDF。
5. 切り替える。旧棚は残し、容量の解放は別の操作にする。
6. **旧版を残さない（2026-11-15 に利用者が決めた終わりの形）。** 切り替えを確かめたら、旧棚とその
   データ、旧系統のコード（旧モデルの問い合わせ・IPC・API v1・移行器の互換の分岐など）をすべて消す。
   棚の置き場も、今の仮の場所（アプリのフォルダーの隣の `…piep.library-v2`）でなく、きちんとした
   場所へ移す。旧系統に関わるものを何も残さない。

新しい領域（ジョブの実行キュー、AI ノートなど）の移行は、2 が動くまで足さない。
土台を広げるほど、旧系統との差と、実データで初めて分かる問題が増える。

### 4.2 削除と回収がない

作品・保存状態・実体を消す操作が一つもない。保存の途中で落ちたときに残る実体と、
壊れて退けた実体（`.damaged`）を片付ける処理もない。スキーマの `storage_operations` は
どこからも使われていない。

- 作品の削除は `library_items` と現在の参照を外す操作として実装する（設計どおり）。
- 回収は「全参照から到達できる実体に印を付け、残りを隔離し、7 日後にも未参照なら消す」。
  読み取り専用の接続で印付けができるので、書き込みを止める時間は隔離の確定だけで済む。
- `storage_operations` は、使う処理と一緒に実装するか、初回の有効化の前に外す（4.6）。

**2026-11-15。** 作品を棚から外す操作と回収を作った（6.28・6.29）。`storage_operations` は回収の記録に使う。

4.1 の 4（書き込みの移行）より前に要る。

### 4.3 配信が一ファイルずつで、同時 4 件を越えると即座に断る

今の API v2 は、資産ごとに manifest を取り、部分ごとに取得する。画像 100 枚の作品は
201 回の要求になる。同時に読めるのは全端末あわせて 4 件で、越えた要求は待たせずに 429 を返す。
携帯が一台で並列に取るだけで、二台目は読めなくなる。

- **読書 bundle を一回の応答にする。** 読書用文書・対応表・全資産の file 記述（ハッシュ・
  長さ・部分の一覧）をまとめて返す。部分の取得は今の形を残す。
- **同時数は端末ごとに数え、短く待たせる。** 全体の上限は残し、一台が占有できないようにする。
- **実体取得の URL を一つに決める。** デスクトップの実装は
  `/entities/{e}/views/{snapshot|edit}/{id}/resources/{kind}/files/{file}/chunks/{ordinal}`、
  Android の設計文書は `/works/{w}/snapshots/{scope}/files/{fileHash}/chunks/{chunkHash}`。
  実装済みの前者を正とし、Android の文書を直す。
- 部分の取得に付けている ETag は役に立たない（中身のハッシュで指定して取るので、
  持っていれば要求しない）。304 のために実体を読んで検証する処理ごと外してよい。

**2026-11-15。** 三つとも作った（6.30）。Android の設計文書の別の URL の形は、統合後の文書には
もう残っていない（この節だけが書いていた）。

### 4.4 利用者の単位

スキーマは利用者 ID を全面に持つが、使うのは一人である。API v2 の許可表
（端末登録・棚 → 利用者）はメモリー上だけで、再起動で消える。

**決定（提案）: 当面、棚の持ち主を唯一の利用者とする。** 登録済みの端末はすべて持ち主に
結ぶ。移行器は既に棚の ID を持ち主として使っている。利用者 ID の列は残す（安く、後で
増やせる）が、許可の管理画面や永続の許可表は、二人目が要るときまで作らない。

### 4.5 デスクトップと携帯で同じものを二度作っている

今の重複は次のとおり。片方を変えるたびに、もう片方を別のリポジトリで手で合わせている。

| 重複 | デスクトップ | Android |
| --- | --- | --- |
| 通信の型 16 個 | `src-tauri/src/server/dto.rs` | `pc_client.rs` と `pcApi.ts`（TypeScript 26 型） |
| 検索の要求と結果 | `MobileSearchRequest` / `MobileSearchPage` | `PcSearchCriteria` / `SearchPage` |
| 登録文字列・接続確認・登録結果 | `server/http.rs` | `PairingPayload` / `Hello` / `PairResult` |
| 本文リンクの判定 | `src/lib/contentLinks.ts` | `src/contentLinks.ts`（手写しで、既にずれている） |
| 本文から文字を取り出す | `plain_text_from_reader_html` | `offline_index.rs` の `page_text` |

新基盤でも、設計文書は「サーバーが生成した HTML を bundle に入れて携帯で表示する」として
おり、読書表示がサーバーと携帯の二段になる。

**決定（提案）: 読書の契約を一つにし、表示の生成も一つにする。**

- `piep-android` を `piep` リポジトリへ統合する（了承済み）。共通 crate は path で参照し、
  git rev の固定をやめる。サーバーと携帯を一つの PR で変えられる。
- 通信の型は crate に置き、TypeScript の型は生成する。v1 の型は `piep-reader-protocol`、
  v2 は既存の `piep-library-protocol`。
- 読書表示は Rust の共通 crate にする。入力は `piep-reader-v1` の文書、出力は表示用の
  HTML と位置の対応。デスクトップも携帯も Rust の層を持つので、同じ crate を手元で呼べる。
  bundle へ生成済みの HTML を入れる必要がなくなり、表示の規則を変えても取り直しが要らない。
- 画面の規則は、見た目を持たない TypeScript の共通パッケージに置く。2026-11-12 に両方を
  突き合わせると、表紙の模様（`coverSigil.ts`、67 行）は一字も違わない写しで、本文リンクの
  宛先の解釈（`contentLinkTarget`）も同じだった。最初に移すのはこの二つと、並べ替えの
  名前、作品の日付・進み具合の文言、API の型。
- 見た目は土台だけを共有する。配色・余白・文字・アイコンを一つの定義から、デスクトップの
  テーマと携帯の CSS 変数の両方へ出す。一覧・シート・下のナビなどの部品は携帯専用のまま
  残し、Mantine は携帯へ持ち込まない。

### 4.6 スキーマの整理は、最初の有効化の前に一度だけ

本番の棚はまだ一つもないので、今なら形を変えられる。有効化した後は前方移行しかできない。

- 9 段の移行を一つの定義にまとめる。途中で作って置き換えた表（`saved_searches` の旧定義など）を残さない。
- 連結表とハッシュを主キーにする表（`file_chunks`、`snapshot_tags`、`snapshot_media` など）を
  `WITHOUT ROWID` にする。行ごとの索引が一本減る。
- `chunk_storage` の主キーは `(chunk, codec)` だが、実体は部分ごとに一つしかない。
  主キーを部分だけにするか、実体のヘッダーから分かる値なので表を外す。
- 逆引きの索引（タグ → 作品、file → 参照元）は、4.1 の 2 と 4.2 で実際の問い合わせが
  決まってから、実行計画を見て足す。

効果は試走で、DB の大きさと時間を測って決める。測る前に変えない。再試走の DB は 430 MB
（プロフィール 5,058 版が入った分、初回の 380 MB より増えた）。これを整理の前の基準にする。

### 4.7 移行器に残る規則

| 残り | 件数 | 決め方 |
| --- | ---: | --- |
| シリーズの「完結」の印 | 142 | 今の値が保存済みの原本にない（128 件は 0、14 件は 1）。後の軽い確認で更新された値で、版を作らずに書き換えていた。新モデルに置き場所がないので、取得元の観測（`source_state`）へ移すか、保存状態を一つ足すかを決める |
| 画像ありの版へ後から足された表紙 | 47 | シリーズ 42、作者 5。今の `cover_path` が指すなら、同じ改稿の補完として保存状態を一つ足す |
| 画像なしの版へ後から足された表紙 | 61 | シリーズ 60、作者 1。上と同じ規則で扱える |

### 6.1 再試走の後で直したもの

読み込みの内訳をコードから追うと、同じファイルを作品の移行・資産の照合・管理領域の

鍵ごとに索引を張る。続きのページは「前のページの最後の鍵と作品」で引くので、何ページ目でも
索引を読む量は同じ。全並べ替えで表を並べ替え直さないことを試験で確かめている
（`EXPLAIN QUERY PLAN` に一時の B 木が出ない）。

- **派生物として扱う。** 行は保存状態・有効な編集・利用者の状態から一つの問い合わせで作る。
  取り込み・編集の有効化・お気に入り・移行の各書き込みが同じ取引の中で作り直す。
  全件の検証は、保存状態から作った値と一行ずつ突き合わせる。
- **作り方の版（recipe）を持つ。** 版が古い行や欠けた行があれば、書き込みで開いたときに
  全行を作り直す（2.8 万件で一度だけ）。並べ替えの鍵や絞り込みの列を後から足すときは、
  列と索引を足して版を上げれば済み、棚の移行をやり直さなくてよい。
- 本文の文字数は本文ファイルだけで決まるので、ファイルごとに一度だけ数えて
  `body_text_stats` に残す（検証で本文と照らす）。一覧の表はこれを読むだけで作り直せる。
- 旧棚と意味を合わせた点: 保存日は「いまの改稿を初めて保存した時刻」（改稿の発見時刻。
  補完や同じ中身の取り直しでは変わらない）。公開日・更新日がなければ保存日へ寄せる。
  題は有効な編集の題を優先し前後の空白を除く。FANBOX の文字数は段落と見出しの空でない文を
  空行でつないで数える。pixiv の更新日は原本に載らないので、取得元の状態
  （`source_entity_state.source_updated_at`）へ移した。
- 旧棚と意味を変えた点: 容量は「保存した原本・画像・添付で、同じ中身は一度だけ」。
  原本から取り出した本文は数えない。旧棚は同じ画像の重複を二度数えていた。
- 一覧は今のところ持ち主一人のもの（編集の題とお気に入りは棚の持ち主の値）。
  利用者を分けるとき（4.4）は、利用者ごとの列を別の表に分ける。

### 6.6 一覧の絞り込み（スキーマ 11・12）

旧棚の一覧の絞り込み（本文の検索を除く 25 種）を `WorkFilter` に移した。項目はすべて
「かつ」でつなぎ、件数とページは同じ条件で引く。

- **一覧の表の列で絞るもの:** 取得元・種類・お気に入り・監視・編集の有無・文字数・画像の数・
  容量・版・日付。日付は並べ替えと同じ式で絞るので、日付で並べて日付で絞るときは同じ索引を使う。
- **保存状態の関係から引くもの:** 表紙・シリーズの有無・画像と添付・タグ・作者・シリーズ。
  タグや名前の集まりは JSON の配列一つで渡し、数によって SQL の形が変わらないようにした
  （問い合わせを使い回せる）。作者・シリーズ・タグから作品を引く逆向きの索引を足した
  （作者やシリーズの画面でも使う）。
- **作品ごとの更新の監視**は、お気に入りと同じ利用者ごとの状態にした（`work_user_state.watching`）。
  旧棚の `downloads.watch_updates` は移行器が移していなかったので、移すようにした（今の棚では全件 0）。
- **取得元の候補**は旧棚と同じ三つの判断（未判断・保留・非表示）にした。以前の表は「非表示」を
  許さず、利用者が候補を外していると移行が止まるところだった。保留の理由（未完・閲覧制限など）は
  原本の JSON にしかなかったので、列に出した。
- **旧棚の「修復」の版。** 同じ版を取り直して欠けを埋めた版（2026-10-31 の取り直しなど）は、
  中身が違えば版を分けるが、作者の改稿ではない。旧棚は改稿の絞り込みに数えないので、新しい棚でも
  版に印（`source_revisions.repair`）を残して数えない。版の番号には数える（旧棚の表示と同じ）。
  602 作品の抜き出しでは 42 作品がこれで、最初の版の題が空で、タグ・説明がなかった。

旧棚と意味を変えたところ: 日付はミリ秒の範囲で受け取る（日の区切りは画面が決める。旧棚は
UTC の暦日だった）。公開日・更新日のない作品は保存日で絞る（並べ替えと同じ値）。作者の名前は、
いま名乗っている名前のほか、保存したどの版で名乗った名前でも引ける。作者・シリーズは取得元の
ID でなく棚の ID で指す（`entity_by_key` で引ける）。シリーズを題で探す旧棚の逃げ道はなくした。

比較の道具は `piep-library compare-filters <旧棚の piep.db の写し> <空の作業フォルダー> <新しい棚>`。
旧棚の実際の分布から値（よく使われるタグ・作者・シリーズなど）を選び、43 通りの絞り込みで
作品の集まりを全件突き合わせる。602 作品の抜き出しでは 43 通りすべてが一致した。

**全棚（27,847 作品）での比較。** 43 通りのうち 42 通りが作品の集まりまで一致した。残る
1 通り（更新日 2025-01-01〜06-30）は新しい棚が 3 作品多い。更新日のない作品を公開日で絞る
（上の「意味を変えたところ」）ためで、意図した違い。全棚には名前を変えた作者がいなかったので、
その場合は試験だけで確かめている。

作品の集まりは一致したが、一度目は速さが目標に届かなかった。要確認の 5 通りが 173〜178ms
（旧棚 4〜8ms）で、お気に入り・表紙・画像と添付・保留中の改稿も旧棚より 2〜60 倍遅かった。
原因と直し方（スキーマ 12）:

- **候補を作品ごとに引いていた。** 「この作品に保留の候補があるか」を一覧の行ごとに確かめる
  形にしたら、SQLite が判断の索引を選んで、行ごとに候補の表をなめていた。候補は数十件なので、
  当てはまる作品を先に集めて一覧と突き合わせる形（`work_id IN (…)`）にした。178ms → 0.03〜0.5ms。
- **保存状態から決まる旗を、絞るたびに関係の表から求めていた。** 表紙・シリーズの有無、作者の
  改稿、画像の数、添付の数を一覧の列にした（作り方の版 5。行を作るときに一度だけ求める）。
  少ない側（お気に入り・監視・編集あり・表紙なし・改稿・添付あり）には部分索引を張った。
  部分索引は値が SQL に書かれているときしか使えないので、旗の値は束縛せずに書く。
- **統計がなかった。** 部分索引から引いて並べ直すか、並べ替えの索引を順に読むかは、件数の
  統計で決まる。統計がないと、お気に入りが 0 件でも全作品を読む。一覧を作り直したときに
  `ANALYZE`、書き込みで開くたびに `PRAGMA optimize`（変わりが少なければ何もしない）。
- **作者・タグ・シリーズで、一覧を全件読んでいた。** 保存版から一覧を引く索引
  （保存版・編集・作者名）を足した。シリーズ 1 位（268 作品）は 6.7 → 0.9ms。作者名は、
  大文字小文字を区別しない並べ替えの索引で候補を集め、区別する比較で正確に絞る形にした。
  索引には編集と作者名も持たせ、「編集なし」「作者を除く」の件数を表の行を読まずに数える。
- **タグは数で形を選ぶ。** 少ないタグは保存版を集めて索引で引き、多いタグは一覧を順に読み
  ながら作品ごとに主キーで確かめる。SQLite は部分の問い合わせが返す数を知らないので、
  絞る前にタグの付いた保存版を数え（索引だけで 1ms 未満）、棚の 10 分の 1 で分ける。
  集めた 2.3 万件の保存版を作品ごとに照らす形は、件数とページで毎回その集まりを作り直して
  25ms かかっていた。主キーで確かめる形は 13ms。

### 6.7 本文の検索（設計、2026-11-14）

旧棚の「本文の検索」は、本文だけでなく題・作者名・作者 ID・タグ・シリーズ名・説明・取得元の ID と
URL を、表記ゆれ（n-gram）・読み（かな・ローマ字）・同義語つきで引く全文索引（Tantivy、v6）と、
別の意味検索からなる。関連度の重みや字句解析は測って調整してあるので、作り直さずに使い回す。

- **索引は派生物。** 新しい棚の `derived/search-index/` に置き、保管・検証・移行の対象にしない。
  消しても棚の保存状態から作り直せる。旧棚の索引（7.8 GiB）は移行しない（4.7 の決定どおり）。
- **索引の中の番号。** 旧棚の索引は作品を 64 ビットの番号で持つ。新しい棚の作品は 128 ビットの ID
  なので、派生の表 `search_documents`（番号・作品・索引した保存版・編集・利用者のタグの世代・
  作り方の版）で対応させる。旧棚の索引の作りをそのまま使え、保存版や編集やタグが変わった作品だけ
  入れ直せる。
- **文書の中身は旧棚と同じ。** 題は有効な編集の題、本文は有効な編集があればその本文、なければ
  保存版の本文に FANBOX の添付（PDF・テキスト）から取り出した本文を足したもの。タグは保存版の

### 6.11 検索の残り：過去の版・意味検索・強調・作者やシリーズの指名（スキーマ 14、2026-11-15）

入り口は `Library::search_works(&TextSearch, &WorkListQuery) -> SearchPage` にまとめた。
`TextSearch` は語・版の範囲（`VersionScope::Current | All`）・形（`SearchMode::Words | Meaning`）を持つ。
`SearchPage` は一覧のページに、作者やシリーズの指名（`intent`）と作品ごとの一致の内訳

強調と一致の理由は `search_decorations(text, &matches)` で、表示する分だけ後から作る。

**過去の版（`VersionScope::All`）。**

- 過去の版は「いまの写しの改稿でない、作品の改稿」すべて。各改稿の最後に公開した写しを使い、

  利用者のタグを足して文書にする。
- 索引は別に持つ（`derived/history/search-index/v6`、対応表 `search_history_documents`）。
  いまの版の索引と同じ作り・同じ同期（世代の印と状態の表）で、`Space { Current, History }` で
  一つのコードを使い分ける。
- いまの版で当たればその関連度。過去の版だけで当たれば最もよい過去の関連度×0.5
  （`HISTORY_WEIGHT`）。旧棚は部分一致の点を 10 で割って 0.01〜8 に収めていた。どちらも

  その版の番号（同点は新しい版）、`historical_matches` は当たった過去の版の数（いまの版が
  当たっていても数える。旧棚と同じ）。
- 旧棚は過去の版を本文の部分一致で走査していた。新しい棚は索引の語で引くので、語の区切りに
  ならない記号だけの断片では当たらない（いまの版の検索と同じ規則にそろう）。

**作者やシリーズの指名。** 旧棚の規則をそのまま移した。

**強調と一致の理由。** 旧棚の作り（`make_match_highlights`・`match_fields_and_score`）を、索引に
入っている文書にそのまま当てる。

- 破壊的な変更: 強調の `text` を、項目全体から「区切りをつないだ窓」に変えた。旧棚は本文全体を
  毎回送っていた。画面はまだ強調を描いていないので、描くときはこの形を前提にする。

**意味検索（`SearchMode::Meaning`）。** 旧棚の仕組み（モデル・384 次元・しきい値 0.18・
説明 0.35 と本文 0.65 の重み）を使う。

- 索引は `derived/search/semantic-v2/index.sqlite`。鍵は別の表 `semantic_documents` で、本文の索引を
  作り直しても埋め込みはやり直さない。
- 埋め込みは変わった部分だけ。説明の塊は文字列の指紋、本文は本文の指紋と塊の数が同じなら前の

### 6.12 アプリへのつなぎ：読み取り専用で開く（4.1 の 2、2026-11-15）

**決めたこと。** 旧棚が正本のあいだ、新しい棚は旧棚から移行した写しで、アプリは読むだけにする
（二重書き込みをしない。書き込みの命令は置かない）。画面の作品の指し方（旧棚の番号）と画像の
指し方（ファイルのパス）は新しい棚に無いので、旧棚の命令を新しい棚へ差し替える互換層は作らず、
新しい棚の形（作品の ID・ファイルの識別子）のまま、別の命令として足す。画面は一覧 → 作品 → 読書の
順に、この命令へ移していく。

**入れたもの（`commands/library_v2.rs`）。**

- 棚の場所は `PIEP_LIBRARY_V2_DIR`、なければアプリのフォルダーの隣の `….library-v2`（中に置くと、
  移行器が旧棚の中への移行を断り、旧棚の全件照合とバックアップにも入る）。無ければ何もしない
  （画面には何も出ない）。あれば起動のときに別のスレッドで開き、本文の検索の索引を同期する。
  旧棚の準備（起動の門）は待たせない。全棚では索引を初めて作るのに約 3 分かかる（6.9）。
- 状態は `library_v2_status`（ない・開いている・索引の同期中・使える・失敗）。使えるときは移行の
  未解決の記録も返す。0 件でなければ、切り替えに使える棚ではない。
- 一覧と本文の検索は `library_v2_search(search, query)` 一つ。語が無ければ一覧（`tag:` などの
  書き方だけでもよい）で、索引の同期中でも読める。語があれば索引の同期が済むまで誤りを返す。
  一致した箇所は `library_v2_decorations`。作品の画面の命令は 6.14。
- 画像は `piep-library` の URI で、ファイルの識別子（中身の SHA-256、64 桁の 16 進）から返す。
  画面は `convertFileSrc(識別子, "piep-library")` で URL にする。中身で指すので、応答は
  変わらないものとして控えてよい（`immutable`）。種類は先頭のバイト列から決める（棚のファイルは
  種類を持たない）。CSP の `img-src` に足した。

**全棚を置いた（2026-11-15）。** piep を閉じて稼働棚を `….library-v2` へ移行した（33.7 分・
未解決 0・読み込み 155 GiB・書き込み 59 GiB・移行先 20.1 GiB／13.3 万ファイル・132,119 ファイルの
復元は全件一致）。段階は作品 10.2 分・最後の検証 9.0 分・全件照合 5.0 分・旧表の保管 4.0 分で、
四度目の試走（6.4）と同じ。インストール版の piep はこの場所を知らないので、移行の後すぐに
起動し直せる。

- アプリと同じ手順（`piep-library app-open`）で開くと、本文の索引を初めて作って使えるまで
  229 秒。二度目からは 0.5 秒で、一覧の最初のページは 1.9 ms。
- 意味検索の引き継ぎ（`piep-library semantic-sync`、稼働棚の索引とモデルの写しから）: 本文の
  ベクトル 27,847 件はすべて引き継ぎ、説明の塊は 2,525 件だけ同じ文で、残り 25,322 件をタグの順の
  違い（6.11）のため埋め込み直した。1,428 秒（23.8 分）。全部を埋め込むと約 5 時間の見込みだった。
  アプリはまだ意味検索の同期を呼ばない。

**まだのもの。**

- 画面。一覧は 6.13、作品の画面は 6.14、読む画面は 6.15、読む画面の前後の作品は 6.16 で試験的につないだ。
- 移行した後に旧棚へ保存した作品は入らない（4.1 の 1「やり直せる移行」が要る）。
- 保存のたびの同期（本文・過去の版・意味検索）。読み取り専用のあいだは、開いたときの同期だけ。

### 6.13 一覧の画面を新しい棚へ（試験中・読むだけ、2026-11-15）

**決めたこと。** ライブラリの作品の一覧（`LibraryPage` の作品タブ）を、設定の「新しい棚（試験中）」の
切り替えで新しい棚から出せるようにした。既定は切ったまま（旧棚の一覧のまま）。切り替えは端末ごとの
好み（`piep.library-shelf-v2`）で、棚が無ければ設定にも出ない。

- 作品は新しい棚の ID（UUID の文字列）のまま並べる。旧棚の番号に読み替える互換層は作らない（6.12）。
  画面の型は `ShelfEntry`（`DownloadEntry` の `id` を文字列にし、表紙を `coverUrl` に持つ）で、
  カード（`WorkCard`）と仮想リストは `DownloadEntry | ShelfEntry` を受ける。番号で動く操作
  （選択・EPUB・改稿の印の照合・お気に入りの先回り）には新しい棚の作品を渡さない。
- 一覧の条件は `features/library/shelfV2.ts` の `shelfRequest` で新しい棚の問い合わせに直す。
  絞り込みはすべて対応する（取得元・種類・お気に入り・更新監視・編集・表紙・シリーズの有無・画像と添付・
  改稿・要確認・文字数・件数・容量・日付・タグ（かつ／または）・作者）。日付は旧棚と同じく UTC の日で
  両端を含む。シリーズの指名（`seriesKey`）は書き方 `series:取得元:キー` にして渡す。
- 新しい棚で答えられない条件（ページ番号・作者の指名・シリーズ順）は、黙って外さずに
  誤りとして画面に出す。読みかけ（旧棚の番号の集合）は 6.17 で答えられるようにした。
  ページ番号は新しい棚の一覧が続きの位置で読み進めるだけなので、一覧はスクロールで読み込む形になる
  （ページ番号の切り替えには理由を出す）。
- 書き換える操作（お気に入り・更新監視・EPUB・削除・複数選択）は、新しい棚が読むだけの写しなので
  押せない形で同じ場所に置く（並びと幅を変えない）。作品を開くと、新しい棚の作品の画面（6.14）に
  なり、そこから読む画面（6.15）へ進める。
- 一致した箇所と理由は、語の検索で一致があったページだけ `library_v2_decorations` で続けて引き、
  カードの一致の印に出す。作者・シリーズとして解釈したときの文言は旧棚と同じ。
- 書き方（`tag:` など）だけで語の無い問い合わせは一覧なので、索引の同期中でも読めるようにした
  （命令の側で `parse_query` の残りの語を見る）。

**確かめたこと。** 開発版（別の識別子のアプリのフォルダー、`PIEP_LIBRARY_V2_DIR` で全棚の新しい棚）で、
開くと索引の同期は 199 ms（差分なし）。設定で切り替えると、一覧は 27,847 件・表紙つきで出て、
スクロールの続き・並び順（文字数）・タグを押した絞り込み・作品を開いたときの表示が動いた。表紙は
`piep-library` の URI で表示された。語の検索は、確かめる操作の道具から検索欄に文字を入れられず
（クリックで入る焦点が、打鍵で外れる）、画面では確かめていない。命令の中身は CLI で測ったもの
（一覧の最初のページ 1.9 ms、6.12。書き方の問い合わせ 551 件で 455 ms、6.11）と同じ関数。

**まだのもの。**

- 作者の顔の画像と、作者・シリーズへのリンク（新しい棚の一覧の一件はそれを持たない）。
- 語の検索の画面での確認。

### 6.14 作品の画面を新しい棚へ（試験中・読むだけ、2026-11-15）

**決めたこと。** 作品の画面（`/works/:id`）は、ID が新しい棚の UUID なら新しい棚の作品の画面
（`ShelfWorkPage`）を出す。旧棚の作品の画面とは読む先も操作も違うので、一つの画面の中で分岐させず
画面を分けた。並び（頭・概要・本文・画像と添付・履歴・保存データ）と見た目は旧棚の画面と同じにし、
タブの部品（ページ送り・情報の一行）は `workPageParts.tsx` に出して両方で使う。

- 命令は 5 つ。`library_v2_work`（一覧の一件・説明・取得元の作者とシリーズの ID・保存した版）、
  `library_v2_content`（本文の一ページの HTML）、`library_v2_media`（画像・添付）、
  `library_v2_version_text`（版の平文、履歴の比較用）、`library_v2_original`（その版を作った
  取得元の応答）。版を指さなければ今読む本文（有効な編集があればそれ）。使われなくなった
  `library_v2_work_card` は消した。
- 本文の HTML は旧棚の変換（`database::parser`）をそのまま使う（`library_view.rs`）。旧棚の変換は
  本文の中の画像・添付を保存名で探すので、新しい棚の「本文の中の指定 → 画像」の対応（reader
  bindings）から、その指定に対して旧棚の変換が探す名前そのものの仮の添付を作って渡す。結び付けは
  新しい棚の対応が決め、名前の推測には頼らない。置き場（`data-local-path`）にはファイルの識別子を
  入れ、画面が `piep-library` の URI にする（添付は `識別子/印`）。
- 添付は、旧棚の変換が「置き場に取得元の ID を含むか」でも探す。置き場の 16 進が短い ID（`f1` など）を
  たまたま含み、別の画像に当たった（試験で見つけた）。本文の中の添付の ID を、16 進に現れない文字で
  囲んだ印に置き換えて照合させる。画像だけ・添付だけの投稿の配列（`images`・`files`）は何番目かで
  結ぶ（項目に ID が無いこともある）。結ばれていない項目は置き場の手がかり（`localPath`）を外し、
  保存された別の画像に当たらないようにする。
- 本文のページ分けは旧棚と同じ（`paginate_reader_html`）。ページをめくるたびに本文全体を組み直さない
  よう、最近の 4 冊を覚えておく。
- 取得元の応答に本文が無い作品（公開範囲の外の投稿など）は、旧棚と同じく空の本文にする。画面は
  「この版には本文がありません」と出す。
- 書き換える操作（お気に入り・更新監視・編集・削除・コレクション・EPUB）は置かないか、押せない形に
  する。読むボタンは読む画面（6.15）へ進む。作者とシリーズのリンクは取得元の ID で旧棚の画面へ。
  添付の原本を開く（PDF）は旧棚の保存フォルダーを使う仕組みなので、まだ開かない（6.19 で開けるようにした）。
- 旧棚の本文にある「添付の文章を本文に差し込む」（`attachment::materialize`）はまだしない（6.18 で差し込んだ）。

**確かめたこと。**

- 全棚 27,847 作品の今の版の本文を組んだ（`library_view_tests.rs` の `probe_a_real_shelf`、
  開発ビルドで 4.5 分、一番遅い作品 86 ms）。本文の中の指定と保存物の結び付き 13,014 件はすべて
  本文の中で引けた（同じ画像を二度指す本文があり、引けた印は 13,022）。「見つからない」印は 65 で、
  61 は保存できなかった画像・添付（新しい棚の対応も「無い」）、残り 4 は本文の指定そのものが崩れて
  いるもの（`[pixivimage:id=…]`・0 ページ目の指定。新しい棚は画像の指定として数えない）。本文の無い
  作品 5 件は空の本文として組めた。
- 開発版で、一覧から作品を開き、頭・本文（ページ送り）・画像と添付・履歴（v1 の本文）・保存データが
  出た。PSD の添付を「見つかりません」と出していた投稿（配列で指す形）は、直した後に添付として出た。

### 6.15 読む画面を新しい棚へ（試験中・読むだけ、2026-11-15）

**決めたこと。** 読む画面（`/reader/:id`）は、ID が新しい棚の UUID なら新しい棚から読む。作品の画面
（6.14）と違って画面は分けない。読む画面の中身はほとんどが読む道具（読書位置・しおり・目次・本文内検索・
縦書き・鍵盤の操作）で、どの棚から読んでも同じだから。読む先だけを `features/reader/readerSource.ts` の
`ReaderSource`（作品の頭・本文の一ページ・目次・本文内検索・画像の URL）として差し替える。

- 作品の頭は、作品の画面と同じ問い合わせの鍵と形で持つ（旧棚は `reader-metadata` の
  `ReaderMetadata`、新しい棚は `library-v2-work` の作品）。読む画面は react-query の `select` で
  共通の形（`ReaderHead`）に読み替える。旧棚の作品の画面・編集画面が同じ鍵を読み書きしているので、
  鍵の中身の形は変えない。
- 版は番号で選ぶ（旧棚と同じ）。新しい棚では、その番号の版の保存状態（snapshot）に読み替えて命令に
  渡す。番号を選ばなければ今読む本文（有効な編集があればそれ）。
- 命令は 2 つ足した。`library_v2_outline`（目次）と `library_v2_search_content`（本文内検索）。
  `library_v2_content` は旧棚の一ページと同じ形にした（本文全体の字数と、pixiv の原稿のページが
  何ページ目から始まるか）。目次と本文内検索は旧棚の処理を、ページの一覧を受け取る関数
  （`reader_outline`・`search_reader_pages`）にくくり出して両方から呼ぶ。畳み方（かな・カナ・
  全角半角）も見出しの拾い方も同じになる。
- 残り時間の目安に使う字数は、旧棚と同じく HTML ではなく本文の平文（検索に使う本文）で数える。
- 読書位置としおりは端末に、新しい棚の作品の ID（小文字の UUID）で憶える。旧棚の作品の番号とは
  別の鍵なので混ざらない。読みかけの棚（旧棚の作品を並べる）には新しい棚の作品を数えない。数字だけの
  鍵を旧棚の作品として読むようにした（頭が数字の UUID を `parseInt` すると、その数字の番号の作品として
  読みかけに載っていた）。**6.17 で改めた**：旧棚から移した作品は旧棚の番号で憶える。
- 書き換える操作（編集）と、旧棚にしか無いもの（保存フォルダー・添付の原本）は、押せない形か出さない。
  頭に「新しい棚（試験中）」と出す。前後の作品は 6.16 でつないだ。添付の原本は 6.19 で開けるようにした。

**確かめたこと。**

- 全棚 27,847 作品の今の版で、読む画面が受け取るものを組んだ（`probe_a_real_shelf` に足した。
  開発ビルドで 500 秒）。pixiv の原稿のページの対応（0 から始まり、増え続け、ページの数を超えない）が
  崩れた作品は 0。残り時間に使う字数は、全作品で移行した字数（旧棚の字数）と一致した（ずれ 0）。目次の
  見出しは 8,218。本文内検索（「の」）の一番遅い作品は 126 ms。本文の中の指定と保存物の結び付きは
  6.14 と同じ（13,014 件すべて引けた）。
- 旧棚の読む画面・目次・本文内検索の試験（42 件）は、処理をくくり出した後も通った。
- 開発版（別の識別子のアプリのフォルダー、全棚の新しい棚）で、一覧 → 作品の画面 → 読むで開いた。
  頭に「新しい棚（試験中）」、編集と保存フォルダーは押せない形で出た。しおりを挟めた。読み進めて作品の画面へ
  戻り、もう一度読むと同じ位置（4%）から始まった。pixiv の作品で本文の挿絵が出て、押すと拡大できた。
  本文内検索は、確かめる操作の道具から検索欄に文字を入れられず、画面では確かめていない（命令の中身は
  上の全棚の調べと試験で確かめた関数と同じ）。

**まだのもの。**

- 編集版の基準の版が古いことの表示（新しい棚の作品の頭に、編集の基準の版がまだ無い）。6.20 で出した。
- 旧棚と新しい棚で同じ作品の読書位置を引き継ぐこと（6.17 でつないだ）。

### 6.16 読む画面の前後の作品を新しい棚から（試験中・読むだけ、2026-11-15）

**決めたこと。** 読み終えたときに出す前後の作品（コレクション・公式シリーズ・作者の投稿順）を、新しい棚の
作品でも出す。札の見た目・名乗り方・数え方は旧棚と同じ（6.15 の読む画面の札をそのまま使う）。

- 命令は `library_v2_neighbors`（作品）の一つ。作品が入っているコレクション・シリーズ・作者ごとに、
  並びの中の位置・数・両隣だけを返す（`Library::work_neighbors`）。旧棚の読む画面は並びを 200 件ずつ
  画面までたどって（長い並びは 25 ページで打ち切り）、隣の作品の詳しい情報をもう一度引いていた。
  新しい棚では棚の中で並べて、隣の作品は一覧の一件と同じ形（表紙の識別子・作者・字数・抜粋）で
  一緒に返すので、一往復で済み、打ち切りもない。
- 並べ方は旧棚と同じ。コレクションは並べた順（棚にない作品は除き、数だけ「未保存 N 作品は除外」と
  出す）、シリーズは取得元の話数（ないものは後ろ）から公開日、作者は公開日の古い順。公開日のない作品は
  保存日で並べる。所属は今の版で引く。前も後もない並び（その作品だけ）は返さない。
- 隣の作品を押すと、その作品を新しい棚の読む画面で開く。読みかけなら「読みかけ・続きから」と出る
  （読書位置の鍵は 6.17）。
- 「前回のあらすじ」（読む順のある並びの前の作品のあらすじ）は、あらすじの記録が旧棚の作品の番号で
  引くので、新しい棚の作品では出さない。コレクションの「一覧」ボタンも、コレクションの画面がまだ
  旧棚だけなので出さない。

**確かめたこと。**

- 旧棚と全作品で突き合わせた（`piep-library compare-neighbors <旧棚の piep.db の写し> <作業フォルダー>
  <新しい棚>`）。旧棚の側は読む画面と同じ問い合わせ（シリーズは `series_order`、作者は
  `source_created_at` の昇順、コレクションは `get_work_collection` の並び）を最後までたどる。
  27,847 作品で、作者の並び 27,844 行・コレクション 26 行は、位置・数・両隣・除外の数まで全部一致した。
  シリーズは 12,832 行のうち 60 行が違い、原因はすべて 1 作品だった。その作品は改稿でシリーズを
  移っていて、旧棚は古い版のシリーズとの結び付き（`download_series`）を消さずに持ち続けていた。
  今の版の保存データ（`detail.series_id`）が指すのは新しい棚と同じシリーズで、**新しい棚が正しい**。
  旧棚では、移る前のシリーズの全回（59 作品）の数と位置が 1 つずれ、その作品自身も移る前のシリーズの
  並びで案内されていた。
- 一作品ぶんを引く時間（リリースビルド、全作品）は中央値 0.19 ms、95% で 0.90 ms、一番遅い作品で
  6.4 ms。全作品の突き合わせは 14 秒で終わった。
- 棚の試験（コレクション・シリーズ・作者の並べ方、話数のない回を後ろへ、一人きりの作者は出さない、
  隣の作品が一覧の一件と同じ中身）と、読む画面の試験（札の名乗り方・数え方・表紙・読みかけの印・
  押すと隣の作品の読む画面へ・旧棚の問い合わせを呼ばない）を足した。

### 6.17 読書位置としおりを旧棚と新しい棚で共有する（試験中・読むだけ、2026-11-15）

**決めたこと。** 旧棚が正本で新しい棚がその写しのあいだは、旧棚から移した作品の読書位置としおりを、
新しい棚でも**旧棚の番号の鍵**（`piep.reader-position.{旧棚の番号}.{版}`・しおりの `{旧棚の番号}`）で読み書き
する。どちらの棚で読んでも同じ記録を続きから使え、読みかけの棚にも載る。旧棚に無い作品だけが新しい棚の
ID で憶える。切り替えのとき（4.1）に端末の記録を棚の `reading_positions` へ移す。

- 新しい棚の作品の一件（`CardView`）に旧棚の番号（`legacyId`）を付ける。移行の記録
  （`migration_records` の `download_current`）は移した時点の今の版（保存状態）を指すので、
  `revision_snapshots` をたどって作品へ結ぶ（`Library::legacy_work_numbers`。開いた棚ごとに一度引いて
  持っておく）。全棚 27,847 作品すべてに番号が付き、旧棚の（取得元・キー）と食い違う作品は 0。
- 読みかけの絞り込み（旧棚の番号の集合）を新しい棚の一覧でも答える。`library_v2_search` に旧棚の番号を
  渡すと、作品の ID に読み替えて絞る。
- 位置は「何ページ目の、何番目の行の目印」で憶えるので、同じ作品は両方の棚で**同じ行でページが切れ、
  同じ並びの目印を持つ**必要がある。全作品で突き合わせて（`piep-library compare-reader-pages`）、
  ずれの原因を二つ直した。
  - **ページの大きさを、画像・添付の置き場を数えずに測る。** 転送用のページは 128 KiB を目安に切る。
    その長さに `data-local-path` の値（旧棚は保存先のフォルダーを含むパス、新しい棚はファイルの識別子）を
    数えていたので、上限に近い作品は棚によって切れる行が違った（行の目印のずれ 47 作品、ページ数の違い
    2 作品）。旧棚にもあった欠陥で、保存先のフォルダーを移すだけで切れ目が動いていた。直したことで、
    旧棚でも 37 作品（うち 2 作品はページ数）の切れ目が変わる。その作品に端末の位置があれば、数行ずれる。
  - **編集の本文を旧棚と同じ関数（`blocks_to_html`）で組む。** 新しい棚で組み直していて、段の間の空行の
    数（`gap`）を数えず一律に一行にしていた。移した編集は段の種類・属性・画像の枠を旧棚のまま持っているので、
    旧棚の段の形へ戻して同じ関数に渡す。
- 直したあとの全作品の突き合わせ：63,268 ページ、27,836 作品で行の目印が全部一致した。残る 11 作品は
  すべて FANBOX の添付の中の本文（PDF など）を差し込む作品で、新しい棚はまだ差し込まなかった（6.18 で直し、
  全作品で一致）。行の目印に響かない HTML の違いが別に 31 作品あった（6.18 で分かり、直した）。

**確かめたこと。**

- 棚の試験（移行の記録から旧棚の番号を引く）、ページの試験（置き場の長さが違っても pixiv・FANBOX の
  どちらも同じ行で切れる。直す前の関数では落ちる）、編集の試験（空行の数・見出し・画像の説明・改ページ・
  残っていない画像が、旧棚の関数と同じ HTML になる）を足した。
- 画面の試験：旧棚の番号を持つ作品は、新しい棚で開いても旧棚の番号の位置から続き、旧棚の番号のしおりが
  出て、新しい棚の ID の位置は書かない。前後の作品の札の「読みかけ」も旧棚の番号で引く。読みかけの
  絞り込みは旧棚の番号のまま新しい棚へ渡す。
- 開発版（別の識別子のアプリのフォルダー、全棚の新しい棚）で、新しい棚の一覧から FANBOX の作品を読み進めて
  戻ると、新しい棚の一覧の「読みかけ」にその作品が出た。端末の記録の鍵は旧棚の番号だった（移行の記録が
  指す旧棚の作品と取得元・キーが一致）。もう一度開くと同じ位置から始まった。

**まだのもの。**

- FANBOX の添付の中の本文の差し込み（6.18 でつないだ）。
- 端末の記録を棚の `reading_positions` へ移すこと（切り替えのとき）。

### 6.18 添付の中の本文を新しい棚でも差し込む（試験中・読むだけ、2026-11-15）

**決めたこと。** FANBOX の添付の PDF・テキストから取り出した本文を、旧棚と同じく添付の位置へ差し込んで
読む画面に出す（作品の画面の本文も同じ命令なので同じ）。

- 検索の文書はすでに差し込んでいた（添付を一時のフォルダーへ書き出して旧棚の `apply_attachment_text` に
  渡す）。読む画面もその同じ関数（`Library::insert_attachment_bodies`）を通す。旧棚が読書の HTML と検索の
  平文を同じ値から作るのと同じ理由で、読める本文と検索に入る本文が食い違わない。
- 残り時間の目安の字数も、差し込んだ本文を含めて数える（旧棚と同じ）。
- 添付だけの投稿（`files`）は、差し込むと `files` から `blocks` と `fileMap` が組み直され、添付を項目の
  元の ID で指す。新しい棚の照合の印（6.14）をその ID にも置くようにした。置かないと添付の箱が
  「見つかりません」になる。
- 差し込んだ本文の頭の「原本を見る」は出さない。一時に書き出したファイルを指していて、すぐ消えるうえ、
  新しい棚ではまだ原本の PDF を開けない（押しても何も起きないボタンを出さない）。**6.19 で改めた**：
  ファイルの識別子を指して出す。
- 画像を配列の何番目かで指す投稿で、照合の印（`piep-image-z0z` など）が画像の説明（alt）と参照にそのまま
  出ていた（31 作品）。組んだあとで取得元の画像の ID に戻す。

**確かめたこと。**

- 全作品の突き合わせ：27,847 作品の 63,268 ページすべてで、ページの切れ目と行の目印が旧棚と一致した。
  残り時間の字数も全作品で一致。HTML の違いは「原本を見る」のボタンがない 7 作品だけ。
- 棚の試験（添付だけの投稿でテキストの添付の本文が差し込まれ、添付の箱は新しい棚のファイルを指し、
  「原本を見る」は出ず、残り時間の字数と検索の文書の本文が同じ）と、印が画像の説明に残らない試験を足した。
- 開発版の画面では確かめていない（該当する 11 作品へ一覧からたどる手立てが、検索欄に文字を入れられない
  ので無い）。命令が返す HTML は上の突き合わせで旧棚と同じ。
- **見つけた欠陥（両方の棚、棚では 0 作品）:** 添付だけの投稿に画像の配列もあると、差し込みで組み直した
  `blocks` に画像が入らず、画像が消える。今の棚に当てはまる作品は無い（PDF・テキストの添付だけの投稿 4 件は
  どれも画像を持たない）。

**まだのもの。**

- 新しい棚で添付の原本（PDF）を開くこと（「原本を見る」はそれと一緒に出す）。6.19 で済ませた。

### 6.19 添付の PDF の原本を新しい棚から開く（試験中・読むだけ、2026-11-15）

**決めたこと。** 旧棚と同じく、取り込んだ本文の頭の「原本を見る」と、作品の画面の「画像・添付」の
PDF から、紙面をアプリの中で開く。

- 差し込んだ印の `localPath` は、一時に書き出した場所から、その添付の**ファイルの識別子**（中身の
  SHA-256）に置き換える（`insert_attachment_bodies`）。旧棚の変換は紙面のある添付（PDF）にだけ
  `localPath` を置くので、ボタンが出るのは旧棚と同じ添付だけ。対応の分からない印は外す。
- 新しい命令 `library_v2_render_pdf_page(作品, ファイルの識別子, ページ, 幅)`。旧棚の
  `render_pdf_attachment_page` と同じく、**その作品の保存した版のどれかに PDF として載っている
  ファイルだけ**を開く（`Library::work_pdf_attachment`）。画面から来た識別子をそのまま開くと、作品と
  関係のないファイルを読ませる口になる。控えは持たず、要求のたびに中身を取り出して描く。
- PDF を描く処理は、場所ではなく中身から描けるようにした（`pdf::render_page_bytes`）。旧棚の
  `render_page` もこれを通す。新しい棚の添付は場所を持たない。
- 画面は旧棚の原本の窓（`PdfOriginalViewer`）をそのまま使う。作品が番号（旧棚）か UUID（新しい棚）かで
  描かせる先を分ける。

**確かめたこと。**

- 全作品の突き合わせ：27,847 作品の 63,268 ページで、ページの切れ目・行の目印・字数に加えて、HTML も
  旧棚と一致した（6.18 で残っていた 7 作品のボタンの違いがなくなった）。突き合わせに「原本を見る」が
  その作品の PDF を指し、1 ページ目を描けることの確認を足した：7 件すべて開けた。
- 棚の試験（ボタンが識別子を指し、一時の場所を出さない／作品の PDF は描けて 2 ページと数える／
  同じ作品の画像や別の作品の ID では開かない）と、画面の試験（読む画面と作品の画面の本文のボタン、
  添付の一覧の PDF から、新しい棚の命令で描く）を足した。
- 開発版の画面では確かめていない（6.18 と同じく、該当する作品へ一覧からたどる手立てが無い）。

### 6.20 編集版の基準の版が古いことを新しい棚でも名乗る（試験中・読むだけ、2026-11-15）

**決めたこと。** 編集のあとに改稿を取り込むと、編集版は古い版の上に載ったままで、新しい版は編集版を
読んでいるあいだ見えない。旧棚の読む画面はこれを「編集版（v… 基準）」と名乗る（`staleEditBase`）。
新しい棚の作品でも同じに出す。

- 作品の頭（`library_v2_work`）に、有効な編集の基準の版の番号（`editBaseVersion`）を足した。
  `Library::edit_base_version` が `edit_revisions.base_snapshot_id` の版の番号（版の一覧と同じ数え方）を返す。
- 古いかどうかは画面で決める（`staleEditBaseOf`：基準の版 < 今の版）。旧棚と同じ式。
- 作品の画面の本文の上の一行と履歴の説明にも、何版をもとにした編集かを出す（旧棚の作品の画面と同じ）。
  古いときは「取り込み済みの v… は表示されていません」と添える。一行の中の文言だけで、並びは変えない。

**確かめたこと。**

- 全作品の突き合わせに、編集の有無・基準の版・古いかどうかの比較を足した：棚で編集のある 2 作品とも
  旧棚と一致（どちらも今の版の上の編集で、古い印の出る作品は今の棚に無い）。
- 棚の試験（版 1 で編集し、版 2 を取り込んでも基準は 1 のまま）と、画面の試験（読む画面は基準が古いと
  「編集版（v1基準）」、今の版なら「編集版」だけ／作品の画面の一行）を足した。
- 開発版の画面では確かめていない（古い印の出る作品が棚に無い）。

### 6.21 作者・シリーズの画面を新しい棚から出す（試験中・読むだけ、2026-11-15）

**決めたこと。** 作者（`/people/…`）・シリーズ（`/series/…`）の画面は、一覧と同じ切り替え（設定「新しい棚
（試験中）」と棚の状態）で新しい棚から出す。画面は旧棚と同じ `EntityPage` を使い、読む先だけを差し替える。

- 頭は `Library::entity_head`（`library_entity.rs`、命令 `library_v2_entity`）。取得元の ID から引き、
  プロフィールの版（名前・説明・リンク・アイコン・ヘッダー画像・表紙・完結・話数）と、作品の数・版の一覧・
  確かめた時を返す。作品にだけ名前の載った作者・シリーズ（自分の版が無い）は作品に載った名前を出す。
- 作品の一覧は `WorkFilter` の `person`・`series`（棚の ID）で絞る。シリーズの既定の並びに
  `WorkSort::SeriesOrder` を足した：作品が属するシリーズの位置のうち最も小さいもの（位置の無い作品は後ろ）、
  同じ位置は公開日。旧棚の `series_order` と同じ鍵で、続きの位置は文字列の鍵で引く。
- タグは `entity_tags`（作品の数の多い順、同じ数は名前の順）、作者のシリーズは `person_series`
  （旧棚の `list_entity_series_paged` と同じ集計・語での絞り込み・鍵と同点の並べ方。続きは件数の位置）。
- 「保存データ」の欄は、今の版を作った取得元の応答のうち最も新しく受け取ったもの（`entity_profile`）。
  旧棚の行を写した記録（`legacy-current-row`）は取得元の応答ではないので除く。旧棚の画面が出していた
  最新の版の JSON は、取り込みの記録の側にある。
- 旧棚へ書く操作（更新監視・情報の更新・アーカイブ・いま確認）は同じ場所に押せない形で置き、理由を
  ツールチップと読み上げに出す（ボタンの文字は変えない。`ActionBarItem.hint`）。コレクションの欄はまだ出さない。
- 新しい棚の一覧と同じく、ページ番号では移動できない。

**確かめたこと。**

- `piep-library compare-entities <旧DBの写し> <空フォルダー> <新棚>` で、作者 370・シリーズ 1,657 を
  旧棚の画面と同じ問い合わせで突き合わせた（4.6 秒）。頭・タグ・作品の並び・作者のシリーズ 1,656 行・
  保存データまで一致。違いは 1 シリーズだけで、旧棚が改稿でシリーズを移った作品の古い
  `download_series` 行を残す欠陥（6.16 と同じ作品）。頭は p99 0.6 ms、作者のシリーズは p99 4.9 ms。
- 突き合わせで直したこと：シリーズの見本の題は「棚に入った順」で選ぶ（保存日では改稿で順が変わり
  141 件違った）／保存データは旧棚の行の写しを除く（142 シリーズで行の写しを出していた）。
- 棚の試験 5 件（頭・版の無い作者・タグ・シリーズ順の続き・作者のシリーズ）と画面の試験 6 件。
- 開発版の画面で、作品の画面から作者・シリーズへたどって確かめた：頭（画像・リンク・件数・「新しい棚（試験中）」）、
  作品・タグ・シリーズ順の既定の並び、プロフィール履歴・保存データ、押せない形の操作、コレクションの欄が出ないこと。

### 6.22 作者・シリーズの一覧とコレクションの欄を新しい棚から出す（試験中・読むだけ、2026-11-15）

**決めたこと。** ライブラリの「作者・クリエイター」「シリーズ」タブと、作者・シリーズの画面のコレクションの欄を、
作品の一覧と同じ切り替えで新しい棚から出す。行の形は旧棚の `EntityFacet`・`WorkCollectionSummary` に合わせ、
カードと画面はそのまま使う。

- 一覧は `library_entity_list.rs`（命令 `library_v2_entities`）。作品の絞り込みは作品の一覧と同じ
  `WorkFilter` を `Library::work_filter_sql` で SQL にして、今の版の作品を作者・シリーズごとに集める。
  旧棚の `search_entity_facets` と同じ定義にした：作者は名前の載った作品から、名前はプロフィール（無ければ
  最も新しい作品に載った名前）、見本の題は作者が公開の新しい順・シリーズが位置の順。語での絞り込み・
  監視の状態・完結・最少の作品数・9 通りの並びと同点の並べ方も旧棚と同じ。
- 改稿の数は「版の番号 − 1」ではなく、取り込んだ改稿（`source_revisions` の 2 番目以降、修復を除く）を数える。
  旧棚の数え方で、作者のシリーズ（6.21）も同じ定義にそろえた。
- 集計は条件ごとに命令の側で覚える（直近 4 通り、棚の世代が変われば捨てる）。ページをめくる・件数を聞く
  たびに 2.8 万行を集め直さない。プロフィールに名前の無い行だけ作品に載った名前を引く。
- コレクションの欄は `entity_collections`（命令 `library_v2_entity_collections`）：今の版で作者・シリーズに
  関わる作品を含むコレクションを、旧棚と同じく更新の新しい順で返す。表紙のマスは棚のファイルの識別子で描く
  （`CollectionCover` が `shelf: "v2"` で読み分ける）。コレクションの画面はまだ旧棚で開くので、ID は旧棚の ID。
- コレクションの更新時刻を棚に持たせた（移行 015：`collections.updated_at`）。既にある棚は、移した時に
  残した旧棚の行（`__all_rows__`）から取り戻す（`restore_collection_times`、開くときに一度だけ）。
  新しく移す棚は取り込みで書く。
- 監視の印は移した時点の登録を出し、押せない形にする（`watchHint`、理由をツールチップと読み上げに出す）。
  「複数選択」は作品・作者・シリーズのどのタブでも押せない形で残す。

**確かめたこと。**

- `compare-entities` に一覧とコレクションの突き合わせを足した（全体 23 秒）。コレクションは作者 370・
  シリーズ 1,657 で 9 行、違い 0。一覧は 60 通り（並び 9 × 向き 2、監視 3、完結 2、最少 3 作品、お気に入り、
  取得元、2 万字以上、タグ、語 3 つ）を最後のページまでめくって旧棚と比べた。違いは説明のつくものだけ：
  容量の並び 4 通り（新しい棚は同じ中身を一度だけ数える、既知の定義の差）と、6.16 の旧棚の古いシリーズの行。
- 集計は覚えていないときで p50 45 ms・p99 70 ms。
- 棚の試験 8 件（一覧 7・コレクションの時刻の取り戻し 1）と画面の試験（読むだけの監視の印・一覧の命令の形・

### 6.24 旧棚からの追いつき（2026-11-15）

**決めたこと。** 移した後も旧棚を使い続けるので、同じ棚へもう一度 `import-legacy` すると、旧棚の今の状態に
追いつくようにした。新しい棚は利用者が書き換えないので、移した行はいつでも旧棚の今の行から作り直してよい。

- 原記録（`__all_rows__`）が前回と違う表は差し替えて未完了に戻し（報告の `changed_tables`）、その領域の
  正規化をもう一度通す。空になった表も、前に移した行を片付けるために通す。
- 作品・版は前から冪等だった（要求 ID を `migration_requests` に残す）。新しい作品と改稿はそのまま入る。
- お気に入りと監視は、旧棚の今の値と違えば合わせる（外した印も写す）。移行が書いた変更は要求 ID を
  `migration_requests('user_state', 作品:世代)` に残し、再開の検査はそれで移行の書き込みと見分ける。要求 ID を
  残す前の移行の形（空から一回で写したもの）は認めて記録を足す。それ以外の利用者の変更があれば、前と同じく断る。
- 整理データは上書きする：コレクションは名前などを更新し、旧棚で消したものは消した印（`entities.deleted_at`）、
  作品の欄は並びごと置き直す。監視の対象・グループ・所属、更新の候補、関係の根拠、まとまりの判定も同じ。
- 編集は、前に移した編集とブロックの ID を引き継いで同じ文書を作り、中身が同じなら作り直さない。旧棚で
  書き換えた編集は前の編集を親にした新しい編集として足し、有効・下書きの指し先を旧棚の今の状態に合わせる
  （変わった作品だけ世代を一つ進める。最初の移行も有効と下書きを一度に指すので世代は 1）。
- 取り込めない変更は、前と同じく未解決として報告する。見本の旧棚でタグの出どころとシリーズの順を書き換えると
  未解決 6 件になり、`import-legacy` は失敗で終わった（アプリが作らない変更なので正しい扱い）。

**確かめたこと。** 見本の棚（150 作品）を移したあと、アプリの保存と同じ変更（改稿・お気に入りの切り替えと
外し・新しい作品・コレクションの追加と改名と削除・編集の書き換え）を 3 回足して追いつかせた。作品・版・
お気に入り・監視・コレクションが毎回旧棚と一致し、未解決 0。棚の試験 2 件（整理データ・編集）を足した。

**稼働中の棚で。** 了承を得て piep を閉じ、稼働中の新しい棚へ追いつきをかけた（40 分・未解決 0）。移した後に
旧棚へ保存した作品はなく（最後の保存は移行より前）、変わった表も 0 だったので、全棚でもう一度通しても何も
変えないことの確かめになった。作品・お気に入り・監視・版・コレクション 7 件が旧棚と一致した。時間の多くは

**まだのこと。** 追いつきは piep を閉じて CLI で行う（アプリの中から呼ぶ形はまだない）。旧棚で消えた

### 6.27 追いつきの速さと、変わった版の扱い（2026-11-15）

**決めたこと。**

- 旧棚で消えた関係（`work_links`）を消す。根拠の行を消し、根拠の残らない関係も消す（根拠が残れば状態を付け直す）。
- 前回から変わっていない保存版は読み直さない。旧棚の版の行・その作品の資産の行・原本 JSON の大きさと更新時刻から
  指紋を作り、`migration_fingerprints`（スキーマ 16）に残す。指紋が同じなら前回の保存状態を使う（報告の
  `unchanged_snapshots`）。指紋は棚の正本ではなく、消しても次の追いつきが全部を読み直すだけ。
- 一度移した版の中身が旧棚で変わると、前の要求 ID のまま送ると「同じ要求で違う内容」で断られていた（指紋の前から
  あった欠陥）。まず前と同じ要求で送り（中身が同じなら前の保存状態が返るだけ）、断られたときだけ読み直した中身
  ごとの要求で送り直す。要求を最初から分けると、同じ中身でも保存状態が一つ増える（見本で 1,083 件が 2,166 件に）。
- 送り直すのは旧棚の今の版だけ。古い版を送り直すと履歴の後ろに積まれて今の版になり、旧棚の今の版と食い違う。
  古い版が変わっていたときは前の保存状態のままにする（報告の `kept_old_snapshots`）。今の版の画像の取得元が
  変わると、画像の識別が変わるので保存状態が一つ増える（旧棚は版を増やさずに上書きする）。

**確かめたこと。** 見本の棚（1,002 作品）で、変わらない追いつきが 48.1 秒から 18.5 秒になった（全 1,081 版を
読み直さない。残りは原記録の照合）。指紋のない移行（稼働中の棚と同じ形）からの追いつきは保存状態を増やさず、
次から全部を読み直さない。古い版と今の版の資産の行を変えた追いつきで、作品・版・お気に入り・監視・
コレクションが旧棚と一致し、未解決 0。棚の試験を 2 件に足した（資産の行の変更・古い版の変更）。

### 6.28 作品を棚から外す（2026-11-15）

**決めたこと。** 設計（4.2）どおり、作品の削除は棚に載っていることを外す操作にした（`remove_work`）。

**確かめたこと。** 一覧・件数から消え、保存版は読め、もう一度の保存で戻ることを棚の試験にした。画面と API には

### 6.29 使われなくなった実体の回収（2026-11-15）

**決めたこと。** 4.2 の回収を作った（`Library::reclaim`、CLI の `reclaim <新棚>`）。

- 参照は「`content_files` を指す外部キーのある列すべて」で数える（表を足しても数え漏れない）。どこからも参照
  されないファイルを台帳から外す。確定したファイルの構成は書き換えられない（トリガー）ので、外部キーの検査を
  確定まで延ばし、親を先に外す。
- 台帳にない部分実体を隔離し（`<hash>.<時刻>.quarantined`）、隔離から 7 日過ぎても参照されなければ消す。
  書き込み途中の一時ファイルは 1 日、壊れて退けた実体は 7 日で消す。
- 保存は実体を置いて（使い回して）から台帳に確定する。その間の実体を退けないよう、実体領域は使い回すたびに
  更新時刻を今にし（保存・確認・受信の判断）、回収は最後に使われてから 1 日過ぎた実体だけを退ける。
- 参照されている実体が隔離にあれば戻す。実体領域にも隔離にもなければ、何も外さずに失敗する。
- 回収・検証・バックアップは同時に走らない（台帳の全ファイルを読む処理の途中で消さない）。
- 回のたびに `storage_operations`（`reclaim`）へ始まりと結果を残す。これでこの表が使われる（4.6 の外す案は取り下げ）。
- 作品を棚から外しても保存版は残るので、その実体は回収されない。回収されるのは、追いつきで差し替えた原記録・
  保存の確定の前に落ちた跡・壊れて退けた実体。

**確かめたこと。** 猶予・隔離・消去・戻し・失敗の各場合を棚の試験にした。見本の棚（1,002 作品）では、追いつきで
差し替えた原記録 1 件を台帳から外し、実体は猶予のあいだ残した（0.65 秒）。そのあとの検証も通った。稼働中の
棚ではまだ回していない。

**まだのこと。** アプリの中から呼ぶ形、完全な削除、回収した容量の画面への表示。

### 6.30 読書 bundle と、端末ごとの同時数（2026-11-15）

**決めたこと（4.3）。**

- `GET …/views/{snapshot|edit}/{id}/bundle` が、読書用文書（`piep-reader-v1`）と渡せる全資産の
  file 記述を一回で返す（`piep-reader-bundle-v1`、型は `piep-library-protocol` の `ReaderBundle`）。
  未保存の資産と原応答は載せない。編集の基準の保存版の資産は、その保存版の view で取る形で載せる。
  部分の取得は今の形のまま。接続情報の `readerBundle` を true にした。
- 渡してよい資産の決まり（原応答は出さない・添付は読書用だけ）を棚の `reader_may_read` に置き、
  bundle と一ファイルの入口の両方で使う。
- 同時数は端末ごとに 4、全体で 8。空きを最大 2 秒待ち、なければ 429 と `Retry-After: 1`。認証は
  端末の識別も返す（`Authority::grant`）。
- ETag と 304 を外した。部分は `immutable` で長く持たせ、記録は毎回確かめる。

**確かめたこと。** loopback の試験で、bundle の file 記述だけから本文と画像を部分ごとに取り直して
元のハッシュに戻ること、未保存の画像は載らないこと、ほかの作品の保存版・ほかの棚・知らない view・
余計な問い合わせを断ること、一台が枠を使い切ってもほかの端末は読めること、待つあいだに空けば
断らないことを確かめた。

**まだのこと。** 本番のサーバーへの組み込みと永続の許可（4.4）、携帯の側の読み取り（4.5）。

### 6.31 書き込みは、正本に切り替えた棚だけ（4.1 の 4、2026-11-15）

**決めたこと。**

- 棚に切り替えの時刻を持つ（`library_meta.switched_at`、スキーマ 17）。NULL のあいだは旧棚から
  移した写しで、アプリは書かない（書けば旧棚からの追いつきが続けられない）。切り替えた棚へは、
  旧棚から移さない（移行器が断る）。二重書き込みはしないまま、書き込みを先に作っておける。
- 切り替えは `Library::switch_over`（試験用に `piep-library switch-over <新棚>`）。移行の未解決が
  残っていれば断る。二度目は前の時刻を返す。アプリの中の切り替えの操作は、最後の追いつきと
  一緒に作る（4.1 の 5）。
- アプリの命令 `library_v2_set_user_state`（お気に入り・更新の監視）と `library_v2_remove_work`
  （棚から外す。保存版・編集・コレクションの行は残り、検索の索引からは続けて消す）。どちらも
  切り替えた棚でなければ断る。画面が一回の操作ごとに要求 ID を作り、送り直しても二度書かない。
- 画面は、切り替えた棚でだけ作品カードのお気に入り・更新監視・「棚から外す」と作品画面の
  お気に入りを押せる。切り替える前は今までどおり押せない形で同じ場所に置く（並びと幅を
  変えない）。書いたあとは、棚の状態のほかの問い合わせを全部古いことにする。
- カードの「読む」は新しい棚の読む画面へ進む（前は押せなかった）。

**確かめたこと。** 切り替える前の棚には命令が書かないこと、未解決が残る棚は切り替えないこと、
切り替えた棚へは旧棚から移さないこと（Rust の試験）。カードが切り替えの前後で押せる・押せないを
変え、押すと作品の ID で書くこと（画面の試験）。

**まだのこと。** 読書位置（今は端末の保存で、鍵が旧棚の番号。切り替えのときに棚へ移す）、
コレクションの編集、編集の保存、取得と保存、EPUB / PDF。旧版の画面にあるタグの編集は無いので、
利用者のタグは画面を作らない。

### 6.32 読書位置を棚へ（4.1 の 4、2026-11-15）

**決めたこと。**

- 正本に切り替えた棚では、読む画面が読書位置を棚の `reading_positions` に書く。形は携帯の位置と
  同じ「ページ（`ReadingAnchor::Page`）とその中の割合」。端末の細かい位置（何行目か）は、
  この端末で開き直すための控えとして端末に残す。命令は `library_v2_reading_position`・
  `library_v2_set_reading_position`（切り替えた棚でなければ断る）。デスクトップの端末の識別は
  棚の ID から決める。
- 棚へは間引いて書く（書くたびに outbox が一つ増える）。同じページでは 15 秒に一度、ページを
  移ったとき・読み終えたとき（`finished`）・離れるときは必ず書く。
- 開くとき、棚の位置がほかの端末のもので、この端末の記録より新しければ（端末の記録は書いた
  時刻 `at` を持つようにした）、棚の位置から開く。時刻を持たない古い端末の記録は端末を優先する。
- 読みかけの棚は、切り替えたあと棚の読書位置で絞る（`WorkFilter.reading`。読み終えた・消した
  位置は除く。ほかの利用者の位置は混ぜない）。

  （`piep.reading-keys-adopted`）、今の本文の読みかけを棚へ引き取る（`library_v2_adopt_device_positions`。
  端末の位置は px なので割合にできず、棚に位置がない作品にだけページの頭として書く）。これで
  読書の記録は旧棚の番号に頼らなくなる（旧版を消す 4.1 の 6 の前提）。
- 設定・作品の画面・読む画面の説明を、切り替えた棚では書く内容に合わせた。

**確かめたこと。** 見本の旧棚（612 作品）を移行して `switch-over` し、開発版をその棚で開いて、
カードのお気に入り・更新監視、作品の画面のお気に入り、読む画面の位置（1 ページ目の 72%）、
読みかけの棚、棚から外す（白地・赤枠の確認）が棚に書かれ画面に出ることを確かめた。見本の棚と
開発版のフォルダーは消した。試験：読みかけの絞り込み（Rust）、端末の記録の引き取り・しおりの

**まだのこと。** 以前の編集版の一覧（6.35 で済み）。取得と保存、EPUB / PDF。

### 6.35 以前の編集版と下書きの知らせ（4.1 の 4、2026-11-16）

- 新しい棚では自動保存の下書きも封をした版として残るので、版の表だけでは「以前に反映した版」と

**確かめたこと。** 戻した版が一覧に載り、反映し直すと外れる・一覧に無い版は断る・別の下書きの反映で前の版が

なっていない版」が載る（Rust）。旧棚の archived の編集が一覧に載り、外した編集も載る（移行の試験）。作品の
画面で、切り替えた棚ではもう一度反映・一覧から外す・すべて外すの確かめが出て、切り替える前は見るだけ

### 6.36 取得と保存を棚へ（4.1 の 4、2026-11-16）

**決めたこと。**

- 取得元の応答から保存の入力（項目・本文・画像と添付の枠）を組む規則を `library/work_capture.rs` に一つにした。
  旧棚の版の移行と、アプリの保存が同じ規則を使う（移した作品と、切り替えた後に保存した作品が同じ形になる）。
- 入口は `Library::save_work`（取得を始めた記録を作り、応答そのものを原本として残し、手元に落とした画像・
  添付を渡す）。中身が今の版と同じなら版を増やさない。失敗したら取得の記録を閉じる。
- アプリの保存（`download_and_save`）は、正本に切り替えた棚があればそちらへ、なければ旧棚へ。棚へ保存する
  ときは題名・作者などの引数を使わず、棚が応答から読む。返り値は `SavedWork`（旧棚の行か棚の作品）。
- 棚への保存で画像と添付を落とし直さないのは、応答の中身（旧棚と同じ `compute_content_details` の指紋、
  FANBOX は更新時刻も）が今の版の原本と同じで、取得元の画像・添付が今の版に全部あるときだけ。そのときは
  棚へ何も書かない。FANBOX の添付は、以前の保存名（`名前.拡張子`、ID を付ける前）で持っている版も同じ添付と
  見なす（見本で 1 件。見なさないと落とし直して、名前が変わっただけの版ができる）。
- 棚から外した作品は、中身が同じでも保存し直せば棚に戻す（`remove_work` の約束。中身が変わったときしか
  戻っていなかったので直した）。
- 保存・更新のジョブは結果を `SavedRef`（旧棚の番号か棚の作品）で持つ。棚の作品は、ジョブの記録の作品番号を
  空にし、監視に載せる設定なら棚の監視を入れる。候補の「手元にあるか・監視しているか」は棚で見る。本文が指す
  挿絵の欠け（一部保存）は、落とした画像の名前から数える。ジョブが終わったら棚から出す画面も読み直す。

**まだのこと。** ジョブの項目（更新の確認の対象）は旧棚の作品から作るので、切り替えた後に新しく保存した作品は
更新の確認に載らない（作品ごとの確認と一回きりの作者の確認は 6.37 で対応）／ジョブ・候補・記録の表は旧棚の piep.db／作者・シリーズの横顔の取得は旧棚だけ／
FANBOX の添付の取り直しの回数の覚え書き（取れない添付を毎回追わない）と pixiv の指紋の覚え書きは旧棚だけ／
改稿でない補完（旧棚の repair）の印は付けない／編集で埋めた挿絵を欠けから除く判断は旧棚だけ。

**確かめたこと。** 保存・同じ中身の保存し直し（版が増えない）・本文の変更（改稿）・失敗（取得の記録が閉じ、
今の版はそのまま）・外した作品の保存し直し（Rust）。見本の旧棚 612 作品を移した棚へ、旧棚の今の版の応答と
ファイルで保存し直して版の増加 0・失敗 0（`piep-library resave-legacy`、5.1 秒・一件最大 101 ms）。同じ棚で、
落とし直さなくてよいという判断が 612 作品すべてで成り立ち、旧棚の版のフォルダーを落とした画像として読んだ
入力が移行の入力と全作品で一致（`PIEP_SHELF_SAVE_PROBE=<旧棚>|<棚>` の probe）。ジョブの後に棚の画面を読み
直す（画面の試験）。開発版での実際の取得は、開発版に取得元の接続がないため未確認。全棚でも未確認。

### 6.37 更新確認の作品の対象と照合を棚へ（4.1 の 4、2026-11-16）

**決めたこと。**

- 正本に切り替えた棚では、作品ごとの更新確認の対象を棚の監視状態から作る。一回きりの作者の確認も、
  その作者に属する棚の作品を使う。500 件ずつ最後までたどり、同じ作品は一度だけ。新作だけの確認には混ぜない。
  以前の画面が作品番号を渡す場合は移行先の対応表で解き、空の範囲を全作品へ広げない。
- ジョブの作品項目は取得元とその作品 ID だけを持つ。処理時に現在版と原応答を棚から読み、棚から外した作品は
  取得しない。以前の形式で残った作品項目も同じ経路へ寄せる。利用者が編集した題・本文を改稿の比較に使わない。
- 確認だけなら、変更を改稿候補として既存の候補の列へ返す。自動保存なら 6.36 の保存へ通す。原応答が同じなら
  画像・添付は落とし直さず、挿絵が欠けた結果は一部保存として返す。取得元の削除や制限で手元の版を失わない。
- pixiv は、最近の本文照合（14 日以内）・原応答のメタデータの指紋・画像や添付の保存状態がそろう場合にだけ
  本文の取得を省く。本文の欠け・制限画像・期間超過は省かない。確認日時は棚の `source_entity_state` に書き、
  照合した版が現在版でなくなった場合は更新しない。改稿を見つけただけでは本文照合の時刻を進めない。
- 「同じ中身なので落とし直さない」判断も、台帳に参照があるだけでは通さず、各部分の実体があるかを確かめる。
  失った実体は保存し直して戻せる。改稿や保存版を増やさない。

**確かめたこと。** 旧棚の作品行が無くても新しく保存した作品が監視の対象と改稿候補になること、監視を外した作品と
棚から外した作品を除くこと、作者ごとの範囲・新作だけの範囲・空の範囲、現在の原応答との照合（pixiv / FANBOX）、
確認日時の逆行・別作品の版・古い版への書き込みの拒否、メタデータで本文を省ける条件、実体欠損後の保存し直しを試験した。
取得元へ接続する実機確認と全棚の確認はまだ行っていない。

**まだのこと。** ジョブ・候補・記録の台帳、登録した作者の web 一覧による改稿走査、その一覧と各作品の確認の
使い回し、FANBOX の作者一覧の使い回しを棚へ移す（一覧の走査と使い回しは 6.38 で対応）。作者・シリーズの横顔、添付の取り直しの記録、補完の印、
編集で埋めた挿絵の扱いも引き続き 6.36 の残り。作品 UUID を指定した画面からの個別確認もまだ。

### 6.38 作者の改稿走査と一覧の共有を棚へ（4.1 の 4、2026-11-16）

**決めたこと。**

- pixiv の作者の改稿走査は、棚にある現在版の作品 ID を web の一覧へ渡す。作品ごとの監視が無い作品も対象にし、
  棚から外した作品は除く。走査には DB の版の項目と確認状態を使い、作品の原応答を全件開かない。
- 作者の走査と各作品の確認は、一つのジョブで同じ作者の一覧を共有する。pixiv は一覧の更新日時と基準値が一致し、
  最近の本文照合と必要な実体がそろえば詳細と本文を取得しない。伏せられた作品・不完全な一覧・欠けた実体を
  「変わっていない」にしない。メタデータと本文へ進む場合も 6.37 の確認を続ける。
- 基準値は棚の `source_entity_state.source_updated_at` に持つ。保存または本文照合より前の更新だと言える場合だけ
  `remember_work_source_update` で覚え、照合した版が現在版でなくなった場合は書かない。棚の API 自身も、本文の
  保存・照合より新しい時刻を基準にすることを断る。基準値が変わると一覧の更新日を追いつかせる。
- FANBOX は、作者の確認では全投稿の一覧を一度読み、新作と過去の保存済み投稿の改稿を同時に調べる。作品の確認も
  同じ一覧を使う。前回位置より古い未保存投稿は再提示せず、古い保存済み投稿を調べても確認位置を過去へ戻さない。
  「新作だけ」はこれまでどおり前回位置より先だけを見る。作者の全一覧を読めなければ改稿確認を完了にしない。
- 取得元で見つからない作品の記録は、旧棚の行を必要としない形にもした。手元の版を残し、同じジョブでの重複と
  前回から同じ保留の件数は従来の規則に従う。再び一覧に載れば、見つからなかったという保留を解く。
- 本文が `detail.text` にある保存形式でも、挿絵の参照の欠けを調べる。欠けを見落として一覧の一致だけで本文を
  省いていた場合を直した。

**確かめたこと。** 旧棚の作品行なしで作者の改稿を候補・自動保存の待機列へ返すこと、一覧の共有、伏せられた作品、
原応答の実体を開かない走査、棚から外した作品の除外、未確認の更新日時・別作品の版・古い版を基準にできないこと、
再確認の日時の一致と期間超過、挿絵の欠け、見つからない作品の保留と再発見、FANBOX の新作と過去の保存済み投稿の
選別を試験した。取得元への実通信と稼働棚での試走はまだ行っていない。

**まだのこと。** 監視対象とグループ、候補、ジョブと記録の台帳は旧棚の `piep.db`。作者・シリーズの横顔の保存、
添付の取り直しの記録、補完の印、編集で埋めた挿絵の扱い、作品 UUID で指定する画面からの個別確認と改稿差分の表示も引き続き残る。

### 6.39 監視対象とグループを棚へ（4.1 の 4、2026-11-16）

**決めたこと。**

- 正本に切り替えた棚では、アプリの作者・シリーズの監視対象とグループの読み書きも棚を使う。

- 本文まで変わった場合や、対応・取得元・実体を確認できない場合は原入力を残して取得を閉じ、手元の版を守る。
  復元した画像の形式と大きさも検査し、読めない元画像を案内画像で置き換えない。
- pixiv の同じ URL の資産も保存状態から復元する。新しい実画像の URL へ前の画像を使い回さない。
  スキーマ・入力記録・IPC の追加はない。

**確かめたこと。** アプリの保存口で表紙・別名の本文画像を保ち、制限画像への HTTP を増やさず、
改稿・保存状態を増やさないことをローカル HTTP で試験した。本文の変更時は通信前に止めて原入力を残すこと、
新しい実画像の URL は実際に取得して失敗を返すこと、取得元不明・不正な画像では手元の版を守ることも試験した。

**まだのこと。** 編集で埋めた挿絵の扱い、単独サーバーの管理 API。取得元との実通信と稼働棚での試走も残る。

### 6.55 保存結果の挿絵の不足へ反映中の編集を織り込む（4.1 の 4、2026-11-18）

**決めたこと。**

- pixiv の保存結果の挿絵の不足は、同じ取得元の改稿を基準にした反映中の編集を確かめる。
  保存状態が補完で変わっても同じ改稿なら適用し、下書きや別の改稿の編集で現在の不足を消さない。
- 実体がある編集画像と、編集で取り除いた参照を不足から外す。未解決の画像・本文に残った指定・
  空の編集画像は不足に残す。省略した 1 ページ目と明示した 1 ページ目を同じ指定として照合し、
  解釈できない指定は元の字句で照合する。
- 通常の保存と同内容で保存を省く経路の双方で判定する。原本の欠損と読書用の対応は変更しない。
  編集を確認できない場合は原本の不足を残し、保存済みの原本を失敗や完全な取得へ読み替えない。
- スキーマ・入力記録・IPC の追加はない。

**確かめたこと。** 下書き・反映・取り消し・再反映、同じ改稿の補完、別の改稿、別作品の保存状態の拒否、
空の編集画像・削除した参照・ページ番号の省略形・未解釈の参照を試験した。アプリの両保存経路で不足が解消し、
編集を下ろした後の保存で不足へ戻ること、原本とその画像の対応が変わらないことも試験した。

**まだのこと。** 編集の反映・取り消し直後の一部保存の再検査、更新確認の省略判定との共有、
単独サーバーの管理 API。取得元との実通信と稼働棚での試走も残る。

更新確認の省略判定との共有、単独サーバーの管理 API、取得元との実通信と稼働棚での試走が残る。

### 6.67 携帯の一覧・作品の画面・表紙を新しい棚から出す（4.1 の 3）

### 6.68 携帯の端末への保存とお気に入りの書き込みを新しい棚へ移す（4.1 の 3）

- 配信用サーバーに、棚の作品のお気に入りを付け外しする口を足した。要求 UUID と更新世代を受け取り、
  棚の受領で一度だけ効かせる。世代が違えば 409 と今の値を返す（端末の時刻で勝者を決めない）。
  一覧と作品の画面は、利用者ごとの値と世代を返す。単独サーバーは旧 API の変更の記録へも写すので、
  デスクトップ版の取り込みと旧 API の画面（作者・シリーズ・コレクション）は同じ値を出す。
- 携帯は接続確認でこの口を知り、棚の作品のお気に入りを押せるようにした。先に変わっていたときは

- 端末への保存は、置き場の鍵を旧 API の番号（`work-{番号}`）と棚の作品の UUID（`shelf-{UUID}`）の

  形式を中身から見て保存する。受け取りの前後で版と編集の UUID を確かめ、途中で変われば保存しない。

- まだ新しい棚に無いもの：作品のコレクション（保存版にも残さない）、以前の版を選んで読むこと。
- サーバーは受領・世代の食い違い・形の崩れ・外した作品・権限・旧 API からの反映を、携帯は 409 の
  見分け、鍵の形と置き場の名前、棚の作品の保存版の一覧・本文・画像・索引・削除、お気に入りの世代の
  受け渡しと食い違い、保存と一覧の変換を試験した。

### 6.69 携帯の作者・シリーズ・コレクションの画面を新しい棚から出す（4.1 の 3）

- 配信用サーバーに、作者・シリーズの一覧・画面・作者のシリーズ・画像と、コレクションの一覧・画面・
  表紙、作品の入ったコレクションの口を足した。形は旧 API と同じ型で、数え方・並べ方はデスクトップの

  UUID で指す。回の作品は一覧と同じ棚の作品の形で、お気に入りは利用者ごと。一覧の集計は棚の世代と
  条件ごとに覚え、ページをめくるたびに集め直さない。旧 API では開けなかった、プロフィールを
  取っていない（作品にだけ名前の載った）作者の画面も、棚の名前で開ける。
- 見本の棚で、作者・シリーズの一覧（作品の数・名前・保存日の順）とシリーズの数は旧 API と全件で
  一致した。
- コレクションの画面は旧棚から移したものを旧棚の ID でも開ける。端末に旧 API から保存した作品が
  持っている ID のまま開けるように。
- 携帯は接続確認でこの口を知り、画面と画像をここから引く。単独の表紙は作品の番号でなく
  `cover/single` で引く。棚の作品を端末に保存するときも、作品のコレクションと作者・シリーズの画像を
  棚から残す（6.68 で残さなかった分）。
- まだ新しい棚に無いもの：検索の候補、以前の版を選んで読むこと（6.70 で移した）。
- サーバーは一覧のページ送り・並べ替え・名前の絞り込み、作者とシリーズの画面、リンクの選り分け、
  画像、コレクションの並び・利用者ごとのお気に入り・表紙の枠・作品の位置、知らない条件と棚に無い
  ものを、携帯は口の知らせ、画像の経路の形、画面の振り分けと変換を試験した。

### 6.70 検索欄の候補と以前の版を読むことを新しい棚へ移す（4.1 の 3）

- 検索欄の候補の組み立て（前方一致・一致した名前を先に・種類の順・よく使う名前の束からの正規化と

- 配信用サーバーに候補の口を足し（`x-piep-suggest`）、携帯は接続確認で知って候補を棚から引く。

- デスクトップの検索欄も、新しい棚の一覧を出しているときは候補を棚から引き、題の候補は新しい棚の

- 作品の画面の版の一覧に、版ごとの写しの ID を添えた。携帯の読む画面は以前の版を選ぶと、その写しの

### 6.71 携帯の読書位置を新しい棚と受け渡す（4.1 の 3）

- 配信用サーバーに読書位置の口を足した（`x-piep-reading`）。位置はデスクトップの読む画面と同じ
  「ページとその中の割合」（`ReadingAnchor::Page`）で、読んでいた版の写しか編集に結ぶ。書き込みは
  お気に入りと同じく要求 UUID と更新世代で、送り直しても一度だけ効き、世代が違えば 409 と今の位置を
  返す（端末の時刻で勝者を決めない）。端末の識別は登録の ID から決まった UUID で、旧 API の位置を
  移すときと同じ値（`server_device`）。
- 一覧は初めに利用者の位置を全部、そのあとは棚の変更の記録（outbox）の番号で変わった分だけを返す。
  返し始める前に番号を控えるので、途中で変わった位置も次の差分で届く。印には同期の世代を入れる。
- 携帯は書き込みを端末の記録（版 5：`shelf_reading_meta`・`shelf_positions`・`shelf_pending`）に
  置いてから送る。409 の今の位置がこの端末のもの（応答の届かなかった前の書き込み）なら今の世代で
  書き直し、ほかの端末のものなら捨てて、読む画面の「続きの位置」の案内に任せる。棚・利用者・同期の
  世代が変われば、位置も未送信の書き込みも捨てる（戻す前の要求を新しい操作として当てない）。
- 読む画面は、棚から開いた今の版の本では位置を棚へ書き、開くとき・前に戻ったときに棚の位置を見る。
  ほかの端末の位置が手元より新しければそこから開く（読んでいる最中は案内だけ）。別の版や編集で読んで
  いた位置はページの目安にする。この端末が書いた位置は手元の細かい位置を使う。旧 API の同期は
  受け渡せない接続でだけ使う。
- まだのこと：単独サーバーの棚は配る写しなので、携帯が書いた位置（とお気に入り）を、写しを入れ替える
  前にデスクトップの棚へ取り込む仕組み（6.84 で作った）。写しを送る仕組み（遠隔転送）は別に残る。
- 試験：受領・世代の食い違い・本文に無いページ・別の作品の版・形の崩れ・外した作品・権限・端末の
  識別・全部と差分の一覧・ページ送り・ほかの利用者・古い印（サーバー）、世代の受け渡し・新しい
  書き込みの残り方・古い世代・同期の世代の変わり目・形の検査（携帯の Rust）、書く先と同期・切った
  とき・開始位置の選び方（携帯）。

### 6.72 更新確認の残り：未保存の改稿と一部保存の補完を棚へ（4.1 の 4）

- 更新確認の命令を見直した。ジョブ・候補・監視・横顔・個別確認はすでに棚へ切り替わっており、
  切り替えた棚でも旧 DB を読んでいたのは、未保存の改稿の一覧と差分、一部保存の補完の 4 つだった。
- 未保存の改稿は、棚の `discovery_candidates` の未判断の改稿で、棚から外した作品を除く
  （`Library::pending_revisions`）。一覧は作品の画面と同じ ID の文字列（棚では作品 UUID）で返し、
  カード・一覧・作品の画面はその文字列で照合する。棚の作品のカードにも「未保存の改稿」の印が出る。
- 差分は作品 UUID で受け、棚に未判断の改稿があるときだけ取得元へ問い合わせる。棚の作品の画面の履歴に
  「取得元の改稿（未保存）」の行を足し、保存済みの今の版と比べる（開くだけでは保存しない）。
- 補完の印は、移した印（`repair_attempt_markers`）を原記録として変えず、新しい試行をスキーマ 25 の
  `incomplete_save_attempts` に書く。対象は保留の種類が `incomplete` の pixiv 作品で、今の版に
  どちらの印も無いもの。版が進めばもう一度だけ試す。棚に無い作品は記録しない。
- 試験：未判断の改稿だけを返すこと・判断と外した作品・保存していない作品の候補（棚）、版ごとに一度・
  記録の重複・棚に無い作品・上限（棚）、旧 DB を落とした古い棚からの移行、棚の作品の印と差分の画面。
- 分離した開発版で、見本から移して切り替えた棚の一覧（リスト表示）に「未保存の改稿」の印が出て、押すと履歴の
  「取得元の改稿（未保存）」が選ばれた状態で開き、差分の取得が棚の経路で接続の確認まで進むことと、v1 を選べば
  版の表示へ戻ることを確かめた（開発版には取得元の接続がないので差分の中身は未確認）。
- まだのこと：単独サーバーの管理 API からの監視の操作。取得元との実通信と稼働棚での試走。

### 6.73 監視の残り：棚の範囲の更新確認を棚で選ぶ（4.1 の 4）

- 監視グループと監視対象の命令（一覧・作成・名前・削除・中身・有効・外す）と顔の画像は、すでに切り替えた
  棚を使っていた。残っていたのは、更新確認を「お気に入り」「読みかけ」の範囲で始めるときに、画面が旧棚の
  検索で作品の番号を集めて「作品」の確認として送っていたこと。
- 切り替えた棚では画面が番号を集めず、範囲（`favorite`・`reading`）のまま送る。棚が自分の絞り込み
  （お気に入り・利用者の読みかけ）で作品を選ぶ。監視の有無に関わらず、画面が知らせる上限と同じ 500 件まで。
  新作だけの確認にはしない。切り替える前は従来どおり。
- 履歴と結果の文言に「お気に入り」「読みかけ」を足した。
- 試験：範囲ごとの作品の選び方・監視中の作品を混ぜないこと・新作だけの確認（棚）、切り替えた棚で番号を
  集めないこと（画面）。開発版には取得元の接続がないので、確認の開始は画面で未確認。

### 6.74 保存した検索を棚へ（4.1 の 4）

- 保存した検索の 3 つの命令（一覧・保存・削除）は、切り替えた棚でも旧 DB を読み書きしていた。棚の側の
  API（持ち主・更新世代・削除記録・outbox）はできていたので、命令を棚へ分岐させた。
- 画面とのやりとりでは ID を文字列にした。棚では検索の UUID、切り替える前は旧 DB の番号の文字列。
  画面は中身を解釈せず、URL の `saved` もそのまま照合する。
- 棚の持ち主は棚そのもの。保存は、ID があればその検索を、なければ同じ名前の検索を上書きし、どちらも
  なければ新しく作る（旧 DB と同じ規則）。毎回新しい要求 ID と、読み直した更新世代で書く。消した検索は
  ID で上書きできず、同じ名前で保存すれば新しい検索になる。削除は削除記録を残し、無い・もう消えた検索は
  `false`。名前・条件の大きさの誤りは旧 DB と同じ文言で先に返し、長すぎる検索語は切り詰める。
- 試験：名前と ID での上書き・並び・作成日時の維持・削除と再作成・不正な ID（棚）、旧 DB の番号の受け渡し。
  開発版で、試しの棚へ保存し、サイドバーから開いて選んだ印が付くこと、削除で棚に削除記録が残ることを確かめた。

### 6.75 コレクションの提案を棚へ（4.1 の 4）

- 提案の 12 の命令（走査・種から作る・一覧・採る・断る・閉じる・走査の片付け・合う作品・名前の案・
  命名の材料 3 つ）は、切り替えた棚でも旧 DB で計算し、旧 DB へ書いていた。
- 計算は旧棚と同じ SQL（約 4,500 行）を使い続ける。棚から作業用の表（旧 DB の形の一部：作品・シリーズ・
  タグ・本文リンク・組の採否・コレクション）をメモリ上に組み、作品は表の中の番号と UUID を対応させる。
  表で表せないもの（意味索引・本文・旧棚のリンクの取り直し）は `SuggestionSource` で切り分けた。
  棚では意味索引を `semantic_documents` の鍵で引き、旧棚のリンクの取り直しはしない。
- 結果は棚の表（`collection_suggestions`・`_seeds`・`_members`・`collection_pair_feedback`）へ書き、
  画面へは旧棚と同じ形で返す。候補の作品は `work`（UUID）で指し、`download_id` は持たない。採ると
  コレクションを棚の一回の編集で作り、命名の出どころは `appearance_json` に残す。採った結果は
  `{id, name}` だけを返す（両方の棚で同じ形）。
- 棚の保存は本文リンクを作っていなかった。保存の後に、今の版の読む用の HTML・本文・説明から旧棚と同じ
  規則でリンクを拾い直し、本文から拾った未判断の根拠だけを入れ替える（利用者の採否とほかの根拠は残し、
  根拠の無くなった関係は消す）。棚に無い作品へのリンクは作品の実体だけを作る。
- 画面：まとまりを探す・受信箱（本文の確認は棚の本文を平文で）・合う作品を探す（棚の一回の編集で足す）・
  名前を考えてもらうを、切り替えた棚で押せるようにした。作品の画面に旧棚と同じ「コレクションに追加」の
  入口を置き、関連作品からのひな型は作品の UUID で作る（作品の入ったコレクションの命令を加えた）。
- 試験：保存での本文リンクの記録と消去、棚に無い作品へのリンク、種からの候補と採用、断った組の記録と
  閉じたときの非記録、走査の重複なしと片付け、合う作品・名前の案・命名の材料、作業用の表の中身。
- 作業用の表は旧 DB と同じ書式にそろえた。公開日時は旧 DB と同じ日本時間（`+09:00`）で書く。番号は旧棚から
  移した作品は旧棚の番号の順、そのあとに保存した作品は保存した順に振る（同じ強さの候補は番号で並ぶ）。
- 実データで突き合わせた（旧 DB と新しい棚の DB の写しだけを使い、本体のファイルは写していない）。種からの候補は
  25 作で旧棚と同じ。走査は上限を外して比べ、本文を読まない条件で 972 件が全部一致した。本文の読み方は、
  本文のファイルがある見本の棚の 612 作で旧棚と全部同じだった。
- 開発版で、試しの棚を使って確かめた。作品の画面から作ったコレクションに入れる、合う作品を探して外した一作を
  除いて足す、まとまりを探す → 本文の確認（段落付きの平文）→ 採ってコレクションを作り開く、まで通った。

### 6.76 棚の数と手入れ（4.1 の 4）

- ホームの集計・横の欄の件数・設定の統計・検索の索引の状態・診断は、新しい棚を見ていても旧 DB を数えていた。
  新しい棚を見ているあいだ（試験中の写しを含む）は、今の版（`work_current_projection`）で数える。最近の保存は
  棚の一覧（保存の新しい順に 4 件）で引き、カードは一覧と同じ棚の作品。読みかけは、端末の記録を棚へ引き取った
  あとは棚の読書位置、引き取る前は端末の旧棚の番号を棚の作品へ読み替えて数える。
- 意味検索の索引は道具からしか合わせていなかった。保存・編集・棚から外すのたびと棚を開いたときに、意味検索を
  使っていれば背景で追いつかせる（一度に一つ。走っているあいだの依頼は終わったあとにもう一度回す）。
  「索引を作り直す」と自動の整備は、切り替えた棚では全文と意味の索引の追いつきになる（旧棚の作り直しも
  待っている分だけを処理していた）。進み具合は旧棚と同じ知らせ。
- 意味検索を使うかは棚のデータではなくアプリの設定（旧棚の移行でも原記録だけを保つ表）なので、アプリの
  フォルダーの `search-settings.json` に置く。無いうちは起動時に旧棚の設定を一度だけ写す。切ると索引を消し、
  走っている追いつきを止める。
- 診断は、棚のファイルが中身の指紋で台帳と結ばれているので、旧棚の「保存フォルダーとの照合」を「台帳と全ファイルの
  照合（`verify`）」に、「未登録のファイル」を「参照されない実体の回収（`reclaim`、使ってから 1 日は残し、隔離して
  7 日後に消す）」に置き換えた。数えるのは台帳と索引の大きさだけで、開いたときに測る。圧縮・統計の整理・全文索引の
  統合（いまの版と過去の版）も棚に対して行い、空き容量が足りなければ何もしない。書き換える手入れは切り替えた棚だけ。
- FANBOX の欠けた添付の数え上げ（旧棚の保存データを読む）は、棚では「一部しか保存できていない作品」の数にし、一覧の
  その絞り込みへ案内する（更新確認で取り直せる）。作者・シリーズ情報の修復は、対象を棚の今の版に載る未取得の
  作者・シリーズから引く（更新の命令はすでに棚へ分かれていた）。保存フォルダーからの再取り込みは旧棚だけ
  （6.83 で設定の「保存とバックアップ」から棚へ戻せるようにした）。
- 試験：件数・統計・ホームの集計（タグ・作者・取得元・月）、追いついていない作品の数、診断の数と手入れの後の照合、
  修復の対象、意味検索の設定の書き戻し。画面は、ホームと診断が新しい棚から読み旧棚に聞かないこと、切り替える前の
  棚では書き換える手入れを押せないこと。

### 6.77 一覧の絞り込み・複数選択・本文のリンク・コレクションの表紙（4.1 の 4）

- 絞り込みの引き出しの選択肢（タグ・作者・種別・添付）と、名前で探す候補・シリーズの指名は、新しい棚を
  見ていても旧 DB から数えていた。棚では今の版から数え、タグは自分で付けたタグと名前でまとめる（一覧のタグの
  条件と同じ）。作者は今の版の作者名でまとめる。名前で探すときの並べ方は旧棚と同じ処理を共有する。
  シリーズの指名は棚の作者・シリーズの一覧で探す。
- 複数選択は旧棚の番号でしか選べず、棚では押せなかった。棚の作品は ID と作品ごと憶え（一覧から外れても
  確認の窓に題名を出せる）、お気に入り・更新監視・棚から外す・コレクションへ入れる・読みかけから外すを棚に
  頼む。消す操作は棚では「棚から外す」（版・編集・コレクションの記録は残る）。読みかけから外すは端末の記録を
  消し、端末の記録を棚へ引き取ったあとは棚の読書位置も消す（新しい命令）。EPUB は 4.1 の 4 の EPUB の項で。
  書き換える操作は正本に切り替えた棚だけで、試験中の写しでは押せない形で理由を添える。
- 作者・シリーズの一覧の監視の切り替えは、監視の命令がすでに切り替えた棚へ書くので、書ける棚では押せる。
- 本文のリンクの宛先は旧棚で引いていた。棚を見ているときは棚に載る作品（外した作品は除く）と作者・シリーズを
  引き、作品は棚の ID の画面へ開く。棚がまだ開けないときだけ旧棚で引く。
- コレクションの表紙は棚の見た目の編集に表紙の画像（取り込んだファイルの指紋）を足した。画像は選んだときに
  棚へ取り込み、見本も保存後と同じ画像で出す。取り込んだまま使わなかった画像は外部キーで参照を数える回収が
  片付ける。「1作を選ぶ」は取得元と作品の番号で選ぶ（棚の作品は旧棚の番号を持たないことがある）。複数選択で
  外すのも同じ鍵で選ぶ。
- 内蔵ブラウザの一覧から読んだ候補の「保存済み」「監視に登録済み」は、切り替えた棚では棚に載る作品と棚の監視の
  登録で見る（止めた登録も登録済み）。作者・シリーズの画面は、アーカイブの書き出し（4.1 の 4 のバックアップの項）
  のほかはすでに棚から読んでいた。
- 試験：選択肢の数え方（自分のタグを含む・同じ作品は一度）と名前で探す並び、リンクの宛先の引き方、表紙の画像の
  設定と外し方（棚に無い画像は断る）。画面は、棚の作品をまとめてお気に入り・外すこと、試験中の写しでは複数選択を
  押せないこと、選択肢を棚から数えること、本文のリンクを棚で引くこと。

### 6.78 AI の手伝い（4.1 の 4）

- AI の手伝いは、新しい棚を見ていても材料を旧 DB から読み、採ったタグと覚え書きを旧 DB に書いていた。棚では
  材料（題名・作者・タグ・概要、あらすじの本文は今読む版）とタグの語彙を今の版から作り、モデルが棚を調べる道具
  （タグを探す・実在を確かめる・件数・一緒に付く数・使われ方）も棚で答える。数え方と上限は旧棚と同じ。
- 採ったタグは棚の自分のタグに書く。一緒に付くタグの候補から採ったものは「手動」、モデルの案から採ったものは
  「モデルの案を採った」の出どころで持ち、外すときは出どころの合うものだけを外す（取得元のタグは外せない）。
  付け外しのあとは検索の索引を追いつかせる。
- 一緒に付くタグの候補は、旧棚と同じ余弦の数え方を棚のタグの名前で行う。数えるのは取得元のタグだけで、
  対象の作品と同じ作者（作者・作り手として載る人が一人でも同じ）の作品は数えない。
- 覚え書き（あらすじ・作者のメモ・前回のあらすじ）はスキーマ 26 の `ai_notes` に置き換えで持つ。作り直せる
  派生物なので版の記録は持たない。鍵は棚の ID（前回のあらすじは `読む話:前の話`）。読み出すときに今の材料から
  指紋を作り直して、材料が変わったかを示す。前回のあらすじの指紋に前回までの覚え書きは含めない（読み出す
  ときに確かめられないため）。旧 DB の覚え書きは移さない（作り直せるもので、手元の旧棚には一件も無かった）。
- 案を出す・候補を見る・覚え書きを読むのは試験中の写しでもでき、タグを付け外しする・覚え書きを残す・消すのは
  正本に切り替えた棚だけ。試験中の写しで作ったあらすじは見せるだけで残さない。
- 画面は、作品の画面（棚）・作者の画面・読む画面の前回のあらすじ・一覧の言葉で探す・コレクションの分け方を
  棚へ頼む。作品は棚の ID（文字列）で渡し、旧棚の番号と取り違えない。前回のあらすじは、読む話と前の話が同じ棚の
  作品のときだけ出す。コレクションの分け方の案から作るコレクションは、棚では作品の鍵で一回に作る。
- 試験：自分のタグの出どころと付け外し、一緒に付くタグの数え方（同じ作者を除く・採ったタグは次から出ない）、
  道具の答え、作者の材料と本文、覚え書きの置き換え・材料の変化の検出・前回のあらすじの受け渡し・削除。画面は、
  棚の作品を棚の ID で頼むこと、試験中の写しではタグを付け外しできないこと、どちらの棚へ頼むかの振り分け。

### 6.79 EPUB（4.1 の 5）

- EPUB は、新しい棚を見ていても旧棚の番号でしか積めず、書き出しも旧 DB の行と保存フォルダーから組んでいた。
  棚では、今読む版（反映した編集があればその基準版と編集）の原応答と、画像・添付を元の名前で一時の置き場の
  `data_assets/{cover,illustrations,files}/` へ書き出し、旧棚と同じ変換に渡す。変換の規則を二つ持たない。
  一時の置き場は、本を組み終えるまで持ってから消す。
- 反映した編集は、旧棚と同じく取得元の形（pixiv の本文・FANBOX のブロック・平文）へ組み直して差し込む。編集の
  画像のうち、版の画像と同じファイルのものは取得元の画像として扱い、それ以外は編集で足した画像として本へ加える。
  本文が指していない足した画像は入れない。
- キューは旧棚の番号と棚の作品の ID（文字列）を混ぜて持つ。書き出しの結果（失敗・不合格・未着手）も同じ形で
  返し、残すものはキューに残る。キューの画面は、旧棚の作品は番号で、棚の作品は ID でまとめて引いて、キューの順に
  並べる。コレクションの一冊は、棚のコレクションの回を順に組み、表紙に選んだ作品の表紙と同じ画像の回を表紙にする。
  テンプレートの見本も棚の作品を選べる。
- EPUB は棚を書き換えないので、試験中の写しでも積める・書き出せる（作品のカード・作品の画面・一覧の複数選択・
  作者とシリーズの複数選択・コレクションの一冊）。
- 試験：書き出す形（置き場と後始末）、表紙と本文の入った本、編集の本文と足した画像、番号と ID の受け渡し。
  画面は、混ぜたキューの書き出しと失敗の残り方、棚の作品のカードからの積み方、コレクションの一冊を棚へ頼むこと。

### 6.80 原寸画像の取り直し（4.1 の 6）

- 新しい棚にも、縮小版で保存された pixiv の表紙・挿絵が残っていた（手元の棚で表紙 26,168 枚・挿絵 438 枚）。
  縮小版の URL で観測した画像のうち原寸と確かめていないものを、今の版から数える（棚全体で 0.1 秒）。
- 取り直しは作品ごとに、保存済みの応答に原寸の在り処を足して、同じ応答の保存と同じ道で保存し直す。URL の
  変わらない画像・添付は棚から戻し、原寸に変わった画像だけを画像サーバーから取る。普段の保存は表紙の枠を
  「持っている」とみて何もしないので、この保存だけは同じ応答でも保存する（経路は `original-image`）。
- 棚は画質の違いを版の違いとして扱わない（縮小版と原寸は同じ画像の別の実体）ので、保存し直しても版は増えず、
  保存状態が一つ増えて原寸が今の画像になる。旧棚の「版を増やさずその場で差し替える」と同じ結果になる。
- 間隔・連続失敗での一時停止・中止・更新の待ち合わせは旧棚と同じ。数と取り直しは見ている棚に対して行い、
  取り直しは正本に切り替えた棚だけで押せる。
- 試験：縮小版の数え方と、原寸で保存し直しても版が増えないこと（pixiv の画像の住所で）、変わった表紙だけを
  取りに行き挿絵は棚から戻すこと。画面は、棚へ頼むことと、試験中の写しでは押せないこと。

### 6.81 バックアップと復元（4.1 の 7）

- 新しい棚を見ていても、設定の「バックアップと復元」は旧棚の分割 ZIP を書き出し・取り込んでいた。棚では、
  棚そのものの自立した写し（`Library::backup`、フォルダー一つ）を作る。写し元を止めずに写し、作ったときに
  中身をすべて検査し、通るまでは棚として開けない形で置く。分割 ZIP は使わない。
- 復元は開いている棚を入れ替えることになるので、その場では行わない。写しを開いて全体を検査し、作品・ファイル・
  容量・同じ棚の写しか・正本に切り替えた写しかを見せてから予約する。次に起動したとき、棚を開く前に、今の棚を
  隣（`…before-restore-<時刻>`）へ退け、写しからもう一つ写しを作って棚の場所に置く。選んだ写しは手元に残り、
  今の棚は消さない。写しが開けない・検査を通らない・写せないときは、退けた棚を戻して今の棚のまま開く。
  予約は一度きりで、結果は隣の記録に残して設定の画面に出す。
- 旧棚の「保存フォルダーを調べる」は旧棚の保存フォルダーを旧棚へ戻す操作なので、新しい棚を見ているあいだは
  押せない形で理由を添える（6.83 で棚へ戻す操作にした）。作者・シリーズのアーカイブ（一部の作品の持ち出し）は、棚から一部の作品だけを
  写す仕組みがまだ無いので、旧棚だけのまま残す。
- 試験：写しの検査（数・同じ棚か・棚でないフォルダーを断る）、予約した入れ替えで今の棚が退けられ写しが残る
  こと、壊れた写しでは今の棚のまま開くこと。画面は、選んだフォルダーの中に新しいフォルダーで作ること、
  検査の結果を見せてから予約すること、予約中は重ねて予約しないこと、前の棚の場所を見せること。

### 6.82 作者・シリーズのアーカイブ（棚の部分写し）

- 6.81 で旧棚だけに残した作者・シリーズのアーカイブを、棚の部分写し（`Library::copy_works`）にした。
  選んだ作者・シリーズの作品（いまの版に名前の載った棚の作品）を、その作者・シリーズ・タグ・全版・取得の
  記録・画像と添付・本文の参照の対応・編集・お気に入り・読書位置・保守の記録・作品の覚え書きごと、
  まだ無いフォルダーへ自立した棚の形で写し、全体を検査してから置く。棚は読むだけなので、切り替える前の
  棚からも書き出せる。
- 部分写しの形式の記録は `library-part.json` で、棚の `library.json` と名前を分ける。部分写しは棚としては
  開けず、復元の入れ替えにも使えない（予約しても起動のときに断る）。
- 取り込みは設定の「バックアップから復元」から。部分写しを選ぶと、入れ替えずに今の棚へ足す
  （`Library::merge_part`）。行は識別子ごと写し、今の棚にある行は書き換えず、無い行だけを足す。
  保存状態の指紋が作品・作者・タグ・ファイルの識別子を含むので、識別子は付け替えられない。だから取り込める
  のは同じ棚（同じ棚の写しを含む）から作った部分写しだけで、別の棚のものは断る。作品ごとに区切って足し、
  同じ作品や作者・タグが別の識別子で保存し直されていてぶつかった作品は、書きかけの行ごと戻して数だけ伝える。
  棚から外した作品は記録が残っているので、棚の一覧へ戻す。
- 公開した保存状態・封をしたファイル・編集・本文の参照の対応は書き換えを拒む仕掛けがあるので、取り込みは
  普段の保存と同じく、封をする前の形で中身を入れてから封をする（編集は親から順に）。実体は台帳より先に写し、
  台帳へ載せる前に中身を確かめる。
- 試験：選んだ作者の作品だけが入り、ほかの作者の作品や表紙は入らないこと、編集・お気に入りが写ること、
  部分写しが棚として開けないこと、同じ場所に重ねて作らず途中の写しを残さないこと。外した作品が記録のまま
  戻り、二度目は何も足さないこと。作品を足す前の写しの棚には新しい作品が足され、別に保存し直された作品は
  足さないこと。別の棚から作った部分写しは断ること。実データ（今の棚の DB の写しと、一人の作者の作品が
  使う実体だけ）で、77 作品・540 ファイルの部分写しが検査を通り、同じ棚の空の写しへの取り込みが全体の検査を
  通り、外した 5 作品が戻ることを確かめた。

### 6.83 保存フォルダーの再取り込みを棚で（4.1 の 7）

- 6.81 で押せない形にした設定の「保存フォルダーを調べる」を、正本に切り替えた棚へつないだ。旧棚の保存先
  （`<取得元>/<作品の番号>/v<版>/`）に残った作品のうち、棚にまだ一度も入っていないものを、取り寄せずに
  フォルダーの中身（`original.json`、無ければ `data.json` と `data_assets/`）のまま棚へ保存する。
- 版は番号の順に一つずつ、普段の保存と同じ道（`save_readable_work`、経路は `reimport`）で保存するので、
  棚の版の記録も同じ順に並ぶ。取得の記録には入力の応答を残す。FANBOX は投稿の形に戻してから保存する。
- 棚にある作品には触れない。棚から外した作品も棚に記録が残っているので対象にしない（外した作品を勝手に
  戻さない）。読めない版は、その版だけ飛ばして理由を返し、画面は件数と同じ行で伝える。フォルダーの数え方・
  リンクや保存先の外を指すフォルダーの断り方・一作品の版の上限は旧棚と同じ。
- 保存したあと、本文の検索の索引と意味検索を追いつかせる。切り替える前の棚では、理由を添えて押せない。
- 試験：版の順と今の版、外した作品を戻さないこと、読めない版の理由、番号でない名前を数えないこと、二度目は
  何もしないこと。画面は、切り替えた棚へ頼み飛ばした理由を記録に出すこと、切り替える前は押せないこと。
  実データ（今の保存先から写した pixiv 4・FANBOX 4 作品、版が 3 つの作品を含む）を空の棚へ戻し、
  本文の長さ・版の数・画像と添付の数・題が今の棚と全部一致し、全体の検査を通ることを確かめた。

### 6.84 携帯の読書位置とお気に入りをデスクトップの棚へ（6.71 の残り）

- 単独サーバーの新しい棚は配る写しなので、携帯が書いた読書位置とお気に入りは、写しを入れ替える前に
  デスクトップの棚へ取り込む。デスクトップ版は今までお気に入りだけを旧棚へ取り込んでいた。
- サーバーに管理の口（`GET /api/v1/admin/shelf/reading?cursor=&limit=`）を足した。棚の持ち主（デスクトップと
  同じ利用者）の読書位置を、携帯の一覧と同じ印（初めは全部、そのあとは変わった分だけ）で、棚の形のまま
  （書いた端末と時刻つき）返す。印が別の写しのもの・崩れたものなら初めから返す。新しい棚を配っていない
  サーバーには口が無く、デスクトップ版は何もしない。
- デスクトップ版は、お気に入りを取り込むのと同じ機会（送る前と、決まった間隔）に読み、正本に切り替えた棚へ
  当てる。二つの棚に共通の更新世代は無いので、どちらが後に読んだかは書いた時刻で決め、サーバーの位置のほうが
  新しいときだけ書く。書いた端末は携帯のまま残すので、読む画面はほかの端末の位置として案内する。この棚が
  書いた位置・棚から外した作品・本文に無い位置は写さない。同じ位置を何度読んでも二度は書かない。印は設定に
  控え、サーバーをつなぎ直すと捨てる。サーバーの棚が別の棚の写しなら当てない。
- お気に入りは旧 API の変更の記録から今までどおり旧棚へ書き、切り替えた棚にも取得元の番号で当てる
  （値が同じなら書かない）。取り込んだら画面に知らせ、新しい棚の画面も読み直させる。
- 試験：写しを配るサーバーの棚で携帯が書いた位置が、一件ずつの印をたどってデスクトップの棚へ届くこと、
  デスクトップのほうが新しい位置は変えないこと、差分の印からは変わった作品だけが届き同じ位置は二度書かない
  こと、崩れた印は初めから返すこと、この棚が書いた位置・棚に無い作品・本文に無いページを写さないこと、
  お気に入りの当て方（サーバーとデスクトップの棚）。管理の口は携帯の鍵では読めず、新しい棚を配っていない
  サーバーには無いこと（サーバー）。実際のサーバーとの往復はまだ確かめていない（サーバーの更新が要る）。

### 6.85 棚の写しを単独サーバーへ送る（6.71 の残り）

- 旧棚の送信は旧棚のファイルの並びに結びついているので、新しい棚には実体の単位の送り方を別に作った
  （口は `docs/plan/library-api-v2.md` の「デスクトップ版から棚を送る」）。正本に切り替えた棚があれば、
  デスクトップ版の送信はその棚を送り、無ければ今までどおり旧棚を送る。自動の送信が変更を見る印も、
  切り替えた棚では棚の操作の記録の通し番号にした（読書位置だけの変更は数えない）。
- 台帳は毎回写し直すので、そのまま送ると実データでは毎回 466 MB になる。台帳も 4 MiB の部分に分けて実体と
  同じ口で送り、受け手は前に受け取った台帳の部分を残しておく。実データ（今の棚の台帳の写し、111 部分）で
  お気に入りを一つ変えると、変わる部分は 4〜5（約 1/25）だった。受け手の台帳の部分は最後の台帳の分だけ残す。
- 受け手は組んだ棚を全体の検査に通してから置き、配るのは次の起動から（見張り役のいるサーバーは組み終えた
  3 秒後に自分で立ち上げ直す。送り手は組み終えた知らせを読むか、配る世代が変わったことで届いたと知る）。
  前の世代の実体はハードリンクで共有し、今と一つ前の世代だけを残すので、戻す先が一つある。送ったあとに
  携帯が前の世代へ書いた読書位置は、起動のときに新しい世代へ写す。写せなくても新しい世代で起動する
  （前の世代は残る）。送る前には、携帯のお気に入りと読書位置をデスクトップの棚へ取り込んでおく（6.84）。
- 直したもの：実体の置き場の `has_object` が、先頭 2 桁のフォルダーがまだ無い置き場で誤りを返していた
  （「無い」と答える）。台帳の部分の置き場の片付けは、棚の実体ではないので隔離を挟まずに消す。
- 試験：二度目は足した作品の実体と変わった台帳の部分だけを送ること、識別子の合わない実体・全体のハッシュの
  合わない台帳・別の棚の受け取りを断ること、受け取りが続きから再開できること、世代を二つだけ残すこと、
  携帯が前の世代に書いた位置が残ること。HTTP の往復はこの試験の中でサーバーを動かし、デスクトップ版の
  送信の処理そのもので確かめた。実データ（今の棚の台帳の写しと一人の作者の実体から作った 77 作品の棚）を
  手元のサーバーへ送ると、初回は 543 個・56 MB を 5.4 秒、お気に入りを一つ変えた二回目は 1 個・2 MB を
  4.4 秒で送り、配った棚は全体の検査を通り作品の数も一致した。実際のサーバー（Maple）へはまだ送っていない。
- 残すもの：受け手は送られるたびに棚の全体を検査する（全棚では約 13 分）。前の世代から共有した実体は前に
  検査を通っているので、新しく受け取った実体と台帳だけを検査すれば短くできる。送り手は台帳を分けるのに
  全部の部分を圧縮している（全棚の台帳で約 29 秒）。識別子だけを先に出し、求められた部分だけを圧縮すれば
  速くなる。見張り役のいないサーバーは、組み終えても手で立ち上げ直すまで切り替わらない（画面はまだ伝えない）。

### 6.86 携帯ごとに棚を読む許可

- 単独サーバーの携帯がどの棚を読めるかは、今まで `server.toml` を手で書くしかなかった。デスクトップ版の
  設定の「サーバー」に、新しい棚を配っているサーバーのときだけ「新しい棚を読む携帯」の切り替えを出し、
  携帯ごとに付け外しする。サーバーは設定へ書き（ほかの設定はそのまま残す）、配っている棚にもすぐ効かせる。
  読む利用者は棚の持ち主（デスクトップと同じ利用者）。管理者の登録には付けられない。端末を解除すると
  許可も消す。
- 試験：棚を配る前は付けられないこと、付けると立ち上げ直さずに読めること、立ち上げ直しても残ること、
  一覧に `readsShelf` が出ること、管理者の登録は断ること（サーバー）。画面は棚を配っているときだけ切り替えを
  出し、押すとその携帯を頼むこと。

### 6.87 棚の置き場をアプリのフォルダーの中へ

- 旧棚がある間、新しい棚はアプリのフォルダーの隣（`….library-v2`）に置く（旧棚の移行器・全件照合・
  バックアップが中の棚を数えてしまう）。旧棚の台帳（`piep.db`）が無くなったら、起動のとき棚を開く前に
  アプリのフォルダーの中の `library` へ名前を付け替えて移し、以後はそこを開く。環境変数で場所を決めて
  いるときは動かさない。今は旧棚があるので、何も動かない。
- 試験：旧棚がある間は動かさず、無くなったら中へ移し、二度目は何もしないこと。

### 6.88 送る仕組みの手直し（6.85 の残り）

- 受け手の検査：組んだ棚の全体を読み直していたのを、新しく受け取った実体を含むファイルと、いま配っている
  棚と構成の違うファイルだけにした。ほかのファイルは実体があることだけを確かめる（共有した実体は前の世代で
  検査を通っている）。試験で、初回は全部、二回目は一部だけを読み直すことを確かめた。共有した実体が後から
  壊れたときは、棚の全体の検査（手入れ）で見つける。
- 送り手の台帳：全部の部分を圧縮していた（全棚の台帳で約 29 秒）のを、先に識別子だけを求め
  （`ObjectStore::plan`、何も書かない）、受け手が求めた部分だけを写しから読み直して符号化する
  （`encode_chunk`、符号化したものが元に戻ることも確かめる）ようにした。保管と同じ分け方・同じ形になることを
  試験で確かめた。
- 見張り役のいないサーバー：組み終えて立ち上げ直しを待つ間、`status` に `shelfPending` を付け、
  設定の「サーバー」に「送ったライブラリは、サーバーを再起動すると読めるようになります。」と出す。
- 携帯のお気に入り：切り替えた棚では、旧棚の口ではなく配っている棚から取り込む
  （`/api/v1/admin/shelf/favorites`、読書位置と同じ印の仕組み）。配っていないサーバーでは今までどおり旧棚の口。
- 食い違いの決め方：読書位置は書いた時刻の新しいほうにしていたので、携帯の時計が遅れていると携帯の位置を
  捨てていた。時計ではなく変更の記録で、デスクトップが前に送ってからその作品を自分で変えたかを見て、
  変えていなければ携帯の値にする。写した変更は版 8 の要求 ID で書き、自分の変更と見分ける。サーバーが
  世代を入れ替えるときも同じ決め方（前の世代にあって新しい世代の記録に無い要求が送ったあとの携帯の変更、
  新しい世代にあって前の世代に無い版 8 以外の要求がデスクトップ自身の変更）。送った番号は、その写しが
  配られ始めた（印の同期 epoch が変わった）ときから使う。分からないとき（番号が無い）は読書位置は時刻で、
  お気に入りはデスクトップの値を残す（初めの一覧は送った写しの古い値も返すため）。
- サーバーの鍵：資格情報マネージャーの一つの名前に置いていたので、別のサーバーにつなぐと前のサーバーの鍵を
  上書きしていた。サーバーの URL ごとの名前に置く。前の版の一つの名前の鍵は、前の版が今も使っているので
  書き換えも消しもせず、URL ごとの鍵が無いときだけ読む。
- 長いパス：実体の公開に使う `MoveFileExW` へパスをそのまま渡していたので、260 文字を超える置き場（深い
  一時フォルダーなど）で「パスが見つかりません」になっていた。`\\?\` を付けた完全なパスにして渡す。
  修正前に落ち、修正後に通る試験を足した。
- 試験：時計の遅れた携帯の位置とお気に入りが写ること、両方で変えたときの決め方、写した変更を自分の変更と
  数えないこと、送った番号が配られ始めてから効くこと、サーバーの鍵の名前、お気に入りの口（初めは全部・印の
  あとは無し・世代の入れ替えで残る）。
- 気づいたこと：古い棚の受信の試験（`a_library_sent_from_the_desktop_can_be_read_from_the_standalone_server`）が、
  全体を回したときに一度だけ意味検索の初期化の「database is locked」で落ちた。単独では通る。この手直しでは
  触っていない箇所。

### 6.89 切り替えたあとの画面と、空のファイルの送信（0.40.1）

- 実機で棚を正本に切り替えたあと、ホーム・一覧・作品の画面が空の旧棚を読み、0 作品と出た。画面が新しい
  棚を読むかは端末の好み（`piep.library-shelf-v2`）だけで決めていたため。アプリの頭で切り替え済みの棚を
  見たら好みを入れたままにし、設定の切り替えは入った状態で外せないようにした。
- 実際の棚を Maple へ送ると「実体の識別子が正しくありません」で断られた。棚に空のファイルが一つあり、保存の
  決まりでは空のファイルは長さ 0 の実体を一つ持つのに、サーバーの受け口が長さ 0 を不正としていた。0 を
  許し、空のファイルを含む棚を送り切って配れる試験を足した。合成の例に空のファイルが無く、実データで
  初めて分かった。

### 6.90 旧棚のコードを消す（6.89 の続き）

稼働棚を切り替え、旧データも消したので、デスクトップ版から旧棚を読む・書く道を外した。後方互換は持たない。

- 起動の準備（`prepare_library`）は棚だけを開く。`piep.db`・`.preview-backup-*`・`downloads/.search-snapshots`・
  `search/semantic-v2/index.sqlite` には触れない。旧棚の復元の後始末、旧キューの引き継ぎ、旧棚の索引・表紙・
  保存の自動の手入れも起動から外した。意味検索のモデルの置き場（`<アプリのデータ>/models`）は変えていない。
- 旧棚と棚に分かれていた命令を一つにした。書庫（`commands/archive.rs`）、AI の旧棚の側（`assist_shelf.rs` と
  まとめた）、旧キューの取り込み、旧棚あての一覧・作品・削除・タグなどの命令を消した。旧 API の棚の送信は
  単独サーバーの旧 API の受け取りの試験のためだけに `server/sync_send_v1.rs` へ分けた。送り手の消えた知らせ
  （`acquisition-audited`・`covers-repaired`）の購読と、聞き手の消えた手入れの進み具合の知らせも外した。
- 画面の「旧棚か新しい棚か」の分かれ道を、棚だけにした。端末の好み（`piep.library-shelf-v2`）、
  「新しい棚（試験中）」の札、「新しい棚では変えられません」で押せなくしていた操作、切り替える前の棚を
  読むだけにする分岐、設定の新しい棚の切り替えの節と旧棚の復元の手順は消した。作品の ID はアプリでは
  棚の UUID だけで、番号で作品を指すのはブラウザーのプレビューの見本だけになった。
- 消すうちに分かったこと:
  - 棚の読む画面の「編集」が押せなかった（旧棚の作品だけに付いていた）。押せるようにした。
  - 切り替える前に作った棚のバックアップは、開くと断られる（`open()` は切り替えていない棚を開かない）
    のに、復元の予約は通っていた。予約の時点で断るようにした。
  - EPUB の書き出しの順が、棚から引いた順になって積んだ順とずれることがあった。積んだ順に並べ直す。

残したもの（次の段階）:

1. 携帯の旧 API（v1）と Android の `pc_get_*`。携帯が端末ごとの棚の許可（6.86）へ移り切ってから消す。
   それまでは単独サーバーが v1 を出し続ける。
2. Maple の旧形式の棚（`C:\ServerData\piep\library`）。1 が済めば読む者がいなくなる。消すのは利用者の了承を得てから。
3. `database/` の部品、`sync_send_v1`、`sync_receive`。命令の多くがまだ型や検索の部品を `database` から借りて
   いるので、借りている物を棚の側へ移してから消す。
4. デスクトップに内蔵したサーバー。旧 API で出す物がもう無いので、残すか消すかを決める。
5. プレビューの見本を棚の形（UUID）に移し、プレビューだけに残した旧形の画面（`PreviewWorkPage`、
   `previewReaderSource`、`previewEditorSource`）を消す。
6. 旧棚の ID（`legacyId`、`migration_records`）と、端末の読書位置を棚の ID へ書き直す一度きりの処理
   （`useAdoptReadingKeys`）。全端末が書き直し終えたら消す。
7. `library_v2_` の名前を外す。移行用の `piep-library` の旧棚の比較・取り込みのコマンド。
