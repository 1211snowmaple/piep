# サーバーモード（β）

## 目的

**本棚を持つのは、いつも 1 つの「piep サーバー」にする。** デスクトップ版も携帯端末も、
そのサーバーにつながって本棚を使う。

サーバーの形は 2 つあり、API・登録・つなぎ方は共通にする。

| 形 | どこで動くか | 向いている人 |
| --- | --- | --- |
| **内蔵サーバー** | デスクトップ版の中。デスクトップ版の本棚をそのまま出す | PC 1 台で使う人。PC を起動している間、携帯から読める |
| **単独サーバー**（`piep-server`） | 常時動いている別の Windows 機 | 電源に関係なく携帯から読みたい人、PC を何台も使う人 |

単独サーバーは、最終的に piep の**本拠**になる。本拠は次の 3 つを兼ねる。

1. **サーバー**: 携帯端末から、家の外からでも本棚を検索して読める。
2. **定期更新**: フォロー中の作者・作品・シリーズの更新確認と保存を、決まった時刻に行う。
   デスクトップ版を開いていなくても新作が届く。
3. **バックアップ**: DB・本文・画像の整合したスナップショットを定期的に作り、外付けのディスクなどへ
   送り出せる。

### なぜサーバーを基本の形にするか

Android 版は、これまで「PC 版が起動していて、同じ Wi-Fi にいるときに PC 版の共有へつなぐ」設計だった。
これに「単独サーバーへつなぐ」を足すと、つなぎ方が 2 系統になる。登録文字列も証明書の扱いも誤りの表示も
二重になる。そこで、LAN での共有も「内蔵サーバーを LAN に出す」ことと捉え直し、1 系統にまとめる。

PC 側の Wi-Fi 共有は main に入っていない（「以前の共有サーバーの実装」）。今なら形を決め直しても、
捨てるものが無い。

### 一般性について

piep は配布するアプリなので、**特定の家の構成を前提にしない。** 単独サーバーに要るのは次の 2 つだけである。

- Windows 機で `piep-server.exe` が動くこと
- その機械に、デスクトップ版と携帯端末から HTTPS で届く URL があること

URL の作り方は利用者が選ぶ。Tailscale Funnel、Tailscale Serve（tailnet の中だけ）、Caddy などの
リバースプロキシ、サーバー自身の TLS（自己署名・証明書ファイル）のどれでもよい。共有フォルダー、VPN、
特定のドメインは要らない。

### β として出す

デスクトップ版では、設定の「サーバー（β）」に現れる。入れるまで何も動かない（待ち受けも送信もしない）。Android 版では、接続先として現れる。
API と保存形式は、β の間は予告して変えてよい。

## 段階

| 段階 | できるようになること | 本棚の基準 |
| --- | --- | --- |
| 1. 閲覧 | 内蔵サーバー。単独サーバーへの写しの送信。携帯からの検索・閲覧・端末への保存。携帯どうしの読書位置の同期 | デスクトップ版 |
| 1.5 導入と更新 | 単独サーバーと Android 版を、デスクトップ版と同じ手間で入れて更新できる。落ちても自分で立ち上がる | デスクトップ版 |
| 2. 本拠の運用 | 定期のスナップショットと外への送り出し。完了・失敗の通知 | デスクトップ版（単独サーバーは写しを守る） |
| 3. 本拠化 | 本拠とデスクトップ版が行の単位ですり合わせる。デスクトップ版はいつでも手元に書け、後から本拠と揃う | **本拠** |
| 4. 定期更新 | 本拠が決まった時刻に更新確認と保存を行う。本拠が止まっている間はデスクトップ版が代わりに行う。認証切れ・失敗の通知 | 本拠 |

順番の理由:

- 1 は単独で役に立つ。3 の土台（ファイルの差分の送受信、管理の経路、認証）もここで作る。
- 1.5 は実際の機械へ置く前に要る。手で置いたものは、次の版から古いまま残る。
- 2 は 1 の写しの上でも意味がある（PC の外にある、整合したバックアップになる）。作りが小さく、
  3 で本棚の基準を本拠へ移す前に、本拠が自分で立ち上がり、更新され、バックアップされる状態にしておける。
- 4 は本拠が本棚に書き込むので、すり合わせの仕組み（3）の後に置く。

段階 3 は、利用者が明示的に「本拠へ移す」を選んだときだけ起きる。内蔵サーバーだけで使う人は、
段階 1 の形のまま使い続けてよい（段階 2〜4 は単独サーバーの機能）。

β に含めないもの: Linux・Docker で動かすこと、デスクトップ版の「読みかけ」との読書位置の同期、
携帯からの本棚の変更（読書位置を除く）、本拠が止まったときに携帯が別のサーバーへつなぎ替えること。

## 現状

### Android 版が使っている API

契約の実体は `piep-android` の `src-tauri/src/pc_client.rs` と `pc_client/offline.rs` で、
`PROTOCOL.md` より広い。サーバーはこの読み取り API を**そのまま**提供する。Android 版の検索・読書・
保存の処理を作り直さずに済むからである。

- API 版は **2**。`GET /api/v1/hello` が `{apiVersion: 2, serverName: "piep"}` を返さないと
  互換性エラーになる。
- 今の登録文字列は `{version: 1, url, fingerprint, secret}`。`url` は
  **私設 IPv4 か 127.0.0.1 の `https://`、ポート必須**でなければ受け付けない。
  証明書は登録時の 1 枚に固定し、ホスト名は照合しない。
- 認証は `Authorization: Bearer <token>`（32 バイトの base64url）。401 は「解除済み」と表示する。

| 操作 | 端点（`/api/v1` の下） | 中身 |
| --- | --- | --- |
| 接続確認 | `GET /hello` | 無認証 |
| 登録 | `POST /pair` | `{secret, deviceName}` → `{deviceId, token, apiVersion}`。無認証 |
| 検索 | `POST /works/search` | `search_downloads_v2` の引数を camelCase で（値を検査してから渡す） |
| 作品情報 | `GET /works/{id}` | `work`・`people[]`・`series[]`・`versions[]`・`isEdited`・`activeEditId`・`activeEditHash` |
| 本文 | `GET /works/{id}/pages/{page}?version=` | 0 起点。`html` の画像は `data-asset-id` |
| 目次 | `GET /works/{id}/outline` | `page` は 1 起点 |
| 本文画像 | `GET /works/{id}/assets/{assetId}` | 画像のバイト列。25 MiB を超えるものは長辺 3072px の WebP にして返す |
| 表紙 | `GET /works/{id}/cover` | 320×480 に収めた WebP |
| 所属コレクション | `GET /works/{id}/collections` | 一覧と、その作品の並び位置 |
| 作者・シリーズ | `GET /entities/{people\|series}?text=&offset=&limit=` | `{items, nextOffset, total}` |
| 作者アイコン・シリーズ表紙 | `GET /entities/{kind}/cover?source=&key=` | WebP |
| コレクション | `GET /collections`、`GET /collections/{id}` | 要約と所属作品 |
| コレクション表紙 | `GET /collections/{id}/cover/{file\|tile-0..3}` | WebP |

上の端点表は、この実装と Android 版のクライアントを突き合わせて作った。**読み取り API はこれを現行の

無いものは少ない（`release_runtime` の改名、`list_collection_positions_for_work` が無い程度）。

### デスクトップ版のデータの置き方

アプリデータ（`%APPDATA%\<識別子>\`）の下に全部ある。

| 場所 | 中身 |
| --- | --- |
| `piep.db` | SQLite（WAL）。36 表 |
| `downloads\pixiv`、`downloads\fanbox` | 作品の版ごとの JSON・画像・添付 |
| `downloads\editor-assets` | 編集画面で足した画像 |
| `downloads\search-index`、`downloads\search` | 全文索引・意味索引 |
| `profiles`、`series`、`collection-covers` | 作者・シリーズ・コレクションの画像と JSON |

規模の目安として、開発者の棚は 27,635 作品・42,501 アセット・74,104 ファイルで、DB が 161 MB、
作品のファイルが約 19.5 GB、全文索引が 7.7 GB ある。

**DB のパスは絶対パスで入っている**（9 表 14 列: `downloads.json_path`、`assets.local_path`、
`people.icon_path` など）。DB をそのまま別の機械に置くと、本文も画像も開けない。機械の間で本棚を
動かす仕組みは、ここが要になる。

実データを調べると、列のほかに JSON の中にも入っていた: `update_candidates.payload_json` の `jsonPath`・
`originalJsonPath`・`personIconPath`（13 行）と、`collection_suggestions.members_json` の `coverPath`・`downloadId`
（全 7 行）。作品の本文 JSON には、無作為の 300 件で絶対パスは無かった。

DB の形は、表と列を足す形で進めてきた（`schema.rs` の `ADD COLUMN`。`SCHEMA_VERSION` は 1 のまま）。
そのため、版が違っても互いの行をおおむね読める。

### 取得元の認証情報と更新確認

- pixiv の refresh token と FANBOX の cookie・UA は、**画面側の設定（`settings.json`）に平文で**
  入っている。更新ジョブを始めるたびに、画面がそれを Rust 側へ渡している。DB には入っていない。
- 定期の更新確認は画面側のスケジューラー（`useUpdateScheduler`、5 分ごとに期限を見る）が起こす。
  **アプリを開いている間しか走らない。**
- 更新ジョブ本体（`commands/update_jobs.rs`、約 5,000 行）は `tauri::AppHandle` から状態を取り、
  進み具合をイベントで画面へ送る（35 か所）。
- 取得元への負荷は、取得元ごとに 1 つの関門（`downloader/pacing.rs`）で抑えている。API の呼び出しの
  間を 800 ms 空け、`Retry-After` があればそれに従う（無ければ 60 秒、最低 5 秒）。

## 正本の位置

本拠が定期更新を行う以上、本拠は本棚に書き込む。デスクトップ版も書き込む（保存、編集、コレクション、
お気に入り、AI 補助の結果）。**書き手が 2 つある。** 単独サーバーを使う場合について、4 つの形を比べた。

| | A. デスクトップ版だけが書く | B. 本拠だけが書く（操作を送る） | C. どちらも書き、行の単位ですり合わせる | D. デスクトップ版は遠隔の画面 |
| --- | --- | --- | --- | --- |
| 定期更新 | 本拠ではできない | できる | できる | できる |
| 本拠が止まったとき | 影響なし | 読めるが変更できない | **変更できる。後で揃う** | 何もできない |
| 変更の待ち時間 | 無し | 本拠の往復ぶん | **無し** | 本拠の往復ぶん |
| 手元での保存 | 今のまま | できない（本拠に頼み、遅れて届く） | **今のまま** | できない |
| 一覧・検索・読書の速さ | 今のまま | 今のまま | 今のまま | すべて通信待ち |
| AI 補助（手元の GPU） | 今のまま | 結果を送る形に変える | **今のまま** | 作り直す |
| 既存のコマンド | 変えない | 約 180 の IPC を「送る先」で振り分け、許可の一覧を保つ | **変えない**（DB の変更を下で拾う） | 全部作り直す |
| 難しいところ | — | 手元の写しとのずれ | **ぶつかったときの規則と、その検証** | 量 |

**C を到達点にする。** B は「本拠が止まると変更できない」「保存した作品が遅れて現れる」を構造として持つ。C は
それが起きない。デスクトップ版は今と同じように手元の DB に書き、その変更を後から本拠とすり合わせる。

本拠の役割は「唯一の書き手」ではなく、**変更の順番を決めて全員へ配る基準**になる。本拠とデスクトップ版が
別々に変えた行は、決めた規則で必ず同じ結果へ揃う（「段階 3」）。この形は台数を選ばないので、デスクトップ版を
何台つないでもよい。

内蔵サーバーでは、デスクトップ版が本棚を持ち、同時にサーバーでもあるので、この問題は起きない。

## 不便になる点と対策

段階 3〜4 で今より不便になりうる点と、その対策。

| 場面 | 動き | 残る不便 |
| --- | --- | --- |
| 一覧・検索・読書・EPUB・AI 補助 | 手元を読む。今と同じ | 無い |
| お気に入り・コレクション・タグ・編集の変更 | 手元に書いて、すぐ画面に出る。本拠へは裏で送る | 無い |
| 手で保存する | デスクトップ版が手元の認証情報で取得する（今と同じ）。すぐ現れ、本拠へは裏で送る | 無い |
| 本拠が定期更新で取った新作 | 本拠が 1 作品保存するごとにデスクトップ版へ知らせ、数秒で届く | 本拠が取得している間は出ない（待っている人はいない）。閉じていた間の分は、次に開いたときに裏で届く |
| 本拠に届かない | 読むのも変更も手で保存するのも続く。つながったら揃う。画面の隅に「本拠と未同期: N 件」と出す | 別の機械で変更した分は、つながるまで見えない |
| 定期更新の時刻に本拠が止まっている | デスクトップ版が代わりに行う（「段階 4」）。本拠はそれを受け取り、同じ対象を確認し直さない | デスクトップ版も閉じていれば、どちらかが動いたときに追いつく |
| 本拠が落ちた | 見張り役が数秒で立ち上げ直す（「段階 2」） | 機械ごと止まったら、携帯は端末に保存した作品だけ読める |
| 本拠の故障 | デスクトップ版の手元に本棚の全部がある。新しい本拠を用意して送り直すか、デスクトップ版を基準に戻す | 直すまで携帯から棚全体は読めない |
| 版の違い | 本拠は自分で更新する。版が違っても読むのも変更も止まらない（「版をそろえる」） | 同期の形式が変わる更新のときだけ、両方が揃うまで送受信が待つ |
| 2 台で同じ箇所を変えた | 決めた規則で揃う。負けた値は記録に残り、画面から見られる（「段階 3」） | 後から変えた方が勝つので、意図と違えば直す |
| ログイン | ログイン画面はデスクトップ版で開き、認証情報を本拠へ渡す。切れたら通知する | FANBOX の cookie が切れたら、デスクトップ版でログインし直す |
| ディスク | デスクトップ版も写しを丸ごと持つ | 手元に何も持たない軽い窓口は β の後で考える |

## 役割と認証

### 3 つの役割

| 役割 | だれ | できること |
| --- | --- | --- |
| 管理者 | デスクトップ版（単独サーバーでは段階 2 までは 1 台、段階 3 から複数。内蔵サーバーではそのデスクトップ版自身） | 本棚の送受信とすり合わせ、携帯と別の PC の登録文字列の発行、端末の一覧・解除、状態の確認、本拠の更新、認証情報の受け渡し、読み手と同じ読み取り |
| 読み手 | 携帯端末（最大 16 台） | 読み取り API、自分の読書位置の読み書き |
| 無認証 | だれでも | `GET /hello`、`POST /pair` だけ |

鍵はすべて暗号学的乱数の 256 ビット。サーバーは SHA-256 だけを持ち、定数時間で比べる。鍵と登録文字列は
記録に出さない。デスクトップ版は管理者の鍵を Windows の資格情報マネージャーに置く。

### 最初のつなぎ方

**内蔵サーバー:** デスクトップ版の「設定 → サーバー（β）」で「この PC をサーバーにする」を
入れ、出す先（LAN の IPv4・自己署名 TLS、または 127.0.0.1 とリバースプロキシ）を選ぶ。携帯の登録は同じ
画面の「携帯を追加」から行う。管理者はデスクトップ版自身なので、管理者の登録は要らない。

**単独サーバー:**

1. サーバーで `piep-server init --data <データの置き場>` を実行する。設定ファイルを作り、**管理者用の
   登録文字列**をその場の画面にだけ出す。有効期限は 30 分で、一度だけ使える。出し直すときは
   `piep-server admin-pair` を使う。段階 2 までは、前の管理者の鍵は新しい登録の時点で失効するので、
   すでに管理者がいるときは `--replace` を求める。段階 3 からは追加になり、
   2 台目以降の PC はデスクトップ版の画面からも追加できる。
2. デスクトップ版の「設定 → サーバー（β）」の「別の機械のサーバーにつなぐ」に貼る。
3. 以後、携帯の登録と解除はデスクトップ版から行う。「携帯を追加」を押すと、サーバーが 10 分だけ有効な
   一回限りの登録文字列を返し、デスクトップ版はそれを QR と文字列で示す。解除は即時に効く（401）。

管理者は、読み手と**別の URL で登録してよい**。たとえば携帯は公開 URL、デスクトップ版は家の LAN の URL を
使う。初回の送信は数十 GB になりうるので、速い経路で送るためである。URL は複数持て、届くものを使う。

### 登録文字列（版 2）

```json
{ "version": 2, "role": "reader", "url": "https://example.ts.net/", "secret": "…", "fingerprint": null }
```

- `role` は `reader`（携帯）か `admin`（デスクトップ版）。
- `url` は任意の `https://` のホスト名か IP。ポートは省略してよい。パスの前置き（`https://host/piep/`）を
  許す。利用者名・問い合わせ・断片は持てない。
- `fingerprint` があれば、その証明書に固定する（自己署名のとき）。無ければ OS が信頼する CA で
  ホスト名まで検証する（Funnel、Let's Encrypt のとき）。

Android 版の今の版 1（LAN の PC 版への共有）は、PC 側の共有が配布版に入っていない（現行の履歴に現れない）ため、
β では版 2 だけにまとめる。
Android 版の版 1 の受け付けは、版 2 の受け付けを入れたときに外す。

### インターネットに出す前提での守り

Funnel などで公開すると、URL は証明書の透明性ログから見つけられる。そのため、**URL が知られていても
読めない**ことを前提に決める。

- 無認証で答えるのは `hello` と `pair` だけ。`hello` は版・サーバー名・機能の一覧だけを返し、作品数や
  棚の名前は返さない。
- `pair` の鍵は 256 ビットで、期限付き・一回限りなので、総当たりは成り立たない。回数の制限は負荷を抑えるためのもので、
  サーバー全体で 1 分に 10 回までにする。間違った鍵からは、どの登録文字列を狙ったのか分からないので、
  失敗を数えて登録文字列を失効させることはしない（他人が失敗を重ねて登録を妨げられてしまう）。
  失敗の理由は区別せず、すべて 401 にする。
- 要求の大きさに上限を設ける（JSON は 64 KiB、送受信のかたまりは 8 MiB）。遅い要求は時間で切る。
- 応答には `Cache-Control: private, no-store` を付け、CORS は有効にしない。誤りは `{code, message}` だけを
  返し、パスや内部の誤り文は返さない。
- 平文の HTTP は **127.0.0.1 でしか待ち受けない。** それ以外のアドレスで待ち受けるときは、サーバー自身の
  TLS（自己署名か証明書ファイル）を必須にする。
- 記録には、端点の型・状態コード・所要時間だけを残す（成功は debug）。鍵・登録文字列・検索語・本文・作品 ID は残さない。

### 読み手の口と管理の口を分けられる

段階 4 で本拠は取得元の認証情報を持つ。そのため、管理の API（`/api/v1/admin/...`）は、**読み手の口とは
別のアドレスで待ち受けられる**ようにする。

```toml
listen = "127.0.0.1:38777"        # 読み手（携帯）。Funnel などで外へ出す
admin_listen = "127.0.0.1:38778"  # 管理者。LAN や tailnet の中だけに出す
```

`admin_listen` を書くと、`listen` 側は `/admin/...` に 404 を返す。書かなければ同じ口で両方を受ける。
手順書では、外へ出す人には分けることを勧める。

トンネルやプロキシが付ける利用者名のヘッダーは、認証にも記録にも使わない。

## サーバーの作り

### 共通の部品

HTTP 層は `piep_lib` に置き、内蔵サーバーと単独サーバーで共有する。差し替えられるのは次の 3 つ。

| | 内蔵サーバー | 単独サーバー |
| --- | --- | --- |
| 待ち受け | 既定は止まっている。入れたときだけ、選んだアドレスで待ち受ける | 常時 |
| 本棚 | デスクトップ版が開いている `Database` | サーバーが開いている `Database`（世代を入れ替えられる） |
| 端末の記録 | デスクトップ版のアプリデータの `server\state.db`（鍵はハッシュ） | `<dir>\state\state.db`（鍵はハッシュ） |

依存は以前の実装と同じ axum・axum-server・rustls・rcgen・subtle を足す。

### piep-server

WebView を持たない常駐プログラム。本体は `piep_lib::server::standalone` にあり、デスクトップ版と同じ
`piep_lib` の `Database` を使う。検索・本文・目次・コレクションの結果がデスクトップ版とずれないことが、
この形を選ぶ理由である（Android 版の `PLAN.md` にある「Android に複製すると結果や改ページが食い違う」と
同じ判断）。入口は `src-tauri/examples/piep-server.rs` に置き、`cargo build --release --example piep-server` で組む。
`src/bin` に置くと、Tauri がデスクトップ版のインストーラーへ同梱してしまうからである。

| コマンド | 何をする |
| --- | --- |
| `piep-server install` | 置き場所と出し方を尋ね、起動時に動くよう登録して動かす。引数なしで開いたときもこれ（段階 1.5） |
| `piep-server uninstall` | 登録を消して止める。置き場所は消さない（段階 1.5） |
| `piep-server init --data <dir>` | 置き場と設定を作り、管理者用の登録文字列を出す |
| `piep-server serve --data <dir>` | 見張り役として本体を起動し、落ちたら立ち上げ直し、更新を当てる（`install` を通していなければ本体を直接動かす） |
| `piep-server run --data <dir>` | 本体。API を出し、バックアップと定期更新の予定を回す |
| `piep-server admin-pair --data <dir> [--replace]` | 管理者用の登録文字列を出し直す。管理者がいるときは `--replace` が要る |
| `piep-server status --data <dir>` | 状態（「状態を見る」の節）を出す |
| `piep-server backup --data <dir>` | スナップショットを今すぐ作る（段階 2） |
| `piep-server restore --data <dir> <snapshot>` | スナップショットから本棚を戻す（段階 2。`serve` を止めてから） |

設定（`<dir>\server.toml`）:

```toml
listen = "127.0.0.1:38777"   # 既定。これ以外は tls が要る
# admin_listen = "127.0.0.1:38778"
public_url = ""              # 携帯の登録文字列に載せる URL。空なら管理者が登録した URL
# tls = "self-signed"        # または { cert = "...", key = "..." }

[backup]                      # 段階 2
# schedule = "daily 04:00"
# keep_daily = 7
# keep_weekly = 4
# after = ["restic", "-r", "E:\\restic-piep", "backup", "{snapshot}", "{library}"]

[update]                      # 段階 2
# auto = true                # 自動で更新する（既定は入）
# window = "03:00-06:00"     # 当てる時間帯

[[notify]]                    # 段階 2
# url = "https://ntfy.example/piep"
# format = "ntfy"            # json / ntfy / uptime-kuma
# events = ["backup_failed", "update_failed", "auth_expired"]
```

定期更新の時刻と対象は、デスクトップ版の画面から変える（本拠の `state` に持つ）。

置き場:

```text
<dir>\
  server.toml
  versions\       本体の実行ファイル（版ごと。直前の版を残す。段階 2）
  library\        本文・画像（downloads\pixiv など、デスクトップ版と同じ形）と、使っている DB（piep.db）。
                  直前の DB を piep.db.previous に 1 つ残す
    downloads\search-index\   サーバーが作る全文索引
  library-trash\  本棚から外したファイル（段階 1 では 7 日、段階 2 からは最も古いスナップショットまで残す）
  incoming\       送信中のかたまりと DB（送信ごと）
  snapshots\      バックアップのスナップショット（段階 2）
  state\          端末・ファイルの記録・読書位置（state.db）、証明書、実行の記録、
                  操作の記録と取得元の認証情報（暗号化。段階 4）
```

起動は Windows のサービスかスケジュールタスク（起動時、SYSTEM）にする。β では手順書でタスクの登録を
案内し、サービスとして登録するコマンドは作らない。

`hello` は `{apiVersion: 2, serverName: "piep", capabilities: [...], beta: true}` を返す。`capabilities` は `read`、
`reading-sync`、`admin-sync`、`row-sync`、`backup`、`self-update`、`scheduled-updates` のうちそのサーバーができるもの。
アプリの版と `syncFormat`（同期の形式の版）は、管理者の鍵を持つ相手にだけ `GET /admin/status` で返す。公開の口で版を
出すと、古い版だと分かって狙われるからである。

## 段階 1: 閲覧

### 内蔵サーバー

以前の `mobile_bridge` の形を、共通の部品の上に作り直す。デスクトップ版が開いている本棚をそのまま出すので、
送信は要らない。PC を起動している間、携帯から読める。

### 単独サーバーへの写しの送信

#### 何を送るか

| 送る | 送らない |
| --- | --- |
| DB の写し（下の加工をしたもの） | 全文索引・意味索引（サーバーが作る） |
| `downloads\pixiv`、`downloads\fanbox`、`downloads\editor-assets` | 埋め込みモデル、閲覧用のブラウザー領域、記録、画面の設定 |
| `profiles`、`series`、`collection-covers` | 書き出しテンプレート、バックアップ |

閲覧用のブラウザー領域と画面の設定には、pixiv・FANBOX のログイン状態が入りうる。**この送信では
取得元の認証情報を送らない**（段階 4 で、別の経路で明示的に渡す）。DB に認証情報が入っていないことは
確かめた。

#### DB の写しの作り方

1. ライブラリの読み取りの関門（`library_gate` の read）を持っている間に、`VACUUM INTO` でデスクトップ版の
   一時領域に書き出す。バックアップの書き出しと同じ関門なので、保存や編集の途中の状態は写らない。関門を
   持つのは書き出しの数秒だけで、転送の間は持たない。
2. 写しの側で、**絶対パスを相対形に直す。** 9 表 14 列の、アプリデータで始まる値を `piep-library:/downloads/...`
   の形にする。アプリデータの外を指す値（あれば）は空にし、件数を送信の結果に出す。こうすると、サーバーには
   デスクトップ版の利用者名や置き場が届かない。
3. 写しの側で、**読むのに要らない表を空にする。** 更新確認の対象・候補・ジョブとその記録、保存と復元の
   途中記録、保存済みアセットの監査記録、コレクションの提案と判断の記録、AI の下書き、意味索引の記録。
   携帯の画面がこれらを使わないことは、実装のときに 1 表ずつ確かめる。段階 3 で本拠へ移すときは、
   手元だけの表を除いてこれらも送る（「段階 3」の節）。

#### 送る手順

管理者の鍵で呼ぶ API（`/api/v1/admin/sync/...`）。送信は同時に 1 つだけ。

1. **始める。** `POST /admin/sync/sessions` で送信を開く。中断した送信が残っていれば、それを続きから使う
   （24 時間で捨てる）。
2. **差分を問い合わせる。** ファイルの一覧（相対パス・大きさ・更新時刻）を 5,000 件ずつ送る。サーバーは
   自分の記録と比べ、変わったもの・無いものの一覧を返す。比べるのは大きさと時刻だけで、毎回 20 GB を
   読み直さない。
3. **足りないファイルを上げる。** デスクトップ版は、返ってきたファイルだけ SHA-256 を計算し、8 MiB ずつの
   かたまりで上げる（`PUT /admin/sync/sessions/{id}/blobs/{sha256}?offset=`）。かたまりはリバースプロキシの
   大きさの上限に引っかからず、切れても途中から再開できる。サーバーは揃ったら SHA-256 を照合する。
   同じ中身のファイルは一度しか上げない。4 本並行で送る。
4. **DB の写しを上げる。** 同じかたまりの仕組みで上げる。前回の確定と SHA-256 が同じなら省く。
5. **確定する。** `POST /admin/sync/sessions/{id}/commit`。サーバーは次を順に行う。
   1. 一覧のファイルがすべて揃っていることを確かめる。欠けていれば確定せず、409 で断る。送り手は開き直して続きから送る。
   2. 受け取ったファイルを `library` へ移す。
   3. DB の写しの `piep-library:/` を `<dir>\library\` に戻す。どちらの形（`\\?\` つき、`/` と `\` の混在）で書かれた
      値も、送る前に同じ相対形にそろえてある。
   4. **索引の記録を引き継ぐ。** 写しの `search_index_state`・`search_index_meta` を、直前の世代のものに
      置き換える。記録は作品ごとに「版＋本文ハッシュ」なので、変わった作品だけが「未索引」になり、
      追いつき処理がその分だけ索引し直す。消えた作品は索引からも消す。意味索引は切る（携帯に AI 検索の
      入口は無い）。
   5. **入れ替える。** 受付を数秒止め（503）、古い `Database` を閉じて `library\piep.db` を置き換え、開き直す。
   6. 一覧に無いファイルを `library` から `library-trash` へ移す（入れ替えの後なので、読んでいる世代は
      困らない）。
   7. 世代の番号・作品数・確定の時刻を返す。索引の追いつきはその後ろで続く。

#### いつ送るか

デスクトップ版の「設定 → サーバー（β）」:

- **今すぐ送る**・**止める**。止めると、上げたかたまりはサーバーに残り、次の送信が続きから使う。
- **自動で送る**（既定は切）。入れると、ライブラリが変わってから **5 分静かになったとき**に送る。
  ダウンロードの途中で何度も送らないためである。変わったかどうかは SQLite の `data_version` で見る。
  起動して落ち着いたあとにも一度送る（変わっていなければ問い合わせだけで終わる）。
- 進み具合は段階（DB の写し → 差分の問い合わせ → ファイル N/M 件・送った量 → DB → 反映 → 索引）で示す。
  ジョブ一覧には、β の間は載せない。
- 前回の結果（送った時刻・反映した世代と作品数・索引の進み具合・失敗の理由）を表示する。

送信の設定は Rust 側で持つ。画面を開いていないときの自動送信が読むためである。

### 読書位置の同期

携帯端末どうしで、続きから読めるようにする。デスクトップ版の「読みかけ」との同期は β に含めない
（デスクトップ版の読書位置は画面側にしかなく、別の設計が要る）。

- 位置はサーバーの `state\state.db` に置く（内蔵サーバーではデスクトップ版のアプリデータの別ファイル）。
  送信で入れ替わる本棚の DB には置かない。
- 作品は `(source, sourceId)` で指す。作品 ID は機械の間で同じとは限らない（デスクトップ版で復元すると
  振り直されうる）ため。
- 1 作品につき、最後に書かれた 1 件を持つ: 本文の版の鍵（`version` と `activeEditHash`）、ページ、
  ページ内の位置（割合）、読了か、端末 ID、端末の時刻、サーバーが受けた時刻。
- 端点（読み手と管理者）:
  - `GET /api/v1/reading?since=<cursor>`: その後に変わった位置の一覧と次のカーソル
  - `PUT /api/v1/reading/{source}/{sourceId}`: 自分の位置を書く。端末の時刻がサーバーの持つものより古ければ
    書かずに、今の値を返す
- 端末は、本の版の鍵が自分の読んでいるものと同じときだけ位置を使う。違うときはページだけを目安にし、
  ページ数を超えていれば最初からにする。
- 書き込みは読むのを止めない。圏外では端末に貯め、つながったら送る。

### Android 版の変更

`piep-android` リポジトリの変更で、デスクトップ版とは別の PR にする。

1. 接続先を「piep サーバー」1 種類にする。登録文字列の版 2 を読み、`validate_url` を上の規則
   （任意の https、ポート省略可、パスの前置き可）にする。版 1 の受け付けは外す。
2. 証明書: `fingerprint` が無ければ、OS が信頼する CA でホスト名まで検証する
   （`tls_danger_accept_invalid_hostnames` を使わない）。あれば今と同じく固定する。
3. 誤りの文言を「サーバーに接続できません。通信状態とサーバーの URL を確認してください」にする。
   「同じ Wi-Fi」は、自己署名の LAN のサーバーのときだけ添える。
4. **読書位置の同期:** 読書画面を開いたときとアプリが前に戻ったときに読み、ページを移ったとき・閉じたときに
   （数秒まとめて）書く。圏外の書き込みは端末に貯める。設定に「読書位置を同期する」（既定は入）を置く。
   `capabilities` に `reading-sync` が無いサーバーでは出さない。
5. 端末への保存・オフライン読書は今のまま使う。

## 段階 1.5: 導入と更新

段階 2 に置いていた「落ちても立ち上がる」「自分で更新する」を前へ出し、Android 版の導入と更新を加えた。
単独サーバーと携帯を実際の機械へ置く前に要る。手で組んで手で置いたものは、次の版から古いまま残るからである。

目標は、デスクトップ版と同じ手間にすることである。

| | 導入 | 更新 |
| --- | --- | --- |
| デスクトップ版 | インストーラーを開く | 案内に従う |
| 単独サーバー | zip を展開して `piep-server.exe` を開き、質問に答える | 自動。デスクトップ版からも頼める |
| Android 版 | デスクトップ版の QR から APK を入れ、登録の QR を読む | アプリ内の案内を押し、OS の確認に答える |

利用者の手作業として残るのは、次のものだけである。

- サーバーを外へ出す手段（トンネルやリバースプロキシ）を用意する。piep は特定の製品を前提にしない。
- Android の「提供元不明のアプリ」の許可（最初の 1 回）と、更新ごとの OS の確認。署名の検証は OS が行う。

Google Play での配布は β に含めない。

### 配布物（単独サーバー）

リリースに次を載せる。作るのは `release.yml` で、デスクトップ版と同じ `TAURI_SIGNING_PRIVATE_KEY` で署名する。

- `piep-server-<版>-windows-x64.zip`: `piep-server.exe` と VC++ ランタイムの DLL 4 つ
- `piep-server-<版>-windows-x64.zip.sig`
- `latest-server.json`: `{"version", "url", "signature"}`

`piep-server.exe` は `MSVCP140.dll` と `MSVCP140_1.dll` を読み込む。VC++ ランタイムの入っていない機械でも動くよう、`vcruntime140.dll`
`vcruntime140_1.dll` と一緒に横へ置く。`DirectML.dll` と `d3d12.dll` は Windows に含まれるので同梱しない。WebView2 は読み込まない。
手元の確認では、PATH を System32 だけにして空のフォルダーから `init` と `serve` が動き、`hello` が返った。

CI は組んだあと、次を確かめる。

- 読み込む DLL が許可した一覧の中にある
- 空のフォルダーへ展開したものが `init` と `serve` で立ち上がり、`hello` に答え、`--version` がタグと一致する
- 署名が公開鍵で検証できる

### 導入（単独サーバー）

`piep-server install` が入口である。引数なしで開いたときも（エクスプローラーからのダブルクリック）これを動かす。

1. 管理者権限が無ければ、UAC で権限を求めて自分を開き直す。
2. 置き場所を尋ねる。既定は `C:\ProgramData\piep-server`。本棚が大きいので、別のドライブも選べる。置き場所のアクセス権は
   SYSTEM・Administrators・導入した利用者だけにする。
3. 外からどう届かせるかを尋ねる。
   - **トンネルやリバースプロキシの裏:** `listen` は `127.0.0.1:38777` のまま、公開 URL を尋ねる。
   - **この機械の接続口へ直接:** `listen` を `0.0.0.0:38777`、`tls = "self-signed"` にする。
   piep は特定の製品を検出も実行もしない。何を使うかは利用者が決め、ガイドで例を挙げるにとどめる。
4. `init` と同じ設定を作り、自分と DLL を `<置き場所>\versions\<版>\` へ、見張り役を `<置き場所>\piep-server.exe` へ写す。
5. タスク スケジューラに「起動時に SYSTEM で `serve` を動かす」タスクを登録して、すぐ動かす。`schtasks /SC ONSTART` の既定は
   3 日で止めてしまうので、実行時間の制限を外した XML で登録する。
6. `hello` が返るのを待ち、管理者用の登録文字列を出す。

やり直しても壊さない。設定と本棚があれば残し、タスクと実行ファイルだけを入れ直す。`piep-server uninstall` はタスクを消して
止めるだけで、置き場所は消さない。手順はスクリプトでも動かせるように、質問は引数（`--data`、`--url`、`--expose`）で飛ばせる。`--no-task` は
タスクを登録せず、置き場所だけを作る。

Linux・Docker は β に含めないので、`install` と `uninstall` は Windows だけである。

### 落ちても立ち上がる

`piep-server serve` は小さな見張り役で、本体（`versions\<版>\piep-server.exe run`）を子として動かす。

- 本体が異常終了したら、5 秒、30 秒、2 分と間を広げて立ち上げ直す。10 分正常に動いたら間を戻す。
- 立ち上げ直したことを記録する。5 回続けて起動に失敗したら `server_down` を記録し、1 時間ごとに試す。
  通知の送り先は段階 2 で足す。それまではログと `status` で見る。
- 見張り役自身は機能を持たないので、ほとんど変わらない。見張り役の更新は、次に機械を起動したときに効く。

`install` を通さず `serve` を動かしたとき（置き場所に `versions` が無いとき）は、見張り役にならず本体を直接動かす。

### 自分で更新する

- **いつ:** 6 時間ごとに確かめる。新しい版があれば取ってきて検証し、設定の時間帯（既定は 03:00〜06:00）に当てる。
  デスクトップ版の「サーバーを今すぐ更新」は時間帯を待たない。デスクトップ版は自分が更新されたあと、サーバーが古ければ
  これを自動で頼む。
- **手順:**
  1. 署名を検証して `versions\<版>\` へ展開し、`--version` が `latest-server.json` の版と一致することを確かめる。
     合わなければ捨て、`update_failed` を記録する。
  2. 送受信が区切りに来るのを待つ（最長 30 分。その後は次の時間帯へ延ばす）。段階 4 からは定期更新のジョブも待つ。
  3. DB を整合した形で写す（`VACUUM INTO`）。段階 2 からはスナップショットを使う。
  4. 見張り役が本体を止め、新しい版を起動する（止まるのは数十秒）。
  5. 新しい版が 60 秒以内に `hello` と DB の検査に通らなければ、前の版と写しへ戻し、`update_failed` を記録し、その版を飛ばす。
- **守り:** 取りに行く先は実行ファイルに固定し、設定や API では変えられない。管理の API が頼めるのは「確かめて当てる」
  だけで、ファイルや URL は渡せない。版を下げるのは、上の 5 の戻しのときだけである。`auto = false` なら、デスクトップ版から
  頼んだときだけ当てる。古い版を残すのは直前の 1 つだけである。

### 導入と更新（Android 版）

- **配布物:** リリースに署名済み ARM64 APK と `latest-android.json`（`{"version", "versionCode", "url", "sha256", "size"}`）を載せる。
  作る手順は `tools/release.ps1` 1 つにまとめ、APK の署名・アプリ ID・版を検査してから出す。
- **作る場所:** タグで CI が動く形を目指す。署名鍵を GitHub Secrets に置くかどうかは利用者が決める。置かない間は同じスクリプトを
  手元で動かす。
- **最初の導入:** デスクトップ版の「携帯を追加」に、APK のページへの QR と登録の QR を並べる。
- **登録:** 登録の QR をアプリのカメラで読む。貼り付けも残す。カメラの権限は、読むボタンを押したときだけ求める。
- **確かめる:** 起動時に 1 日 1 回と、設定の「更新を確かめる」。取りに行く先は実行ファイルに固定する。新しい版があれば、
  設定とライブラリの上部に控えめに知らせ、読書中は割り込まない。サーバーと `apiVersion` が合わないときの案内からも更新へ進める。
- **当てる:** 押すと大きさを示して取ってきて SHA-256 を確かめ、OS のインストーラーへ渡す。`REQUEST_INSTALL_PACKAGES` と
  FileProvider を使う。本当の守りは OS の検査（同じ署名鍵で、`versionCode` が増えていること）で、SHA-256 は壊れた取得を捨てるためである。
  端末に保存した作品と登録は更新で消えない。

### 確かめ方

| 何を | どう |
| --- | --- |
| 導入 | CI で空のフォルダーへ展開して起動する。タスクの登録は手元の機械で確かめる |
| 見張り役 | 試験用の本体を落として立ち上げ直しと間隔を見る |
| 更新と戻し | 手元の HTTP で配った偽の版で、署名の不一致、版の不一致、起動しない版、戻しを試験する。取りに行く先の差し替えは試験の組み立てだけで効く |
| Android の更新 | エミュレーターで、前の版から手元で配った新しい版へ上書きし、登録と端末内の作品が残ることを見る。実機は利用者が行う |

## 段階 2: 本拠の運用

### 版をそろえる

**版が違っても、読むのと変更を止めない。** 更新の順番を利用者に意識させないために、次の 3 層に分ける。

| 層 | 決めごと | 違うときの動き |
| --- | --- | --- |
| 読み手の API | `apiVersion` は壊す変更のときだけ上げる。足す機能は `capabilities` で知らせる | 携帯は知っている機能だけ使う。`apiVersion` が違うときだけ、更新を促す |
| DB の形 | 今までどおり表と列を足す形で進める。消す・意味を変えるのは、形式の版を上げるとき | 各機械は自分の形で動く |
| 同期の形式（`syncFormat`） | 束は列の名前つきで運ぶ。壊す変更のときだけ上げる | 同じ形式なら版が違っても同期を続ける。**知らない列・表の値は、受け手が保留の表に取っておき**、自分が新しくなったときに当てる。形式が違うときは送受信だけが待ち、手元の読み書きは続く。画面には「本拠の更新を待っています」か「デスクトップ版を更新してください」と出す |

こうすると、利用者がすることは、デスクトップ版の更新の案内に従うことだけになる。

### スナップショット

- **いつ:** 設定の予定（既定は毎日 04:00）、`piep-server backup`、デスクトップ版の「今すぐバックアップ」、
  段階 3 で本拠へ移す直前、自動更新の直前、`restore` の直前。
- **何を:** DB は SQLite のバックアップ API で、書き込みの関門を持っている間に写す（数秒）。写しは
  `PRAGMA quick_check` で確かめ、`snapshots\<時刻>\piep.db` に置く。同じ場所に、その時点の `library` の
  ファイル一覧（相対パス・大きさ・SHA-256）を書く。
- **本文・画像は複製しない。** 作品のファイルは版ごとのディレクトリに足されていくだけなので、スナップショット
  ごとに 20 GB を写す意味が無い。その代わり、**本棚から外したファイルはすぐには消さず `library-trash` に移し、
  いちばん古いスナップショットより古くなってから消す。** これで、保持しているどのスナップショットからでも、
  DB とファイルの組を戻せる。
- **保持:** 既定は日ごとを 7 つ、週ごとを 4 つ。
- **外へ送る:** 設定の `after` に、スナップショットを作った後に動かすコマンドを書ける。`{snapshot}`
  （その回のスナップショットのディレクトリ）と `{library}` を置き換えて渡す。restic なら、変わらない
  ファイルは送らないので、2 回目以降は小さい。コマンドが動いている間は、`library-trash` の掃除と
  ファイルの移動を止める。
- **戻す:** `piep-server restore` は、`serve` を止めた状態で、スナップショットの DB を新しい世代として置き、
  一覧にあって `library` に無いファイルを `library-trash` から戻す。足りないファイルがあれば、戻す前に
  一覧を示して止まる。外から戻すとき（restic）は、restic で取り出したディレクトリを `restore` に渡す。
- 結果（時刻、所要時間、DB の大きさ、確かめた結果、`after` の終了コード）を記録し、状態と通知に出す。

段階 1・2 では、本拠のスナップショットは「デスクトップ版の写し」のバックアップになる。PC の外にある整合した
控えとして、それだけで役に立つ。

### 通知

設定の `[[notify]]` に、出来事を知らせる先を書く。

| 形式 | 送り方 |
| --- | --- |
| `json` | `POST`。本文は `{event, title, message, at, server}` |
| `ntfy` | `POST`。本文は文、`Title`・`Priority`・`Tags` の見出しを付ける |
| `uptime-kuma` | push の URL に `GET`（`status=up\|down&msg=...`）。さらに `heartbeat_minutes` ごとに、正常なら `up` を送る（止まったことに気づける） |

出来事: `sync_applied`・`sync_failed`、`backup_finished`・`backup_failed`、`update_finished`・`update_failed`、
`auth_expired`、`index_ready`、`disk_low`（空きが設定値を下回った）、`server_started`、`server_restarted`、`server_down`、
`self_updated`、`sync_conflict`。

- 通知の URL には鍵が入りうるので、記録には URL のホスト名だけを残す。設定ファイルは SYSTEM と管理者だけが
  読めるようにする（手順書）。
- 送れなかったら 3 回まで間を空けて送り直し、それでもだめなら状態に「通知の失敗」として出す。通知の失敗で
  本来の仕事は止めない。

## 段階 3: 本拠化

### 仕組みのあらまし

1. 本拠もデスクトップ版も、今までどおり自分の DB に書く。**既存のコマンドは変えない。**
2. 同期する表に付けたトリガーが、変わった行と列を記録する。
3. 溜まった変更を「束」にして、本拠へ送る。本拠は規則に従って当て、通し番号を振って記録に載せる。
4. 他の機械は、本拠の記録を自分の続きから受け取って当てる。規則が決定的なので、どの機械も同じ結果になる。

### 変更の記録

トリガーは、起動時に表の定義から生成する（列を足しても書き忘れない）。

- 記録の中身: 表、行の鍵（下の「持ち運べる鍵」）、挿入・更新・削除、変わった列、時刻。
- 他の機械から受け取った変更を当てている間は記録しない。
- 実際に値が変わった列だけを記録する。同じ行・同じ列の変更は、送るときに最後の 1 回にまとめる。
- 連鎖の削除は親の削除だけを送る（子の削除は、親が消えたあとでは鍵が作れないので記録から除く）。
- 時刻は混成論理時計にする。機械の時計に基づくが、受け取った時刻より必ず先へ進めるので、時計がずれていても順序が
  壊れない。同時なら機械の ID で決める。

### 持ち運べる鍵

整数の ID は機械ごとに違ってよい。束の中では、ID を自然キーに、絶対パスを `piep-library:/` に直して運ぶ。
**整数の ID は機械の外へ出さない。**

| 同期する表 | 行の鍵 |
| --- | --- |
| `downloads` | `source`, `source_id` |
| `download_versions`、`assets` | 作品, `version` / 作品, 相対パス |
| `download_people`、`download_relations`、`download_series`、`download_tags` | 作品と各自の主キー。タグは名前 |
| `tags`、`people`、`series`、`entity_versions`、`update_targets`、`update_candidates` | 既存の一意の列 |
| `work_collections`、`collection_suggestions` | 既存の文字列の ID |
| `work_collection_members`、`collection_pair_feedback`、`work_links`、`ai_notes` | 既存の主キー・一意の列 |
| `watch_groups`、`watch_group_members`、`saved_searches` | 名前 |
| `work_edit_revisions`、`work_edit_blocks` | 新しく足す `sync_id` / それと `block_order` |

**手元だけの表（同期しない）:** 保存と復元の途中記録、更新ジョブとその記録、保存済みアセットの監査、保存の修復の
試行記録、全文索引・意味索引の記録、検索機能の設定、形の印。下書きの状態の編集版も送らない。「反映」したときに
初めて送る。打っている間に通信を起こさないためである。

`update_candidates.payload_json` と `collection_suggestions.members_json` は、JSON の中のパスと `downloadId` も直す。

### 送受信

- **束を作る:** 変更が 5 秒静かになったら、または 1 分経ったら、ライブラリの読み取りの関門の中で記録と行の値を読む。
  手元で新しく足されたファイルの一覧も載せる。
- **ファイルが先、行が後:** 受け手は、束が指すファイルのうち無いものを、段階 1 のかたまりの仕組みで先に揃え、それから行を
  1 つのトランザクションで当てる。途中で切れても、半端な作品は現れない。大きな束は作品の単位に分ける。
- **本拠の記録:** 本拠は当てた変更に通し番号を振り、90 日残す。各機械は自分の続きの番号を持つ。
- **すぐに知らせる:** デスクトップ版は `GET /admin/sync/events` を開いたままにし、本拠の記録が進んだら受け取りに行く。
  本拠の進み具合（「本拠で保存中 12/40 件」）も、ここで届く。
- **受信で触るもの:** 消えた行のファイルは `library-trash` へ移す。全文索引と意味索引は、機械ごとに既存の追いつき処理が
  変わった作品だけを索引し直す。
- **ずれの確かめ:** 1 日 1 回、表ごとに鍵と値のハッシュを比べる。違えば、違う部分の行を取り直し、`sync_drift` を記録する。
  ファイルは週 1 回、段階 1 の差分の問い合わせで確かめる。
- **長く離れていた機械:** 記録が 90 日より前に切れていたら、手元の未送信の変更を先に送り、写しを受け取り直す。

### ぶつかったときの規則

| 場面 | 結果 | 試作での確認 |
| --- | --- | --- |
| 同じ行の別の列を変えた（手元でお気に入り、本拠で題の更新） | 両方残る | 済 |
| 同じ列を変えた | 後に変えた方が勝つ。順序が逆でも同じ | 済 |
| 同じ作品を両方で保存した | 自然キーで 1 件にまとまる。ID は機械ごとに別のまま | 済 |
| 同じ名前のタグを両方で作った | 1 つにまとまり、紐づけも揃う | 済 |
| タグを片方で外し、片方で足した | 両方効く | 済 |
| 一方が削除し、他方が変更した | **削除が勝つ。** その後で保存し直せば現れる。`library-trash` とスナップショットから戻せる | 済 |
| 同じ版番号に違う内容の版ができた | 本拠が、後から届いた方を次の番号へ振り直す。ファイルは `v{n}` のディレクトリごと移し、結果を全員へ配る。`current_version` は大きい方 | 未（実装の最初に確かめる） |
| 編集の反映がぶつかった | 別の編集版として両方残し、今使う版は後勝ち。`sync_conflict` を通知する。以前の版から戻せる | 未 |
| コレクションの並びが重なった | 位置の列は後勝ち。同じ位置が重なれば、鍵の順で振り直す | 未 |

負けた値は `sync_conflicts` に 30 日残し、「サーバー（β）」の画面から見られる。`favorite` や `last_checked_at` のような値は
負けても騒がない。題・本文の編集に関わるものだけ通知する。

### 受け取る側の守り

本拠は読み手の口を公開している。管理者の鍵が漏れた場合も含めて、束で本拠のファイルを読み出せないようにする。

- 表と列は、組み込みの許可一覧にあるものだけを受け付ける。名前を SQL に直接入れない。
- パスの列は `piep-library:/` で始まり、`..` を含まず、ライブラリの中に解決されるものだけを受け付ける。
- 読み手の API は、ファイルを開く直前にもライブラリの中か確かめる。
- ファイルは宣言された SHA-256 と大きさを照合してから置く。

### 移り方と戻し方

1. 段階 1 の送信で、本拠が最新の写しを持っている状態にする。
2. デスクトップ版でいつものバックアップ（書き出し）を取るよう促す。本拠でもスナップショットを作る。
3. 「本拠へ移す」を押すと、デスクトップ版は最後の送信を行う。このときは手元だけの表を除くすべてを送る。
4. `work_edit_revisions` に `sync_id` を足し、トリガーを付ける。すり合わせを始める。
5. 2 台目以降の PC は、本拠から写しを受け取ってから始める。

**戻し方:** 「本拠から切り離す」で、未送信を送ってトリガーを外し、デスクトップ版を単独の本棚に戻す。本棚の中身はそのまま
手元にある。本拠が壊れているときも同じ操作ができる（送れなかった変更は手元に残るので失われない）。トリガーと記録の
表を外せば、`sync_id` の列が残るほかは今の piep と同じ DB に戻る。

### 試作で確かめたこと

開発者の棚（27,635 作品）の DB の写しで、使い捨ての試作を動かした。ファイルは複製していない。

- 整数の ID をすべて振り直し（本拠と同じ ID の作品が 0 件）、自然キーと相対パスで組み立て直すと、同期する 24 表が
  完全に一致した（この試作は同じ置き場に戻したので、`\\?\` つきの 38,306 件の資産などはパスの変換を通っていない。
  変換そのものは段階 1 の実データの確認で別に確かめた）。行き先の無い参照は 0 件。持ち運べる形にするのに 1.5 秒、組み立てに 4.6 秒、全行の JSON で 159 MB。
- 記録のトリガーの負担は、300 作品の保存（タグ 15、アセット 10 ずつ）で 22 ms が 187 ms になる程度。ネットワークからの
  取得に比べて無視できる。
- 2 台が別々に変更してすり合わせると、上の表の「済」の場面で 24 表が完全に一致し、外部キーの違反も無かった。

確かめていないこと: 表の「未」の場面、3 台以上、混成論理時計（試作は 1 台の PC の時計を使った）、`ai_notes`・`saved_searches`・
`watch_groups`（開発者の棚に行が無い）の中身の形、ファイルを伴う送受信、実際の更新ジョブと同時に動かしたときの関門との関係。

## 段階 4: 定期更新

### 動かし方

更新ジョブは `tauri::AppHandle` に結びついている。本拠でこれを動かす方法を、段階 4 の最初に試作して決める。

1. **窓を持たない Tauri の実行環境で `piep-server` を動かす。** 更新ジョブのコードに手を入れずに済む。
   SYSTEM のスケジュールタスク（画面の無いセッション）で起動・常駐できること、WebView を作らないことを確かめる。
2. 1 がだめなら、**ジョブが使う状態とイベントの送り先を差し替えられる形に切り出す**（デスクトップ版は
   `AppHandle`、本拠は自前の状態と記録・通知）。手間は大きいが、確実に動く。

### 予定

- 今のデスクトップ版の予定の考え方（`updateSchedule`）を Rust へ移し、本拠で回す。予定と対象は本棚と一緒に同期する。
- 既定は 1 日 1 回、決めた時刻から 0〜30 分ずらして始める（毎日同じ秒に取得元を叩かない）。間隔は 6 時間より短くできない。
- 取得元ごとにジョブは 1 つだけ。
- **止まっていた分の追いつき:** 起動時に、予定の時刻を過ぎていれば 5 分後に始める。取得元の作品は待っていても消えないのが
  普通なので、短い停止なら追いつくだけで足りる。
- **手で保存する・「今すぐ確認」:** デスクトップ版が手元で行う。結果は同期で本拠へ届く。

### 本拠が止まっている間の代役

- デスクトップ版は、本拠の「最後に更新確認を行った時刻」を同期で知っている。**本拠に届かず、かつ予定の時刻を 1 時間過ぎている**
  とき、デスクトップ版が今の予定（`useUpdateScheduler`）で更新確認と保存を行う。設定で切れる（既定は入）。
- 本拠に届く間は、デスクトップ版は定期更新をしない。二重に取得しないためである。
- デスクトップ版が複数あるときは、機械の ID の順に 10 分ずつずらして始め、他が動いたことを同期で知れば止まる。本拠に届かない
  同士で同時に動くことはありうるが、規則で 1 件に揃う（取得元への負荷が一時的に増えるだけ）。
- 本拠が戻ると、代役の結果を受け取る。`update_targets.last_checked_at` が同期されるので、本拠は同じ対象を確認し直さない。

### 取得元への負荷

人が見ていない間に動くので、今より慎重にする。

- 今の関門（取得元ごとに呼び出しの間を 800 ms、`Retry-After` に従う）はそのまま使う。関門は機械ごとなので、手で保存して
  いる間は 2 台ぶんになりうる。手での保存は少量なので許容し、429 を受けたらそれぞれが後退する。
- 429・5xx・通信の失敗が続いたら後退する: 1 分、2 分、4 分…と倍にし、最長 60 分。同じ取得元で 5 回続けて失敗したら、
  その回の残りをやめて「後退中」とし、次の予定から普通に戻る。
- 1 回の上限を設ける: 確認は 2,000 件、保存は 300 作品まで。残りは次の回に回す（大量の新作が一度に来ても、
  取得元へ一気に行かない）。
- 取得元の利用規約と、取得元が示す間隔の求めに従う。β の間は既定の値を控えめに置く。

### 取得元の認証情報

- **渡し方:** ログインはデスクトップ版で行う（ログイン画面はデスクトップ版の WebView にしかない）。設定の
  「サーバー（β）」に「この認証情報を本拠に渡す」を置き、押したときだけ管理の口へ送る
  （`PUT /admin/credentials/{pixiv|fanbox}`）。pixiv は refresh token、FANBOX は cookie と UA。**本棚の同期では運ばない。**
  デスクトップ版は手で保存するために、自分の控えを持ち続ける。
- **持ち方:** 本拠は、`serve` を動かしているアカウント（SYSTEM）の **DPAPI** で暗号化し、`state\credentials\` に置く。
  その機械のそのアカウントでしか戻せない。
- **出さない:** API は認証情報を返さない。状態として「設定済み・最後に通った時刻・切れている」だけを返す。記録・
  画面・誤りの文に出さない。消すときは `DELETE /admin/credentials/{provider}`。
- 今の piep は refresh token を書き戻さず、同じ token を使い続けている。そのため本拠とデスクトップ版が同じ token を
  同時に使える。取得元の仕様が変わって token が入れ替わるようになれば、機械ごとに別のログインにする必要がある。
- **認証切れ:** pixiv の更新が `invalid_grant` で断られた、FANBOX が 401・403 を返した、ログインへ転送された、のどれかで
  「切れた」とする。その取得元の予定を止め、`auth_expired` を通知し、デスクトップ版の画面に「ログインし直して渡す」を出す。

段階 4 では、本拠が取得元の認証情報を持つ。外へ公開しているなら、管理の口は分けておく（「読み手の口と管理の口」）。

## 状態を見る

管理の API `GET /api/v1/admin/status` と `piep-server status` が同じ中身を返す。デスクトップ版の
「設定 → サーバー（β）」はこれを表示する。β では、専用の Web の管理画面は作らない。

- 本棚: 世代、作品数、最後に反映した時刻、索引の進み具合、空き容量
- 本拠: 版、`syncFormat`、動いている時間、最後の立ち上げ直しとその理由、更新の状態（最新か、次に当てる版、最後の失敗）
- 送受信: 最後の送信・受信、途中のものがあればその進み具合、機械ごとの未同期の件数、ぶつかりの記録、ずれの確かめの結果
- 定期更新: 次の予定、最後の結果（確認・保存・エラー・保留の件数）、待っている列、後退中か
- 認証情報: 取得元ごとの状態
- バックアップ: 最後と次、結果、保持しているスナップショット、`after` の結果
- 端末: 登録した端末、最後に使った時刻
- 通知: 最後の失敗

外の監視には、無認証の `GET /api/v1/hello` か、`uptime-kuma` 形式の通知の heartbeat を使う。

## テストと確認

- 単体: パスの相対化と戻し（14 列と JSON の中、アプリデータの外を指す値の扱い）、要らない表の消去、索引の記録の引き継ぎ、
  差分の判定、かたまりの再開と SHA-256 の照合、検索条件の検査、`data-local-path` の置き換え（以前のテストを移す）、
  登録の回数制限、読書位置の新旧の判定、`library-trash` の保持と掃除、後退の間隔、認証情報が応答と記録に出ないこと、
  更新の署名の検証（壊れた署名・別の鍵・古い版を断ること）。
- 同期の性質: 「ぶつかったときの規則」の各場面を、**当てる順番を入れ替えても同じ結果になること**（2 台と 3 台）を、無作為の
  変更列で確かめる。トリガーの生成が全部の表の列に追いつくこと（新しい列を足すと失敗するテスト）。持ち運べる鍵に
  整数の ID や絶対パスが混ざらないこと。切り離すと、`sync_id` のほかは今の DB と同じになること。
- 結合: 一時ディレクトリでサーバーを立て、管理者の登録 → 送信 → 携帯の登録 → 検索 → 本文 → 画像 → 読書位置 →
  解除後 401 を HTTP で通す。作品を 1 つ足して送り直すと、その作品のファイルだけが上がり、その作品だけが索引し直されること。
  どの応答にも `C:\` やアプリデータの置き場が出ないこと。段階 2 ではスナップショット → 作品を消す → 戻すで元に戻ること、
  本体を殺すと見張り役が立ち上げ直すこと、起動しない版へ更新すると前の版へ戻ること。段階 3 では、本拠を止めている間の変更が
  つなぎ直したあとに揃うこと、切り離すと単独の本棚に戻ること。段階 4 では、本拠を止めるとデスクトップ版が代役をし、戻ったあと
  同じ対象を確認し直さないこと。
- 版の違い: 古い版のサーバーと新しい版のデスクトップ版（と逆）を組み合わせ、列が足された行が保留を経て揃うこと。
- 公開の前提: 無認証で `hello`・`pair` 以外が 401 になること、`pair` の回数制限、大きすぎる要求の拒否、平文で 127.0.0.1
  以外に待ち受けようとすると起動を断ること、`admin_listen` を分けたとき読み手の口で `/admin` が 404 になること、束で
  ライブラリの外のパスを書けないこと。
- 実データ: `src-tauri/examples/server_real_library_check.rs` で、開発者の棚の DB を本実装の送信に通し、抜き出した作品を
  読み手の API で読み切る（段階 1 の結果: 399 作品、パス 191,337 件の変換で外へ出るものは 0、応答へのパスの漏れは 0。
  動画・音声・PDF の資産は読み手の API の対象外なので 404 を返す）。ファイルは、**棚を丸ごと複製しない**約束があるので手元の確認は
  作品を絞った送信で行い、全件は単独サーバーの機械への初回送信で確かめる。
- Android エミュレーター: 版 2 に対応した Android 版で、内蔵サーバー（自己署名 TLS、`adb reverse`）と、公開 URL の
  単独サーバーの両方につなぐ。

## 代案

### 本拠だけが書く（操作を送る）

デスクトップ版の変更を操作として本拠へ送り、本拠だけが DB を書く形。規則が要らず単純に見えるが、本拠が止まると変更できず、
保存した作品が遅れて現れ、約 180 の IPC に送り先の振り分けと許可の一覧が要る。当初の案だったが、これらの不便を
構造として持つので採らない。

### SQLite のセッション拡張・CRDT の拡張

変更の記録に SQLite のセッション拡張を使う案、cr-sqlite のような CRDT の拡張を使う案。どちらも行を機械の主キーのまま運ぶので、
ここで要る「整数 ID を自然キーへ」「絶対パスを相対へ」の翻訳を挟みにくい。トリガーで記録するほうが単純で、外せば元の形に戻せる。

### 共有フォルダーで送る

SMB 共有へ robocopy で送る案。速いが、共有の用意が要り、同じ LAN か VPN の中に限られる。一般の利用者に共有フォルダーの
権限設定を求めたくないので採らない。HTTP の送信が遅すぎると分かったら、家の LAN での近道として足すことはありうる。

### Linux・Docker

`piep_lib` は Tauri に依存している。DB・検索・本文の部分を Tauri に依存しないクレートに切り出せば、`piep-server` を
Linux でも組める。β の反応を見てから決める。段階 4 の「動かし方」で 2 を選んだ場合は、その切り出しの一部になる。
