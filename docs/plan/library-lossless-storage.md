# ライブラリ全体の可逆圧縮と画像の改稿判定

策定日: 2026-11-07。状態: 基盤を実装中。ここで「採用」とする方式は実装の基準であり、
現在の棚がこの形式になっているという意味ではない。既存データの変換はまだ行わない。

DB の論理構造は [ライブラリのデータモデル再設計](library-data-model.md) に従う。
旧 DB・旧 API との恒久的な後方互換は要求しない。旧形式を読む処理は移行器に限定する。

## 1. 目的と決定

本文だけ、画像だけ、バックアップだけを圧縮するのではなく、普段使うライブラリ全体の
保管量と通信量を減らす。保存した作品・過去版・利用者の編集・添付・付随情報を保持し、
作品を読むたびにライブラリ全体を展開しなくてよい構造にする。

採用する方式は **元ファイルのバイト列を復元できる Zstandard 圧縮と、内容ハッシュによる
重複排除**。ファイル名・URL・作品が違っても中身が同じなら、一つの実体を共有する。
圧縮しても小さくならない実体は無圧縮で保管する。

大きな単一 ZIP を普段の棚として使う方式、画像の再エンコード、Windows 固有の圧縮機能への
依存は採用しない。JPEG XL など画像専用の可逆再圧縮は初版に含めない。
追加方式を実装する場合も、本仕様と同じ完全復元の検査を必要とする。

| 比較した方式 | 初版の判断 | 理由 |
| --- | --- | --- |
| 実体ごとの Zstandard/raw と重複排除 | 採用 | 任意のファイルを完全復元でき、作品単位の読み出し・バックアップ・端末転送を共通化できる |
| NTFS 等の透過圧縮 | 利用者の任意利用にとどめる | パスを保てる利点はあるが、別ファイルシステム・端末へ方式を引き継げず、内容の重複排除も別途必要 |
| 単一 ZIP/7z に棚全体を格納 | 日常の保存には不採用 | 部分更新・同時アクセス・障害からの復旧を複雑にする。バックアップの容器としての使用とは別 |
| PNG 最適化や可逆 WebP 化 | 原本の置き換えには不採用 | 画素が一致しても元ファイルのメタデータやバイト列が戻る保証にはならない |
| JPEG XL の JPEG 完全復元モード | 将来の追加候補 | JPEG 向けの改善余地はあるが、すべての保存ファイルを扱う共通方式の完成を先にする |

既存の PNG・JPEG・PDF・EPUB 等は既に圧縮されていることが多く、汎用圧縮による
追加削減が小さい場合がある。全体の効果は、これらの比率と完全一致の重複量に左右される。
初版を入れただけで原寸画像の増加量を相殺できるとは約束しない。

## 2. 現在の問題と解決策

| 問題 | 採用する解決策 | 守る条件 |
| --- | --- | --- |
| 原寸画像の取得で保存量が増える | 全種類の保存ファイルを共通の保管層へ入れ、可逆圧縮と重複排除を行う | 原寸・色・メタデータ・添付を捨てない |
| 同じ画像が別作品・別の版・表紙と挿絵に重複する | 元バイト列の SHA-256 で実体を共有する | 見た目が似ているだけの画像は統合しない |
| 大きなアーカイブは一冊読むにも展開が必要 | 小さな独立した実体を読み、大きなファイルだけ分割する | 他作品や過去版の展開を要求しない |
| ファイルパスを直接読む箇所が多い | 読書・編集・検索・書き出し・サーバーの読み書きを共通の保管 API に通す | 圧縮ファイルのパスを既存の画像表示へ直接渡さない |
| 表紙の品質別 URL の違いが改稿に見える | 取得元の画像識別情報と、取得・保存・配信用の情報を分ける | 作者の表紙差し替えは検出する |
| 一部の失敗で移行後のファイルが読めなくなる | 書き込み・復元検査・参照確定・元ファイル解放の順を記録する | 読めることを確認するまで元ファイルを解放しない |
| 共有実体を作品削除に巻き込むおそれがある | 作品の参照を外す操作と、未参照実体の回収を分ける | 他作品・過去版・編集・バックアップの参照を守る |
| モバイルで同じ内容を繰り返し転送する | 認証付きキャッシュ・条件付き取得・未取得実体だけの転送を行う | 品質を下げる操作と、可逆な通信削減を混同しない |
| 圧縮率だけでは実際の節約が分からない | 元の量、重複排除後、圧縮後、キャッシュ込みの実使用量を別々に示す | 既存のハードリンクを二重に節約と数えない |

## 3. 「情報を捨てない」の定義

### ファイルとデータベース

- 保存対象の各ファイルは、復元後の長さと SHA-256 が変換前に一致することを必須とする。
  改行、JSON の空白・キー順、EXIF、ICC、透過、アニメーション、添付の内容も含む。
- JSON を読み取って整形し直すこと、画像をデコードして別形式にすることは、この圧縮処理で
  行わない。画素が同じだけでは完全復元を満たさない。
- DB は作品・タグ・全保存版・編集・読書位置・お気に入り・監視・コレクションなどの
  利用者データを論理的に保存する。稼働中の DB の物理ページ配置や WAL の履歴までは
  固定しない。バックアップとして採取した DB ファイル自体はバイト単位で復元する。
- 元のファイル名・論理配置・取得 URL・MIME・版との対応は保持する。移行時の更新日時は
  記録するが、OS 固有のアクセス時刻・物理配置・ファイル ID の再現は保証しない。
- 圧縮保守を理由に過去版・編集下書き・保存済みのバックアップ・取得不能作品を消さない。
  圧縮はバックアップや暗号化の代わりではない。

### 対象範囲

| データ | 普段の扱い | バックアップでの扱い |
| --- | --- | --- |
| 全作品・全保存版の原本 JSON、表示用 JSON、画像、添付、元 EPUB/PDF が保存されている場合のそのファイル | 共通保管層で可逆圧縮・重複排除 | すべての参照と実体を保持 |
| 作者・シリーズの保存履歴、紹介文、画像 | 同上 | 同上 |
| 編集で追加した画像、コレクション表紙 | 同上。編集の基準版との対応も保持 | 同上 |
| EPUB テンプレートなど利用者が編集する通常ファイル | 編集時は通常ファイル。保存時に検証済みのスナップショットを作る | スナップショットを可逆圧縮し、元バイト列を保持 |
| `piep.db`、設定、進捗・復旧記録 | 稼働中は通常形式。DB の独自圧縮 VFS は初版では導入しない | SQLite の整合したスナップショットと設定を可逆圧縮 |
| 全文・意味検索の索引 | 各エンジンの通常形式を使う | 標準では再構築対象。完全フォルダー書き出しでは任意で含める |
| AI モデル、再取得できる実行資材 | 通常形式。ファイルを削除して容量を節約することはしない | 標準では再取得対象。完全フォルダー書き出しでは任意で含める |
| 表示用変換画像、一時展開物 | 容量上限のあるキャッシュ | 原本ではないため標準バックアップに含めない |
| 既存バックアップ、ログ、未認識ファイル、接続用の資格情報 | 自動変換・整理の対象外。量を分けて報告 | 未認識ファイルは完全フォルダー書き出しで保持。秘密情報の扱いは既存方針を維持 |

「ライブラリ全体」は全ファイルを同一方式で包むという意味ではない。内容を保護する
対象は棚全体で、頻繁に更新される DB や独自形式の索引には通常の読み書きを残す。
それらの量も総容量から除外せず、未圧縮分として表示する。

## 4. 保管形式 v1

### 実体と参照

保管層は `objects/v1/` に置く。実体は公開後に書き換えない。
取得元の URL、ローカルパス、原寸か縮小版かは実体の識別子にしない。

- 8 MiB 以下のファイルは一つの実体にする。
- 8 MiB を超えるファイルは先頭から 4 MiB ごとに分割し、最後だけ端数とする。
  ファイル全体のハッシュと、順序付きの部分実体一覧の両方を記録する。
- 各実体 ID は展開後の元バイト列の SHA-256 とする。同じ内容は作品・版・種類を問わず共有する。
  ファイル全体と部分実体は別の記録であり、同じハッシュ空間の役割を混同しない。
- 大きなファイルの途中読みは必要な部分だけを復元する。圧縮データの途中へ元ファイルの
  オフセットでシークしない。初版では差分圧縮と内容依存の可変長分割は導入しない。
- 保存名・MIME・取得先・作品 ID・版・画像の役割は参照側が持つ。同一実体を表紙と挿絵で
  共用しても、それぞれの参照の情報は残る。

実体ヘッダーは形式版、符号化方式 `raw` / `zstd`、元サイズ、格納サイズ、元 SHA-256 を持つ。
Zstandard は実体ごとに独立したフレーム、チェックサム有効、外部辞書なしで使う。
初版の圧縮レベルは 3 とし、元データが `N` バイトのとき、ヘッダーを含めた圧縮表現が
無圧縮表現より `max(1024, ceil(N × 0.01))` バイト以上小さい場合だけ採用する。
満たさなければ `raw` にする。画像も拡張子だけで圧縮可否を決めず、この規則を使う。

これは「必ず小さくする」仕様ではない。索引や参照の管理分を含めた棚全体の実容量は
実測する。圧縮処理はストリームで行い、元のファイル全体をメモリへ載せない。

### 記録と共通 API

新 DB で保管層が持つ論理的な記録は次の四つとする。実際の列定義は実装 PR で定めるが、
以下の関係と完全性の条件は変更しない。

| 記録 | 主な内容 |
| --- | --- |
| 実体 | ID、方式、元・格納サイズ、検査状態、保管場所 |
| ファイル | 元ファイルのハッシュ・長さ、順序付き実体一覧 |
| 参照 | 所有する作品・版・編集等、役割、元の相対パス、ファイル ID、取得情報 |
| 操作記録 | 保存・移行・削除・復元の段階、対象、確定状態、再開位置 |

版・作者・シリーズ等の単位で復元用マニフェストを持つ。マニフェストにはファイルの
ハッシュ・長さ・相対パス・部分実体一覧・所有関係を記録し、DB が壊れても原本を
取り出せるようにする。利用者の編集など DB にしかない情報の復元には DB バックアップが
必要であり、マニフェストだけで棚全体を復元できるとは扱わない。

`read` / `stream` / `read_range` / `materialize` / `verify` / `export_original` を
保管 API の責務とする。読み手は保存方式を知らず元バイト列を受け取る。
ファイルパスが必要な外部ツールや WebView には、要求したファイルだけを検証して一時展開する。
一時展開物は共用原本として扱わず、外部からの変更が原本へ伝わるハードリンクを作らない。

旧形式の通常ファイルを読む処理は移行器へ閉じ込める。新形式の日常処理では、
旧絶対パス・新実体 ID の両方を扱う恒久的な互換層や二重書き込みを持たない。
原寸への取り直しも新しい実体の追加と参照差し替えで行い、共有実体への上書きを禁止する。

### 検査と削除

- 保存時と移行時は、一度復元して元の長さ・ハッシュとの一致を確認する。
- 読み出す部分実体を初めて検証済みキャッシュへ入れる際に、長さとハッシュを検査する。
  未検証のストリームでは検査完了まで成功を確定しない。破損を空本文や欠損画像へ置き換えない。
- 実体ヘッダー・復元サイズ・メモリ使用量には上限を設け、指定サイズを超えて展開しない。
  チェックサムだけで完全性を保証せず、元 SHA-256 も照合する。
- 同じハッシュの既存実体がある場合も、破損状態なら共有せず修復対象にする。
- 作品削除では参照だけを外す。回収は全作品・全版・編集・削除隔離・進行中の保存・
  バックアップの固定参照から到達可能な実体を印付けした後に行う。
- 参照カウントだけを唯一の削除根拠にしない。回収は保管層への書き手を止めて行い、
  未参照実体を一度隔離する。隔離から 7 日以上経過し、再走査でも未参照のものだけ消す。
- 検査が失敗・中断した場合は回収しない。圧縮率を上げる目的で未認識ファイルを消さない。

## 5. 表紙の改稿判定

品質別の URL を判定に混ぜない。以下の三つを別々に記録する。

| 情報 | 判定・用途 |
| --- | --- |
| 取得元の表紙識別情報 | 作者が違う表紙へ差し替えたかを判定する |
| 取得 URL、取得時刻、寸法、形式、原寸確認結果 | 取得した表現と取得経路を記録する |
| ファイルのハッシュ・保管方式 | 完全性・重複排除・復元に使う |

pixiv の既知の URL 形式に限り、サイズ指定・原寸/master の区別・変換用の末尾・
拡張子を取り除き、画像を指すパスの日時と固有部分から比較キーを作る。
すべての URL を汎用的に加工しない。未知の形式は元 URL の厳密比較へ戻し、
識別情報を取得できない場合は「変更なし」を確定しない。

このキーは取得元の識別であり、画像内容の完全な証明ではない。同じ URL のまま中身が
差し替わる事象はキーだけでは検出できない。既存の本文の定期確認とは別に、画像の
再検証も必要になる。再検証時に同じ取得表現でハッシュが変わった場合は画像変更の
候補として扱い、縮小版と原寸のハッシュの違いとは区別する。

本文・題名・説明・タグ等の比較規則は維持する。表紙変更は作品の履歴に残すが、
原寸への補完、可逆圧縮、重複排除、配信形式の変更だけでは作者の改稿を増やさない。

旧データの取得 URL と `cover_original_url` は取得事実として保持し、原本 JSON を
書き換えない。別欄方式は移行器が新モデルの取得記録へ変換する。軽量メタデータ比較、全文の内容比較、
保存版比較、修復判定で同じ表紙識別関数を使う。

比較規則に版番号を付け、旧指紋と新指紋を直接比較しない。保存済み JSON から新指紋を
作り直し、取得直後のデータにも同じ規則を適用してから切り替える。処理中は旧比較を
使うか、取得済みの本文を比較し、指紋移行自体を改稿として登録しない。
新 DB への全体移行では、新形式の指紋作成を終えてから新しい棚の書き込みを有効にする。

画像の再検証は公開元への通信を伴うため、ローカルの圧縮処理には組み込まない。
通常の更新確認の通信制限・中止・認証の分担に従う。

## 6. 移行と障害時の動作

初回の既存棚の変換は利用者が「ライブラリを可逆圧縮」を実行して開始する。
別ルートへ新 DB と新実体を構築し、その後の新規保存は同じ保管層を使う。
「通常ファイルへ書き出す」は原本ファイルの復元であり、旧アプリで同じ棚を使えるという
保証とは分ける。

1. 旧 DB と全所有関係・通常ファイルを列挙する。リンク・ジャンクションを追跡せず、
   未認識ファイルは別報告する。欠損・曖昧な所属があれば完了扱いにしない。
2. 同じファイルビューから SQLite Backup API で整合した移行前バックアップを作る。
   旧棚の変更を止め、別ルートに新 DB を作る。
3. 元ファイルから部分実体を作成し、一時保存・復元検査・同期・公開を行う。
   所有関係を新スキーマの entity/revision/snapshot/file へ移し、旧 ID の対応表を残す。
4. DB 確定後にマニフェストを生成する。未生成分は操作記録から再生成できるようにする。
   マニフェストと DB を独立した二つの正本にしない。
5. 全元ファイル・全版・編集・採否等の利用者データを照合し、読書・バックアップ復元を検証する。
6. 完成した新棚へ切り替える。旧棚の容量解放は、その後に利用者が明示的に実行する。

中止は現在の実体処理を安全に終えてから効かせ、検証済みの範囲と操作記録を残す。
新棚が完成するまでは旧棚のファイルを解放しない。再開時に移行元の世代が変わっていれば
無条件に続けず、元を固定し直して差分を再検査する。

切り替え前は旧棚へ戻せる。新棚で保存・編集を始めた後に旧棚へ戻っても、追加操作は
反映されていないことを明示する。旧 DB のバックアップだけを戻す操作を完全な復元として
提供しない。新棚からの通常ファイル書き出しでは、元バイト列と所有関係を取り出せる。

移行中は移行元と移行先の両方のプロセスロックを持ち、旧アプリの同時起動を防ぐ。
新棚が完成するまでは通常の保存・編集・同期の書き込みを止め、旧棚の固定した状態を
読み取り用に提供する。中止後に旧棚の運用を再開できるが、移行の再開時に世代を再検査する。
新棚の日常の圧縮・再圧縮では、対話的な読書・保存を優先し、確定段階の短い錠だけを持つ。
圧縮ワーカーは最大 2、復元ワーカーも最大 2 とし、回収との競合を調整する。

必要空き容量は「旧棚全体を残しながら作る新実体、新 DB、DB バックアップ、記録、
一時領域」の上限から見積もる。試算せず固定の割合で開始しない。
初回移行では新旧を並行保持する領域が必要になる。空き容量不足では追加書き込み前に止まる。
再開可能な中断と、復元不能な破損は別の状態として表示する。

新形式の識別は DB を開いて修復・初期化するより前に行う。既に配布した旧アプリに
後付けの保護はできないため、移行先は旧アプリが通常使う保存先と異なる新ルートにする。
旧保存先には新形式を直接置かず、移行後の保存先切り替えを明示する。
旧アプリを使う場合は移行前の旧棚を使い、通常ファイル書き出しを旧 DB の互換保証には
使わない。旧側を残した分の容量は節約に数えない。
旧側の自動起動・定期ジョブも新側へ切り替える。新旧の棚で別々に書き進めた場合は、
自動で合流できるとは案内しない。

## 7. バックアップ、書き出し、サーバー

二種類の書き出しを用意する。

- 通常形式: 各ファイルを元のバイト列に復元し、相対配置・所有関係のマニフェストと
  整合した新形式 DB を書き出す。原本は一般の道具で開けるが、旧アプリの復元機能との
  互換は要求しない。新 DB を旧 DB と偽って渡さない。
- 圧縮形式: 整合した DB スナップショット、マニフェスト、参照される実体を格納する。
  一回のバックアップ内では実体を一度だけ含め、単独で復元できるものを既定とする。
  分割ファイルにしても、必要な全パートと完全性の一覧を一緒に渡す。

圧縮形式は単純な巨大な固体圧縮にしない。実体の独立性を保ち、原本が既に圧縮済みなら
外側で何重にも圧縮しない。過去バックアップに依存する増分連鎖は初版に含めない。
バックアップ間で同じ実体を共有する保存先方式も初版の対象外とする。

バックアップ開始時に DB と必要実体の集合を固定し、完了まで回収から保護する。
固定後は不変実体を読むため、長時間の書き出し中ずっと作品保存を止める必要はない。
復元は未知の方式・欠損パート・実体不一致・相対パス逸脱を変更開始前に拒否する。
管理情報が失われた場合に備え、アプリの画面を使わずマニフェストから原本ファイルを
復元・ハッシュ照合する道具も同時に提供する。

サーバーへ棚を送る場合も、DB/マニフェストの参照と実体を別に扱う。
受け手が検証済みの実体を持っていれば転送せず、全参照先が検証済みになってから
新しい棚の状態を公開する。受け手の実体はローカル側の回収では削除しない。

## 8. モバイル通信

保存方式、HTTP の通信圧縮、表示用画像の品質は独立した設定とする。

- 本文・一覧 JSON は既存の HTTP 圧縮を継続する。クライアントが対応を表明した方式だけ返す。
- 新しいネイティブクライアント間の原本取得は実体 ID と保管方式を交渉し、未取得の
  部分実体だけを転送する。実体を復元後、元ハッシュを検証して端末キャッシュへ確定する。
  中断後は検証済み部分から再開できる。大きなファイルの一部分だけで完成扱いにしない。
- 新方式に非対応の端末と通常のブラウザーには、元のファイルを標準 HTTP で返す。
  保管用の zstd を非対応のブラウザーへそのまま返さない。
- 認証後に ETag / If-None-Match を評価する。未変更なら 304 で本文を再送しない。
  ETag は原本または派生物の内容と表現に対応し、原寸・縮小・形式違いの間で共有しない。
- 画像への一律 `no-store` は、明示的な端末保存方針と整合する認証付きの私的キャッシュへ
  改める。標準 HTTP では `private, no-cache` により再利用前に認証・再検証する。
  認証応答や秘密情報には `no-store` を維持する。
- 端末の実体キャッシュはサーバーと登録端末の単位で分け、ログアウト時に削除する。
  オフライン保存は別の明示操作とし、その保持・削除は既存の端末保存方針に従う。
  登録解除で止められるのは以後の通信であり、取得済みファイルの遠隔消去は保証しない。
- 原本取得はファイルの完全復元を保証する。可逆な画像形式への変換も、元ファイルを
  バイト単位で復元できなければ原本取得とは呼ばない。
- 現在の端末幅に応じた縮小・非可逆 WebP は「通信節約用の表示」と明示して残す。
  「原本」と切り替え可能にし、画質を変えずに通信量を削減したという説明には含めない。

同じ画像を原本で何度も送らずに済むことと、初回に大きな原本を送る量が減ることは別である。
既に圧縮された画像の初回転送はほとんど減らない場合もある。

## 9. 画面と容量の説明

利用者向けの操作は「容量を調べる」「ライブラリを可逆圧縮」「検証」「中止・再開」
「通常ファイルへ書き出す」にする。通常画面で圧縮方式やハッシュ値を選ばせない。
取り直しと圧縮は独立した操作にし、圧縮のために公開元へ接続しない。

容量調査は利用者が実行したときに行い、画面を開いただけで全件を読み直さない。
試算は推定と実測を区別し、サンプルの偏りと未調査件数を出す。

表示する値は次のとおり。

1. 各論理ファイルを通常保存した合計量。原本・過去版等の内訳も示す。
2. 現在の物理使用量。既存ハードリンクの重複を除き、既に得ている節約を含める。
3. 完全一致の重複排除後の量。
4. 圧縮後の実体量、管理情報、稼働 DB・索引・モデル、キャッシュを含めた総使用量。
5. 旧形式の残存分、移行前バックアップ、未認識ファイル、外部バックアップの量。
6. 作業中の最大必要空き容量、処理済み量、残量、失敗・欠損件数。

「節約できた量」は同じ対象範囲の変換前後の物理使用量で比較する。
重複排除の効果と圧縮の効果を二重に足さない。索引の削除やキャッシュ削除による
減少は、可逆圧縮の成果とは別に示す。固定の削減率や増減 GB 数を約束しない。

## 10. 受け入れ条件

実装の完了には、合成例だけでなく実際の棚の整合した写しで以下を満たすことを必要とする。

| 確認 | 必須の結果 |
| --- | --- |
| 全ファイルの圧縮→復元 | 長さと SHA-256 が全件一致。対象不明・未処理・欠損は別報告 |
| DB の比較 | 作品・全保存版・編集・タグ・お気に入り・監視・コレクション等の論理データが一致 |
| 読書・編集・全版検索・PDF/EPUB・添付書き出し | 旧形式と同じ内容が取得でき、基準版の画像が保持される |
| 表紙の判定 | 原寸補完・保存方式変更は改稿 0 件。実際の差し替えは検出。未知 URL は保守的に扱う |
| 同じ実体を参照する二作品の一方を削除 | 他方・過去版・編集が正常に読める |
| 各確定段階での強制終了、ディスク不足、破損 | 読める原本を失わず、再開・復旧・失敗箇所の提示ができる |
| 一時展開と通常形式への復元 | 原本全件がバイト単位で一致。キャッシュを全削除しても読める |
| バックアップ・復元 | 別ルートの空の棚へ復元し、全参照・DB・原本ハッシュが一致する |
| モバイル | 原本をバイト単位で復元。二回目はキャッシュ/304、再開時は未取得部分だけを転送 |
| 認証・破損 | 他端末の参照やキャッシュを利用できない。未知方式・改ざん・展開上限超過を拒否 |

性能は同じ機械・同じ棚・同じ操作列で、通常形式と圧縮形式の冷間・温間それぞれを計測する。
一覧・検索・読書ページ表示の p95 の増分は、各操作で `max(従来値の 20%, 100ms)` 以下を
初版の出荷条件とする。巨大添付の復元は別項目として時間・最大メモリを報告する。
初版のバックグラウンド圧縮に追加されるメモリは 256 MiB 以下を基準とし、
復元データの全量を抱え込む実装は認めない。達しなければ既定有効化せず実装を見直す。

容量の実測は JSON、PNG、JPEG、その他画像、PDF/EPUB/ZIP、その他添付に分ける。
高圧縮率のテキストだけで棚全体の効果を示さない。削減率は出荷条件に固定せず、
管理分込みで増える棚は変換を勧めない。

## 11. 実装の順序と初版の境界

1. 表紙の識別規則と指紋の移行、読み取り専用の容量調査を実装する。
2. 共通保管 API を導入し、パスを直接読む全機能を通す。開発時の旧形式アダプターは
   移行器の準備に限り、新形式の通常動作へ恒久的に残さない。
3. 新データモデルと Zstandard/raw 実体、部分復元、重複排除、マニフェスト、保存・回収の復旧を実装する。
4. 圧縮形式と通常形式のバックアップ・復元・外部復元道具を完成させる。
5. モバイル・単独サーバーの読取互換と認証付きキャッシュを整える。
6. 実データの往復検証後、別ルートへの既存棚の移行と新規保存への適用を提供する。
7. 対応するネイティブ端末に、実体単位の差分取得と中断再開を追加する。

既存棚の変換を提供する前に、通常形式への復元とバックアップを必ず完成させる。
初版は圧縮レベルの詳細設定、画像専用再圧縮、作品間の類似差分圧縮、外部辞書、
巨大パックの再編成、稼働 DB の圧縮 VFS、旧バックアップの自動再圧縮を含めない。
これらを将来追加する場合も、過去版の削除や原本の再エンコードを可逆圧縮と呼ばない。
