# 検索の当たりすぎと、句の検索が落ちること

2026-09-07 の調査記録。**どちらもまだ直していない。** 直す前に、何が起きているかを
測って残しておく。

## 分かったこと（要約）

- **n-gram の欄に句（フレーズ）の検索を投げている。** n-gram のトークンは位置を
  持たないので、句の意味が消える。具体的な語で棚の43%が当たる
- **その句の検索が Tantivy の中で落ちる。** 開発ビルドだけで、配布ビルドでは
  落ちない。ただし前提違反そのものは配布ビルドでも起きている

二つは無関係ではない。落ちるのは句の検索であり、その句が壊れているのは上の理由
である。

## 1. 当たりすぎる

「空倉第一高校異文化交流部」で **4,013 件**（棚 9,370 件の43%）が当たる。

欄ごとに測ると、犯人は一つだけだった。

| 件数 | 欄 | 変種 |
| ---: | --- | --- |
| 4,013 | `body_reading_romaji` | `sora kura dai ichi koukou i bunka kouryuu bu` |
| 16 | `body_reading_kana` | `そら くら だい いち こうこう い ぶんか こうりゅう ぶ` |
| 1 | `excerpt_reading_romaji` | 同上 |

読みの正規化で「空倉第一高校異文化交流部」は空白区切りの読みになる。空白を含む
ので `query_literal` が引用符で包み、Tantivy は**句の検索**として組む。

組まれた句を覗くと、**85 個の語がすべて位置 0 にある。**

```
PhraseQuery { phrase_terms: [(0, "so"), (0, "sor"), (0, "or"), (0, "ora"),
  (0, "ra"), (0, "a "), (0, " k"), (0, " ku"), (0, "ku"), ...], slop: 0 }
```

位置がすべて 0 だと、句は並び順を縛れない。**「この n-gram が全部どこかにある」
だけの条件に化ける。** 2〜3文字のローマ字断片（`so` `or` `ra` `a ` ` k`）は、
ローマ字に開いた日本語の本文ならまず含まれる。だから43%当たる。

かなの欄が 16 件で済むのは、かなの2文字が英字の2文字よりずっと絞り込めるから
であって、仕組みが違うからではない。**同じ壊れ方をしている。**

原因は piep 側にある。`register_tokenizer` が使っている
`NgramTokenizer::all_ngrams(2, 3)` は、Tantivy の説明にこうある。

```
/// With this tokenizer, the `position` is always 0.
```

**位置を持たないトークナイザの欄へ、位置を要る問い合わせを投げている。**

直し方の候補（どれも索引の作り直しを伴う）。

- n-gram に位置を振る包みを自前で書く。句が本当に隣接を縛るようになり、精度は
  大きく上がる。`INDEX_VERSION_DIR` を上げて全件作り直し
- n-gram の欄は位置を持たせずに索引し、問い合わせも句をやめて語の AND にする。
  精度は上がらないが、嘘の句をやめられる

どちらも索引の形式が変わるので、この版では入れない。

## 2. 句の検索が落ちる

```
target (4194) should be greater than or equal to doc (4461)
```

棚の索引で再現する。`BLEACH 空倉第一高校異文化交流部` のような2語の検索で出る。

呼び出しの連鎖は全部 Tantivy の中である。

```
Intersection::advance
  -> BufferedUnion::seek_danger      ← 子が追い越していても target をそのまま渡す
       -> PhraseScorer::seek_danger  ← 前提違反を検出して落ちる
```

`buffered_union.rs` は子の現在位置を見ずに target を配る。

```rust
for docset in self.docsets.iter_mut() {
    match docset.seek_danger(target) {   // target < docset.doc() でも渡す
```

`DocSet` の**既定の**実装は安全で、追い越していたら何もしない。落ちるのは
既定を上書きしている `PhraseScorer` だけである。

こちら側で包んで避けられないかを当たった。

| 包み | `seek_danger` | 効果 |
| --- | --- | --- |
| `BoostScorer` | 中へ転送 | 効かない（piep は既に field boost を使っている） |
| `ConstScorer` | 上書きしない＝既定 | 効くが点数が定数になり、関連度順が壊れる |

union は `Intersection` の内側にあるので、外側を包んでも届かない。届かせるには
`QueryParser` をやめて問い合わせ木を自前で組むことになる。

実害の切り分け。

| | 開発ビルド | 配布ビルド |
| --- | --- | --- |
| 2語の検索 | **落ちる** | 落ちない（25件返る） |

`debug_assert!` なので配布物では消える。`panic = "abort"` なので配布物では
`catch_unwind` も効かないが、そもそも落ちない。**踏むのは `tauri dev` のとき
だけである。**

ただし前提違反は配布ビルドでも起きているので、返ってきた 25 件に取りこぼしが
無いとは言えない。

上の 1 を直せば句そのものが健全になるので、これも一緒に消える見込みが高い。
順序としては 1 が先である。

## 索引は壊れていない

作り直しの取りこぼしを疑って測ったが、そちらは健全だった。

```
segments: 13 / 一致した distinct id: 4,013 / 重複して出た id: 0
```

## 測り直し方

`cargo run --release --example field_probe -- "<語>"` のような使い捨ての example を
書いて、欄ごとの件数と組み上がった問い合わせを出した。残していない。同じことを
するなら、`ensure_index` で索引を開き、`query_variants` で変種を作り、欄ごとに
`QueryParser::for_index(&index, vec![field])` で数えるとよい。
