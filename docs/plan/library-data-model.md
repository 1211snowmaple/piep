# ライブラリのデータモデル再設計

策定日: 2026-11-07。状態: 基盤を実装中。現行アプリの棚の切り替えは未提供。
対象は SQLite のテーブルだけでなく、原本・改稿・修復・編集・画像・圧縮保管・
検索用データ・サーバーとの受け渡しを含む。

## 1. 決定と互換性の境界

既存の `downloads` 中心のスキーマへ列を足し続けず、新しいデータモデルへ移す。
旧テーブル名、絶対パス、版番号を参照 ID として使う API、旧クライアントの読み書き、
新旧形式を普段の動作で混在させる仕組みは維持しない。

守るものは保存済みデータと利用者の操作結果である。旧形式を読み込む一方向の移行器と、
元ファイルを復元する書き出しを用意する。古いアプリで新しい棚を開ける保証はしない。
元ファイルの完全復元と、古いアプリ向けの DB 互換は別の要件とする。

SQLite は継続する。現状の件数を理由に別の DB サーバーへ移す根拠はない。
設計の目的は表の数を減らすことではなく、正本の重複と関係の曖昧さをなくし、
圧縮・修復・改稿・同期がそれぞれ独立して正しく動くようにすることである。

[ライブラリ全体の可逆圧縮](library-lossless-storage.md) と合わせて実装する。
この文書が論理モデルと移行・互換性の判断を、圧縮仕様が元バイト列の保管方式を定める。

まだ既存のデスクトップ・携帯の保存経路を置き換えていない。

| 取得元の確認日時 | 作品の詳細確認日時とプロフィールの確認・取得日時を別々に保持する基盤を実装。未確認を公開日時や保存日時で埋めない。新しい取得処理との接続は未完了 |
| コレクション・監視・採否・編集等の完全な移行、未知データの扱い | コレクションの順番・固定・メモ、監視・グループ、候補の保留、関係ごとの採否、コレクション提案の判断と候補は基盤を実装。保存検索・AI ノート・端末状態等が未完了。未対応の正本がある棚は切り替えてはならない |
| デスクトップ画面・既存の保存処理・全版検索・PDF/EPUB への新モデル接続 | 未完了 |
| 携帯・単独サーバーの新プロトコル・認証付きの実体転送 | 未完了 |
| 本番棚への移行、既定有効化、リリース | 未実施 |

移行先の `activation_problems()` と検証道具の終了状態は、単なるファイルの往復検査と
全機能の移行完了を区別する。原記録を保存できたという理由で、未対応の利用者データを
正規化済みに扱ってはならない。

取得処理は上流への接続前に `begin_acquisition` を呼び、応答の原本を解釈前に
`record_acquisition_payload` で記録し、`complete_acquisition` で保存する。
同じ対象では後から開始した取得を優先する。後の取得を中止した場合も、先の取得を
自動的に復活させず、新しい要求で取り直す。端末の時計や応答の到着順では決めない。
開始時の現在版・更新世代が保存直前と違う場合も、その結果を現在版に適用しない。
別の対象の取得やお気に入りの操作では、この対象の取得を失効させない。

競合で不採用となった入力も、受信原本・本文・画像・添付と、それらを結ぶハッシュ付き
入力記録を保存する。中止・未完了の処理でも、既に受信して記録した原本は残す。
不採用・中止は作者の改稿や新しい保存版を作らない。保存の確定・現在版の切り替え・
取得の完了・outbox は一つのトランザクションで行い、失敗時にはまとめて巻き戻す。
同じ要求の完全一致する再送は以前の結果を返すが、現在版を以前へ戻さない。
スキーマ 3 はこれらの取得記録を追加する前方移行で、既存の原本や履歴を作り直さない。
単独の検証道具の `acquisition <新棚> <取得UUID>` で、状態と受信済み原本の参照を
再起動後も確認できる。これを既存の取得ジョブや画面へ接続する部分は残っている。

### 実データでの検証範囲

2026-11-08、稼働棚から独立した検証用コピーで、作品 4 件・作者/シリーズの
プロフィール保存状態 12 件・編集 2 件/104 ブロック・画像/添付の記録 51 件を確認した。
コピー内の元ファイル 83 件（完全一致を除くと 71 種類）について、元バイト列への復元と
SHA-256 の一致を確認した。記事 2 件は本文の JSON 構造、画像の順序、添付・リンク・
文字属性を比較し、保存日時 16 件、取得元タグ、編集の基準版も照合した。
元の棚と移行先を利用できない状態にしても、別ルートのバックアップだけで検証に成功した。
移行を再実行しても新しい履歴を重ねず、移行先 DB の論理データが変わらないことも確認した。
ファイルシステムからの全件照合でも、このコピー内の 83 パスすべてが元の一覧・ハッシュと
一致し、未解決ファイルは 0 件だった。除外理由の記録を追加した後も、再実行の不変性と
独立バックアップの検証に成功した。稼働棚全体の全件照合ではない。
確認状態の前方移行もこの独立コピーで検証した。作品 4 件のうち詳細確認日時のある 2 件と
未確認の 2 件が一致し、プロフィール 4 件の確認・取得日時を保った。原本・改稿履歴・
現在版・更新世代は変えず、再実行と別ルートのバックアップでも同じ状態を読み出せた。
共通読取 API は独立バックアップを使い、保存状態 16 件・編集 2 件から 119 件を所属指定で
書き出してハッシュを照合した。元の 83 パスにある 71 種類の元ファイルをすべて覆い、
本文・編集文書 6 件、記事の構造、編集 104 ブロックも一致した。別作品の保存状態の指定は
拒否し、この検証でライブラリの論理データを変更していない。

コレクション提案は別の独立コピーで 7 件・候補 108 件・プレビュー 98 ファイルを照合した。
採否、当時の表示名、選択、順番、根拠、名前候補が一致し、プレビューの元バイト列も
復元して SHA-256 を照合した。根拠と名前候補は元の JSON の字句を保持し、小数や未知の
属性を再解析して変えない。提案部分だけのコピーなので、作品の保存版を省いたことによる
未解決の記録は残す。提案の確認に成功したことを棚全体の切り替え完了とは扱わない。

これは一部の実データを使った保管・移行の確認であり、棚全体の移行完了、容量削減率、
読書画面や検索・書き出しの動作確認ではない。全件移行と各利用経路の確認は引き続き必要。

現在情報については別途、旧 DB の写しと保存原本 27,847 作品分を読み取り専用で照合した。
すべての原本に取得元タグと作者名の記録があり、現在の一覧情報と一致した。旧 DB の現在版番号も
すべて最新保存版と一致した。これは現在情報の整合性の確認であり、過去版・全ファイルの
移行と復元の全件検証ではない。

違反 0 件は現行データが壊れていることを意味しない。しかし、定義されていない関係は
この検査では検出できない。実コードとスキーマから確認できる課題は次のとおり。

| 現行の問題 | 具体的な箇所 | 新設計での解決 |
| --- | --- | --- |
| 作品・現在版・表示用集計・利用者状態が同じ行に入る | `downloads` の本文パス、作者名、版、favorite、容量等 | 永続的な作品、取得元の履歴、利用者状態、一覧用集計を分ける |

| 修復と作者の改稿が同じ版一覧に入る | `download_versions.change_kind` | 作者の改稿、取得観測、修復後の保存状態を分ける |
| 原本 JSON にしか過去のメタデータがない | 履歴行は過去のタグ・説明・作者関係を持たない | 各保存スナップショットに当時のメタデータと関係を持つ |
| 作者・シリーズの関係を複数系統で持つ | `download_relations` / `download_people` / `download_series` | 版に属する関係を一系統にし、表示用複製は派生と明示する |
| 参照先の存在・型・所有者を DB が保証しない関係がある | `entity_versions`、編集の `base_version`、文字列の source/key 等 | 型付きの実体と複合 FK によって所有関係まで制約する |
| ファイルの場所がデータの識別に使われる | `json_path` / `local_path` / `cover_path` | 論理 ID、元ファイルのハッシュ、物理配置を分離する |
| 改稿・同じファイル・保存状態の識別にハッシュが混在する | `content_hash`、meta_hash、原本ファイルの読込 | 目的・比較規則の版が明確な別々の指紋にする |
| お気に入りが棚と端末側の記録へ二重に反映される | `downloads.favorite` と server store の favorite_changes | 利用者状態の正本と変更記録を一つのトランザクションで確定する |
| schema 1 へ押し直す方式が形の変更を表さない | `CREATE IF NOT EXISTS` と不足列補完 | 順序付きマイグレーション、形式識別、対応する schema の範囲を導入する |

## 3. 分けるべき六つの概念

| 概念 | 意味 | 変更される例 |
| --- | --- | --- |
| 実体の識別 | どの作品・作者・シリーズか | 未保存作品の発見時に作る。保存を削除しても必要な参照は残る |
| 取得元の改稿 | 作者が内容を変えた一つの状態 | 本文・説明・タグ・表紙の差し替え等 |
| 取得観測 | いつ、どの経路から何を取得できたか | 再取得、取得不能、原寸の発見 |
| 保存スナップショット | その版について、その時点で何を保持できたか | 欠けた説明・画像の補完、再解釈 |
| 利用者の編集と状態 | 利用者が加えた内容・お気に入り・読書位置等 | 編集、整理、読み進めたとき |
| 元ファイルと物理保管 | 元バイト列、圧縮表現、保管場所 | 可逆圧縮、重複排除、ルート移動 |

例: 同じ版の表紙を 240px JPEG から原寸 PNG へ補完した場合、取得観測と保存
スナップショットを追加する。取得元の改稿は増やさない。さらにその PNG を Zstandard で
保管しても、元ファイルの ID と保存スナップショットは変わらない。

## 4. 識別子と正本

- 永続的なエンティティ、版、保存スナップショット、編集には UUIDv7 を使う。
  DB では 16 バイト BLOB、API では UUID 文字列とする。並び順を UUID の時刻に依存させない。
- ファイル・圧縮前の部分実体は SHA-256 を ID とし、32 バイト BLOB で持つ。
- `provider + entity_kind + external_key` は取得元の識別として一意にする。
  pixiv の小説 ID とイラスト ID、作者 ID を同じ名前空間として扱わない。
- ローカル取込はローカル名前空間と生成 ID を使う。URL がないことを欠損としない。
- 同じ作者名・似た作品名・同じ画像だけでは作品や作者を自動統合しない。
  サービスをまたぐ関係は明示的なリンクとして持つ。
- ローカルの SQLite 行番号、絶対パス、表示用の第何版という番号を外部参照に使わない。
- 取得時点の事実は不変の記録へ、現在の表示名や集計は再生成可能な表示用データへ置く。
  原本を変更せず、新しい解釈や補完は別のスナップショットにする。

## 5. 採用する論理スキーマ

以下の表名は新モデルの名前であり、旧表に同名の列を加えるという意味ではない。
各主キー・参照・一意条件を実装時の DDL と回帰テストへ落とし込む。

### 5.1 作品・作者・シリーズ・コレクション

| 表 | 正本として持つもの | 主な制約 |
| --- | --- | --- |
| `entities` | ID、種別、作成時刻、削除状態 | 種別は work/person/series/collection。ID と種別の組も UNIQUE |
| `external_identities` | 取得元・種別・外部キーと entity の対応 | provider/kind/key UNIQUE。entity の種別も複合 FK で一致 |
| `works` / `people` / `series` / `collections` | 種別固有の情報 | entity との 1 対 1、種別一致を DB 制約で保証 |
| `entity_current` | 作品・作者・シリーズの現在の snapshot | entity ごとに一行。同じ entity の公開済み snapshot を複合 FK で参照 |
| `library_items` | 保存している作品、ライブラリへ入れた時刻 | work ごとに一行。現在の保存状態の参照とは分ける |
| `collection_members` | 利用者が決めた所属と順番 | collection/work UNIQUE。未保存作品も works を参照できる |
| `work_links` / `link_evidence` | 作品間の関係と根拠 | from/to を work FK で参照。関係と複数の根拠を分ける |

`entities` は参照の共通の足場だけにする。作品の全項目を key/value へ詰める EAV 方式には
しない。作品削除はまず library_items とその保存参照を対象とし、コレクション等から参照
される作品の識別まで連鎖削除しない。完全削除は専用の処理として分ける。

### 5.2 改稿・保存状態・取得記録

| 表 | 正本として持つもの | 主な制約 |
| --- | --- | --- |
| `source_revisions` | entity、作者の変更として区別する版、発見時刻、順序 | entity/ordinal UNIQUE、entity/id UNIQUE。内容のハッシュだけに UNIQUE を付けない |
| `acquisition_observations` | entity、取得経路、元の取得時刻と今回の記録時刻、取得原本・入力本文・正規化した入力の file ID | 原本と入力は保管層 FK。観測と作品の所有者を一致させる |
| `revision_snapshots` | entity、source revision、時計と独立した連番、メタデータ、本文 file ID・形式・比較用指紋、解釈規則の版 | entity/revision の複合 FK。公開済み行は更新しない |
| `snapshot_observations` | snapshot を作る根拠となった観測 | 多対多。別 entity の観測を結び付けない |
| `snapshot_people` / `snapshot_series` | その保存時点の作者・シリーズ、役割・順序・表示名 | snapshot と people/series の FK。現在の作者名への追従と当時の名前を区別 |
| `tags` / `snapshot_tags` | その保存時点の取得元タグ | provider の識別・表示名を保持。snapshot/tag UNIQUE |
| `revision_snapshots.field_states_json` | その項目が既知・未取得・制限・解釈不能のどれか | 小さな状態の集合を snapshot 内に保持。空文字や NULL に状態を兼務させない |
| `snapshot_files` | 本文原本以外の添付・元 EPUB/PDF 等と役割 | snapshot、slot、file ID の FK。相対名を保持 |

同じ内容へ戻す改稿はあり得るので、内容ハッシュが同じという理由で履歴を潰さない。
初回保存と作者の差分が確認できたときに source revision を作る。同じ版の補完・原寸取得・
パーサーの改善では新しい snapshot を同じ source revision の下へ追加する。
同じ入力・同じ解釈の再取得は観測だけにできる。

欠損項目の補完は「未知→既知」として扱う。既知項目に作者側の変更があれば新しい改稿に
する。異なる取得経路が既知の値で矛盾する場合は自動で同じ版へ混ぜず、採用規則と根拠を
残して確認対象にする。比較できないことを「変更なし」に読み替えない。

スナップショットのタグ・説明・関係は、その時点の正本である。一覧用に現在値を複製しても
当時の値の代わりにしない。過去版検索も同じ snapshot を読む。

取得元の原本 JSON と、読書・検索で使う文書構造も区別する。原本はそのまま file として
保持し、解釈結果は規則版を持つブロック構造として保持する。画像の位置は元の記法から
snapshot の slot へ解決する。原本 JSON の絶対パスや取得 URL を新しい読書モデルの参照先にしない。
解釈規則を改善したときは新しい snapshot を作り、既存の編集の基準を差し替えない。

本文の保存形式と比較規則も分ける。本文の元バイト列のハッシュは復元確認に、
`body_semantic_hash` と規則版は本文の変化の比較に使う。小説の記法・字下げ・空白を
通常保存で削らず、記事ではブロック順・装飾・画像・リンク・添付の構造を保持する。
検索用の文章はそこから作る派生データとし、元の構造を置き換えない。

比較規則 v1 は改行の CRLF/LF、既知のプレビュー URL、アプリが注入した画像・添付の
`localPath` を表現の差として扱う。元の値とバイト列は原本・本文ファイルに残す。
未知の属性は比較から無条件に除外しない。途中までしか取れた本文は観測に保管し、
既知の完全な本文へ上書きしない。新しい比較規則は v1 の意味を変更せず、別の版として追加する。

保存日時は取得元の記録を UTC ミリ秒へ正規化し、移行処理を行った日時と区別する。
元の日時文字列も移行証跡に残す。履歴の順番・現在状態を日時の大小から決めず、連番と
明示的な参照で管理する。v1 の本文解釈と旧原本 JSON の読み込み上限は 16 MiB とし、
超過を正常な空本文へ置き換えず、未解決として止める。添付ファイルの保管上限とは分ける。

### 5.3 画像の識別・品質別ファイル・圧縮

| 表 | 持つもの | 主な制約 |
| --- | --- | --- |
| `source_media` | 取得元で同じ画像を表す ID。既知の比較キーと規則版 | 取得元/媒体種別/規則版/既知キー UNIQUE。未知は無理に共有しない |
| `media_renditions` | media、file ID、寸法、形式、原寸確認の有無、品質区分 | media と file は別々の FK。取得品質が不明なら unknown |
| `media_observations` | 取得 URL・経路・時刻・結果と rendition の対応 | URL を原本の ID やファイルの共有キーにしない |
| `snapshot_media` | snapshot 内の cover/inline/illustration 等の役割と安定した slot、media、採用 rendition | slot は snapshot 内で UNIQUE。media と rendition の対応も複合 FK で一致 |
| `content_files` | 元ファイルの SHA-256・長さ | 同じ元バイト列は一つ。名前や MIME は参照側で保持 |
| `file_chunks` | file 内の順番・offset・chunk ID | file/順番 UNIQUE。重複・隙間・長さ不一致を公開前に検査 |
| `chunks` | 元の部分実体の SHA-256・長さ | ハッシュで共有 |
| `chunk_storage` | chunk の raw/zstd 表現、格納量、相対配置、検査状態 | chunk と codec に対する表現を管理。再圧縮で chunk ID は変えない |

元ファイルのハッシュは「同じバイト列」の判定に限る。表紙の変化は source_media、
取得できた品質は rendition、圧縮は chunk_storage の変更として扱う。
rendition のファイルを後から別の内容で上書きしない。補完するときは新しい rendition と
snapshot を追加するため、過去に使った画像や編集の基準が勝手に変わらない。

共有する取得元の画像 ID・rendition・画像の観測・取得元タグの辞書も更新禁止にする。
snapshot の子行だけを固定しても、参照先の名前や画像情報の変更で過去の表示が変わるためである。
検証では元ファイルの SHA-256 に加え、本文の比較用指紋と、取得観測・関係・採用画像を
含む保存状態の構成用指紋を再計算する。ファイル単体が正常でも、参照の不一致は成功扱いにしない。

DB に画像や圧縮済み添付の大きな BLOB を詰め込まず、保管層の実体を参照する。
DB とファイルシステムは同じトランザクションではないため、保存操作記録によって確定と
回収を調整する。マニフェストはこの参照構造から生成する復元用の写しで、独立した正本にしない。

### 5.4 利用者が作るデータ

| 表 | 持つもの | 主な制約 |
| --- | --- | --- |
| `edit_documents` | work と編集中・適用中の編集への参照 | work/利用者で一行。active/draft は同じ work の編集を参照 |
| `edit_revisions` | 不変の編集内容、base snapshot ID、親編集 ID | base snapshot が同じ work に属する複合 FK |
| `edit_blocks` / `edit_media` | 編集ブロックの安定 ID・順序・参照画像 | block の画像は固定された file/rendition を参照。現在版の画像へ暗黙に差し替えない |
| `work_user_state` | お気に入りなど作品に対する状態 | 利用者/work UNIQUE。取得元のタグとは別にする |
| `user_tags` / `work_user_tags` | 利用者の付けた分類 | 取得元タグとは名前が同じでも区別 |
| `reading_positions` | work、snapshot または edit、ブロックと位置、端末、更新世代 | 内容の参照先が同じ work に属する。表示ページ番号だけに依存しない |
| `watch_targets` / `watch_groups` / `watch_group_members` | 作品・作者・シリーズの監視対象と利用者のまとめ | entity ID へ FK。種別の許可を検査 |
| `discovery_candidates` / `candidate_decisions` | 発見した作品、保留・拒否・保存の判断と理由 | ジョブとは独立。取得元側が再提示しなくても判断を保持 |

編集内容を公開した後は更新しない。下書きの保存も新しい edit revision として確定し、
draft の参照を移す。自動保存で同じ内容を再送した場合は冪等に処理する。
読書位置は未解決の旧ページ番号も移行証跡として保持し、確実に対応できない位置を推測して
新しい本文へ適用しない。改稿後の位置変換に失敗したら元の版で開けるようにする。

新しい位置は、原本テキストの UTF-8 境界、記事の固定されたブロック内の境界、または
編集ブロック UUID とその境界で表す。本文がない版、存在しないブロック、文字の途中、
別作品の版は拒否する。位置の消去は世代付きの記録として残し、古い要求の再送で復活させない。
位置と outbox は同時に確定し、送信元端末の時計で競合の勝者を選ばない。

### 5.5 派生データと運用データ

- `work_current_projection` は一覧用の題名・作者名・字数・論理容量・画像数等を持つ。
  正本ではなく、snapshot ID と生成規則の版で作り直せる。元ファイルを毎回読んで一覧を作らない。
- 検索索引・監査・AI ノートは入力 snapshot/edit ID、規則・モデルの版、処理世代を持つ。
  古い入力の処理完了が新しい状態を完了済みにしないよう、世代を比較して公開する。
- AI ノートの利用者による修正文は編集データとして別に保持し、再生成で失わない。
- ジョブとその項目・操作記録は ID と FK で結ぶ。ジョブ payload の JSON に正本の
  メタデータや作品の状態を重複して持たせない。外部入力の未解釈情報は JSON に残せる。
- 認証鍵、端末トークン、TLS 資材は引き続き機器側の領域に置く。作品 DB のバックアップや
  同期対象に無条件で混ぜない。

## 6. 制約・指紋・更新の確定

### DB 制約

新テーブルは原則 STRICT とし、全接続で foreign_keys を有効化する。
状態値は CHECK、個数・長さは非負、真偽は 0/1、ハッシュと UUID は型と長さを制約する。
重要な所有関係は存在の FK だけでなく、`work_id + snapshot_id` のような複合 FK を使う。
一つの current/active/draft を列への参照か部分 UNIQUE 索引で表し、アプリの慣習にしない。

公開済みの履歴・snapshot・ファイル参照は挿入のみとし、現在を指す参照と運用状態だけを
通常更新する。明示的な完全削除は別のトランザクションで行う。
制御された削除でも、共有ファイルを FK の CASCADE だけで物理削除しない。

### 指紋を用途別にする

| 指紋 | 入力 | 変化の意味 |
| --- | --- | --- |
| `source_semantic_fingerprint` | 既知の本文・題名・説明・タグ・関係・source_media の識別 | 作者側の変更の候補。欠損状態を含めて比較する |
| `metadata_probe_fingerprint` | 本文を取らず分かる項目と文字数、項目の取得状態 | 軽量な再取得判断。完全な改稿判定には使わない |
| `snapshot_manifest_hash` | snapshot に採用したメタデータ・参照ファイル・解釈規則 | 保持状態や解釈の変更。作者の改稿と同義ではない |
| `file_hash` / `chunk_hash` | 元バイト列 | 完全一致、復元検査、重複排除 |

取得 URL、圧縮 codec、物理パス、取得日時を作者の意味的な指紋へ入れない。
本文の表現は元の文字列を基本にし、意味が変わり得る空白・句読点を勝手に正規化しない。
各指紋には規則版を付け、別の規則版同士を直接比較しない。
同一 URL の内容差し替えは URL 由来のキーだけで保証できないため、表紙の既知形式の
正規化と定期的な原本再検証を組み合わせる。圧縮処理は公開元へ接続しない。

### 保存・補完・編集の一貫性

1. 公開元からの取得と大きなファイルの圧縮は DB の書き込みトランザクション外で行う。
2. 元ファイルの実体を検証して公開し、保存操作の予定と所有者を記録する。
3. 一つの短い DB トランザクションで観測・版・snapshot・参照・current・表示用データ・
   後処理通知を確定する。現在の世代が取得開始時と違えば比較し直し、盲目的に上書きしない。
4. DB 確定後に検索等の後処理とマニフェスト生成を行う。完了状態は処理した世代に限る。
5. DB 未確定の実体は復旧記録で保護し、回収時に確認する。確定済みなのにマニフェストが
   未作成なら DB から再生成する。全体を分散トランザクションに見せかけない。

画像の再取得と編集が同時に走っても、編集が参照する base snapshot は変えない。

読み取りは対象の entity と、公開済み snapshot または確定済み編集の ID を指定する。
本文・画像・添付は、その保存状態にある論理的な識別子で選ぶ。原応答は、その snapshot と
結び付いた取得記録の ID で選ぶ。ファイルのハッシュだけでは、この読み取り API を呼べない。
画像が未保存の場合は取得元の識別と欠損を返し、別の保存版の画像に置き換えない。
未保存の本文も、空の本文を保存した状態とは区別する。

本文の解釈形式、元の応答バイト列、画像の品質、MIME 型、元バイト列のハッシュは分けて返す。
記事の本文は構造を持つ JSON、編集は編集文書の JSON として読み、原応答とは呼ばない。
原応答は形式を推測して開かず、保持したバイト列として書き出す。大きな添付の部分読みは
選んだ元ファイルのバイト範囲に対して行い、復元や転送中は DB の錠を持ち続けない。
新規ファイルへの書き出しでは全体のハッシュを照合してから公開し、既存ファイルを上書きしない。

単独の検証道具では `resources <新棚> <対象UUID> snapshot|edit <保存状態UUID>` と
`export-resource` で照合できる。これは画面や HTTP 配信を新方式へ切り替えたことを意味しない。

## 7. 検索と性能の最適化

正規化は正本に適用し、表示のたびに多数の表を結合することは要求しない。
一覧・絞り込みは work_current_projection と現在関係の派生表から読み、
保存確定時に同じトランザクションで更新する。起動時に全件を作り直さない。

既定検索は現在 snapshot、履歴を含む検索は snapshot ID を返す。現在のタグで過去版を
絞り込んだように見せない。履歴検索は意味的な版と補完 snapshot の重複を整理し、
作品単位へ集約するが、ヒットした版を利用者が開ける情報を残す。

索引は実際の SQL・EXPLAIN QUERY PLAN と棚の写しの測定に基づいて設ける。
基本は current の並び順と keyset pagination、外部キーの子側、source の外部キー解決、
snapshot の所属、未処理ジョブ、参照される file/chunk の探索を優先する。
使わない列へ機械的に索引を付けず、同じ先頭列を持つ索引も削除前に実行計画を比較する。

WAL、単一の書き手と読み取りプールを継続する。各ドメインを別々の DB に分割して
原子的な更新を難しくすることはしない。検索索引、端末認証、再生成可能なキャッシュは
それぞれの責務で分離できる。容量削減を目的に、DB 全体を独自圧縮 VFS へ変更しない。

「高速化した」は測定後にだけ言う。現在の索引数やテーブル数が多いという理由だけで
削除しない。圧縮仕様の p95・メモリ条件に加え、保存・編集・現在版/過去版検索・
一覧・バックアップの時間と読み込むファイル数も比較する。

## 8. サーバーと利用者状態

データ形式・API の最低対応版を明示し、非対応の端末は接続時に更新を案内する。
サーバーへ SQLite ファイルをそのまま書き戻す仕組みを新モデルの更新プロトコルにしない。
新しい棚の導入時の完全なスナップショット転送と、その後の変更の転送を分ける。

初版の正本は一つの書き込み先サーバー（ローカル利用では内蔵）とする。
複数機が同時に取得元の履歴を増やす全面的な多重書き込みは導入しない。
UUID は多重書き込みの競合解決の代わりにはならない。

`work_user_state`・読書位置・所属等の変更は、本体の変更と送信用 outbox を同じ DB
トランザクションで確定する。各要求は request ID と期待する世代を持ち、再送しても
二重反映しない。サーバーの単調増加 sequence をカーソルとし、端末の時計だけで勝者を決めない。
古い世代の競合を返し、状態を取り直して利用者操作を再適用できるようにする。

削除は tombstone として配布する。カーソルの保持期限を過ぎた端末は完全な状態を
取り直す。すべての変更ログを永久に残すイベントソーシングは採用しない。
作品の正本と端末側の写しを別々に更新して後で帳尻を合わせる処理を減らす。

実体ハッシュを知っていることを閲覧権限とは扱わない。file/chunk の取得では、認証した
端末が参照できる作品・snapshot からその実体へ到達できることを検査する。
キャッシュはサーバーと端末登録の単位で分け、重複排除で権限境界を越えない。

## 9. 旧データの移行と不明データ

### スキーマの版

DB に SQLite application_id と user_version、ライブラリ UUID、保存形式版、
最低読取/書込版、適用済み migration の順序・チェックサムを持つ。
チェックサムではスキーマ定義の CRLF を LF に正規化し、チェックアウト環境の違いで
同じ定義の棚を拒否しない。定義そのものの変更は引き続き検出する。
既知の旧形式は読み取り用移行器だけで扱う。未知の DB・より新しい DB・部分破損は
自動初期化せず、理由を出して止める。履歴表の有無だけで同じ形式と判断しない。
今後は既存 migration を書き換えず、前方へ進む migration を追加する。
新形式のスキーマ 2 は提案の表を追加する前方移行として実装した。スキーマ 1 の実データの
検証用コピーを開き、ライブラリ ID・データの世代・既存の表・最初の移行記録を変えずに
追加できることを確認した。最低対応版と過去のチェックサムを照合してから DDL を実行し、
失敗時には一つのトランザクションで版番号と DDL を巻き戻す。
スキーマ 2 から 3 への更新も、前述の 4 作品の独立コピーで照合した。旧表の論理データ、
ライブラリ ID と世代、先の 2 件の移行記録を保ち、106 個のファイルが検証に成功した。
再度開いてもデータは変わらず、元のコピー側も変更していない。
スキーマ 4 は確認状態に `last_deep_checked_at` を追加する。取得元の公開・更新日時とは
別に扱い、プロフィールの既存の確認・取得日時から詳細確認を推測しない。
旧作品の値が不明なら NULL のままにし、解釈できない日時は移行の未解決として残す。
単独の検証道具の `source-state <新棚> <対象UUID>` で確認できる。

### 移行手順

1. 旧 DB と全ファイルの整合した移行元を固定する。既存の backup を消さない。
2. 別ルートへ新 DB と実体を構築し、旧整数 ID → 新 UUID の対応表を残す。
3. 取得元の識別から entity を割り当て、JSON と履歴行を読んで revision/snapshot/観測を作る。
4. タグ・作者・シリーズ・編集・候補への採否・監視・コレクション・AI ノート等を移す。
   読書位置や端末の登録情報を含む周辺 DB も、対象・非対象を一覧にして取りこぼさない。
5. 全元ファイルの復元ハッシュ、全論理レコードの対応、所有 FK、件数の差を検査する。
6. 新ライブラリ単独で読書・編集・履歴検索・バックアップ復元が成功してから切り替える。
7. 旧側の容量解放は別の明示操作にし、新側が未完成の間は旧データを消さない。

初回の移行先は空の新形式ライブラリに限る。作品に参照されていない元ファイルが登録済みの
場合も混在させない。再開では各表の原記録を照合し、移行後に通常の取得が進んだ棚へ旧履歴を
再適用しない。明示された旧現在版が復元した保存状態を指していることも検査し、不一致や
参照先の欠損は永続的な未解決項目として残す。最新らしい別の保存状態へ割り当てて完了にしない。

旧棚の `downloads`・`profiles`・`series`・`editor-assets`・`collection-covers`・
`templates`・`fonts` はファイルシステムからも走査する。DB に載っていないファイルも
原本として保持し、相対パスと元ハッシュを記録する。同じバイト列の別ファイルが移行済みでも、
そのパスの用途と所属が確認できなければ完了にしない。走査の間に変更されたファイルは
それぞれの内容を保持し、一致しない状態や前回から消えたファイルは未解決として残す。

管理領域外は除外理由を記録する。DB は各表の原記録として保存し、錠・動作ログ・
再生成できる索引やモデル・ブラウザーの認証情報は作品の原本に混ぜない。
`settings.json` と `server` は専用の移行ができるまで未解決とし、未知のルート項目も
未解決にする。これらの内容を推測して読み込んだり、認証情報ごと保管したりしない。
移行中は永続的な未完了の印を持ち、中止・異常終了した棚を完成扱いにしない。

旧パスの版判定は移行器にだけ残す。新形式の日常読み取りにパス推測を持ち込まない。
旧形式へ戻す目的で新旧モデルの二重書き込みはしない。

### 推測で履歴を変えない

- 既存の source 行は、初回保存か改稿の候補として元の順序を保持する。repair 行は、
  根拠が一致する場合だけ同じ source revision の追加 snapshot にする。
- 旧データの判定が不十分で修復か改稿か確定できなければ `legacy_unclassified` として
  全 snapshot と元の版番号・change_kind を残す。1,904 件を機械的に消してまとめない。
- 欠けた過去メタデータを現在値で埋めず、unknown とする。原本 JSON にあれば取り出す。
- 元 URL がないローカル画像も file として保持する。media の取得元が不明なら unknown。
- アセットの版や編集の基準を一意に決められない場合は、原ファイルを保ち移行の未解決項目に
  する。近い名前の版へ割り当てて完了にしない。
- 旧データにしかない未知の項目は旧原本と移行証跡へ保持し、黙って捨てない。

後方互換を捨てるとは新モデルを旧実装に合わせないという意味であり、欠損や推測を
許容して移行を成功扱いにするという意味ではない。

## 10. 完成条件と実装単位

実装 PR は次の順で分ける。仕様の策定だけで現行 DB のテーブルを入れ替えない。

1. 新スキーマの DDL、制約テスト、保存形式識別。外部キー・所有者・状態の不正を DB が拒否する。
2. 保管層と取得元の比較規則。URL の品質違い、部分取得、圧縮形式を区別する。
3. 新モデルを正本にした保存・読書・編集。過去 snapshot を不変に保つ。
4. 新モデルからの一覧用データ・検索・監査・履歴比較。検索結果が正しい版を開く。
5. サーバーと端末の対応版、利用者状態・outbox・冪等な再送。
6. 旧棚の移行器、全件照合、元ファイル書き出しとバックアップ復元。

少なくとも次の失敗をテストで防ぐ。

- 別作品の snapshot を現在版・編集基準・読書位置として指定できない。
- 他媒体の rendition を表紙へ混ぜられない。原寸補完と圧縮で作者の版が増えない。
- 修復で過去の表示・編集画像が変わらない。作者が元の内容へ戻した改稿が消えない。
- 一作品の削除が共有画像、別作品、編集、バックアップを破壊しない。
- 同じ要求の再送で改稿・お気に入り・所属が二重に反映されない。
- 古い解析結果が新しい snapshot の検索処理を完了済みにしない。
- 移行で unknown が現在値へ置き換わらず、過去版・編集・却下の判断が保存される。
- 旧 DB と新 DB の比較は表の行数の一致だけでなく、移行対応表を通した意味的な全件照合を行う。

新構造に関するすべての受け入れ条件と圧縮仕様の全件往復検証を満たしてから、本番の棚への
移行を提供する。DB サイズ・速度の改善量はその検証で報告し、設計だけで削減率を約束しない。
