#### P3-01 `retry_after` に上限が無い（`Instant + Duration` の panic と実質の停止）
- ファイル:行: src-tauri/src/downloader/pacing.rs:19-22, 28-45（呼び出し: pixiv_api/aapi.rs:139、pixiv_api/web.rs:510、pixiv_api/token_manager.rs:140、fanbox_api/client.rs:142）
- 何が起きるか: `Retry-After` の値を `u64` のまま秒にして `defer` へ渡す。`Duration::from_secs(u64::MAX)` を `Instant::now() +` すると panic する。panic しない大きな値（数年）でも `wait()` が門の Mutex を持ったまま `sleep_until` するので、その取得元への全要求が止まり、`defer` 自身も同じ Mutex を待つ。一時停止・中止も、いま門で待っている要求には届かない。
- 根拠: CONFIRMED（コードの読み。実際にそういう値を返す相手は未確認）。`.max(5)` の下限はあるが上限が無い。
- 重大度: 停止
- 直し方の案: `Duration::from_secs(seconds.clamp(5, 600))` のように上限を置く（再試行の最大待ちは update_jobs.rs の `MAX_RATE_LIMIT_BACKOFF_MS`=5 分と揃える）。上限を超える指定は「その取得元は今は無理」として呼び出し側へ誤りで返す。試験を足す。
- 同種の探索: `retry_after`・`Retry-After` を grep → 呼び出しは上の 4 箇所だけで全部同じ関数を通る。他に外部の値をそのまま待ちにしている所は見つからず。

#### P3-02 `index_existing_assets_in_other_versions` が実行時に OS の TEMP 全体を走査する
