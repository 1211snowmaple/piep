## 指摘

### N-01 接続設定の保存で、新しい設定を書いたあとに試験の印を書く（落ちると戻らない）
- ファイル:行: `src-tauri/src/server/standalone.rs:412-419`（`save_connection`）
- 何が起きるか: `config_previous` → `config`（新）→ `config_trial` の順に書く。新しい設定を書いたあと、印を書く前に落ちる（あるいは印の書き込みだけが失敗して Err になる）と、試験の印が無いまま新しい設定が有効になる。新しい設定で起動できなければ `restore_trial` が働かないので、管理画面から直せない（管理画面自体が上がらない）。印を書く失敗は呼び手には「refused」として見え、設定ファイルだけが変わっている。
- 根拠: CONFIRMED（コードの順序）。落ちる確率は小さい。
- 重大度: 停止
- 直し方: previous → trial → config の順にする。trial を書けなければ config に触らない。
- 同種の探索: `write_atomic(` を server 内で全部挙げ、複数ファイルを順に書く 4 か所（`save_connection`、`roll_back`、`switch_to_pending`、`place_programs`）を確かめた。後の三つは「印→本体」の順か、再開できる順で問題なし。

### N-02 `restore_trial` が戻しに失敗しても印を消す。戻しも atomic でない
- ファイル:行: `standalone.rs:422-427`
- 何が起きるか: `fs::copy(previous, config)` が失敗（previous が無い・ロック）しても `remove_file(trial)` を実行する。失敗した設定が残ったまま、次の起動からは試験の印が無いので二度と戻されない。`fs::copy` は上書きの途中で落ちると設定が欠ける。
- 根拠: CONFIRMED。
- 重大度: 停止（二重の失敗が要る）
- 直し方: コピーは一時ファイル→rename（`write_atomic`）にし、成功したときだけ印を消す。失敗は戻り値で呼び手へ返す（今は bool）。
- 同種の探索: `fs::copy` を server 内で検索し、`place_programs`・`restore_databases` は一時名経由か、別の理由で許容。

### N-03 自己署名の証明書と鍵を続けて書き、間で落ちると二度と起動できない
- ファイル:行: `src-tauri/src/server/tls.rs:44-63`（報告の行番号 94-116 は main と合わないので主担当が直した）
- 何が起きるか: 証明書（111 行）→鍵（113 行）の順に `fs::write`。間で落ちる・鍵の書き込みに失敗すると `cert.exists() != key.exists()` で「自動では作り直しません」の Err が出続け、サーバーが起動しない（見張り役は再起動を繰り返す）。直し方（どれを消すか）も文言にない。書き込み自体も途中の切れた PEM を残しうる（空・半端な証明書は `pem_fingerprint` の Err で同じ結果）。
- 根拠: CONFIRMED（コード）。頻度は低い。
- 重大度: 停止
- 直し方: 一時ファイルに両方を書いて fsync し、鍵→証明書の順で rename（片方だけ残る状態を作らない）。欠けているときの文言に「この二つのファイルを消すと作り直す（登録済みの端末は登録し直しになる）」と書く。
- 同種の探索: 秘密を書くファイルは server 内でここだけ（`fs::write` を検索）。`install` の `task.xml` は一時物。
- 追記（安1）: 秘密鍵の書き込みに権限の指定が無い。`install` なら置き場の ACL（保護された DACL）が効くが、`init`/`serve` で利用者の置き場を使うと、フォルダーの既定の権限のまま。

### N-04 戻しの失敗で見張り役が終了する（サーバーが上がらなくなる）
- ファイル:行: `src-tauri/src/server/watchdog.rs:387-390, 399-401, 416, 430-431`（`fail_update(...)?`、`resume_rollback(paths)?`、`resume_requested_rollback(paths)?`）
- 何が起きるか: `roll_back` は `restore_databases`（DB の置き換え。Windows ではウイルス対策などが `state.db` を掴んでいると失敗しうる）や `write_atomic` の失敗で Err を返す。`run` はそれを `?` で外へ返すので、見張り役が終了し、サーバーも立ち上がらない。再起動してくれるのは起動タスク（`RestartOnFailure` 1 分 × 3 回）だけで、その後は手動。`rollback-version` の印が残るので同じ失敗を繰り返す。更新に失敗した版を戻す場面（=一番助けが要る場面）で、一時的な失敗が全体の停止になる。
- 根拠: CONFIRMED（コードの流れ）。実環境で起きる頻度は推定。
- 重大度: 停止
- 直し方: 戻しの Err は `note` に残し、間隔を置いて再試行する（Backoff を使う）。失敗中に新しい版を起動し直さない保証（印）は今のままでよい。
- 同種の探索: `watchdog::run` の `?` は 8 か所。起動前の `resume_*`（387-388）と `fail_update`（400・416）が当てはまる。`spawn_body` の失敗は backoff で続く。

### N-05 更新の起動確認の 60 秒に、棚の DB の完全な検査が入っている
- ファイル:行: `watchdog.rs:19, 408`（`READY_LIMIT` 60 秒）と `standalone.rs:696-703`（`PRAGMA quick_check(1)` を ready の前に実行）
- 何が起きるか: 準備の印は `hello` の応答後に DB の検査を終えてから書く。検査はファイル全体を読むので、大きな棚（数 GB）や遅いディスクでは 60 秒を超え、更新が「応答しませんでした」で戻され、その版が `skipped`（もう試さない）に入る。
- 根拠: 推定（実棚の DB の大きさでの `quick_check` の所要時間は未測定。読み取りだけで測れる）。
- 重大度: 停止（更新が不要に失敗する）・誤った表示
- 直し方: 検査は印を書いたあとに回す（検査の失敗は別の記録で知らせる）か、READY_LIMIT を印を待つ処理と検査で分ける。測った値を台帳に書く。
- 同種の探索: `READY_LIMIT`・50 秒の `report_ready` の待ち（standalone.rs:690）・install の `wait_for_ready` 60 秒（install.rs:386）が同じ前提。

### N-06 更新の履歴が 50 件に達すると、起動のたびに「更新した」の記録が増える
- ファイル:行: `standalone.rs:724-745`（`history.entries.len() > before || history.entries.len() == 50`）
- 何が起きるか: 上限 50 件で `before == 50` なら、何も足されていなくても `len()==50` が真になり、先頭の一件を監査記録に書き直す。以降は起動（再起動・見張り役の立ち上げ直し）のたびに同じ「更新した」「失敗して戻した」が記録に溜まる。
- 根拠: CONFIRMED（条件式）。
- 重大度: 誤った表示（記録の汚れ）
- 直し方: 追加の有無を `reconcile` が返す（件数でなく bool）。切り詰めを考えるなら先頭の `at` の比較にする。
- 同種の探索: `HISTORY_LIMIT` を使う箇所は `push` のみ。ほかの「件数が等しい」判定は無し。

### N-07 入れ直しの途中で失敗すると、止めたサーバーが戻らない
- ファイル:行: `install.rs:446-451, 245, 268-288`
- 何が起きるか: `secure_install_root`（断るなら止める前に断る、というコメントがある）のあと `stop_task()` で動いているサーバーを止め、その後の `lay_out` → `place_programs` → `clear_install_transitions` で「前のバージョンへの復旧が残っています」の Err などを返すと、タスクは再登録されず、サーバーは止まったまま。利用者は窓の文言を読んで入れ直せるが、その間（と見なかったとき）携帯が読めない。
- 根拠: CONFIRMED（順序）。
- 重大度: 停止（利用者が気づけば直せる）
- 直し方: 復旧の印の検査と DLL の置き換えの下調べを `stop_task` の前に出す。失敗時は `schtasks /Run` で戻す。
- 同種の探索: `command_uninstall` は止めたあと消すだけで問題なし。

### N-10 ログインの待ちが並列に抜けられる
