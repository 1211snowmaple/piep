# 更新管理の改善 — 提案レポート

実施日: 2026-08-16

## 実運用で見つかった 2 件の不具合（2026-08-17 調査・修正）

### ① 「10 / 10件を処理 · 候補 101」— 数字は整合しているが、意味が伝わっていなかった

`totals` / `processed` は **候補を除いた項目**（監視作品と監視対象）だけを数えていた（`sync_update_job_counters`）。
つまり「10 / 10」は**監視対象を10件確認し終えた**という意味で、そこから 101 件の候補が見つかった、という表示だった。

ただし、これは**表示の不具合でもあった**。候補は「保存する」と決めた時点で待機列に入り、ワーカーが順に処理する
（`next_update_job_item` は候補も拾う）。にもかかわらず総数から外れていたため、**自動保存モードで 101 件を保存している
最中でも進捗は 10/10（＝完了）と表示され続けた**。

→ 待機列に入った候補を総数と処理済みに数えるよう修正。見つけただけの候補は「作業」ではないので数えない。

### ② 一度出た候補が、チェックを外すと二度と出てこない

**再現する筋道が特定できた。**

1. 作者を走査するとき、`fetch_pixiv_user_novels_since` は一覧を新しい順に辿り、
   **前回位置（`last_seen_source_id`）に当たったところで打ち切る**。
2. 走査の最後に `mark_update_target_checked` が、**一覧の先頭（最新作）の ID を前回位置として記録する**。
   保存したかどうかは見ていない。
3. 候補は `update_job_items` に入る＝**そのジョブの持ち物**で、次のジョブには引き継がれない。

結果、「一度候補に出た最新作」を保存しないまま次の確認をすると、一覧はその作品より新しいものしか返さず、
候補も引き継がれないため、**その作品は二度と現れない**。チェックを外した＝「今は選ばない」だけのつもりが、
永久に取りこぼす操作になっていた。

→ **候補をジョブから独立させた**（`update_candidates` テーブル）。保存も拒否もされていない候補は、
次のジョブの開始時に自動で戻ってくる。あわせて「今後この作品は出さない」という明示の操作（取り消し可）を追加し、
無視すると決めたものだけが出なくなるようにした。

| 状態 | いつ消えるか |
|---|---|
| pending（決めていない） | 保存されたとき／「今後は出さない」を選んだとき |
| dismissed（無視すると決めた） | 「すべて解除」で pending に戻すまで残る |

## 実装したもの（2026-08-17）— A-1

`downloads` に 2 列を足した（既存のライブラリには起動時に自動で追加される）。

| 列 | 中身 |
|---|---|
| `meta_hash` | 本文を除いたメタデータの指紋（題・キャプション・表紙URL・タグ・シリーズ・**文字数**の SHA-256） |
| `last_deep_checked_at` | 最後に本文まで突き合わせた時刻 |

更新確認は次の順になった。

```
① 詳細だけ取得（本文なし）        … 1リクエスト
② 指紋が一致 かつ 深い確認が14日以内 → スキップ（ここで終わり）
③ そうでなければ本文を取得        … 従来どおりハッシュで版を判定
```

**取りこぼしを明記する。** 文字数が1字も変わらない修正（誤字の置換、句読点の差し替えなど）は指紋に現れない。
これに対処するため `DEEP_CHECK_INTERVAL_DAYS = 14` を置き、**指紋が同じでも14日を過ぎていれば必ず本文まで取りに行く**。
取りこぼしうるのは「14日以内の、文字数が変わらない改稿」だけで、それも次の深い確認で必ず拾われる。
`meta_hash` を作れない形で保存された作品（文字数を持たない取得経路）は指紋が NULL のままになり、従来どおり毎回本文まで確認する。

実装中に見つけた不具合も直した: 保存する JSON は表紙 URL を 2 つ持つ（最上位＝原寸優先で選び直したもの、`detail`＝詳細 API の large）。
最初の実装は最上位を先に読んでいたため、更新確認が受け取る `detail` 側と永久に一致せず、短絡が一度も効かなかった。
指紋は必ず `detail` から作るようにし、その前提をテスト（`the_saved_work_and_the_fetched_detail_agree_on_one_signature`）で固定した。

検証: `commands::downloader::pixiv_meta_signature_tests`（保存側と確認側の一致、変化の検出、取りこぼしの明文化、指紋なしの扱い）と
`database::schema::tests::an_existing_library_gains_the_columns_added_later`（既存ライブラリへの列追加）。

## 1. いまどう動いているか

### 1-1. 監視の 2 系統

| 系統 | 何を追うか | どこに記録 | 誰が有効にするか |
|---|---|---|---|
| 作品の監視 | 保存済み作品の**改稿** | `downloads.watch_updates` | カードの監視ボタン |
| 対象の監視 | 作者・シリーズの**新作** | `update_targets` | 更新センターの追加フォーム、作者／シリーズ画面 |

### 1-2. ジョブの流れ

```
start_update_job(scope, mode, concurrency)
  └ build_initial_items … work / target の作業項目を作る
      └ ワーカー（項目ごとに 800ms 間隔）
          ├ work   : 保存済み作品を取り直し、変わっていれば新しい版として保存
          ├ target : 作者・シリーズの一覧を last_seen_source_id 以降だけ取得し、未保存の作品を候補に積む
          └ candidate: （auto_save のとき、または利用者が選んで保存を押したとき）候補を保存
```

- 状態は `queued / running / paused / auth_required / canceling / canceled / completed / failed`。
- 認証切れは項目を消費せずに `auth_required` で止まる（再接続後に再開できる）。
- アプリ終了で中断されたジョブは、起動時に `paused`（「前回の起動中に中断されました」）へ回収される。
- 同時実行の既定は 取得 3 / 保存 2 / 一覧取得 1。

### 1-3. 変更の検知（実測）

`compute_content_details`（`downloader.rs`）が算出するもの:

| 取得元 | ハッシュの材料 | `source_updated_at` |
|---|---|---|
| pixiv | タイトル・キャプション・表紙 URL・タグ・シリーズ ID・**本文** の SHA-256 | **常に `None`** |
| FANBOX | 本文ブロックのテキスト（無ければ JSON 全体） | `updatedDatetime` |

保存側は `hash_changed || updated_changed` で版を上げる。**この判定は精度が高い。**

一方、更新ジョブ側の事前判定はこうなっている（`process_work_item`）。

```rust
// pixiv
let metadata = fetch_pixiv_novel_metadata(...).await?;           // ① 1 リクエスト
let metadata_updated_at = string_at(&metadata_value, &[&["create_date"], ...]);
if dl.source_updated_at == metadata_updated_at && dl.source_updated_at.is_some() {
    return Ok(ItemOutcome::Skipped(...));                        // ← pixiv では成立しない
}
let data = fetch_pixiv_novel(...).await?;                        // ② もう 1 リクエスト
```

`dl.source_updated_at` は pixiv では常に `None` なので、**この短絡は一度も成立しない**。しかも比較しようとしている `create_date` は投稿日であって改稿日ではない。結果として、監視中の pixiv 作品 1 件につき毎回 2 リクエストが飛び、そのうち 1 本は無駄になっている。

## 3. 改善案

### A. 検知の精度と効率

#### A-1. pixiv の軽量シグネチャで本文取得を省く（U2）

`PixivNovelDetail`（`fetch_pixiv_novel_metadata` の戻り値）は、本文以外のハッシュ材料を**すべて**持っている。

```rust
pub struct PixivNovelDetail {
    pub id, pub title, pub user, pub tags, pub caption,
    pub create_date, pub text_length,   // ← 文字数まで分かる
    pub series_id, pub series_title, pub cover_url,
}
```

`downloads` に `meta_hash TEXT` を足し、`sha256(title|caption|cover_url|tags|series_id|text_length)` を保存する。更新確認は次の順になる。

```
① メタデータ取得（1 リクエスト）
② meta_hash が一致 → Skipped（本文は取りに行かない）
③ 不一致 → 本文取得 → 従来どおり content_hash で版を判定
```

- **効果**: 変わっていない pixiv 作品の確認が 2 リクエスト → 1 リクエストになる。監視 500 件なら 500 リクエストの削減。
- **取りこぼし**: 「文字数が 1 字も変わらない修正（誤字直しの置換など）」は検知できない。対策として `last_deep_checked_at` を持ち、**14 日に一度は本文まで取りに行く**（設定可能）。
- **FANBOX** は `updatedDatetime` で既に 1 リクエストで済んでいるため変更不要。

#### A-2. 「何が変わったか」を候補と履歴に出す（U5）

版は `download_versions` に残っており、`text_length` も版ごとに持っている。候補の副題を次のように作れる。

```
星を編む人 第十三話 ・ 改稿（+1,240字 / 章 +1）・ 前回保存 2026-05-02
```

- 差分の算出は保存時（`download_and_save` が版を上げるとき）に `text_length` と章数の差を `update_job_items.payload_json` に積むだけで足りる。
- さらに踏み込むなら、版どうしの本文差分（行単位）を作品ページの履歴タブで表示する（C-2）。

#### A-3. 作者・シリーズ走査で既存作品の改稿も拾う（U4）

現在は `get_download_by_source(...).is_some()` で既存作品を候補から外している。ここを次の三分岐にする。

```rust
match state.db.get_download_by_source(&source, &source_id)? {
    None => 候補（新作）,
    Some(dl) if 一覧の更新日時 > dl.source_updated_at => 候補（改稿）,
    Some(_) => スキップ,
}
```

FANBOX の投稿一覧は `updatedDatetime` を持つので即座に効く。pixiv の一覧は投稿日しか持たないため、**pixiv では「監視オンの作品」経路のまま**とし、A-1 と合わせて効率を上げる。

#### A-4. 監視対象の自動登録（U3）

- 作品を保存したとき、その作者とシリーズを**監視候補**として提示する（保存完了の通知から 1 クリックで登録）。
- シリーズの一部を保存したら、そのシリーズは自動で監視対象にする（`updateWorkflow.ts` に同趣旨の実装が既にある）。
- 設定に「保存した作品を自動で監視する」（既定オフ）。オンなら `watch_updates` を保存時に立てる。

#### A-5. 削除・非公開の検知（U7 の一部）

404 / 非公開エラーを**失敗ではなく状態**として扱い、`downloads` に `source_status`（`available` / `missing` / `restricted`）を持たせる。ライブラリのカードに小さな印を出し、更新確認の対象から自動で外す（手動で再確認できる）。これは「消えた作品を手元に残しておく」という piep の目的に直接効く。

### B. 自動化と通知

#### B-1. スケジュール実行（U1）

```
設定 › 更新
  [ ] アプリの起動時に確認する
  [ ] 定期的に確認する   間隔: 6時間 / 12時間 / 1日 / 3日
      実行時の動作: 確認のみ / 自動保存
      同時実行数: （既存の 3 段）
```

実装は Rust 側に 1 本のタイマータスクを置き、最終実行時刻を `app_settings` に保存する。**アプリを開いていない間に溜まった分は、起動時に 1 回だけ実行する**（起動のたびに何度も走らせない）。既存の `active_jobs()` ガードにより、手動ジョブと重なっても二重起動はしない。

#### B-2. OS 通知とトレイ（U6）

- `tauri-plugin-notification` を追加し、ジョブ完了時に「新しい候補 3 件」を OS の通知として出す。クリックで更新センターを開く。
- 常駐（トレイ）は piep の性格（開いて使うアプリ）に合わないため、**トレイ常駐は採らない**。通知は「アプリが起動している間」に限る。

#### B-3. レート配慮の自動調整（U7）

- 429 / 5xx を受けたら、その取得元への間隔を指数的に伸ばす（800ms → 1.6s → 3.2s、上限 30s）。成功が続いたら戻す。
- 1 ジョブあたりのリクエスト上限（既定 2,000）を設け、超えたら「続きは次回」として安全に打ち切る。打ち切り位置は `update_job_items` の状態に残るので、次回はそこから再開できる。

#### B-4. 自動保存の安全弁

- `auto_save` モードで一度に保存する件数の上限（既定 50）。超えた分は候補のまま残す。
- 連続 5 件の保存失敗でジョブを `paused` にする（現在の認証切れと同じ扱い）。

### C. 見せ方と操作

#### C-1. 候補を種類で分ける（U5）

いまは候補が 1 つの平らな一覧になっている。**新作 / 改稿 / 続編**の 3 分類に分け、それぞれに件数バッジと一括選択を置く。分類は `targetType`（work / author / series）と A-2 の差分情報から作れる。

#### C-2. 差分ビュー

作品ページの履歴タブから、版どうしの本文差分を見る。既に `download_versions` にテキストがあり、ブロックエディタ（`work_edit_blocks`）も持っているため、行単位の差分表示は追加のデータ取得なしで作れる。**「改稿を追う」機能の価値は、差分が見えて初めて完成する。**

#### C-3. 監視対象の健康表示（U8）

一覧の各行に、最終確認・**最後に新作を見つけた日**・連続エラー回数・次回予定を出す。
1 年以上ヒットのない対象は「休眠」として畳み、確認間隔を自動で伸ばす（D-3）。

#### C-4. ジョブセンターへの統合

`src/features/jobs/operationJobs.ts` が EPUB 書き出しや保存の進捗を扱っている。更新ジョブだけが別の画面に閉じているので、**進行中の作業は 1 か所に集める**（更新センターは「対象の管理と候補の選別」に専念する）。

#### C-5. 棚・保存検索を対象にする（U11）

`scope` に `shelf`（お気に入り・読みかけ・更新監視）と `saved_search` を足す。`saved_searches` は既にテーブルがあるので、対象の組み立て（`build_initial_items`）で検索を実行して作品 ID を集めるだけで済む。

### D. 運用の健全性

#### D-1. 履歴の自動整理（U9）
完了したジョブは 30 日または 50 件を超えた分から削除する（起動時に 1 回）。ログは 1 ジョブあたり 2,000 行で頭を落とす。

#### D-2. ポーリングの見直し（U10）
`update-job-progress` イベントが来ている間はポーリングを止め、**イベントが 5 秒来ないときだけ**スナップショットを取りに行く（取りこぼしの保険としてのポーリング）。

#### D-3. 適応間隔
対象ごとに「更新の来る頻度」を学習し、確認間隔を変える。毎日更新するクリエイターは毎回、年に一度の作者は週 1 回。`update_targets.metadata_json`（現在未使用）に直近のヒット間隔を持たせれば、スキーマ変更なしで実装できる。

## 4. 優先順位

| 順 | 案 | 理由 | 概算 |
|---|---|---|---|
| 1 | **A-1**（pixiv の軽量確認） | 誤りに近い挙動の是正。相手先への負荷が半減し、確認時間も縮む | 1 日（DB 列 1 本追加） |
| 2 | **B-1**（スケジュール実行） | 「追う」が自動で回り始める。U1 は機能全体の前提 | 1.5 日 |
| 3 | **A-2 + C-1**（差分の要約と候補の分類） | 候補を選ぶ判断ができるようになる | 1.5 日 |
| 4 | **A-4**（監視の自動登録） | 監視対象が増えないと自動化が空回りする | 半日 |
| 5 | **B-2**（OS 通知） | 自動実行の結果が届く | 半日 |
| 6 | **A-3 / A-5**（既存作品の改稿・削除検知） | 取りこぼしの解消 | 1.5 日 |
| 7 | **C-3 / D-1 / D-2 / D-3**（健全性） | 長く使ったときに効く | 1.5 日 |
| 8 | **C-2**（差分ビュー） | 価値は高いが独立した機能。単独で計画してよい | 2〜3 日 |
| 9 | **B-3 / B-4 / C-4 / C-5** | 規模が大きくなってから | 各 0.5〜1 日 |

1〜5 まで（およそ 5 日）で、「登録しなくても監視対象が増え、放っておいても確認が回り、結果が通知で届き、候補は中身を見て選べる」という状態になる。
