# AI 補助の方針

利用者が明示的に設定したときだけ、外部のモデルに手伝わせる。piep の中心は
「手元に残して読む」ことなので、AI はその邪魔をしない範囲でだけ働く。

## β版として提供する

AI補助と意味検索はβ版の機能として、入口のメニューと設定画面に明示する。
アプリの版とは分けて扱い、有効化は利用者が選ぶ。モデルの応答や構造検査が通っても、
意味品質の合格とは扱わない。特にあらすじの網羅性とタグの意味判定は未確立で、
設定画面に原文・根拠の確認が必要なことを示す。
機能がない画面でも入口から対応する画面と設定への道を案内する。

## 既定で無効

有効にするのは利用者である。外部宛先は HTTPS に限り、**宛先ごとに同意を取る**。
一度どこかを許したことが、別の宛先を許したことにはならない。

対応する接続先は、認証の要らないローカルの OpenAI 互換サーバーか、認証の要らない
HTTPS 先に限る。

## 平文の鍵を持たない

設定 JSON にもリクエストの型にも API キーの置き場を作らない。鍵が要る接続先に
対応するなら、OS の資格情報ストアを入れる別の変更として扱う。**平文の置き場を
一つ作ると、そこが唯一の置き場になる。**

## 機能ごとに分ける

AI 補助は <!--stat:assist.features-->7<!--/stat--> の機能に分かれている。機能ごとに、
有効化・モデル・追加指示・送信する項目・件数の上限を設定できる。

| 機能 | 何をするか |
|---|---|
| `collection_naming` | コレクションの名前を考える |
| `collection_split` | 一つの束を分けるべきか見る |
| `work_tagging` | タグを補う |
| `work_synopsis` | あらすじを書く |
| `author_style` | 対象作品のタグを数えて題材メモを作る（モデル呼出しなし） |
| `search_interpretation` | 「言葉で探す」の意図を整理する |
| `reader_recap` | 前の作品を思い出す |

一括の有効化にしないのは、送る中身が機能ごとに違うためである。あらすじは本文を
送るが、コレクションの命名は許可された題名・公式シリーズ・作者・タグを使う。
題名を送らない設定なら公式シリーズも送らない。同じ同意で扱ってよいものではない。

タグ補完では概要の送信は既定でオフにする。概要を送らない場合は、送信を許可した
題名と既存タグの範囲で候補を探す。送っていない本文の内容を評価の正解にしない。
保存済みの入力設定が一部だけでも、未指定項目には機能の既定値を補い、概要の送信を
意図せず有効にしない。明示的な送信許可・不許可は保持する。

## 追加指示は、契約を上書きできない

利用者が書いた追加指示は、**固定の JSON 契約と安全規則の後ろに置く**。前に置くと、
出力の形や送信の制限を指示で壊せてしまう。

## 試していないモデルは走らせない

共通のモデルと違うモデルを機能ごとに指定できるが、**その接続先とそのモデルで一度
試験が通るまで実行しない**。動くかどうか分からないモデルに本文を送っても、失敗の
形が分からないだけである。

## 生成物には出どころを付ける

タグ補完は候補ごとに支持・不支持・不明を判定し、支持された候補だけを返す。
根拠はモデルに引用を書かせず、存在を検証した文番号から原文を表示する。選ばれた
根拠文は全文を表示し、文末の否定や対象範囲を文字数の上限で隠さない。候補は
棚の使用頻度順である。24件を超える場合は概要の作品内容と編集指示をモデルで
判別し、候補選択・明示語・頻出24語を合わせて絞る。その後6件ずつ判定する。
利用者は「タグ名：条件」を一行ずつ指定できる。条件は分類基準であり、個々の作品の
正解指定として扱わない。指定があれば一候補ずつ判定し、条件付きの候補は候補選択で
落とさない。返すのは
元の候補順で最大5件である。内容判別と候補選択もモデルの判断なので、完全な
注入防止や全候補の網羅は保証しない。文番号が
正しくても、タグを意味的に支持するとは限らないため、採用は利用者が決める。

「棚の併用候補」は別の操作で、棚にある他作品の取得元タグの併用統計から候補を出す。
候補作成には本文・概要の読取やモデル接続を使わない。共起はこの作品への適合根拠ではないため、
採用ボタンを押すまでは何も変更しない。採用したタグには手動の印を付け、一覧でモデル採用タグと
区別する。手動タグは手動用の操作で外し、取得元のタグは外さない。
集計は対象作品自身と同じ取得元・同じ非空の作者IDの作品を除き、手動・モデル採用タグは
集計に加えない。作者IDが不明なら作者単位の除外はできない。2作品以上で併用された候補を
最大5件表示し、共通タグを持つ対象作品数Nと、そのうち候補を併用する作品数Mを示す。
タグ保存後の通常の検索索引更新だけが失敗した場合、保存済みの状態をエラーに明記し、
画面は実際のタグを再取得する。索引更新には通常の本文読取があり得る。

作者メモはモデル呼出しを行わないネイティブ例外である。現在の作者範囲から題名・タグだけを
一度のDB読取で集め、本文や概要は読まない。作品ごとに重複タグを一回だけ数え、設定の
`maxTagsPerItem` までを対象にする（既定30、最大100）。指定された `maxItems` があれば直近順で
その件数を対象にする。現在の設定画面の既定は200件なので、200件を超える作者では全件表示では
なく対象N/全M作品と分母を表示する。`maxItems` が未指定なら対象範囲全体を集計する。題材の
上位タグと件数を示し、タグが使えない場合は題名の引用例だけを示す。
題材の観測に限り、文体や作者の全作品の傾向を推定しない。

検索のタグ条件は「すべて」または「いずれか」を保持する。未知語・時期・人物の範囲は
検索文に残す。既存条件との結合でAND/ORや除外の意味が変わる場合は適用を止めて示す。
期間や登場人物の条件が厳密なデータベース絞り込みになったと誤表示しない。

命名は18文字・説明30文字の生成契約を検査し、超過した名前を途中で切って採用しない。
分割は共通語が対象の2作品以上に実在することと、全案の位置の一意性を検査する。
不正な位置を黙って取り除いて別のグループに作り変えない。未分類の作品は残せる。

あらすじと前回のあらすじは、原文の文を選ぶ抽出方式を使う。入力が上限内なら作品内容の
文をすべて残し、出力命令との判別だけをする。長文ではモデルが重要な事実ごとに1〜3文の
まとまりを優先順で返し、アプリがまとまり単位で通常300文字・8文まで採用して原文順に戻す。
本文は最初に一度だけ文へ分け、元の文番号と文の内容を階層要約の各段階で維持する。
統合入力には元本文で連続する範囲も示す。選択された抜粋を再分割・再採番せず、
モデルの選択で途中に落とした文を後の選択段階で復元できるとは扱わない。引用内では文を切らず、独立した
先頭の括弧注記は閉じ括弧まで保つ。入力上限を超える一つの文や台詞は途中で分割せずエラーにする。
一文だけで300字を超える原文を含むまとまりは、
そのまとまりだけを最大600文字まで排他的に採用できる。選ばない長文を理由に短文の集合へ
例外予算を広げない。一文を途中で切らず、
300/600文字の上限は選択原文の予算である。最終表示では、選択した文番号の間に欠落があれば
連続した原文のブロックを分け、「原文の冒頭／途中／末尾を省略」の表示をアプリが付ける。
この表示は原文予算とは別で、表示文字数は300/600文字を超えることがある。原文の空白と改行も保持する。
選択メモに本文末尾の文が揃っていない場合は、確認用として元本文の末尾から最大4文・500文字の
連続した原文を別に添える（work_synopsis / reader_recap v11）。この欄はモデル選択の途中で
落ちた文も元本文から取る。途中で文を切らず、最後の一文が500文字を超える場合は欄を出さない。
末尾の原文には後記や告知も含まれ得るため、重要箇所や物語の結末と判定した表示にはしない。
確認用の原文は既定では折りたたみ、開いたときだけ全文を読む。原文の空白と改行を保持する。
追加欄は選択メモの予算とは別で、全表示はさらに最大500文字と欄名の分だけ長くなる。
抜粋であり要点や結末を網羅しないことを示す。主欄の `text` と確認用原文の `sourceTail` は、
API・保存・表示を通して別の項目で扱う。DBでは nullable な `source_tail` 列へ保存し、
確認欄のないメモへの上書き時はこの列も消す。欄名の文字列から表示範囲を判定しない。
旧メモは本文をそのまま表示し、文字列の分割による自動変換は行わない。
主欄に付ける省略表記と原文中の同じ表記の区別や、原文位置へ戻る参照は未対応である。
優先まとまりが上限に収まらない場合はそのまとまりを採らず、重複・不正IDなど構造違反は
一度だけ選び直す。それでも検証できなければ保存しない。原文抽出でも、重要事項の漏れや
指示語の不明瞭さ、まとまり選択の誤りは残り得る。

作品・作者・前話を切り替えたら、提案の選択状態と要求の受け口を分離する。検索文を
編集中・画面を閉じた後の旧応答を現在の条件として適用しない。推論枠の待ち時間は
30秒で打ち切り、別のAI処理が続いていることを知らせる。

Qwen3.5は構造化抽出を非推論で実行する。LM Studio 0.4.23では
`reasoning_effort: none`とJSON Schemaの併用を実測した。これは現行の互換API文書に
未掲載の指定なので、更新後も合成試験で確認する。非推論を求めた応答が内部思考だけで
出力枠を使い切ったら、枠を増やして同じ要求を繰り返さず、設定の不整合を返す。

モデルが作ったものには、次を必ず添える。

`featureId` / `promptVersion` / `modelId` / `inputFingerprint` / `configFingerprint` / `createdAt`

保存したメモは、開くたびに今の入力から指紋を計算し直す。題名・タグ・本文が変わって
いれば「古い」と表示する。**モデルの出力は事実ではなく、いつ・何から作られたかが
分からないと判断に使えない。** これは[推測はするが、断定はしない](02-principles.md)の
具体化である。

## 入口は、作用範囲で置き場所を変える

| 作用する対象 | 置き場所 |
|---|---|
| 画面全体で一つに決まる（言葉で探す、あらすじ、タグ補完、作風メモ、命名・分割） | アプリのヘッダー右側 |
| 同じ画面に複数あり得る（候補カードごとの命名、リーダーの前作要約） | 対象のすぐそば |

一つのヘッダーに束ねると、実行先が分からなくなる。逆に、対象が一意なものを本文の
中に置くと、探さないと見つからない。

タブで対象が変わる場合は、**今のタブにだけ機能を登録する**。別のタブで誤って実行
される機能をヘッダーに残さない。

保存済みの生成結果は元の本文位置に残す。入口だけを移し、結果と採用・破棄の操作まで
画面から切り離さない。

## 使えないときも押せる

ヘッダーの星は常に一つ。実行できる状態では黒い輪郭だけで、カーソルを合わせたとき・
キーボードで焦点が当たったとき・メニューを開いている間だけ紫の輪郭になる。

すべて未設定か対象外のときは、星の面を薄い灰色、輪郭を一段濃い灰色にする。
**それでも押せる。** 押すと、足りない条件と設定への導線が出る。押せないボタンは、
なぜ押せないかを説明する機会を捨てている。
