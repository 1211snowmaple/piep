# データの持ち方

すべて `%APPDATA%\com.hiron.piep` の下にある（実際のパスは
**設定 → ローカルライブラリ** に表示される）。

| 場所 | 中身 |
|---|---|
| `piep.db` | 作品のメタデータ、タグ、履歴、更新監視の設定 |
| `downloads/` | 本文の JSON と画像。取得元・作品ごとのフォルダー |
| `templates/` | EPUB テンプレート |
| `.piep-library.lock` | 起動中のプロセスが持つ助言ロック |

→ テーブルの一覧は [スキーマ](../reference/schema.md)（ソースから生成）

## 原本は書き換えない

これは [設計原則](02-principles.md) の一番目から直接出てくる。

```
取り込んだそのまま        original_json_path  ← 絶対に書き換えない
表示・検索に使う形        json_path
利用者の編集             work_edit_revisions / work_edit_blocks
```

編集は**リビジョン**として積まれる。`work_edit_revisions` は `base_version`
（どの版に対する編集か）と `status`（`draft` / `active` / `archived`）を持ち、
本文はブロック単位で `work_edit_blocks` に入る。

つまり、編集しても原本は失われない。改稿を取り込んでも過去の版は残る。
**取り消せない操作を作らない**ための構造である。

## スキーマの移行

`SCHEMA_VERSION` は 1 である。preview 時代に v1 / v2 と振っていた番号は、
単一の定義へ畳んで振り直した。

**移行は「加える」だけで行う。** `create_schema` はすべてのテーブルを
`CREATE TABLE IF NOT EXISTS` で作るので、どの世代のライブラリでも一度の冪等な
適用で現行に追いつく。既存の行はそのまま残り、バージョンだけが押し直される。

### `CORE_TABLES` に何も足さないこと

`CORE_TABLES` は、そのデータベースが piep のものかを見分けるための**指紋**である。
アプリが作るテーブルの一覧ではない。

この一覧に無いテーブルが欠けていても異物とは見なさない。逆に、
**ここに新しいテーブルを足すと、それ以前のビルドが作ったライブラリはすべて
「見知らぬスキーマ」と判定され、退避のうえ初期化される。**

新しいテーブルは `create_schema` にだけ足す。`CORE_TABLES` は触らない。

## 作品と、その周りのもの

```
downloads ──┬── download_tags ── tags
            ├── assets                 画像などの実体
            ├── download_versions      改稿の履歴
            ├── download_people ── people    作者
            ├── download_series ── series    公式シリーズ
            ├── download_relations     作品どうしの関係
            ├── work_edit_revisions    利用者の編集
            └── work_collection_members ── work_collections
```

## コレクション

**コレクションは、読む単位を利用者が自分で決めるための仕組みである。**

公式シリーズがあるのになぜ別に要るのか。理由は、まとまりの実態が
サービスの都合と一致しないからである。

- 作者・投稿サービス・公式シリーズをまたいで作品を入れられる
  （pixiv の前編と FANBOX の後編を同じまとまりにできる）
- 同じ作品が複数のコレクションに属せる
- 「前編→後編」のような**読む順のあるもの**と、「お気に入り短編集」のような
  **順序を重視しないもの**の両方を表せる

### 候補は下書きであって、決定ではない

`collection_suggestions` に入るのは**提案**である。公式シリーズ、本文中のリンク、
題名、作者、タグ、投稿日、本文の類似度から生成するが、**確定はしない**。

題名や本文が似ているだけでは、同じ連載なのか、同じ世界の別作品なのか、単に
題材が似ているだけなのかを区別できない。所属と最終的な順序を決める権限は
利用者に残る（`collection_pair_feedback` が判断を覚える）。

### コレクションの使い先

コレクションは正本であり、次の三つがその利用先になる。

| 使い先 | 何が起きるか |
|---|---|
| ライブラリ | タブとして一覧でき、作者詳細にも所属タブが出る |
| リーダー | どのコレクションから読み始めたかを保持し、読了位置に前後作品を出す |
| EPUB | ある時点の並びをスナップショットとして1冊へ書き出す（`export_collection_epub`） |

**EPUB のキューを永続化してグループに見せるのではなく、コレクションを正本にして、
キューは書き出し用の一時的な作業領域に留める。** 逆にすると、まとまりの価値が
EPUB 画面の中に閉じてしまう。

## 検索の索引

本体のデータとは別に索引を持つ。索引は**いつでも作り直せる派生物**であって、
失われても作品は失われない。

| 索引 | 何を引くか |
|---|---|
| Tantivy | 全文。n-gram と読みの正規化で、かな・カナ・ローマ字・部分一致を吸収する |
| 意味検索 | fastembed + ONNX Runtime（DirectML で GPU 実行）。近い意味の作品を引く |

診断画面から、索引の完成度・実データでの検索速度・最適化を確認できる。

## バックアップ

マニフェスト＋分割 ZIP で書き出す。**復元は取り込む前に中身を検査する。**
保存フォルダーからの再取り込みもできる。
