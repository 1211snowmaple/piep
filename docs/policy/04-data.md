# データの持ち方

すべて `%APPDATA%\com.hiron.piep` の下にある（実際のパスは
**設定 → ローカルライブラリ** に表示される）。

| 場所 | 中身 |
|---|---|
| `piep.db` | 作品のメタデータ、タグ、履歴、更新監視の設定 |
| `downloads/` | 本文の JSON と画像。取得元・作品ごとのフォルダー |
| `collection-covers/` | 利用者が選んだコレクション表紙の管理コピー。バックアップ対象 |
| `templates/` | EPUB テンプレート |
| `delete-staging/` | 削除の一時隔離。クラッシュ時は次回起動で復旧または削除完了 |
| `.piep-library.lock` | 起動中のプロセスが持つ助言ロック |

→ テーブルの一覧は [スキーマ](../reference/schema.md)（ソースから生成）

## 原本は書き換えない

これは [設計原則](02-principles.md) の一番目から直接出てくる。

```
取り込んだそのまま        original_json_path  ← 絶対に書き換えない
表示・検索に使う形        json_path
利用者の編集             work_edit_revisions / work_edit_blocks
```

編集は**リビジョン**として積まれる。`work_edit_revisions` は `base_version`
（どの版に対する編集か）と `status`（`draft` / `active` / `archived`）を持ち、
本文はブロック単位で `work_edit_blocks` に入る。

つまり、編集しても原本は失われない。改稿を取り込んでも過去の版は残る。
**取り消せない操作を作らない**ための構造である。

## スキーマの移行

`SCHEMA_VERSION` は 1 である。preview 時代に v1 / v2 と振っていた番号は、
単一の定義へ畳んで振り直した。

**移行は「加える」だけで行う。** `create_schema` はすべてのテーブルを
`CREATE TABLE IF NOT EXISTS` で作るので、どの世代のライブラリでも一度の冪等な
適用で現行に追いつく。既存の行はそのまま残り、バージョンだけが押し直される。

### `CORE_TABLES` に何も足さないこと

`CORE_TABLES` は、そのデータベースが piep のものかを見分けるための**指紋**である。
アプリが作るテーブルの一覧ではない。

この一覧に無いテーブルが欠けていても異物とは見なさない。逆に、
**ここに新しいテーブルを足すと、それ以前のビルドが作ったライブラリはすべて
「見知らぬスキーマ」と判定され、退避のうえ初期化される。**

新しいテーブルは `create_schema` にだけ足す。`CORE_TABLES` は触らない。

## 作品と、その周りのもの

```
downloads ──┬── download_tags ── tags
            ├── assets                 画像などの実体
            ├── download_versions      改稿の履歴
            ├── download_people ── people    作者
            ├── download_series ── series    公式シリーズ
            ├── download_relations     作品どうしの関係
            ├── work_edit_revisions    利用者の編集
            └── work_collection_members ── work_collections
```

## コレクション

**コレクションは、読む単位を利用者が自分で決めるための仕組みである。**

公式シリーズがあるのになぜ別に要るのか。理由は、まとまりの実態が
サービスの都合と一致しないからである。

- 作者・投稿サービス・公式シリーズをまたいで作品を入れられる
  （pixiv の前編と FANBOX の後編を同じまとまりにできる）
- 同じ作品が複数のコレクションに属せる
- 「前編→後編」のような**読む順のあるもの**と、「お気に入り短編集」のような
  **順序を重視しないもの**の両方を表せる

### 束の証拠と、ただの文脈を分ける

手がかりを一つの点数に足してはいけない。以前は公式シリーズ 0.58 と同一作者 0.12 を
足して 0.70 になり、採用閾値 0.44 を越えていた。結果、151作のシリーズを種にすると
**「同じ棚に載っている」だけの作品が60件、チェックの付かないまま並んだ**。

| 区分 | 手がかり | 役割 |
|---|---|---|
| **束の証拠** | 本文リンク／題名の連番／公式シリーズで話数が**隣接** | これが一つも無ければ候補にしない |
| **文脈** | 同一作者／同一シリーズに同居／共有タグ／投稿時期／本文の近さ | 順位づけと説明にだけ使う |

同じシリーズに載っていることと、続けて読むべきことは違う。話数が隣り合って
初めて証拠になる。

### 確度%ではなく、根拠の一行を出す

「確度 74%」は根拠になっていないのに、数字であるという理由だけで信じてしまう。
画面に出すのは**なぜ束なのか**である。

```
本文のリンクで3作がつながっています
題名が連番になっている7作です
「幽谷霧子」を共有し、本文も近い13作です（作者3人）
```

### 束は三系統に分ける

証拠の種類が違えば、順序の意味も名前の付け方も違う。

| 系統 | 何から作るか | 順序 |
|---|---|---|
| `sequence` | 本文リンク・題名の連番・公式シリーズの連番 | **意味を持つ** |
| `theme` | 共有タグ＋本文ベクトルの近さ | 意味を持たない |
| 版違い | 版の呼び名を除いた題名の一致 | 束ではない。畳んで代表だけ見せる |

`theme` の近さは**絶対値で測らない**。同じ題材ばかりの棚では無作為な2作でも
余弦が 0.94 ある（実測）。棚の対の平均と標準偏差を取り、そこからの隔たり
（z ≥ 2.0）で判断する。しきい値は棚ごとに違うので、固定値は置けない。

共有タグが1つだけの大きな束は、まとまりではなく**絞り込みの結果**である。
束としては出さず、保存した検索として扱うほうが正しい。

### 名前は一つに決めない

候補は名前の案を複数持つ（`name_options_json`）。題名の共通部分・公式シリーズ名・
共有タグ・作者、そして任意で利用者のモデルが出した案。先頭が既定になる。

**検索用の正規化キーを表示名に使わない。** `normalize_search_text` はカタカナを
ひらがなへ倒し記号を落とすので、そのまま名前にすると
「はいすぺいけめん女子の綾城さん」になる。表示用の語幹は
`collection_rules::display_title_stem` が別に作る。

公式シリーズ名も、そのままでは使えない。pixiv のシリーズには「有償依頼」151作の
ように受注区分がそのまま入っている。タグにも「リクエスト品」がある。
どちらも作者の管理用ラベルであって、物語の共通点ではない。

### 候補は下書きであって、決定ではない

`collection_suggestions` に入るのは**提案**である。題名や本文が似ているだけでは、
同じ連載なのか、同じ世界の別作品なのか、単に題材が似ているだけなのかを区別
できない。所属と最終的な順序を決める権限は利用者に残る
（`collection_pair_feedback` が判断を覚える）。

`origin` が `seed` の候補は1作から広げたもので、利用者が自分で作らせたもの。
`sweep` の候補は棚全体の走査で出たもので、走査のたびに作り直す。

### 束ねる対象にしないもの

- **告知・活動報告** — 「2023年5月進捗のご報告」が5件で1つの連載に見える
- **リンクのハブ** — 次数が5以上で本文の薄い作品は、リンクの橋にしない。
  告知記事1件が16本のリンクを持ち、無関係な17作を1つに縫い合わせていた
- **取得元をまたいだ同じ作品** — `author_id` は取得元ごとに違うので、
  同じ作者は**表示名**で突き合わせる。pixiv 版と FANBOX 版が続きとして
  二度並ばないようにする

### 束にしなかったものも返す

大きすぎるタグは束にしないが、**黙って捨てもしない**。「洗脳」824作は読む単位に
ならないが、利用者にとっては確かに一つの見方である。走査は
`saved_search_suggestions` としてそれを返し、画面は「保存した検索にする」を勧める。

### 一括で閉じられないなら、出さないほうがまし

走査は300件を超える候補を出す。1件ずつ閉じさせるなら、見つけないほうがましである。

- 画面に出すのは一度に12件。残りは「もっと見る」
- `dismiss_swept_suggestions` で系統ごと・全部をまとめて閉じられる
- 閉じるのは下書きだけ。**否定は記録しない**ので、走査し直せば同じものが出る

### すでにある束にも同じ機能が効く

束は作ったあとで中身が変わる。作品を足せば共有タグが変わり、外せば題名の共通部分も
変わる。作ったときの名前に縛られる理由は無い。

- `collection_name_proposals` が、いまの中身から名前の案を出し直す
- `db_name_collection_with_model` が、モデルにも名前と説明を考えてもらう
- どちらも**保存はしない**。案を並べるだけで、決めるのは利用者

### タグの出どころを混ぜない

`download_tags.tag_source` に、そのタグがどこから来たかを持つ。

| 値 | 意味 | 取り直しで |
|---|---|---|
| `origin` | 取得元が付けていた | **消えて入れ直される** |
| `manual` | 利用者が付けた | 残る |
| `llm` | モデルの案を利用者が採った | 残る |

**混ぜてはいけない。** 取得元が付けたタグとモデルが足したタグは確からしさが
違う。どちらか分からなくなった時点で、両方が信用できなくなる。
取り直しで消してよいのも `origin` だけで、取得元が知らないことを取得元の都合で
消してはいけない。あとから取得元も同じタグを付けたら、出どころは `origin` へ移る。

外せるのも `llm` のぶんだけ。取得元のタグは画面から外せない。

### 名前をモデルに考えてもらう（任意）

piep はモデルを同梱しない。OpenAI 互換のエンドポイントを設定で指すだけで、
LM Studio・Ollama・llama.cpp のいずれでも繋がる。既定は切ってあり、切ったままでも
決定的な案から名前は出る。

- 送るのは**題名・作者・タグ・公式シリーズ名だけ**、最大12作。本文は送らない
- 宛先は既定でこの端末の中だけ。外部は HTTPS に限り、同意をURLそのものへ
  結び付ける。URLを変えたら同意も試し書きの結果も破棄する
- HTTP redirect は追わない。検証したローカルURLから外部へ転送される経路を作らない
- 出力は JSON schema で縛り、検証に落ちたら決定的な案に戻す
- 婉曲な名前しか返さないモデルはある。**piep 側で回避はしない。**
  どのエンジンを使うかを決める権利は利用者にある

設定は「探す → 試す → 使う」の順にする。**番号を打たせない。**

1. よくある置き場所（LM Studio 1234、Ollama 11434、llama.cpp 8080…）を
   一度に叩いて、応答したものだけ出す。全部止まっていても2秒足らずで終わる
2. **保存する前に試し書きをする。** つながることと使えることは別で、
   安全調整の強いモデルは接続できても題材を言い換えた見出しを返す。
   棚から締まった束（3〜8作のタグ）を拾って渡し、返ってきたものを見せる
3. 見て納得したら有効にする

埋め込み専用のモデルは一覧から外す。選んでから使えないと分かるのは遅い。

**アプリ自身に推論はさせない。** 意味検索の埋め込み（fastembed + ONNX Runtime）は
同梱しているが、生成モデルは事情が違う。数GBの重みを配布物に載せることになり、
GPU の有無で挙動が変わり、モデルを選ぶ自由も失われる。この棚の題材では
「どのモデルなら婉曲にならないか」が実用の分かれ目なので、**選べることが要件**である。

### モデルに頼める仕事

どれも**押したときだけ動く**。裏で走るものは一つも無く、設定していなければ
機能そのものが画面に出ない。返ってくるのはすべて案で、採る操作は別にある。

| 仕事 | 送るもの | 置き場所 |
|---|---|---|
| 束の名前と説明 | 題名・作者・タグ・シリーズ名 | 候補の一覧、コレクション詳細 |
| タグの補完 | 題名・概要・いまのタグ・棚の語彙 | 作品詳細 |
| 言葉で探す | 説明の文・棚の語彙 | ライブラリの検索欄 |
| 作風のメモ | 題名とタグ（最大18作） | 作者ページ |
| 束の分割 | 題名とタグ | コレクション詳細 |
| あらすじ | **本文全体**（約2,800字ずつ分割し階層要約） | 作品詳細 |
| 前回のあらすじ | **本文全体**（同上） | リーダーの、読む順がある文脈 |

本文を送るのは下2つだけで、`allow_body` を別に許可しないと**材料を読む前に
断る**。許していない相手のために本文を読み出すこと自体をしない。
先頭と末尾だけを抜き出してはならない。本文を隙間なく分割し、全チャンクから
部分記録を作り、原文範囲と順序を保ったまま段階的に統合する。1リクエストと
1レスポンスには固定のバイト上限を置く。

タグと検索語は**棚の語彙から選ばせる**。新語を作らせると、検索にも束ねにも
使えないものが増える。語彙に無い語が返ってきたら捨てる。

覚え書き（あらすじ・前回のあらすじ・作風）は `ai_notes` に、**どのモデルが
書いたか**と一緒に残す。モデルを替えたときに古い文が混ざっていることに
気づけるようにするためで、失われても作品は失われない派生物である。

### 合本と、本文の無い作品

- **合本**（「【前編＋中編】…」）は分冊のあいだにある別の作品ではなく、二つを
  まとめた版である。分冊がそろっているときだけ畳む — 合本しか手元に無いなら、
  それが本体だからで、消せば束から作品そのものが消える
- **本文0字の作品**（実測29件）は行だけあって中身が無い。一冊のEPUBには入れず、
  「収録できない」側に数える。そのまま入れると空の章になる

### コレクションの使い先

コレクションは正本であり、次の三つがその利用先になる。

| 使い先 | 何が起きるか |
|---|---|
| ライブラリ | タブとして一覧でき、作者詳細にも所属タブが出る |
| リーダー | どのコレクションから読み始めたかを保持し、読了位置に前後作品を出す |
| EPUB | ある時点の並びをスナップショットとして1冊へ書き出す（`export_collection_epub`） |

**EPUB のキューを永続化してグループに見せるのではなく、コレクションを正本にして、
キューは書き出し用の一時的な作業領域に留める。** 逆にすると、まとまりの価値が
EPUB 画面の中に閉じてしまう。

## 検索の索引

本体のデータとは別に索引を持つ。索引は**いつでも作り直せる派生物**であって、
失われても作品は失われない。

| 索引 | 何を引くか |
|---|---|
| Tantivy | 全文。n-gram と読みの正規化で、かな・カナ・ローマ字・部分一致を吸収する |
| 意味検索 | fastembed + ONNX Runtime（DirectML で GPU 実行）。近い意味の作品を引く |

診断画面から、索引の完成度・実データでの検索速度・最適化を確認できる。

## バックアップ

マニフェスト＋分割 ZIP で書き出す。**復元は取り込む前に中身を検査する。**
保存フォルダーからの再取り込みもできる。

「ライブラリ全体」には作品ファイルだけでなく、タグの出どころ、本文編集の全リビジョン、
保存した検索、コレクションの表紙・命名元・系統、候補への採否フィードバックを含む。
DBの連番IDは持ち運ばず、取得元の作品キーと管理領域内の相対パスへ置き換える。
カスタム表紙は選択元の絶対パスではなく `collection-covers/` の実ファイルを収録する。

`ai_notes` はモデルから再生成できる派生キャッシュであり、バックアップ対象には含めない。
一方、利用者が採用した `llm` タグや候補への採否は利用者の判断なので、派生物として
捨ててはいけない。
