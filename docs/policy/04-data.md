# データの持ち方

すべて `%APPDATA%\io.github.u1211snowmaple.piep` の下にある。作品は棚（`library/`）に
まとめて持つ。棚の実際のパスは **設定 → 保存とバックアップ** に表示される。開発では
環境変数 `PIEP_SHELF_DIR` で棚の場所を差し替えられる。

| 場所 | 中身 |
|---|---|
| `library/` | 棚。作品の本文・画像・添付、メタデータ、タグ、版の履歴、編集、コレクション、更新監視、利用者の状態 |
| `library/library.json` | 棚の名札。形式（`piep-library`、版 1）と棚の ID。これがあるフォルダーだけを棚として開く |
| `library/library.db` | 台帳（SQLite、WAL）。どの作品がどの版で、どのファイルでできているか |
| `library/objects/v1/` | ファイルの実体。元のバイト列の SHA-256 で置く、書き換えない部分実体 |
| `library/derived/` | 全文検索と意味検索の索引。台帳から作り直せる |
| `library/.library.lock` | 棚を開いているプロセスが持つ排他ロック |
| `library.restore-request.json` | 棚の隣。予約した復元（下の「バックアップ」） |
| `library.restore-result.json` | 棚の隣。前回の起動での入れ替えの結果 |
| `library.before-restore-<UNIX 秒>/` | 復元で退けた前の棚 |
| `models/` | 意味検索のモデル。棚の外に置くので、バックアップには入らない |
| `templates/` | EPUB テンプレート |
| `downloads/` | 保存フォルダーから取り込むときの置き場（`<取得元>/<作品の番号>/v<版>/`） |
| `search-settings.json` | 意味検索を使うかの設定。棚のデータではなく、アプリの設定 |

利用者向けの説明は [データの置き場所とバックアップ](../guide/04-your-data.md) にある。

→ テーブルの一覧は [スキーマ](../reference/schema.md)（棚の台帳の SQL を順に当てた結果から生成）

保存フォルダーからの取り込み（`commands/reimport.rs`）は、`downloads/` の作品フォルダーを読んで
棚へ保存し直す。

## 棚の形

**台帳と実体はひと組で、名札がそれを棚と認める。** 三つは次の決まりで結び付く。

- `library.json` の棚の ID と、台帳の `library_meta.library_id` が一致しなければ開かない。
  設定で指した棚かどうかも、台帳を書き換える前にこの ID で照合する（`Library::open_matching`）
- 棚を作るのは空のフォルダーだけ。作っている間は名札の代わりに `.creation.json` を置き、
  台帳と実体の置き場ができてから `library.json` へ改名する。途中で止まったら、その記録が
  あるときだけ再開する。見知らぬ中身のあるフォルダーを棚にしない
- 開いている間は `.library.lock` を排他で取る。二つめのプロセスは開けずに断られる
  （アプリを開いたまま `piep-library` で同じ棚を触ることはできない）
- 起動では、予約した復元があれば棚を開く前に入れ替える。`library.json` が無ければ空の棚を
  作って正本に切り替える。正本に切り替えていない棚（`library_meta.switched_at` が NULL の、
  移行で作った写し）は開かない

実体は、元のバイト列の SHA-256 で `objects/v1/<先頭2桁>/<ハッシュ>.obj` に置く。同じ中身は作品・
ファイル名・保存場所によらず一つしか持たない。実体は書き換えず、検証を通ったものだけを公開する。
どのファイルがどの部分実体でできているかは台帳の `content_files`・`file_chunks` が持つ
（`crates/piep-storage`）。

- 8 MiB 以下のファイルは一つの実体にする。超えるものは先頭から 4 MiB ごとに区切り、最後だけ端数にする。
  ファイル全体のハッシュと、順序の付いた部分の一覧の両方を持つ。途中を読むときは要る部分だけを戻す
- 実体ごとに独立した zstd（レベル 3、チェックサムあり、外部辞書なし）を試し、元が `N` バイトのとき
  `max(1024, ceil(N / 100))` バイト以上縮んだときだけ使う。縮まなければそのまま置く。画像も拡張子では
  決めない。「必ず小さくする」決まりではない
- 読むときは、長さ・元の SHA-256・展開の大きさの上限を確かめる。壊れた実体を空の本文や欠けた画像に
  置き換えない。同じハッシュの実体があっても、壊れていれば共有せずに直す対象にする
- 取得元の URL・ローカルのパス・原寸か縮小版かは、実体の識別にしない。保存名・MIME・作品・版・画像の
  役割は参照の側が持つ。原寸への取り直しも、実体を足して参照を差し替える。共有の実体を上書きしない
- 読み手は保存の形を知らずに元のバイト列を受け取る。パスの要る外のツールや WebView には、要るファイル
  だけを検証して一時に展開する。一時の展開物から棚の実体へハードリンクを張らない

## 識別と指紋

- 作品・作者・シリーズ・版・保存版・編集は UUIDv7 で指す。台帳では 16 バイトの BLOB、API では UUID の
  文字列。並び順を UUID の時刻に頼らない。ファイルと部分は SHA-256（32 バイト）で指す
- 取得元の識別は `provider` と種類と `external_key` の組で一意にする。pixiv の小説・イラスト・作者の ID を
  同じ名前空間として扱わない。同じ作者名・似た題・同じ画像だけでは、作品や作者を自動でまとめない。
  サービスをまたぐ関係は明示のリンクとして持つ
- SQLite の行番号・絶対パス・「第何版」という表示の番号を、外への参照に使わない

**指紋は用途ごとに分ける。** 保存版（`revision_snapshots`）は次の二つを別々に持つ。

| 指紋 | 入力 | 変わったときの意味 |
| --- | --- | --- |
| `semantic_hash`（と本文の `body_semantic_hash`） | 本文・題・説明・タグ・関係・画像の識別など、作者が変えうる中身 | 作者の改稿の候補 |
| `manifest_hash` | 保存版に採った中身と参照するファイルと、その読み方 | 持っているものや読み方の変化。作者の改稿とは限らない |
| ファイル・部分の SHA-256 | 元のバイト列 | 完全一致・検証・重複の排除 |

- 取得した URL・圧縮の方式・置き場所・取得の日時を、作者の中身の指紋に入れない。本文は元の文字列を
  基にし、意味の変わりうる空白や句読点を勝手に揃えない
- 指紋にはそれぞれ規則の版（`semantic_rule`・`body_semantic_rule`・`manifest_rule`）を付け、版の違う
  指紋どうしを直接比べない。規則を変えるときは保存してある中身から指紋を作り直す。指紋の作り直しは改稿に
  数えない。`manifest_hash` を変えたら、それに結んだ記録（`bindings_hash` や取得の読み方の記録）も移す
- 原寸への補完・可逆圧縮・重複の排除・配る形の変更だけでは、作者の改稿を増やさない

**表紙と挿絵は、品質によらない識別で比べる**（`library/identity.rs` の `image_identity`）。pixiv の既知の
URL の形に限り、大きさの指定・原寸か master か・変換の末尾・拡張子を取り除いて、日時と固有の部分から
比べる鍵を作る。知らない形は元の URL をそのまま比べ、識別が取れなければ「変わっていない」と決めない。
この鍵は取得元の識別であって中身の証明ではない。同じ URL のまま中身が差し替わったことは、鍵だけでは
分からない。

**保存は短い一つのトランザクションで確定する。** 取得と大きなファイルの圧縮は書き込みのトランザクションの
外で行い、実体を検証して置いてから、取得の記録・版・保存版・参照・今を指す印・表示用のデータを一度に
確定する。今の世代が取得を始めたときと違えば比べ直し、黙って上書きしない。検索などの後の処理は確定のあとに
行い、処理した世代に限って済んだとする。画像の取り直しと編集が同時に走っても、編集が基にする保存版は
変えない。

## 原本は書き換えない

これは [設計原則](02-principles.md) の一番目から直接出てくる。

```
取得したそのままの応答   acquisition_observations.raw_file_id
保存版（題・本文・添付・画像）  revision_snapshots ── snapshot_files / snapshot_media
利用者の編集            edit_revisions ── edit_blocks / edit_media
```

**書き換えないことは台帳のトリガーで強制する。** 公開した保存版（`revision_snapshots` の
`published=1`）とその構成（ファイル・画像・作者・シリーズ・タグ）、改稿（`source_revisions`）、
取得の記録、封をした編集（`edit_revisions` の `sealed=1`）、確定したファイル（`content_files` の
`sealed=1`）は、更新しようとすると SQLite が断る。

取得元の改稿を取り込むと、改稿（`source_revisions`）と保存版が足される。過去の版は残り、
今の版は `work_current_projection` が指す。

編集は**リビジョン**として積まれる。`edit_revisions` は `base_snapshot_id`（どの保存版に
対する編集か）と `parent_id`（前の編集）を持ち、本文はブロック単位で `edit_blocks` に入る。
`edit_documents` が反映中の版（`active_id`）と下書き（`draft_id`）を指す。反映を替えると前の
反映は `edit_archive`（以前の編集版）に残り、そこから戻せる。

つまり、編集しても原本は失われない。改稿を取り込んでも過去の版は残る。
**取り消せない操作を作らない**ための構造である。

編集本文の画像は `edit_media` が中身の識別子（`content_files`）で持つ。編集後に取得元の改稿を
取り込んでも、編集の挿絵が今の版の画像へ付け替わることはない。

### 外すことと、実体の回収

作品を棚から外す（`remove_work`）と、一覧・全文検索の索引・過去の版の索引から消える。
作品の識別・保存版・編集・利用者の状態・コレクションの行は残る（コレクションでは保存のない
作品として出る）。同じ作品をもう一度保存すれば棚に戻る。行を完全に消す操作は持たない。

台帳のどの行からも参照されなくなったファイルだけを回収する（`reclaim.rs`）。参照は
「`content_files` を指す外部キーのある列すべて」で数えるので、表を足しても数え漏れない。
作品を外しても保存版は残るので、その実体は回収されない。

- 編集や表紙に画像を選ぶたびに、台帳に 1 日間の保留を作る。正式な参照を保存するのと同じ
  トランザクションでその選択の保留を外す。保存されなかった保留は期限を過ぎたら回収で外す
- 保存側の実体の書き込み・再利用から台帳確定までは、回収側の最後の参照確認・隔離と重ねない。
  回収用の実体一覧の走査中も保存できる。最後に使われてから 1 日たっていない実体は退けない
- 棚の全体送信では、台帳の写しを作る段階でその写しが指す実体を確保する。送信側が写しを
  手放すまでと、中断時に読み出しが残っていればその読み出しが終わるまで、実体を回収しない
- 退けた実体は `<ハッシュ>.<退けた時刻 ms>.quarantined` として隔離し、7 日たってから消す
- 隔離した実体があとで参照されていれば、次の回収で戻す。参照されている実体が実体領域にも
  隔離にもなければ、何も回収せずに失敗する
- 回収はバックアップ・検証と同時には走らない

## スキーマの移行

台帳の定義は `src-tauri/src/library/schema.rs` にある。`schema.sql` が 1 番、
`migration_002_*.sql` 以降が 2 番からの移行で、`MIGRATIONS` に並べた順に当てる。
`VERSION` は最後の番号である。

**移行は、すでに出したものを書き換えず、新しい番号を足して行う。** 当てた移行は
`schema_migrations` に番号・指紋・時刻を記録する。指紋は SQL の SHA-256 で、改行を LF に
揃えてから取る（Git のチェックアウト設定による CRLF の違いはスキーマの変更ではない）。
出した移行の SQL を書き換えると、それを当てた棚は記録が合わずに開けなくなる。

新しく作るときは、空の台帳にだけ全部の移行を一つのトランザクションで当て、記録を書き、
`application_id`（`0x504C5632`）と `user_version` を押す。

開くときは、次の順に確かめる。どれかが合わなければ、その棚は**開かない**。

1. WAL や DDL を当てる前に、`application_id` と `user_version` で見分ける。piep の台帳で
   ないもの、コードの `VERSION` より新しいものは断る
2. `library_meta` の棚の ID が名札と一致する
3. `schema_migrations` の記録が 1 番から `user_version` まで欠けずに並び、各指紋が今のコードの
   SQL の指紋と一致する
4. `library_meta` の保存形式・最低読取版・最低書込版が、このビルドの扱える範囲（1）にある

台帳が古い版なら、残りの移行を一つのトランザクションで順に当て、記録を足して
`user_version` を上げる。途中で失敗すれば全部が戻り、棚は元の版のまま残る（`schema.rs` の
試験が、移行ごとに既存の行が残ることと失敗で戻ることを確かめている）。

### 見分けられないものを作り直さない

開けない棚は誤りとして止まり、**初期化も退避もしない。** 名札が無い、ID が合わない、
記録が合わない、新しすぎる、のどれでも、利用者の棚を空の棚で置き換えることはしない。
新しく作るのも空のフォルダーと空の台帳だけで、テーブルのある台帳に定義を当てて自分のものに
することはない（`new_schema_has_enforced_ownership_and_never_resets_a_foreign_database`）。

見分けるのは `application_id`・`user_version`・移行の記録・名札の ID であって、テーブルの
有無ではない。

### 棚の保守

アプリの診断画面から、次の手入れができる（`commands/library_health.rs`）。

| 操作 | 中身 |
|---|---|
| 台帳の手入れ | 統計を整える（`PRAGMA optimize`）。空き領域の回収（`VACUUM`）は、空きが足りるときだけ |
| 索引の最適化 | 全文検索の索引（今の版と過去の版）の断片を一つにまとめる |
| 検証 | 未確定の記録・外部キー・`integrity_check` を確かめ、全ファイルを部分実体から復元してハッシュを照合する |
| 回収 | どこからも参照されない実体を片付ける（上の「外すことと、実体の回収」） |

アプリの外からは `piep-library`（`src-tauri/src/bin/piep-library.rs`）で、棚の `verify`・
`backup`・`reclaim` などを行える。アプリと同じ `.library.lock` を取るので、アプリを閉じてから
使う。

## 作品と、その周りのもの

```
entities ── external_identities          取得元の ID（取得元・種類・作品キー）
works
 ├── source_revisions                    改稿（取得元での版）
 │    └── revision_snapshots             保存版（そのときのメタデータと本文）
 │         ├── snapshot_files            原本・添付
 │         ├── snapshot_media ── source_media / media_renditions   画像
 │         ├── snapshot_people ── people     作者
 │         ├── snapshot_series ── series     公式シリーズ
 │         └── snapshot_tags ── tags         取得元のタグ
 ├── work_current_projection             今の版（一覧の行）
 ├── library_items                       棚に載っているか
 ├── edit_revisions / edit_documents     利用者の編集
 ├── work_user_tags ── user_tags         自分で付けたタグ
 ├── work_user_state / reading_positions お気に入り・読書位置
 ├── work_links                          本文リンク
```

作品・作者・シリーズ・コレクションは `entities` に識別を持ち、台帳の中では UUID で指す。
取得元の番号は `external_identities` が対応を持つ。

## 添付の中の本文

規制を避けるため PDF や `.txt` に入れて配られた本文も、直接の投稿と同じに読めるようにする。
全文検索と意味検索に載り、縦書き・横書きで読め、しおりと本文内検索が効き、EPUB に書き出せ、
編集できること。「開ける」だけでは足りない。

**取り出した段落を、投稿と同じ `blocks` の形でメモリの上で差し込む**（`src-tauri/src/attachment.rs`
の `apply_attachment_text`）。読む画面・検索・EPUB・編集は、どれもこの仕組みを知らずに動く。
経路ごとに受け渡しを足すより、入口を一つにするほうが食い違わない。保存版も添付の原本もそのまま
残る。FANBOX の「ファイル」形式（`blocks` を持たない）には、取り込む本文があるときだけ `blocks` を
組む。段落の境でページが割れるので、2万字が一枚に載らずに済む。

**取り出した本文は保存しない。** 取り出しは PDF から決まり、1冊 50ms 以下で終わる計算の結果で
あって、資料ではない。控えを持つとバックアップ・復元・失効・作り直しがそろって要る。

**取得元の指紋に混ぜない。** 作品の文字数や本文の指紋は取得元が返したものの値で、piep が作った量では
ない。混ぜると、次の更新確認で手元と取得元が食い違い、変わっていない作品が毎回「2万字増えた」と出る。
一覧の文字数は投稿の本文の長さのままで、読む側には取り込んだ本文の前の印が「18ページ・21,717文字」と
伝える。

**本文の作り方を変えたら、影響のある作品だけを索引へ戻す。** 取得元は何も変えていないので、本文の
指紋だけを見ると索引は「全件が最新」と判定し、すでにある作品は永久に検索へ出ない。索引の文書は
作り方の版（`search_documents.recipe`、`library_search/index.rs` の `RECIPE`）を持ち、版が上がった
文書だけを作り直す。全文と意味の両方を作り直す。片方だけだと、字面では出るのに言葉で探すと出ない
作品ができる。

**取り込めなかったことは、その場に一行で伝える。** 画像だけの PDF、鍵付き、壊れたもの、見慣れない
文字コードは珍しくない。黙って 📎 の箱だけを残すと、本文が入っているのに空に見える作品と、本当に
音源しか無い作品が同じ顔になる。理由の一行は数に入れず、段落を作らず、検索にも EPUB にも入れない。

**原本は紙面のまま見せる。** 取り込みが正しいかを利用者が確かめられるよう、pdfium で描いた紙面を
読む画面の印の「原本を見る」と作品の画面から開く。外のアプリへは渡さない（`commands/shell.rs` は
起動してよい種類を絞っている）。控えは持たず要求のたびに描き、次のページを先に描いておく。要求する
幅は 200 画素に丸める。

### PDF から段落を作る

pdfium（BSD、`pdfium-render` 経由。`src-tauri/vendor/pdfium/` の README に理由と上げ方）で、
上から当てて当たった段で止める。

| 段 | 条件 |
| --- | --- |
| 1. 構造ツリー | タグ付きの PDF |
| 2. 行の組み直し | タグが無く、文字の層がある |
| 3. OCR | 文字の層が無い（入れていない） |

- 段落の中の改行は折り返しなので落とす。両側が ASCII の英数字のときだけ空白を入れる（欧文の語が
  潰れないように）
- ページをまたぐ段落は、ページの最後の行が右端まで届いているかで決める。文末の約物で見ると、段落の
  途中の改ページが句点の直後に来たときに切り違える。見る行は紙面の最後ではなく、印の中の最後の行
- ページごとに、pdfium が返す全文字数と拾った文字数を突き合わせ、合わなければそのページだけ行から
  組み直す。段落の精度を落としてでも、黙って本文を欠けさせない
- 柱とページ番号（`/Artifact`）は本文ではない。印を持たない空白は直前の段落へ付け（Word は語の
  切れ目の空白を別に出す）、印を持たない文字は落として数えない。落とす量が柱として説明できる大きさを
  超えたら、構造ツリーの取りこぼしと見て行の組み直しへ回す
- 素朴な抽出・poppler・MuPDF（AGPL）・`lopdf`（描画が無い）は使わない。描画は原本の表示にも
  OCR にも要る

試験は、実物で確かめた性質だけを持つ最小の PDF をその場で書き出して使う（`src-tauri/src/pdf/fixture.rs`）。

### テキストファイルと zip

`.txt` は書かれた改行が段落の切れ目なので、組み直さない。文字コードは UTF-8 を先に試す（Shift_JIS の
復号はほとんどのバイト列を受け取ってしまう）。続く空行は一つにまとめ、8MB を超えるものは断る。紙面を
持たないので「原本を見る」は出さない。`.zip` は開かない。棚の実物は音源と画像で、取り込む本文が無かった。

## コレクション

未登録・シリーズ内部・サービス跨ぎの続き物を見つける改善方針は、
[まとまりの発見](../plan/collection-discovery.md) に定める。まだ作っていない要件と、今の実装を分けて書いている。

**コレクションは、読む単位を利用者が自分で決めるための仕組みである。**

公式シリーズがあるのになぜ別に要るのか。理由は、まとまりの実態が
サービスの都合と一致しないからである。

- 作者・投稿サービス・公式シリーズをまたいで作品を入れられる
  （pixiv の前編と FANBOX の後編を同じまとまりにできる）
- 同じ作品が複数のコレクションに属せる
- 「前編→後編」のような**読む順のあるもの**と、「お気に入り短編集」のような
  **順序を重視しないもの**の両方を表せる

コレクションは台帳の `collections`・`collection_members` が持つ。提案の計算（走査・種からの
提案・追加の候補・名前の案）は、`library_suggestion_corpus` が棚の今の版から作業用の表を
メモリ上に組み、その上で走らせる。結果は台帳の `collection_suggestions`・
`collection_suggestion_seeds`・`collection_suggestion_members`・`collection_pair_feedback`
へ書く（`library_suggestions.rs`）。以下の規則は、その計算と画面の決まりである。

### 束の証拠と、ただの文脈を分ける

手がかりを一つの点数に足してはいけない。以前は公式シリーズ 0.58 と同一作者 0.12 を
足して 0.70 になり、採用閾値 0.44 を越えていた。結果、151作のシリーズを種にすると
**「同じ棚に載っている」だけの作品が60件、チェックの付かないまま並んだ**。

| 区分 | 手がかり | 役割 |
|---|---|---|
| **束の証拠** | 本文リンク／題名の連番／公式シリーズで話数が**隣接** | これが一つも無ければ候補にしない |
| **文脈** | 同一作者／同一シリーズに同居／共有タグ／投稿時期／本文の近さ | 順位づけと説明にだけ使う |

同じシリーズに載っていることだけで、同じ物語とは判定しない。棚全体の走査では、
大きなシリーズ内の独立した前後編も探す。題名の章・話数・前後編を階層として扱い、
本文リンクの向きが話数と食い違う場合は、確認が必要な仮の順序として示す。
参考リンクと完全版への誘導を、続編リンクと区別する。

### 確度%ではなく、根拠の一行を出す

「確度 74%」は根拠になっていないのに、数字であるという理由だけで信じてしまう。
画面に出すのは**なぜ束なのか**である。

```
本文のリンクで3作がつながっています
題名が連番になっている7作です
「幽谷霧子」を共有し、本文も近い13作です（作者3人）
```

### 束は三系統に分ける

証拠の種類が違えば、順序の意味も名前の付け方も違う。

| 系統 | 何から作るか | 順序 |
|---|---|---|
| `sequence` | 本文リンク・題名の連番・公式シリーズの連番 | **意味を持つ** |
| `theme` | 共有タグ＋本文ベクトルの近さ | 意味を持たない |
| 版違い | 版の呼び名を除いた題名の一致 | 束ではない。畳んで代表だけ見せる |

`theme` の近さは**絶対値で測らない**。同じ題材ばかりの棚では無作為な2作でも
余弦が 0.94 ある（実測）。棚の対の平均と標準偏差を取り、そこからの隔たり
（z ≥ 2.0）で判断する。しきい値は棚ごとに違うので、固定値は置けない。

共有タグが1つだけの大きな束は、まとまりではなく**絞り込みの結果**である。
束としては出さず、保存した検索として扱うほうが正しい。

### 名前は一つに決めない

候補は名前の案を複数持つ（`name_options_json`）。題名の共通部分・公式シリーズ名・
共有タグ・作者、そして任意で利用者のモデルが出した案。先頭が既定になる。

**検索用の正規化キーを表示名に使わない。** `normalize_search_text` はカタカナを
ひらがなへ倒し記号を落とすので、そのまま名前にすると
「はいすぺいけめん女子の綾城さん」になる。表示用の語幹は
`collection_rules::display_title_stem`、走査では `parse_sequence_title` が別に作る。

公式シリーズ名も、そのままでは使えない。pixiv のシリーズには「有償依頼」151作の
ように受注区分がそのまま入っている。タグにも「リクエスト品」がある。
どちらも作者の管理用ラベルであって、物語の共通点ではない。

### 候補は下書きであって、決定ではない

`collection_suggestions` に入るのは**提案**である。題名や本文が似ているだけでは、
同じ連載なのか、同じ世界の別作品なのか、単に題材が似ているだけなのかを区別
できない。所属と最終的な順序を決める権限は利用者に残る
（`collection_pair_feedback` が判断を覚える）。

`origin` が `seed` の候補は1作から広げたもので、利用者が自分で作らせたもの。
`sweep` の候補は棚全体の走査で出たもの。同じ規則・顔ぶれのIDを安定させて再計算し、
採否は保つ。採用時は確認画面で選択・編集した作品配列の順序をそのまま保存する。
走査候補の一部を却下した場合、選択外の作品とのペアに否定を記録しない。

### 束ねる対象にしないもの

- **告知・活動報告** — 近況報告が複数あるだけで1つの連載とみなさない
- **リンクのハブ** — 次数が5以上で本文の薄い作品は、リンクの橋にしない。
    リンクの多い告知記事が無関係な作品を結びつけることがある
- **取得元をまたいだ同じ作品** — 作者表示名と題名は候補生成の手掛かりであり、
  本人確認ではない。同一サービスでは別作者IDを混ぜない。版の代表に元のリンクを
  引き継ぎ、跨サービスの本文包含も確認して、同じ本文を二度読む並びを減らす

### 束にしなかったものも返す

大きすぎるタグは束にしないが、**黙って捨てもしない**。「洗脳」824作は読む単位に
ならないが、利用者にとっては確かに一つの見方である。走査は
`saved_search_suggestions` としてそれを返し、画面は「保存した検索にする」を勧める。

### 一件ずつ確認し、途中で止められる

候補は系統ごとに最大200件を安定した順序で示す。続き物を既定にし、未登録作品の発見を
優先する。シリーズ内の前後編にも枠を残し、題名と作者で絞り込める一覧から選ぶ。

詳細には取得元と根拠を示し、本文プレビューから戻っても作品選択や読む順を保つ。
名前は入力でも既存案の選択でも決められる。採用後は次の候補を確認できる。
閉じる操作と保留は候補を削除しない。保留と編集中の値は画面の生存期間中に保持し、
アプリを終了しても候補そのものと確定した採否は台帳に残る。

### すでにある束にも同じ機能が効く

束は作ったあとで中身が変わる。作品を足せば共有タグが変わり、外せば題名の共通部分も
変わる。作ったときの名前に縛られる理由は無い。

- `propose_collection_names` が、いまの中身から名前の案を出し直す
- `name_collection_with_model` が、モデルにも名前と説明を考えてもらう
- どちらも**保存はしない**。案を並べるだけで、決めるのは利用者

### タグの出どころを混ぜない

取得元が付けたタグと、自分で付けたタグは**別の表に持つ。**

| 出どころ | 置き場 | 取り直しで |
|---|---|---|
| 取得元 | 保存版ごとの `snapshot_tags` | 新しい保存版が取得元の今のタグを持つ。過去の保存版のタグはそのまま |
| 自分（`manual`） | 作品ごとの `work_user_tags` | 変わらない |
| モデルの案を採った（`accepted_model`） | 作品ごとの `work_user_tags` | 変わらない |

**混ぜてはいけない。** 取得元が付けたタグとモデルが足したタグは確からしさが
違う。どちらか分からなくなった時点で、両方が信用できなくなる。
取り直しで変わってよいのも取得元のタグだけで、取得元が知らないことを取得元の都合で
消してはいけない。自分のタグは作者の保存版を変更しない。

同じ名前が取得元にも自分のタグにもあれば、出どころ付きの一覧では取得元の一件だけを見せる
（`work_tags_with_source`）。自分のタグを足すときも、すでに付いている名前は足さない。

外せるのは自分のタグだけ（`manual` と `accepted_model` をそれぞれの出どころで外す）。
取得元のタグは画面から外せない。

### 名前をモデルに考えてもらう（任意）

piep はモデルを同梱しない。OpenAI 互換のエンドポイントを設定で指すだけで、
LM Studio・Ollama・llama.cpp のいずれでも繋がる。既定は切ってあり、切ったままでも
決定的な案から名前は出る。

- 送るのは**題名・作者・タグ・公式シリーズ名だけ**、最大12作。本文は送らない
- 宛先は既定でこの端末の中だけ。外部は HTTPS に限り、同意をURLそのものへ
  結び付ける。URLを変えたら同意も試し書きの結果も破棄する
- HTTP redirect は追わない。検証したローカルURLから外部へ転送される経路を作らない
- 出力は JSON schema で縛り、検証に落ちたら決定的な案に戻す
- 婉曲な名前しか返さないモデルはある。**piep 側で回避はしない。**
  どのエンジンを使うかを決める権利は利用者にある

設定は「探す → 試す → 使う」の順にする。**番号を打たせない。**

1. よくある置き場所（LM Studio 1234、Ollama 11434、llama.cpp 8080…）を
   一度に叩いて、応答したものだけ出す。全部止まっていても2秒足らずで終わる
   名前は番号で決めつけず、応答から名指しする（`/health` の `service`、`/models` の
   `owned_by`）。名乗らないものだけ「ポート番号からの推測」と断って出す。8080 は
   llama.cpp とは限らず、Strata も使う
2. **保存する前に試し書きをする。** つながることと使えることは別で、
   安全調整の強いモデルは接続できても題材を言い換えた見出しを返す。
   棚から締まった束（3〜8作のタグ）を拾って渡し、返ってきたものを見せる
3. 見て納得したら有効にする

埋め込み専用のモデルは一覧から外す。選んでから使えないと分かるのは遅い。

**アプリ自身に推論はさせない。** 意味検索の埋め込み（fastembed + ONNX Runtime）は
同梱しているが、生成モデルは事情が違う。数GBの重みを配布物に載せることになり、
GPU の有無で挙動が変わり、モデルを選ぶ自由も失われる。この棚の題材では
「どのモデルなら婉曲にならないか」が実用の分かれ目なので、**選べることが要件**である。

### モデルに頼める仕事

どれも**押したときだけ動く**。裏で走るものは一つも無く、設定していなければ
機能そのものが画面に出ない。返ってくるのはすべて案で、採る操作は別にある。

| 仕事 | 送るもの | 置き場所 |
|---|---|---|
| 束の名前と説明 | 題名・作者・タグ・シリーズ名 | 候補の一覧、コレクション詳細 |
| タグの補完 | 題名・概要・いまのタグ・棚の語彙 | 作品詳細 |
| 言葉で探す | 説明の文・棚の語彙 | ライブラリの検索欄 |
| 作者の題材メモ | 対象作品のタグを端末内で集計（モデル・通信なし） | 作者ページ |
| 束の分割 | 題名とタグ | コレクション詳細 |
| あらすじ | **本文全体**（実文脈長・区切り数で分割し、重要文を階層的に選択） | 作品詳細 |
| 前回のあらすじ | **本文全体**（同上） | リーダーの、読む順がある文脈 |

本文を送るのは下2つだけで、`allow_body` を別に許可しないと**材料を読む前に
断る**。許していない相手のために本文を読み出すこと自体をしない。
先頭と末尾だけを抜き出してはならない。本文を隙間なく分割し、全チャンクから
部分記録を作り、原文範囲と順序を保ったまま段階的に統合する。1リクエストと
1レスポンスには固定のバイト上限を置く。

タグと検索語は**棚の語彙から選ばせる**。新語を作らせると、検索にも束ねにも
使えないものが増える。語彙に無い語が返ってきたら捨てる。

覚え書き（あらすじ・前回のあらすじ・作風）は台帳の `ai_notes` に、**どのモデルが
書いたか**（`model_id`）と一緒に残す。モデルを替えたときに古い文が混ざっていることに
気づけるようにするためで、失われても作品は失われない派生物である。材料と文の作り方の指紋
（`input_fingerprint`・`prompt_version`）も持ち、変わっていれば古いと示す。
覚え書きは対象と種類ごとに一行で、版の記録ではなく置き換えで持つ。
あらすじ・前回のあらすじの主欄と確認用の末尾原文は、`text` と nullable な
`source_tail` 列へ一緒に保存する。置き換えでは `source_tail` も書き直すので、確認用原文の
ないメモに上書きすれば、前の `source_tail` は消える。

### 合本と、本文の無い作品

- **合本**（「【前編＋中編】…」）は分冊のあいだにある別の作品ではなく、二つを
  まとめた版である。分冊がそろっているときだけ畳む — 合本しか手元に無いなら、
  それが本体だからで、消せば束から作品そのものが消える
- **本文0字の作品**（実測29件）は行だけあって中身が無い。一冊のEPUBには入れず、
  「収録できない」側に数える。そのまま入れると空の章になる

### コレクションの使い先

コレクションは正本であり、次の三つがその利用先になる。

| 使い先 | 何が起きるか |
|---|---|
| ライブラリ | タブとして一覧でき、作者詳細にも所属タブが出る |
| リーダー | どのコレクションから読み始めたかを保持し、読了位置に前後作品を出す |
| EPUB | ある時点の並びをスナップショットとして1冊へ書き出す（`export_collection_epub`） |

**EPUB のキューを永続化してグループに見せるのではなく、コレクションを正本にして、
キューは書き出し用の一時的な作業領域に留める。** 逆にすると、まとまりの価値が
EPUB 画面の中に閉じてしまう。

## 検索の索引

本体のデータとは別に索引を持つ。索引は棚の `derived/` に置く**いつでも作り直せる派生物**で
あって、失われても作品は失われない。バックアップにも入らない。

| 索引 | 置き場 | 何を引くか |
|---|---|---|
| 全文（今の版） | `derived/search-index/` | Tantivy。文書は作品ごと。n-gram と読みの正規化で、かな・カナ・ローマ字・部分一致を吸収する |
| 全文（過去の版） | `derived/history/search-index/` | 作り方は同じで、文書は改稿ごと |
| 意味検索 | `derived/search/semantic-v2/` | fastembed + ONNX Runtime（DirectML で GPU 実行）。今の版の作品ごとに、説明と本文のベクトルを持つ |

索引の文書は整数の鍵しか持てないので、作品・改稿との対応と、文書をどの保存状態から作ったかは
台帳の表（`search_documents`・`search_history_documents`・`semantic_documents`）に持つ。同期は
状態の違うものだけを作り直し、棚に無いものの文書を消す。起動では棚を開いたあと、別のスレッドで
同期する。

通常の検索は今の版の索引だけを引く。「過去版も含む」を明示した検索だけ過去の版の索引も引き、
結果は作品ごとに一件へまとめる。過去の改稿だけで一致した作品は、いちばん関連度の高い改稿の
関連度を半分にして並べ、一致した版を示す。意味検索は今の版だけを引く。作者・タグ・シリーズなどの
絞り込みは一覧の絞り込み（今の版）にかかる。

診断画面から、索引の追いつき具合と大きさの確認と、索引の最適化ができる。

## バックアップ

**バックアップは、棚そのものの自立した写しである**（`commands/backup.rs`、
`Library::backup`）。分割 ZIP は使わない。棚は実体を指紋で持つので、写しはそのまま棚として
開いて検査できる。

- 写し元を止めずに作る。台帳は SQLite のバックアップ API で写し、写した台帳が参照する
  ファイルの実体を写す。写す間は、写し元の実体が回収されない
- 写しは書き出し先の隣の `.piep-backup-<ID>.part` に作り、名札の代わりに
  `.backup-marker.json` を置く。作った瞬間から、棚としては開けない
- 写した中身を全部検査し（`verify`）、通ったら書き出し先の名前に改名して、最後に名札を
  `library.json` にする。**検査を通るまで、写しを棚として公開しない**
- 作品の識別子・保存版・編集・コレクション・利用者の状態など、台帳の行は識別子ごとそのまま
  写る。`derived/` の索引は写さない（開いたあとで作り直す）

**復元は、その場では行わない。** 開いている棚を入れ替えることになるからである。

1. 選んだ写しを開いて検査し、通ったら棚の隣に `library.restore-request.json` として予約する。
   今の棚の中（またはその親）、作者・シリーズのアーカイブ、正本に切り替える前に作った写しは
   予約の時点で断る
2. 次に起動したとき、棚を開く前に入れ替える。写しをもう一度開いて検査してから、今の棚を消さずに
   `library.before-restore-<UNIX 秒>` として隣へ退け、写しから**もう一つ写しを作って**
   棚の場所に置く。選んだ写しは手元に残る
3. 入れ替えに失敗したら、退けた棚を元に戻す。結果は `library.restore-result.json` に残し、
   予約は成否によらず消す（失敗した予約で起動のたびに止まらない）

**作者・シリーズのアーカイブは、棚の部分写しである**（`Library::copy_works`、`partial.rs`）。
選んだ作品の保存版・編集・利用者の状態・タグ・覚え書きなどを、自立した棚の形で写す。名札は
`library-part.json` で、棚としては開けず、棚の入れ替えには使えない。

取り込み（`Library::merge_part`）は今の棚に**無い行だけを足す。** 今の棚にある作品・記録は
書き換えない。行は識別子ごと写しているので、取り込めるのは同じ棚（同じ棚の写しを含む）から
作った部分写しだけである。同じ作品や作者が別の識別子で保存し直されていれば、その作品は足さずに
数だけ伝える。棚から外していた作品は、残っていた記録のまま棚へ戻す。

覚え書き（`ai_notes`）は台帳の表なので、棚のバックアップにはそのまま入る。部分写しにも、
作品の覚え書きは作り直すと重いので一緒に入れる。利用者が採用した `accepted_model` のタグや
候補への採否は利用者の判断なので、派生物として捨ててはいけない。
