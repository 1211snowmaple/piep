# 取得の方針

piep が外部と通信するのは、**pixiv と FANBOX からデータを取得するときだけ**である。
それ以外の通信路は持たない。

## 相手のサービスに負担をかけない

これは礼儀の問題であると同時に、**利用者のアカウントを守るための実務**でもある。
乱暴に取ると制限を受けるのは利用者本人である。

- 画像などのアセット取得は同時 4 本に制限する
  （`asset_downloader.rs` のセマフォ）
- 更新確認の同時実行数は利用者が選べるが、**既定値は控えめにする**
- 速く大量に取ることを目的にした機能は作らない。
  制限を迂回する仕組みも作らない

利用にあたっては pixiv および FANBOX の利用規約に従う。

## 認証

内蔵の WebView2 でサービスにログインする。**piep がパスワードを受け取ることは
ない。** 利用者はサービス自身のログイン画面に入力する。

| サービス | 方式 |
|---|---|
| pixiv | OAuth。未認証／アクセストークンのみ／自動更新付きリフレッシュトークンの3状態を扱う（`pixiv_api/token_manager.rs`）。加えて、ログイン画面を通ったときに web のセッション Cookie も受け取る |
| FANBOX | セッション Cookie |

pixiv の Cookie は**付け足しであって、接続の条件ではない**。取れなくてもログインは
成功とし、更新確認は従来の経路で動く。Cookie は UA と対でだけ意味を持つので
（`cf_clearance` が発行時の UA に紐づく）、**片方だけを保存しない**。

### 要る鍵だけを持つ

ログイン窓が持ち帰る Cookie には、解析や広告の識別子まで混じっている
（実測で pixiv は 36 個 2,869 文字、FANBOX は 14 個 1,086 文字）。
**相手が要るのはセッションひとつで、実測でもそれだけで返事は変わらない。**

残すのは次の二つだけとし、取得元ごとに別の作法を作らない
（`auth::essential_cookies`）。

- セッション（`PHPSESSID` / `FANBOXSESSID`）— 名乗るための鍵そのもの
- `cf_clearance` — 内蔵ブラウザが自分で通り抜けた Cloudflare の通行証

**利用者の閲覧履歴に当たるものを、送りもしないし持ちもしない。**
保存済みの古い値にも同じ規則を通すので、繋ぎ直さなくても余計なものは出ていかない。

## 二つの口を、仕事で分ける

pixiv には相手はひとつでも口がふたつある。どちらも上位集合ではないので、
**それぞれが一意に優れている仕事だけを割り当てる。同じ仕事を両方にさせない。**

| 仕事 | 使う口 | 理由 |
|---|---|---|
| 本文・挿絵の取得 | アプリ API（`/webview/v2/novel`） | `[pixivimage:]` を解決できるのはこちらだけ |
| 変わったかどうかの検出 | web（`/ajax/user/{id}/novels`） | 更新時刻を持ち、100件をまとめて返す |
| シリーズの表紙 | web（`/ajax/novel/series/{id}`） | アプリ API は各話の画像しか返さない |
| 本文の退避路 | web（`/ajax/novel/{id}`） | 本文の中身はアプリ API と一致する。切り出しが壊れた日のために |

退避路へ降りるのは、webview から本文を**切り出せなかったとき**だけ。取得制限や
404 では降りない（相手を二度叩くだけになる）。web は `[pixivimage:]` を解決しない
ので、挿絵を参照する作品でここへ降りたときは、**欠けたまま保存せずに失敗させる**。

取得した資格情報はローカルにのみ保存する。**ログや診断の出力に混ぜない。**

## 保存の流れ

```
内蔵ブラウザでページを開く
   ↓ 「候補を取得」
そのページから見つかった作品・シリーズ・作者を候補として並べる
   ↓ 利用者が選ぶ
本文 JSON と画像を downloads/ へ保存し、メタデータを piep.db へ
```

**候補の提示と実際の保存を分ける。** 開いたページから何が取れるかを見せてから、
何を取るかを利用者が決める。

## 保存するもの

- 本文（原本の JSON をそのまま `original_json_path` に）
- 画像などのアセット
- タグ、公開日、作者、シリーズといったメタデータ

→ [データの持ち方](04-data.md)

## 取得できなかったとき

失敗の理由には分類の札を付ける（`[取得制限]` など）。ジョブは失敗した分だけを
後から再試行できる。**全部やり直させない。**

閲覧制限は通信障害と区別し、`held`（保留）として保存する。通常の更新確認・
失敗分の再試行・まとめ保存では再取得しない。一覧の `isRestricted` が分かっている
ときは本文への問い合わせ自体を省く。空の本文・添付や閲覧制限のプレビューを
保存成功にせず、保存先フォルダーも作らない。保存済みの完全な版は守る。

「保留・非表示」は期限なく残る、取り消せる一覧とする。支援プラン・連携アカウント
の変更後、利用者が選んだ作品だけを再確認する。必要額と作者IDが分かる場合は
支援プランをジョブにつき一度だけ照合し、不足している投稿の本文は取得しない。
閲覧可能になったものだけ候補へ戻し、保存・監視登録は利用者の別操作とする。
非表示の一括解除でも閲覧制限は解除しない。保留状態と理由はバックアップに含める。

投稿自体の無料公開・必要額変更など、保留時の情報が古くなる場合もある。
「投稿の公開条件も再確認」では古い必要額による事前判定を省き、選んだ投稿を
1件ずつ確認する。一度に20件まで、開始間隔は1分以上とし、実際の閲覧制限は
必ず尊重する。これにより、支援プランを上げなければ永久に戻せない状態を避ける。

過去の候補を次の更新確認に戻すのは、現在選択されている監視対象に属する場合だけ。
作者名ではなく取得元のIDで照合する。一度きりの保存失敗が作者の監視登録を意味する
ことはない。保存元がなくなった改稿候補は未保存の新作へ正規化する。

結果表示は全件失敗・一部失敗・完了（保留あり）を区別し、保留をエラーや保存済みの
件数に混ぜない。生のジョブ状態 `failed` は互換性のため維持し、成功した処理が
混在する場合に表示層で「一部失敗」とする。

## 取得先への配慮

PixivのAPIクライアント・アクセストークンとFANBOXの接続はジョブ内で再利用する。
認証情報の異なるジョブ間では共有しない。APIの間隔は取得元ごとにアプリ全体で
800ms以上あけ、ページ送り・同時ジョブにも適用する。429では `Retry-After` を
尊重し、指定がなければ60秒待つ。再試行はジョブ側だけが担い、多重化しない。
FANBOXのCloudflare確認は連続再試行せず一時停止する。保留の明示的な再確認も
開始間隔を1分以上あける。閲覧制限を回避する経路は設けない。

## 改稿の扱い

同じ作品を取り直したとき、前の版は `download_versions` に残る。
上書きして消すことはしない。
