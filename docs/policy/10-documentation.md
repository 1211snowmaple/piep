# ドキュメントの作り

## 三種類しかない

**分けるのは、誰が書くかではなく誰が読むかである。**

| 種類 | 誰のためか | 場所 | 誰が書くか |
|---|---|---|---|
| **使い方** | piep を入れた人 | `docs/guide/` | 人が書く |
| **方針書** | 次に手を入れる人 | `docs/policy/` | 人が書く。ここが唯一の一次資料 |
| **リファレンス** | 境界を触る人 | `docs/reference/` ほか | ソースから生成する。人は書かない |

この三つ以外は置かない。

かつてここは二種類だった。人が書くものと、機械が生成するものである。書き手で
分けたその表には**使う人の居場所が無かった**ので、使い方の説明は README へ溜まり、
サイトの外に出た。サイトのホームでいちばん目立つボタンが「方針を読む」を指し、
piep を入れた人が最初に押すボタンが設計文書へ向いていた。

### まだ実装していない設計は `docs/plan/` へ

方針書は今どうなっているかを書く。**これから作るものは方針書ではない。**

置き場が無いと、計画は方針書に混ざる。実際 `policy/11-collection-discovery.md` は
「依存順の実装チケット」と「棄却する仮説」を持ったまま、01〜10 と同じ番号列に
並んでいた。禁止だけを足しても同じことが起きるので、置き場のほうを作る。

`docs/plan/` の文書は**実装した時点で消す**。残すべきものは方針書へ移す。
消す前提なので、ここには日付を書いてよい。

### 日付入りの調査レポートを `docs/` に置かない

かつて `docs/` は日付入りの調査・提案レポートだけで埋まっていた。14本あって、
「今どうなっているか」を書いた文書は一本もなかった。実装済みの提案書が提案の
まま残り、読むと「まだ無い機能」に見えた。1529行の現状棚卸しは、書かれた翌月には
もう古かった。

**方針書には日付を書かない。** 「いつ調べたか」ではなく「今どうなっているか」を
書く現在形の文書とし、**更新はソースの変更と同じコミットで行う**。

調査の経緯を残したいときは、コミットメッセージと git 履歴に書く。
そこが本来の置き場所である。

## 生成されるもの

```bash
npm --prefix docs-tools run docs:build
```

| 生成物 | 元 | 道具 |
|---|---|---|
| [IPC コマンド契約](../reference/ipc.md) | `#[tauri::command]` と `invoke()` | 自作の抽出器 |
| [イベント契約](../reference/events.md) | `emit()` と `subscribeTauriEvent()` | 同上 |
| [スキーマ](../reference/schema.md) | `schema.rs` の `CREATE TABLE` | 同上 |
| Rust API | `src-tauri/src/` の `///` `//!` | `cargo doc` |

**LLM は使っていない。** すべて構文解析による決定論的な変換である。だから
同じソースからは必ず同じ出力が出るし、CI で機械的に検査できる。

生成物は git で追跡しない。読む場所は GitHub Pages である。

→ 仕組みの詳細は [`docs-tools/README.md`](https://github.com/1211snowmaple/piep/blob/main/docs-tools/README.md)

## 数を手で書かない

散文の中の数は必ず古くなる。ここに書いてあった「140個中わずか6個」は、書いた
時点ですでに違っていた。`index.md` の「28のテーブル」も、英語コメントの
「約620行」も同じである。**三つとも、抽出器がすでに数えていた値を手で写した
ものだった。**

だから数の置き場を一つにする。文の中では次のように書く。

```markdown
コマンドは <!--stat:commands.total-->159<!--/stat--> 個ある
```

HTML コメントは GitHub でも VitePress でも描画されないので、読む人には数字しか
見えない。書き戻すのは `sync-stats.mjs` で、`docs:check` が古くなっていないかを
検査する。**知らない名前を書いたら落ちる**ので、綴り違いが「二度と更新されない数」
になって残ることもない。

| 使える名前 | 何の数か |
|---|---|
| `commands.total` `commands.documented` `commands.undocumented` `commands.called` | IPC コマンド |
| `events.total` `tables.total` | イベントとテーブル |
| `screens.count` | 画面（`readme-shots.spec.ts` の `shots` 表） |
| `assist.features` | AI 補助の機能（`assist.rs` の `current_prompt_version`） |
| `comments.rust.english` `comments.ts.english` | 英語のまま残る説明コメント |
| `policy.count` `guide.count` | 方針書と使い方の本数 |

数える先が増えたら `sync-stats.mjs` の `STATS` に足す。**数える場所はソースで
あって、文書ではない。**

## 使い方の説明は、実際の画面と突き合わせる

境界の契約にはドリフト検査があるのに、人が読む説明には何も無かった。画面が一つ
増えても、増えたことを誰も教えてくれない。

突き合わせる相手は `e2e/readme-shots.spec.ts` の `shots` 表である。ここは
「どの画面を撮るか」の一次資料で、経路まで持っている。撮る側と説明する側が同じ表を
見ていれば、片方だけが増えたときに気づける。

`docs/guide/03-screens.md` の各節には `<!--screen:home-->` のような目印を置く。
見出しの文言は日本語で自由に付けたいので、対応づけは文言ではなく目印で行う。
`check-guide-screens.mjs` が両方向を見て、どちらかにしか無ければ落とす。

スクリーンショットは CI でも撮り直している（`playwright test` が `readme-shots` を
含む）。撮る手順は各画面を実際に開き、主題の文字が出るまで待つ。だから**説明した
画面が壊れたり消えたりすれば CI が落ちる**。

ただし撮った絵とコミットされている絵を画素で突き合わせてはいない。手元は開発
サーバー、CI は静的配信で、描画が完全に一致する保証が無いためである。そこを厳密に
比べると、本題でない失敗が増える。見た目が変わったときは手元で撮り直す。

## コメントの書き方

**記述言語は日本語に統一する。**

### 何を書くか

型と名前から読み取れることは書かない。書くのは、**コードを見ても分からないこと
だけ**である。

```rust
// 悪い例 — 型を読めば分かる
/// ダウンロードIDを受け取り、DownloadEntry を返す。

// 良い例 — コードを見ても分からない
/// これは認識のための指紋であって、アプリが作るテーブルの一覧ではない。
/// ここに新しいテーブルを足すと、既存のライブラリがすべて異物と判定されて
/// 退避・初期化される。何も足してはならない。
```

判断の基準はひとつ。**その説明が無かったら、次に触る人が事故を起こすか。**
起こすなら書く。起こさないなら書かない。

### Rust

```rust
//! モジュールの役割と、担保している不変条件。
//! 「何をするか」ではなく「なぜこの形か」を書く。

/// 一行で何であるかを述べる。
///
/// 詳しい説明。呼ぶ側が知らないと事故る前提はここに書く。
///
/// # Errors
/// どんなときに `Err` になるか。
///
/// # Panics
/// パニックしうるなら必ず書く。
```

角括弧はリンク記法として解釈される。`[newpage]` のような literal を書くときは
`` `[newpage]` `` のようにバッククォートで囲む（`cargo doc` の警告はゼロを保つ）。

### TypeScript

```ts
/**
 * 一行で何であるかを述べる。
 *
 * 詳しい説明。なぜこの実装かを書く。
 *
 * @param id 説明が要る引数だけ書く。型から自明なものは書かない
 * @returns 型から自明でないときだけ書く
 */
```

**連続した `/** */` を1つの宣言の上に置かない。** TypeScript は両方を同じ宣言に
紐付けるので、別の関数の説明が混ざって表示される。

### 移行

英語で書かれた既存のコメントは**一括では翻訳しない**。

| | 残り |
|---|---:|
| Rust の `///` `//!` | <!--stat:comments.rust.english-->536<!--/stat--> 行 |
| TS の JSDoc | <!--stat:comments.ts.english-->476<!--/stat--> 行 |

この数は日本語の文字を含まない説明コメントの行数で、目安である（URL だけの行や
`# Errors` のような見出しも混ざる）。厳密ではないが、**手で書いた見積もりが古く
なるよりは正しい**。

モジュール見出し（`//!` と各ファイル冒頭）から先に日本語化し、残りは触った
ファイルから直す。生成されるサイトは日英が混ざっていても壊れないので、
段階移行で困らない。

## IPC コマンドの説明を増やす

`///` の付いたコマンドは <!--stat:commands.total-->159<!--/stat--> 個中
<!--stat:commands.documented-->37<!--/stat--> 個である。Rust の `///` は内部の関数や
構造体には手厚く付いていて、**フロントとの境界にはほとんど付いていない**。

ここが最大の空白であり、ラチェット検査（[品質](09-quality.md#境界のドリフト検査)）が
守っているのはこの数字である。**コマンドに触ったら説明を書く。**

書くべきは、フロント側が知らないと事故る前提である。

- この呼び出しは何を変えるのか（読むだけか、書くのか）
- 失敗する条件
- 前後関係（先に呼んでおくべきものがあるか）
- 数字の意味（何が分母で何が分子か）
