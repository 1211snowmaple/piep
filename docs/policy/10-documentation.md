# ドキュメントの作り

## 二種類しかない

| 種類 | 場所 | 誰が書くか |
|---|---|---|
| **方針書** | `docs/policy/` | 人が書く。ここが唯一の一次資料 |
| **リファレンス** | `docs/reference/` ほか | ソースから生成する。人は書かない |

この二つ以外は置かない。

### 日付入りの調査レポートを `docs/` に置かない

かつて `docs/` は日付入りの調査・提案レポートだけで埋まっていた。14本あって、
「今どうなっているか」を書いた文書は一本もなかった。実装済みの提案書が提案の
まま残り、読むと「まだ無い機能」に見えた。1529行の現状棚卸しは、書かれた翌月には
もう古かった。

**方針書には日付を書かない。** 「いつ調べたか」ではなく「今どうなっているか」を
書く現在形の文書とし、**更新はソースの変更と同じコミットで行う**。

調査の経緯を残したいときは、コミットメッセージと git 履歴に書く。
そこが本来の置き場所である。

## 生成されるもの

```bash
npm --prefix docs-tools run docs:build
```

| 生成物 | 元 | 道具 |
|---|---|---|
| [IPC コマンド契約](../reference/ipc.md) | `#[tauri::command]` と `invoke()` | 自作の抽出器 |
| [イベント契約](../reference/events.md) | `emit()` と `subscribeTauriEvent()` | 同上 |
| [スキーマ](../reference/schema.md) | `schema.rs` の `CREATE TABLE` | 同上 |
| フロント API | `src/` の JSDoc | TypeDoc |
| Rust API | `src-tauri/src/` の `///` `//!` | `cargo doc` |

**LLM は使っていない。** すべて構文解析による決定論的な変換である。だから
同じソースからは必ず同じ出力が出るし、CI で機械的に検査できる。

生成物は git で追跡しない。読む場所は GitHub Pages である。

→ 仕組みの詳細は [`docs-tools/README.md`](https://github.com/1211snowmaple/piep/blob/main/docs-tools/README.md)

## コメントの書き方

**記述言語は日本語に統一する。**

### 何を書くか

型と名前から読み取れることは書かない。書くのは、**コードを見ても分からないこと
だけ**である。

```rust
// 悪い例 — 型を読めば分かる
/// ダウンロードIDを受け取り、DownloadEntry を返す。

// 良い例 — コードを見ても分からない
/// これは認識のための指紋であって、アプリが作るテーブルの一覧ではない。
/// ここに新しいテーブルを足すと、既存のライブラリがすべて異物と判定されて
/// 退避・初期化される。何も足してはならない。
```

判断の基準はひとつ。**その説明が無かったら、次に触る人が事故を起こすか。**
起こすなら書く。起こさないなら書かない。

### Rust

```rust
//! モジュールの役割と、担保している不変条件。
//! 「何をするか」ではなく「なぜこの形か」を書く。

/// 一行で何であるかを述べる。
///
/// 詳しい説明。呼ぶ側が知らないと事故る前提はここに書く。
///
/// # Errors
/// どんなときに `Err` になるか。
///
/// # Panics
/// パニックしうるなら必ず書く。
```

角括弧はリンク記法として解釈される。`[newpage]` のような literal を書くときは
`` `[newpage]` `` のようにバッククォートで囲む（`cargo doc` の警告はゼロを保つ）。

### TypeScript

```ts
/**
 * 一行で何であるかを述べる。
 *
 * 詳しい説明。なぜこの実装かを書く。
 *
 * @param id 説明が要る引数だけ書く。型から自明なものは書かない
 * @returns 型から自明でないときだけ書く
 */
```

**連続した `/** */` を1つの宣言の上に置かない。** TypeScript は両方を同じ宣言に
紐付けるので、別の関数の説明が混ざって表示される。

### 移行

英語で書かれた既存のコメントは**一括では翻訳しない**。

| | 量 |
|---|---|
| Rust `///` の英語分 | 約620行 |
| Rust `//!` の英語分 | 15行 |
| TS JSDoc の英語分 | 約650行 |

モジュール見出し（`//!` と各ファイル冒頭）から先に日本語化し、残りは触った
ファイルから直す。生成されるサイトは日英が混ざっていても壊れないので、
段階移行で困らない。

## IPC コマンドの説明を増やす

現在、`///` の付いたコマンドは 140個中わずか6個である。Rust の `///` 1125行は
内部の関数や構造体に付いていて、**フロントとの境界にはほとんど付いていない**。

ここが最大の空白であり、ラチェット検査（[品質](09-quality.md#境界のドリフト検査)）が
守っているのはこの数字である。**コマンドに触ったら説明を書く。**

書くべきは、フロント側が知らないと事故る前提である。

- この呼び出しは何を変えるのか（読むだけか、書くのか）
- 失敗する条件
- 前後関係（先に呼んでおくべきものがあるか）
- 数字の意味（何が分母で何が分子か）
