# Rust 側の方針

## コマンドの設計

`commands/` は IPC の入口である。**入口であって、仕事場ではない。**

```rust
#[tauri::command]
pub async fn db_get_downloads(app: tauri::AppHandle, ids: Vec<i64>) -> Result<Vec<DownloadEntry>, String> {
    run_db_blocking(app, move |state| state.db.get_downloads(&ids)).await
}
```

| 決めごと | 理由 |
|---|---|
| 戻りは `Result<T, String>` で統一 | IPC は JSON を渡す。型の付いたエラーを送っても向こうでは文字列になる |
| 中身は `database/` `epub/` `downloader/` に置く | コマンドが薄いと、同じ処理をテストから直接呼べる |
| DB 作業は `run_db_blocking` へ | SQLite の操作は同期的で、async の中で走らせると WebView の応答が止まる |
| 引数は snake_case のまま書く | Tauri 2 がフロント側で camelCase に変換する（`source_id` → `sourceId`） |

新しいコマンドを足したら **`generate_handler!` への登録を忘れないこと。**
忘れても Rust はコンパイルが通り、フロントから呼んだときに初めて失敗する。
この取りこぼしは CI が検出する（[検査](09-quality.md#境界のドリフト検査)）。

→ 一覧は [IPC コマンド契約](../reference/ipc.md)

## イベント

進捗のように、コマンドの戻りでは表せないものを送る。

```rust
let _ = app.emit("update-job-progress", snapshot);
```

コマンドと違い、**送る側と受ける側のどちらにも相手を指す型が無い。**
名前が合っているかどうかは実行するまで分からないので、送出と購読の対応も
自動で突き合わせている。

→ 一覧は [イベント契約](../reference/events.md)

## データベース

### 接続

`rusqlite` を `r2d2` のプールで持つ。ライブラリは一つのプロセスが排他的に持ち、
起動時に助言ロックを取る。

ロックファイルは**終了後もディスクに残す**。消してしまうと、既存のプロセスが
古い inode のロックを持ったまま、別のプロセスが別の inode を作ってロックできて
しまう。OS はハンドルが落ちた時点で解放する。

## 検索

二つの索引を併用する。**どちらもいつでも作り直せる派生物**で、失われても
作品そのものは失われない。

### 全文検索（Tantivy）

日本語のために、次を積み重ねている。

- 形態素解析（lindera + ipadic）
- n-gram（部分一致のため）
- 読みの正規化（`wana_kana` + `unicode-normalization`）でかな・カナ・ローマ字の
  表記ゆれを吸収する

**書き手は一つだけ。** Tantivy は一つのディレクトリに `IndexWriter` を一つしか
許さない。アプリは起動時にライブラリを一つ開いて排他ロックを取るので、これが
実際の使われ方と一致する。テストを並列に走らせると一つのプロセスに何十もの
writer ができ、Windows では "Access is denied" でコミットが失敗する。だから
`cargo test` は `--test-threads=1` で走らせる。

### 意味検索

`fastembed` + ONNX Runtime。Windows では DirectML で GPU 実行する。
モデルは数百MBあるので、使う場合だけ取得する。

近似最近傍は `hnsw_rs`。

## 更新監視

監視している作品の改稿、作者の新作、シリーズの続編を一つのジョブで確認する。

### 変わったかどうかを、二段で見る

pixiv の作品詳細 API には**更新時刻に当たるフィールドが無い**。改稿を知る手段は
web（`/ajax/user/{id}/novels`）の `updateDate` だけで、こちらは 1 リクエストで
100 件をまとめて返す。

1. **web の一覧**（`WebUpdateIndex`）— 保存済みの `source_updated_at` と同じなら、
   アプリ API を一度も叩かずに終わる
2. **メタデータの指紋**（`pixiv_meta_signature`）— 一覧が使えないとき、および
   一覧が「変わった」と言ったときの裏取り
3. **本文**（`DEEP_CHECK_INTERVAL_DAYS`）— 指紋に出ない改稿のための保険

指紋を残してあるのは、一覧が使えない状態（セッションが無い・切れた）でも
**今までどおり動くべき**だから。web の一覧は速さのための前段であって、
正しさの前提ではない。

### 少なく返ってきた一覧を、「変わっていない」と読まない

web の一覧はログインしていないと R-18 作品を**黙って**落とす。`error` は false の
まま件数だけが減るので、数えなければ「更新なし」と区別できない。

**投げた ID の数と返ってきた件数が違えば、それ自体を失敗として扱う**
（`PixivError::PartialListing` → `AuthRequired`）。ジョブを止めて再接続を促す。
黙って通すと、セッションが切れた日にライブラリ全体が「最新です」と表示される。

### 更新時刻を覚えてよいとき

`source_updated_at` を覚えるとは「次はこの値と同じなら本文を見ない」と決めること。
**手元の本文がその更新のあとのものだと言えなければ覚えない**（`may_remember`）。

- 本文を取り直した直後 → 覚える
- 本文まで突き合わせた時刻がその更新より後 → 覚える
- どちらとも言えない／時刻が読めない → 覚えない

言えないまま覚えると、その改稿は二度と拾われなくなる。覚えそこねても、次の確認で
従来どおり確かめるだけで済む。

### 数え方

**待機列に入ったものを総数と処理済みに数える。見つけただけの候補は数えない。**

かつて `totals` / `processed` は候補を除いた項目だけを数えていた。「10 / 10件を
処理 · 候補 101」は「監視対象を10件確認し終え、そこから候補が101件見つかった」
という意味だったが、伝わらなかった。

さらに悪いことに、候補は「保存する」と決めた時点で待機列に入りワーカーが順に
処理するのに、総数から外れていた。**自動保存で101件を保存している最中も、
進捗は 10/10（完了）のままだった。**

### 一度断ったものを覚える

チェックを外すだけでは「今は選ばない」の意味しかなく、次の確認でまた出る。
「二度と出さない」を伝える口を別に用意している
（`dismiss_update_candidate`）。

## エラーの扱い

- 利用者に見せるメッセージは日本語で、**次に何をすればよいかを書く**

  > このライブラリは別のpiepプロセスで使用中です。ほかのpiepウィンドウを
  > 閉じてから、もう一度起動してください。

- 失敗の理由には分類の札を付ける（`[取得制限]` など）。まとめて数えられるようにする
- 進捗イベントは失敗しても無視してよい（`let _ = app.emit(...)`）。
  受け手が居ないことは異常ではない
