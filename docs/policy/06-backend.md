# Rust 側の方針

## コマンドの設計

`commands/` は IPC の入口である。**入口であって、仕事場ではない。**

```rust
#[tauri::command]
pub async fn list_saved_searches(app: tauri::AppHandle) -> Result<Vec<SavedSearchView>, String> {
    run_db_blocking(app, move |state| {
        let library = state.shelf.library()?;
        saved_search_shelf::list(&library)
    })
    .await
}
```

| 決めごと | 理由 |
|---|---|
| 戻りは `Result<T, String>` で統一 | IPC は JSON を渡す。型の付いたエラーを送っても向こうでは文字列になる |
| 中身は `library/` `epub/` `downloader/` などに置く | コマンドが薄いと、同じ処理をテストから直接呼べる |
| DB 作業は `run_db_blocking` へ | SQLite の操作は同期的で、async の中で走らせると WebView の応答が止まる |
| 引数は snake_case のまま書く | Tauri 2 がフロント側で camelCase に変換する（`source_id` → `sourceId`） |

新しいコマンドを足したら **`generate_handler!` への登録を忘れないこと。**
忘れても Rust はコンパイルが通り、フロントから呼んだときに初めて失敗する。
この取りこぼしは CI が検出する（[検査](09-quality.md#境界のドリフト検査)）。

→ 一覧は [IPC コマンド契約](../reference/ipc.md)

## イベント

進捗のように、コマンドの戻りでは表せないものを送る。

```rust
let _ = app.emit("update-job-progress", snapshot);
```

コマンドと違い、**送る側と受ける側のどちらにも相手を指す型が無い。**
名前が合っているかどうかは実行するまで分からないので、送出と購読の対応も
自動で突き合わせている。

→ 一覧は [イベント契約](../reference/events.md)

## データベース

### 接続

書き込みは `Mutex<Connection>` の一本だけが行い、読み取りは読み取り専用の接続を借りる
（`Library::reader`）。ライブラリは一つのプロセスが排他的に持ち、起動時に助言ロックを取る。

ロックファイルは**終了後もディスクに残す**。消してしまうと、既存のプロセスが
古い inode のロックを持ったまま、別のプロセスが別の inode を作ってロックできて
しまう。OS はハンドルが落ちた時点で解放する。

## 検索

二つの索引を併用する。**どちらもいつでも作り直せる派生物**で、失われても
作品そのものは失われない。

### 全文検索（Tantivy）

日本語のために、次を積み重ねている。

- 形態素解析（lindera + ipadic）
- n-gram（部分一致のため）。n-gram の欄にも語の位置を持たせる。位置が無いと句の検索が
  ばらばらの文字に当たり、具体的な語で棚の4割が当たった（`a_phrase_matches_only_where_the_words_actually_sit_together`）
- 読みの正規化（`wana_kana` + `unicode-normalization`）でかな・カナ・ローマ字の
  表記ゆれを吸収する

**書き手は一つだけ。** Tantivy は一つのディレクトリに `IndexWriter` を一つしか
許さない。アプリは起動時にライブラリを一つ開いて排他ロックを取るので、これが
実際の使われ方と一致する。テストを並列に走らせると一つのプロセスに何十もの
writer ができ、Windows では "Access is denied" でコミットが失敗する。だから
Rust の試験は `cargo nextest` でテストごとに別のプロセスに分けて走らせる。

**書き手を捨てて統合を打ち切らない。** tantivy の書き手は捨てると、走っている統合の
結果も捨てる。保存のたびの少しずつの同期は使い回す書き手で書き、統合は既定の方針に
任せる。書き手を手放すとき（使われないまま5分たった、作り直しに場所を譲る、単独サーバーが棚を
入れ替える）は、統合が終わるのを待つ。作り直しと 2,000 件以上の同期だけを排他の書き手で書き、最後に
一つにまとめる。少しずつの同期まで使い捨ての書き手で書いていたころ、実際の棚で
1文書だけのセグメントが4千個たまり、打ち切られた統合の書きかけが 39GB 残って、保存
1件に15秒かかった。

既定の検索対象は現在版で、Tantivyにも現在版の題名・本文・現在版だけの添付を一作品
一文書で入れる。`versions=all` が明示されたときだけ、保存済みJSONと版ごとのテキスト
添付を読み、現在版の結果と作品IDで統合する。過去版だけに一致した結果は版番号を返す。
版別の作者・タグ・シリーズ・あらすじは保存していないため、それらの条件は現在の作品
メタデータへ適用する。

索引を作る原本の読み込みや解析に失敗したときは、空本文として成功させない。
直前の索引を保持し、その作品を未処理のまま残して再試行できるようにする。

SQLのページカーソルは並び順だけでなく、正規化した絞り込み全体のscopeを持つ。条件を
変えたあとに古いカーソルを送っても境界として使わず、新しい一覧の先頭から答える。

### 意味検索

`fastembed` + ONNX Runtime。Windows では DirectML で GPU 実行する。
モデルは数百MBあるので、使う場合だけ取得する。
GPUでの埋め込みは一度に16断片までにし、ローカルLLMや画面描画のための余力を残す。
作品数の上限だけでは長編の断片数を抑えられないため、推論のバッチも制限する。
CPUで実行する場合はライブラリの既定のバッチを使う。この制限だけで外部の推論
サーバーとのメモリ競合がすべて解消するとは限らない。

**索引は一作品につき一行。** 別のデータベース（`semantic-v2`）の `semantic_works`
に、メタデータのベクトルと、本文断片の正規化重心だけを持つ。検索結果も必ず一作品
一候補で返す。

**一節検索はしない。** 「この段落に似た段落」を返す機能を持たないので、そのため
だけの索引も持たない。本文断片のデータベース、ANN のシャード、HNSW、RRF による
hybrid 合成は、作られたまま使われていなかったので消した。近似最近傍のライブラリも
依存から外してある。

**通常検索は Tantivy のままにする。** 「言葉で探す」では入力文をLLMなしで意味索引へ
渡せる。LLM が使える場合はタグと検索文への言い換えも選べる。既存の絞り込みタグは
消さずに統合する。本文の語句を覚えているときは通常検索が有利で、意味検索の結果から
同じ語で通常検索に切り替えられる。

**有効・無効はデータベースに永続化する。** 手動の再構築、自動保守、新規保存、編集や
タグ変更による個別の再索引が、すべて同じ値を見る。無効にすると作品ベクトルと被覆
状態を削除する。

**長さで順位が上がらないようにする。** 一作品一行にしたのは、断片のヒット数を
作品ごとに足し上げていたせいで長編が有利になっていたためである。断片を作品へまとめる
必要が出たときも、ヒット数の単純加算はしない（最大値か、固定個数の平均を使う）。
件数・カーソル・完了条件の分母も、結果の単位とそろえる。

**失敗を成功に変えない。** 利用者が明示的に実行した意味検索が失敗したときは、空の
成功結果へ変換せずエラーとして返す。埋め込みモデルの初期化失敗もプロセス全体に
固定せず、次の操作で試し直せるようにする。

## 更新監視

監視している作品の改稿、作者の新作、シリーズの続編を一つのジョブで確認する。

作品ごとの監視と一回きりの作者の確認は、棚の作品から対象を作る。ジョブには取得元の作品 ID を残し、
実行時の今の版の取得した応答と比べる。棚から外した作品は取得せず、利用者の編集は改稿として数えない。
確認日時は、照合した保存版が今の版である間だけ棚へ記録する。pixiv の本文を省くには、14 日以内の本文の
照合・メタデータの一致・要る実体があることを、すべて満たす必要がある。一覧と作品情報の両方で、読書用の
対応と反映中の編集を確かめる。取得元の応答に不足や閲覧の制限が記録されていれば、本文を確かめ直す。

作者の一覧の走査も棚の今の版を使い、同じジョブの作品の確認と一覧を共有する。更新日時を基準に覚えるのは、
手元の本文の保存か照合より前の更新だと言える場合だけ。FANBOX は過去の保存済みの投稿も調べるが、前回の
位置より古い未保存の投稿を再び出さず、確認の位置を過去へ戻さない。

監視の対象とグループは棚に置き、棚の UUID で指す。操作は要求 ID と監視設定の世代で確定し、同じ要求を
送り直しても一度しか書かない。ジョブの確認の結果は設定の世代を進めず、実行を始めた対象へだけ記録する。
消して登録し直した対象へ、前のジョブの確認位置を書かない。候補の元の入力・保留・非表示の判断も棚へ書く。
見つけ直しても利用者の判断を戻さず、保存のあとの片付けでも非表示は取り消さない。

ジョブ・実行の項目・ログは棚の実行キュー（`AppState::jobs()`）にある。入力は圧縮したファイルで、表示用の
写しと保留の印は別に持ち、保存の結果は作品 UUID へ FK で結ぶ。開始と再開の排他、止めたあとの取り出しの
禁止、中断のあとの一時停止への復旧は同じ台帳で確定する。ジョブを消しても棚の判断は残る。完了していても、
保存待ちや再試行できる候補があれば封をしない。終わったジョブの履歴（`job_history`）は再開できるキューと
分けて履歴タブへ出し、項目とログは当時の順にページで分ける。集計と空の終了日時を今の作品から補わない。
一覧から外す操作は元の記録を変えず、表示の状態と outbox へ確定する。

### 改稿は、作者を追っていれば分かる

**監視の単位は作者・シリーズであって、作品ではない。** 作品ごとの
`watch_updates` は「これだけを見たい」と絞るための道具で、改稿に気づくための
前提ではない。2,619 件を一つずつ監視に載せてもらう設計にはしない。

だから作者の確認は二つを同時に行う。

| 見るもの | どこから |
|---|---|
| 新作が増えたか | 取得元の作品一覧（前回位置から先） |
| **保存済み作品が直されたか** | 取得元での最終更新（`source_updated_at`）との突き合わせ |

FANBOX は取得元の一覧が更新時刻を持つので、ずっとこうなっていた。pixiv だけが
できなかったのは、**アプリ API の一覧にも作品詳細にも更新時刻が無い**から。
web（`/ajax/user/{id}/novels`）の `updateDate` を通せば、この非対称は消える。
1 リクエストで 100 件を返すので、作者の全作品を並べても往復はアプリ API の 1% で済む。

### 変わったかどうかを、三段で見る

1. **取得元での最終更新**（`source_updated_at`）— 同じなら、そこで終わる
2. **メタデータの指紋**（`pixiv_meta_signature`）— 更新時刻が使えないとき、および
   使えても裏を取りたいとき
3. **本文**（`DEEP_CHECK_INTERVAL_DAYS`）— 指紋に出ない改稿のための保険
   （pixiv だけ。FANBOX の一覧の更新日時は本文を直すと進むので、一覧の日時が同じなら
   本文を取り直さない。14 日ごとに保存済みの投稿をまとめて取り直すと、それだけで
   全作者の全投稿を取り直すことになるため）

指紋を残してあるのは、一覧が使えない状態（セッションが無い・切れた）でも
**今までどおり動くべき**だから。web の一覧は速さのための前段であって、
正しさの前提ではない。

### 少なく返ってきた一覧を、「変わっていない」と読まない

web の一覧はログインしていないと R-18 作品を**黙って**落とす。`error` は false の
まま件数だけが減るので、数えなければ「更新なし」と区別できない。

**投げた ID の数と返ってきた件数が違えば、それ自体を失敗として扱う**
（`PixivError::PartialListing` → `AuthRequired`）。ジョブを止めて再接続を促す。
黙って通すと、セッションが切れた日にライブラリ全体が「最新です」と表示される。

### 更新時刻を覚えてよいとき

`source_updated_at` を覚えるとは「次はこの値と同じなら本文を見ない」と決めること。
**手元の本文がその更新のあとのものだと言えなければ覚えない**（`may_remember`）。

- 本文を取り直した直後 → 覚える
- 本文まで突き合わせた時刻がその更新より後 → 覚える
- どちらとも言えない／時刻が読めない → 覚えない

言えないまま覚えると、その改稿は二度と拾われなくなる。覚えそこねても、次の確認で
従来どおり確かめるだけで済む。

### 数え方

**待機列に入ったものを総数と処理済みに数える。見つけただけの候補は数えない。**

かつて `totals` / `processed` は候補を除いた項目だけを数えていた。「10 / 10件を
処理 · 候補 101」は「監視対象を10件確認し終え、そこから候補が101件見つかった」
という意味だったが、伝わらなかった。

さらに悪いことに、候補は「保存する」と決めた時点で待機列に入りワーカーが順に
処理するのに、総数から外れていた。**自動保存で101件を保存している最中も、
進捗は 10/10（完了）のままだった。**

### 一度断ったものを覚える

チェックを外すだけでは「今は選ばない」の意味しかなく、次の確認でまた出る。
「二度と出さない」を伝える口を別に用意している
（`dismiss_update_candidate`）。

保留候補を再び確認へ戻すときは、全体の先頭件数で打ち切らず、キーを使って500件ずつ
たどってから確認範囲に絞る。別の作者の候補が多くても、指定した作者の古い候補を落とさない。

候補の原入力は字句を保って可逆圧縮する。保留一覧には本文を含まない表示用の写しを使い、
作品の保存の状況と開く先も棚から引く。
明示した再確認は、通信を始める前の候補の判断の世代を持つ。途中で利用者が判断を変えたら結果を断り、
原入力の更新と保留の解除は一度に確定する。閲覧制限による保留は「非表示の解除」だけでは候補へ戻さない。

### 監視グループ

監視対象（作者・シリーズ）は、利用者が作るグループで束ねられる
（`watch_groups` / `watch_group_members`）。束ねるのは「毎日見る作者」のように、
**その束だけを確認したい**ときのため。グループの確認は `scope: "targets"` に
中の対象の ID を渡すだけで、新しい確認の仕方は持たない。

- **一つの対象がいくつのグループに入ってもよい。** タグと同じで、所属は排他でない
- **グループを消しても監視対象は消えない。** 監視対象を消せば、グループからも抜ける
- **グループの確認に作品ごとの監視は混ぜない。** 束ねたのは作者・シリーズだけなので
- **止めている対象は、グループの中でも確認しない。** 止めるのは対象そのものの状態
- 自動確認の範囲にもできる。範囲にしたグループが消えていたら、**すべてへ広げずに
  止まる**（絞った意味が無くなるため）。画面から消したときは範囲を「すべて」に戻す

棚が開く途中は確認を始めない。作者・シリーズが無く作品ごとの監視だけがある場合も、棚で対象の
有無を確かめる。グループの指定や空の対象の指定を、全部の対象へ置き換えない。

既定の束（すべて・作者・シリーズ・停止中）は対象の性質から決まるので、表には置かない。
バックアップは所属を**グループ名で**持ち運ぶ（ID はライブラリごとに違う）。戻すときは
同じ名前のグループへ入れ直し、無ければ作る。グループ自体の名前・並び順・作成と更新の
時刻も保存するので、中身の無いグループも運ぶ。既存の同名グループは変更しない。

## エラーの扱い

- 利用者に見せるメッセージは日本語で、**次に何をすればよいかを書く**

  > このライブラリは別のpiepプロセスで使用中です。ほかのpiepウィンドウを
  > 閉じてから、もう一度起動してください。

- 失敗の理由には分類の札を付ける（`[取得制限]` など）。まとめて数えられるようにする
- 進捗イベントは失敗しても無視してよい（`let _ = app.emit(...)`）。
  受け手が居ないことは異常ではない
